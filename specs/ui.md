# Jx UI Kit Specification

## Interface Elements Authored as Jx Documents

**Version:** 0.1.39-draft\
**Status:** Partial\
**Updated:** 2026-09-11\
**License:** MIT\
**Applies to:** `packages/ui/`, `packages/studio/src/surfaces/`

Companion to [spec.md](./spec.md) §4, §13 and §16, [embedding.md](./embedding.md), and [studio-ui-guidelines.md](./studio-ui-guidelines.md). Defines `@jxsuite/ui`: the set of interface elements Jx Studio's chrome is built from, the theme they draw on, the icons they carry, and the model by which a host composes them into a surface. Every element is a Jx document the runtime interprets; nothing in the kit is a hand-written class.

---

## 1. Overview

> **Status: Partial.** §5.6 and §8 are implemented; §2 through §7, §9 and §10 are partly built, each marker saying what is short. The catalogue in §5 is the plan of record for the elements, and each entry is marked as it lands.

Jx Studio's chrome was Adobe Spectrum Web Components rendered by lit-html templates. The kit replaces it with elements authored in Jx for three reasons that are stated here so the decision stays a decision: Studio's second design principle says Studio is itself a Jx application, and the chrome is the one part of it that was not; a visual website builder is the hardest interface the component model will be asked to express, and building it in Jx forces the runtime, compiler and schema to grow what any large application host needs; and one design system, authored as documents and aligned to the platform's own overlay, colour and cascade standards, replaces a library's private engine and token pipeline.

The kit is **interpreter-first**. Its elements register through `defineElement` from bundled JSON (embedding.md §6), so the canvas that edits a component and the shell that runs it read the same bytes. A compiled distribution is a later optimisation and never a correctness dependency.

## 2. Principles

> **Status: Partial.** Four of the five are held by a gate rather than by memory. Principle 1 is `packages/studio/scripts/check-surface-purity.ts`, which refuses a surface that mixes the kit with anything else, and the kit's conformance test, which holds every component document to §3.2. Principle 2 is the same test's light-DOM check: no component document carries `$shadow` anywhere in it. Principle 4 is studio-ui-guidelines.md §12 and the command registry's own checks. Principle 5 is the conformance test's scan of every behaviour sidecar for an attribute, class, style or markup write — the roving prop writes §5.1 sanctions are the only thing it lets through. Principle 3 is the one still short: modality, light dismissal and the invoker commands are the platform's, but anchoring is not yet (§6), so the kit's menus still place themselves by coordinates. One correction to principle 2's cascade claim, made on evidence from a browser pass: the THEME sheet is layered, but an element's own rules are emitted by the runtime's style engine, unlayered, as `[data-jx="…"]` at (0,1,0) and adopted after every linked sheet — so a host rule wins by being heavier or by being adopted later, never by layer alone, and a bare-class override of an element's rest look ties it and loses on order (the dock handles in `packages/studio/styles/shell-frame.json` and the Edit column's in `surfaces/canvas-stage.json` are the worked examples, and §5.5 records the rule they follow).

1. **The element is the unit of reuse; the document is the unit of composition.** A Studio surface is a document that projects host state into kit elements. The kit carries no knowledge of Studio's state; a surface carries no markup of its own beyond the kit's.
2. **Light DOM, one cascade.** Every relationship the kit is built on is an id reference — `aria-activedescendant`, `aria-controls`, `aria-labelledby`, `popovertarget`, `commandfor`, `anchor-name` — and id references do not cross a shadow boundary. No element declares `$shadow` in this version; `part` attributes are the only sanctioned style hooks (§3.2), and the kit's own sheet lives in a cascade layer so a host's rule always wins (§9).
3. **The platform owns what it can.** Modality, focus containment, light dismissal, anchoring and transitions are `<dialog>`, `popover`, invoker commands, CSS anchor positioning and `@starting-style`. The kit adds behaviour only where the platform has none: roving focus, typeahead, pointer math, measurement.
4. **One list of actions.** A surface renders projections of Studio's command records (studio-ui-guidelines.md §12). The kit prints what it is given — a title, a chord, a disabled reason — and never formats or invents one.
5. **No imperative DOM beyond the allowed set.** A behaviour sidecar may call `focus()`, measure, call an element's own `showPopover()`, `hidePopover()`, `showModal()`, `close()`, `scrollIntoView()` and `setPointerCapture()`, and call a native form control's own value-stepping API on the element's own inner control. A sidecar that writes attributes on another element is a defect. The stepping clause is narrow and has a reason: `HTMLInputElement.stepUp(n)` and `stepDown(n)` clamp to `min` and `max` and snap to the step grid measured from `min`, and hand-rolled `value ± step` diverges from that grid the moment the value is off it (`min=0`, `step=0.3`, `value=0.5`: stepping up once is 0.6, and adding the step gives 0.8). They are also unreachable from a document body, because `call` resolves no owner for an `event#/` pointer and would invoke them with an undefined receiver.

## 3. Authoring Model

> **Status: Partial.** The contract below is normative for every element that exists and is enforced over every one of them: `packages/ui/tests/conformance.test.ts` walks the kit's component documents and asserts each is a valid custom-element document, names every internal node with a `part`, styles only through tokens, ships no CSS class, says what hidden means to it, names only glyphs the kit ships, declares no handler parameters and documents every prop. It used to say the contract was "followed by `jx-icon`" and would become normative "as §5 lands" — a new element joins the claim by existing now, rather than by being remembered. It stays Partial because §5 is: the elements still on the plan of record (`jx-menu-group`, `jx-table`) have not been held to it yet, and §3.2's form association is a decision rather than a clause anything implements.

### 3.1 Element, part, surface

| Kind        | Where                                 | Registers as                         | Owns                                                                                                                            |
| ----------- | ------------------------------------- | ------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| **Element** | `packages/ui/components/jx-*.json`    | a custom element via `defineElement` | its own box and every declaration that paints it, plus whatever local state, keyboard contract and ARIA contract that box needs |
| **Part**    | a `part`-named node in one template   | nothing; addressed as `[part="…"]`   | a named region of its element, styled from that element's own `style` object                                                    |
| **Surface** | `packages/studio/src/surfaces/*.json` | a document a host mounts             | the projection of host state into elements                                                                                      |

There is no fourth kind. **The kit ships no CSS class and no stylesheet.** Every declaration lives in the `style` object of the definition that owns the box it paints, or of the document node that writes it. The only sheet the kit emits is the token block of its own `project.json` (§4.2), and that block holds design tokens and nothing else.

The kind is decided by **how many definitions draw the box**, never by how much behaviour it has:

- A box **two or more definitions draw** is an **element**. It gets a tag, a `style` object and a catalogue entry (§5), even when it owns no state, no keyboard contract and no ARIA role. `jx-kbd` and `jx-divider` are exactly that. They are elements not because they earn one but because a definition is the only place a declaration is allowed to live, and there is no shared definition for them to live in until one exists.
- A box **exactly one definition draws** is a **part** of that definition, and its declarations go under `& [part="…"]` in that definition's own style. A badge drawn only by `jx-action-button` is `[part="badge"]`, not `jx-badge`.
- A part is **promoted** to an element the first time a second definition needs it. The promotion moves declarations and mints a tag; nothing is rewritten.

An element that would once have been called a recipe still owes §3.2 everything §3.2 asks for. What it does not owe is behaviour it does not have: a `jx-divider` declaring `role="separator"` and nothing else is a complete element, and the absence of state is not evidence that it should have been a class.

**`className` is never a look.** A `class` attribute in a document is legal for one reason: a platform or third-party contract the schema does not own, such as `electrobun-webkit-app-region-drag` or Tabulator's own class names. A runtime handle is `part`, which `regions.ts` resolves identically. A class written to reach a rule is a defect.

**Host position is a contract too**, because some parents accept only particular children. §3.5 states the legal table shapes and the forbidden one; the general rule is that an element which cannot legally stand where its box must appear is redesigned to BE that box, never wrapped around it.

The sentence this replaces — _"A `<kbd>`, a divider, a field label and a help line own none of those and are recipes"_ — was true of a schema that could not express them. It can: a definition's own `style` object reaches every box it draws, a usage site's style merges with it, and a declaration value may read state (spec.md §9.1). A recipe was the answer to a question the schema now answers, so the kind no longer exists.

### 3.2 The element contract

Every element document declares, and its catalogue entry in §5 records:

- **`tagName`** with a hyphen, and **typed `state` entries** for its props: `type`, `default`, `attribute`, `description` (spec.md §5.2). The interpreter installs a property accessor per entry and reads an observed attribute into state when the element connects, before `$props` merge, so a property a parent set wins (spec.md §16.2, §16.5).
- **`part`** on every internal node. In light DOM a consumer addresses `jx-x > [part="control"]`; should an element ever opt into a shadow root the same names become `::part()` with no consumer change.
- **Slots** by the names the catalogue lists: `icon`, `value`, `description`, `submenu`, `prefix`, `suffix`, `end`. The interpreter's light-DOM slot distribution is real for named slots, and a `<slot>` UNWRAPS: its matches stand in its place and it leaves no node (spec.md §16.6). So a `part` on a `<slot>` names nothing, and an element asks whether a slot received anything by asking `:empty` of the part CONTAINING it.
- **A `display` in the base block, or the default.** An element whose base block declares no `display` is given `display: block` in its own rule (spec.md §9.6). An element whose visibility the platform owns must opt out with `"display": "revert-layer"` in that block — a popover, a `hint` tooltip, a menu. It rolls the cascade back one layer instead of beating anything, so a closed panel still computes `none` and an open one still takes its own `:popover-open` value. **Plain `revert` is not good enough, and the difference is invisible on a shipped page.** Both roll back past the author origin to the UA rule there. On the Studio canvas the runtime renames `popover` to `data-jx-popover`, so the UA rule matches nothing and Studio re-supplies it inside `@layer jx-canvas-ua`: `revert` rolls back to the user-agent origin, finds no popover attribute and nothing hiding the element, and the closed panel is drawn over the artboard — measured in Chrome 152 at `inline`, 35x17. `revert-layer` lands on Studio's own rule and measures `none` in both places. Any other value is the `base-display` defect `@jxsuite/schema/overlays` reports.
- **ARIA forwarding.** A control observes `aria-label`, `aria-labelledby` and `aria-describedby` and forwards them to its inner native control, which is what names it until form association exists.
- **Events.** Native events bubble from inner native controls. A custom event is declared with `emits` on the function that dispatches it, and is dispatched with `bubbles: true, composed: true`.
- **Tokens.** An element's style references `--jx-*` tokens and never a raw colour. A conformance test refuses a hex in an element's style.
- **Declarative first.** State changes are `$expression` nodes or structured bodies; keyboard `$switch` on `event#/key`; a sidecar (`$prototype: "Function"` + `$src`) only for what the closed operator set cannot express (§2 principle 5).

### 3.3 Behaviours

A behaviour is a pure `(state, event)` function exported from a module under `packages/ui/src/behaviors/` — except `onMount`, which receives `(state, host)`, the element itself being what a sidecar most often needs (spec.md §16.4), registered through `preloadModule` under the `$src` specifier the documents use (embedding.md §6). The kit ships roving focus, typeahead, menu navigation, the anchor-position fallback measurement, label scrubbing, split dragging, overflow measurement, tree drag and drop, and colour math. Each is named in the catalogue entry of the element that uses it.

### 3.4 Composition from a host

A host mounts a surface with `mount()` (embedding.md §2) and hands its records and functions in as scope. A surface `$map`s a host array with a `key` (spec.md §10.4), calls a host function through `call` with positional arguments, and reports back with `dispatchEvent`. Which records a surface receives, and what they are projections of, is the Studio half of the contract (studio-ui-guidelines.md §9).

### 3.5 Host position

An element's box has to stand somewhere, and some parents accept only particular children. Where the two conflict, **the element is redesigned to BE the box, never wrapped around it.**

A table is the case that decides the rule. Three shapes, and only the first two are legal:

- **The element IS the table.** `jx-table` declares `display: table` and `role="table"`, with `jx-tr` as `display: table-row` and `role="row"`, and `jx-th`/`jx-td` as `display: table-cell` with `role="columnheader"` and `role="cell"`. The roles are not optional: a role-less CSS table is announced as a layout table, and the semantics are the whole reason a table is a table. There is no native `<table>` in this shape, so the HTML parser has nothing to foster-parent and a prerendered page survives.
- **The element is INSIDE a cell.** Anything may sit in a `<td>`; nothing about it is special.
- **The element WRAPS a native `<table>` and its rows are slotted through it.** Forbidden. Anything at all between `<table>` and its row groups — a custom element, a `<slot>`, or a plain `<div style="display: contents">` — demotes the table's semantics, and no `display` on the intruder rescues it.

The same reasoning governs an element in running text, which must declare `display: inline-block` or `inline` rather than take the block default (spec.md §9.6), and an element inside a flex or grid row that must generate no box of its own, which declares `display: contents`. Each is a declaration the definition makes deliberately, and each is the answer to "where does this box have to stand".

## 4. Theme and Tokens

> **Status: Partial.** The token sheet is built and adopted (`packages/ui/project.json`, `src/theme.ts`), and it holds design tokens and nothing else — the recipe classes that once shared it are elements now (§3.1). The density and forced-colour rules for individual elements land with those elements.

### 4.1 Three layers

1. **Ramp** — `--jx-gray-50…975`, `--jx-blue-*`, `--jx-red-*`, `--jx-green-*`, `--jx-amber-*`: luminance-ordered steps, theme-independent, with quarter steps at the dark end of the neutral ramp because a dark interface lives in a ten-luminance band. The neutral ramp carries a faint cool cast (OKLCH hue about 250, chroma about 0.006) so grey does not read brown beside the accent.
2. **Semantic** — `--jx-bg`, `--jx-bg-panel`, `--jx-bg-input`, `--jx-bg-overlay`, `--jx-border`, `--jx-border-strong`, `--jx-fg`, `--jx-fg-dim`, `--jx-fg-muted`, `--jx-accent`, `--jx-accent-solid`, `--jx-accent-hover`, `--jx-accent-fg`, `--jx-accent-8…50`, `--jx-hover-bg`, `--jx-danger`, `--jx-success`, `--jx-warning`, `--jx-tag`, `--jx-signal`, `--jx-handler`, `--jx-map`, `--jx-switch-c`, `--jx-switch-track`, `--jx-switch-thumb`, `--jx-field-label-w`, `--jx-popover-offset`, `--jx-spin-color`, `--jx-spin-track-color`. Every colour is a `light-dark()` pair over ramp steps or a mix of another token; none names a hex outside the ramp. Two of those names are a trap worth stating: `--jx-switch-c` is the colour the canvas and the code views paint the `$switch` KEYWORD, which is why it sits in the syntax run beside `--jx-tag` and `--jx-handler`; `jx-switch` the control draws on `--jx-switch-track` and `--jx-switch-thumb`. The track is one ramp step rather than a `light-dark()` pair because only one step clears WCAG 1.4.11's 3:1 on all four of its axes at once, against the page and against its own thumb in each scheme.
3. **Aliases** — Studio's own `--bg`, `--fg`, `--accent`, … resolve these (`--bg: var(--jx-bg, #111114)`), so the names its style gate checks keep their shape and the values change in one place. A site overrides a token by declaring `--jx-*` on `:root` in its own `style`.

### 4.2 Declaration

The tokens are the `style` block of the kit's `project.json`, which is where a site keeps its design tokens (site-architecture.md §10.2), so opening the kit in Studio shows the values the shell runs on. That block's one top-level key is `"@layer jx-ui"`, authored like any other at-rule, and `themeCSS()` is `buildStyleRules` over it and nothing else — it writes no CSS text of its own. The layer used to be a template literal wrapped around the builder's output, which made this module a THIRD reader of the same block beside the runtime and the site builder, and three readers of one block can disagree about what it means. They did: the site builder dropped every `&`-prefixed block as page content, so a project forcing a colour scheme shipped a sheet without it. A test now asserts the two agree declaration by declaration.

`color-scheme: light dark` follows the operating system; `:root[data-theme="light"]` and `:root[data-theme="dark"]` force one, and `light-dark()` resolves against whichever applies. The attribute is deliberately not `data-color-scheme` (spec.md §9.5), which is the **document's** axis: a dark builder editing a light page is the ordinary case, and two axes need two attributes. `data-density="compact"` and `"comfortable"` re-declare the control height and body size.

### 4.3 Scales

| Family  | Tokens                                                                                                                  |
| ------- | ----------------------------------------------------------------------------------------------------------------------- |
| Type    | `--jx-text-xs/sm/md/lg` = 10/11/12/14px with `--jx-leading-*` = 14/16/18/20px, a four-step scale on a 4px line grid     |
| Space   | `--jx-space-1…7` = 2/4/8/12/16/24/32px                                                                                  |
| Control | `--jx-control-h` = 24px (20px compact, 28px comfortable); `--jx-icon-size` = 16px                                       |
| Radius  | `--jx-radius-xs/sm/md/lg` = 2/4/6/10px                                                                                  |
| Focus   | `--jx-focus-ring` = `2px solid var(--jx-accent)`, drawn on `:focus-visible` only, `Highlight` under forced colours      |
| Shadow  | `--jx-shadow-popover`, `--jx-shadow-dialog`: shadows are for surfaces that float; panels are separated by 1px hairlines |
| Fonts   | `--jx-font-sans` (Inter, then the system stack), `--jx-font-mono`                                                       |

### 4.4 Motion and preferences

`--jx-dur-1` (150ms) for state changes and exits, `--jx-dur-2` (200ms) for a surface entering, one `--jx-ease-out` and one `--jx-ease-in`. `prefers-reduced-motion: reduce` sets both durations to `0ms`, which zeroes every transition in the kit at once; `forced-colors: active` swaps the focus ring for the system `Highlight`.

### 4.5 Registered properties

`--jx-accent` is registered as a `<color>` and the two durations as `<time>` with `@property`, so an invalid override falls back to the initial value rather than unsetting the token, and a colour transition interpolates.

## 5. Element Catalogue

> **Status: Partial.** Thirty-eight elements are built under `packages/ui/components/`, each with a `stylebook/` page, and each subsection's own marker names them; §5.6 is complete. What remains is the plan of record: `jx-menu-group` (§5.1) and `jx-table` (§5.4), each of which gains an `Implemented` marker as it lands. The five builder entries — `jx-dimension-field`, `jx-box-editor`, `jx-token-field`, `jx-breakpoint-bar` and `jx-inline-edit` — are no longer pending: §5.5 records the audit that folded two onto elements that exist and dropped three, and their rows say where each lives instead.

Each entry records: `tagName`; props (typed `state` entries); events (`emits`); parts; slots; the WAI-ARIA pattern and its keyboard contract, with any deviation from the ARIA Authoring Practices named; tokens consumed; and what lives in a sidecar.

### 5.1 Primitives

> **Status: Partial.** `jx-textfield` is built: one native `<input>` or, with `multiline`, `<textarea part="input">`, whose `value` the reader and the host both write (a write equal to what is there never moves the caret), with `label` forwarded as `aria-label`, `invalid` as `aria-invalid`, `error` and `help` sentences drawn under it (the error region is permanent and empty until it has something to say, so the first refusal is announced through `aria-live` rather than only a later one; a host that refuses the SAME sentence twice must clear `error` and set it again, because a live region announces a change and an equal write is not one, and both sentences carry ids the control names in `aria-describedby` so a reader who returns to the field hears the refusal before the guidance), `labelledby` and `describedby` forwarded (the host's own description last), `mono`, `size`, `type`, `name`, `autocomplete`, `disabled`, `readonly` and `required`; `selectValue(host, mode)`, `focusField(host)` and `clearField(state, event)` in `@jxsuite/ui/behaviors/textfield` are its three imperative doors. `clearable` renders a `[part="clear"]` button holding the `x` glyph, shown only while the value is non-empty; clicking it empties the value, returns focus to the control and dispatches `input` then `change` FROM THE HOST, and it cancels `pointerdown` so the blur cannot fire a stale `change` for the same gesture first. Escape does the same thing from the keyboard. Both are keyed on `clearable`, NOT on `type="search"` — Firefox draws no clear button for a search field, so the kit's own is the affordance rather than a duplicate of one — and both are suppressed on a `disabled` or `readonly` field, which would otherwise hand the reader a live control that empties a field it had refused to let them edit. Enter is cancelled on a SINGLE-LINE search field, where the platform would otherwise submit the form around it, and left alone on a textarea, which never submits and where the key inserts a line. `grows` hands a textarea's height to `field-sizing: content`, floored by `rows` where it is given and by the fixed three-row box where it is not, so opting into growth can never make a field shorter on an engine that lacks the property. The control carries the field's value as its DEFAULT value as well as its current one, so a form reset cannot leave the element and its control saying different things: the value is the element's own state, and a reset the element never hears leaves that state where it was, so restoring a default is a host write of `value` until form association (§3.2) exists. `jx-button` and `jx-action-button` are built: each wraps one native `<button part="control">` that carries the type, the accessible name (`label`, `labelledby`, `describedby` forwarded) and the invoker attributes (`popovertarget`, `popovertargetaction`, `command`, `commandfor` forwarded, because the platform reads them from the button itself); `variant`, `size` and `quiet` are host data attributes the sheet reads; a `loading` button keeps its width, says `aria-busy`, and refuses the next activation at the control itself with `stopPropagation` as well as `preventDefault` — the propagation half is the load-bearing one, because a consumer's own handler is bound to the element rather than to the control inside it and would otherwise still run; a toggling action button flips `selected`, carries `aria-pressed` and dispatches `change`; `stacked` puts the icon above a visible label (the rail's shape), `haspopup`/`expanded` reach the control as `aria-haspopup`/`aria-expanded` for a menu button, and `badge` draws a count over the corner. `jx-button`, `jx-action-button`, `jx-textfield`, `jx-checkbox`, `jx-switch` and `jx-swatch` each declare a **property-only `tabindex`** forwarded to the native control inside them: the focusable node is that control and not the host, so a roving container (§5.5) writes a declared prop instead of reaching into another element's internals, and it is deliberately not an observed attribute because an attribute would land on the host as well and turn one control into two tab stops. `[part="control"]` is not always that node — on `jx-checkbox` and `jx-switch` it is the `<label>` WRAPPING the input — so a container looking for something to focus takes the first NAMED part that is actually focusable rather than the first named part. `jx-select` is built, as a native `<select>` and not a combobox — the paragraphs below are its contract. `jx-menu` and `jx-menu-item` are built as specified below, in `packages/ui/components/`, with the menu behaviour in `src/behaviors/menu.ts`; `jx-menu` is placed by explicit viewport coordinates until anchor positioning lands (§6), and `jx-menu-group` and the recipes are pending. A `jx-menu` is always an `auto` popover; `jx-menu-item` reads `value`, `disabled`, `destructive`, `requires`, `checked` and `haspopup`, dispatches a bubbling `select` whose `detail` is its value, and stops the click at itself so a row inside a submenu does not also activate the row that owns it. `jx-menu` takes a `floor`, the lowest edge it and its submenus may reach, and a submenu that would leave the viewport on the right flips to its parent's left. Both are exercised by `packages/ui/tests/menu.test.ts`, and Studio's context and settings menus are built on them.

**`jx-select` is a native `<select>`, and the reason it can be is `appearance: base-select`.** The element exists to draw rows in the faces, colours and border styles they name, and to delimit a project's own rows from the generic ones below them — the two things a plain select could not do and the whole case for a kit element here. `base-select` makes the control's OWN list styleable, so the element needs no popup of its own and keeps, for nothing, the platform's typeahead, its scroll-into-view, its form participation, its `:open` state and its accessibility tree. **Both `appearance` declarations are mandatory**, and they are written in one style object so that neither can be forgotten: `base-select` on the control alone yields a styleable trigger over an unstyleable UA picker, and on `::picker(select)` alone it yields nothing at all. A row is `{ value, label, description?, disabled?, face?, swatch?, line? }`, and the last three are the drawing channels: each reaches its own `<span>` as a custom property set inline on that span, so seventy rows intern the rules two rows do (spec.md §9.1). `<selectedcontent part="preview">` mirrors the picked option's CHILDREN into the closed trigger and never the option's own style, so whatever must show closed lives on a child span, and the description is hidden there by `[part="preview"] [part="description"]` because it belongs to the list rather than to the answer. A group draws BOTH halves of its delimiter: the `optgroup`'s `label` is what names it in the accessibility tree, and a `<legend part="group-heading">` inside it is what draws the heading. Neither half substitutes for the other — strip the legend and the group keeps its name with nothing to look at, an empty band above its first row.

**Four things a document must never author here**, each of which passes every scripted test and fails a real one. The `selected` content attribute, in any spelling: the reader's first pick sets that option's dirtiness flag and the attribute stops moving selectedness from that moment, so a document carrying it is right until the first keystroke and wrong after it — measured in Chrome as `selected` on one option and `select.value` reading the FIRST row. `label` on an option: it suppresses the option's children in the picker while `<selectedcontent>` still mirrors them into the trigger, so the row and the trigger stop agreeing. An `option[hidden]` without the element's own `display: none` rule: the element declares `display: flex` on every option, an author declaration beats the UA's `[hidden]` rule, and a hidden option stays in `select.options` and selectable either way — so the rule is what makes `hidden` mean anything. And `content` on an unscoped `::checkmark`, or `order` on a `:checked` one: the UA generates the mark on EVERY option and hides the unchecked ones with `visibility: hidden`, so content declared for all of them reserves width in all of them (a ten-character mark took every row from 102px to 229px) and order declared for one of them misaligns the rest. Geometry and order go on every mark; colour goes on the checked one.

**Selectedness is a property write that the sidecar keeps alive.** The `value` binding runs while the `<select>` is still being built, before any `$map` has appended an option, so the platform refuses it — and the effect never re-runs, because nothing it read changed. `mountSelect` in `@jxsuite/ui/behaviors/select` is the other half: a `MutationObserver` on the control re-asserts `select.value` whenever the option list changes, and it watches `data-value` as well as `childList` because a host write to `value` mutates no option and would otherwise be silent. The document is what makes that write audible, by binding `data-value` to the same state. A value no row holds falls silently to index 0, so the sidecar synthesises a stand-in row carrying `part="unlisted"` — which is also how the computation tells its own row from the listed ones and so does not oscillate. The empty string is a VALUE, the inherit row a reader can arrow to, and never absence. There is deliberately no `onUnmount`: the runtime initialises an element once (spec.md §16.4), so a sidecar that disconnected its observer on removal could never install another, and an ordinary re-parent would leave an element rendering, reactive and deaf.

**What the element authors, what a call site may add, and what only a property can say.** The only tags the DOCUMENT writes inside the control are `select`, `option`, `optgroup` and `legend`. A call site may add its own native rows through the default slot — `option` and `optgroup` elements written as children — and may put an `<hr>` between them, which the element draws as a hairline separator; those are the two shapes a `<select>` accepts, so nothing else belongs there. Slotted content is distributed ONCE, at mount (spec.md §16.6), so rows that change over time are `options` and `groups` rather than children. Those two, and the sidecar-owned `unlisted`, are property-only: a list cannot be an attribute, so they carry no `attribute` key and a host sets them as properties. The element `emits` nothing of its own — the control's `input` and `change` bubble out of it unchanged, so `event.target` is the inner `<select>` and its `value`, `validity` and `form` are live.

**An unlabelled separator between PROJECTED rows cannot be drawn, and a named group is the answer rather than a workaround.** `<hr>` is legal inside a `<select>` and the element draws it as a hairline, but it can only arrive through the default slot — and slotted content is distributed once, at mount (spec.md §16.6), so it can never fall between two rows of `options` or `groups`, which are the lists that change. Neither list carries a separator kind either: an `options` row is a value, a label and three drawing channels, and a `groups` entry draws BOTH halves of its delimiter, so asking a group to be the rule alone means asking it to go unnamed. The kit does not intend to close this. A run of rows worth separating is a run worth naming, and a heading is something a reader can aim at where a hairline only says the list has ended: the three unlabelled dividers in Studio's Add-signal picker became Values, Data sources and Logic, and `ADD_GROUPS` in `packages/studio/src/panels/signals-panel.ts` is that change. An unnamed run is therefore read as rows that have not been grouped yet, not as a missing element.

**No custom element may stand among a `<select>`'s rows, and that used to be guaranteed by an absence.** A custom element inside a `<select>` survives insertion and draws; with `role="option"` the open accessibility tree reads `combobox expanded → MenuListPopup → option "Alpha" selectable`, which is a convincing forgery. Measured in Chrome against a real one: `select.options.length` 0, ArrowDown then Enter gives `value ""` and `selectedIndex -1`, and no `change` event fires. **A test asserting the tree passes while the control does nothing**, which is why the defence had to be structural rather than a test: the kit shipped no `jx-option`, so there was nothing to reach for.

**§5.3's `jx-option` is built now, so that absence is gone and a lint stands in its place.** `custom-element-in-select` in `@jxsuite/schema/a11y` fails ANY document — a kit element or a Studio surface, both of which already run `findA11yDefects` in their own conformance suites — that puts a custom element inside a `<select>` or inside a `jx-select`. It is deliberately broader than the element that provoked it: an `<option>`'s content model is text, so a `jx-icon` in that position is the same forgery with a different tag, and every custom element there fails the same way for the same reason. A native `option`, `optgroup`, `hr` or `slot` is untouched, which is the whole legal vocabulary of a `<select>`. Every row of this element is still a native `option`; a `jx-option` is a `jx-listbox` row and is never legal here.

**`jx-menu` is a list of ACTIONS, and a picker you choose by LOOKING is a different element.** A menu row carries a glyph in `slot="icon"`, a label, a chord in `slot="value"` and ONE secondary line in `slot="description"` — and in Studio that line is already spoken for: `surfaces/menu.json` fills it with `Needs …`, the sentence saying why a disabled row cannot act, which is the `requires` value the kit otherwise carries only as a `title`. There is no image channel beside the glyph, no second line left over for a caption, and no paging: a menu is exactly as long as the rows it was handed, all of them built before it opens. So a browser over a project's files — a thumbnail, a size caption under the name, a filter field above the list — is not a menu with richer rows, and the kit does not grow one. A second fact settles it independently: `jx-menu` is itself `popover="auto"`, so a filter field cannot stand above one inside the same panel. `packages/studio/src/surfaces/media-browser.json` is what that surface is instead — a `jx-popover` holding a filter field over a group of plain buttons — and it states both reasons in its own `$description`.

### 5.2 Overlays

> **Status: Partial.** `jx-dialog` is built: a native `<dialog part="dialog">` opened modally through `showModal(host)` in `@jxsuite/ui/behaviors/dialog` or a `--show` invoker command aimed at the element, with `headline`, `confirm-label`, `secondary-label`, `cancel-label`, `destructive`, `dismissible` (which maps to `closedby`) and `size`; it dispatches `confirm`, `secondary`, `cancel` and `close`, leaves closing after `confirm` to the host so a refused value can keep it open, and carries a `[part="overlay-slot"]`. Its `open` state is mirrored from the platform's `toggle`, never written. **Focus on open is claimed, not left to markup order**: the confirm button carries `autofocus`, and a `destructive` dialog gives it to cancel instead, because `showModal()` otherwise focuses the first focusable descendant — which for a Save, Discard and Cancel footer is Discard, so answering with Enter threw the reader's work away. `jx-button` forwards `autofocus` to its inner control for this. `jx-popover`, `jx-tooltip` and `jx-spinner` are built, and so are `jx-toast` and `jx-toast-host`.

**`jx-popover` places itself by measured viewport coordinates, and the `anchor` prop is dropped rather than deferred.** CSS anchor positioning requires the ANCHOR to declare `anchor-name`, and §2 principle 5 forbids a sidecar writing a style or an attribute on another element — so for a panel over a consumer's own button there is no way to establish the relationship at all, and a prop that worked only when the trigger was inside the element would be a trap rather than a subset. The arrangement `jx-menu` already ships is the one both use. When a consumer can author `anchor-name` on their own trigger the anchor path returns additively with its `@supports` fallback, and `unsafe-anchor` starts applying; until then that rule never fires. `offset` is a token, `--jx-popover-offset`, for the reason §5.3 gives about numeric props: a removed attribute restores its declared default, but a numeric prop still cannot express "unset".

**`popover` is written as a LITERAL `"auto"`, and the mode is not a prop.** The lint reads the raw attribute string, so a `${…}` template or a `$ref` answers null for the mode and blanks the one check the attribute exists to police. `manual` is not offered either: it forfeits light dismiss and Escape, which are the two things this element exists to inherit, and a panel that must survive an outside click is a `jx-dialog`.

**Four style rules carry the element, and their reasons are not interchangeable.** No `display` in the base rule and none inside any at-rule block, so the UA's `[popover]:not(:popover-open) { display: none }` is what hides a closed panel. A `:popover-open` rule that DOES set `display`, which is load-bearing twice: without it the flex layout never turns on, and — because `declaresDisplay` is a deep test — a definition with no display anywhere gets `display: block` INJECTED by `defineElement`, and that injected rule beats the UA's. `&[hidden]:popover-open { display: none }`, because the UA's `[hidden]` rule sits one specificity step below the element's own. And no literal `id` on the root, so a consumer supplies it and `popovertarget` and `aria-controls` resolve.

**A popover restores focus relative to its INVOKER**, which HTML establishes through `popovertarget` or through `showPopover({ source })`. A call with no source leaves focus where it was, so a reader who closes a menu tabs from the top of the document. `openAt(host, anchor)` passes the source inside a `try`/`catch`, since the options bag is newer than the method.

**`jx-tooltip` answers SC 1.4.13 rather than eliding it**: the panel is hoverable (`pointer-events: auto`, and it stays shown while the pointer is on it), dismissible with Escape, and persistent while hovered or focused. `interestfor` with `interest-delay-start` is the platform's own version of that pairing and is the primary path where it exists; a small sidecar covers the engines without it, because the kit ships to site authors and one engine has it. The element writes no `aria-describedby`: it cannot without touching another element, so the host names it onto its control with two id references, which resolves only because the kit is light DOM.

**`jx-spinner`'s rotation is exempt from §4's reduced-motion rule, deliberately.** `--jx-dur-*` is zeroed under `prefers-reduced-motion: reduce`, which is right for a transition and wrong for a busy indicator: a zero-duration spin is a frozen spinner, and a frozen spinner reads as a hang. So the rotation carries its own `--jx-spin-dur` and the preference SLOWS it instead of stopping it. Its keyframes name is `jx-spin`, the first the kit mints, and the prefix is the whole mitigation for a name the style builder hoists document-global.

**A toast carries no live region; the stack does.** `jx-toast-host` is the region and `jx-toast` has no role of its own, which is the answer to the objection that deferred this element: two regions for one message announces it twice, and Studio's `surfaces/toasts.json` sits inside a host that already speaks. `live` decides what the stack is, and the role and the attribute move together as `services/announce.ts` argues they must: `polite` writes `role="status"`, `assertive` writes `role="alert"`, and `off` writes neither, for a host that announces through its own announcer instead. `aria-atomic="false"` is written out rather than inherited from the role, which supplies `true`: a stack re-read whole would deliver one new message by reciting three old ones. The cost is that a toast used off a host is drawn and not announced, and the answer to that is a host.

**The clock is suspended rather than restarted, and that is SC 2.2.1 as an author can honour it.** `timeout` is milliseconds and `0` is sticky, which is also the default, so a numeric prop that cannot express "unset" (§5.3) never has to: a removed attribute coerces to `0` and lands on "nothing disappears unless a host asked". While the pointer is over a toast, while focus is inside it, or while anything in its stack is being read, its clock does not run, and it resumes with the time that was LEFT. The three are NAMED holds rather than one flag, because they overlap: a pointer leaving a toast the reader has tabbed into must not restart a clock the focus is still holding. Attention is measured at the STACK, not the toast, so an older message cannot retire out from under a reader answering a newer one, which would move the very control they were reaching for.

**A recovery control is reachable before it expires, and the element says how.** Three things together, none of them sufficient alone: the stack never takes focus when a toast arrives; reaching it stops every clock in it, so once a reader is there nothing can expire under their hand; and `hotkey` (`F8` by default, empty to turn it off) is the door in, moving focus to the first control in the stack and remembering where it came from. Escape gives focus back, and so does a toast closing while the reader is standing in it, so nobody is left on an element the platform has just hidden. A press carrying Ctrl, Alt or Meta is left alone. The gesture is deliberate rather than ambient: the stack sits at the end of the document, where Tab reaches it last and a clock may run out first, so the reader asks for it in one press instead of racing to it.

**`close` says why.** `detail.reason` is `timeout`, `dismissed` or `action`, and it is dispatched only when the element itself decided: a host writing `open = false` hears nothing back about a thing it just did. Using the slotted recovery control closes the toast and reports `action` without stopping the click, because an answer that has been given is not still being asked and the control's own handler is entitled to have run. The dismiss button is always drawn, so a sticky toast is never a permanent one. Order in a stack is DOM order and is never reversed: what a reader hears, what they tab through and what they see are one order, whichever corner `placement` pins the stack to.

### 5.3 Forms

> **Status: Partial.** `jx-checkbox`, `jx-switch` and `jx-number-field` are built, in `packages/ui/components/`, with the number field's stepping in `src/behaviors/number-field.ts`; the recipes below are built in the kit's own `project.json` and emitted with the theme. `jx-combobox`, `jx-listbox` and `jx-option` are built, in `packages/ui/components/`, with the list's bookkeeping in `src/behaviors/listbox.ts` and the field's keyboard in `src/behaviors/combobox.ts`; the paragraphs below are their contract. `jx-field` is built, with the id minting and the naming of the slotted control in `src/behaviors/textfield.ts`.

Each of the three wraps ONE native control and writes none of the ARIA the platform already supplies. `jx-checkbox` is a native checkbox inside the `<label part="control">` that names it, and exists because HTML gives `indeterminate` no content attribute at all: a mixed box cannot be a template on `attributes`, where it would parse, validate and silently do nothing, so it needs a state entry the interpreter installs as an accessor. `jx-switch` is a second element rather than a variant of the first, because the affordance is the host's choice and a switch has no mixed state; it carries `role="switch"` on its native checkbox, which ARIA in HTML permits and which maps checkedness to the on and off state, so the element must never write `aria-checked` — a hand-written one desyncs the moment the reader clicks. `jx-number-field` keeps `value`, `min`, `max` and `step` as STRING entries, because a numeric entry coerces a removed attribute through `Number()` and so could never express "unset" (§16.5 of spec.md now restores the declared default instead, but a numeric prop still cannot say "empty"), and it never writes `aria-valuenow`, `valuemin` or `valuemax`, which the native spinbutton derives from the value it holds.

**Checkedness is bound twice, on purpose.** The live state is a PROPERTY on the inner control, because the checkedness dirty flag is set the first time the reader clicks and the content attribute stops controlling the live value from then on — a binding written into `attributes` looks correct up to that click and silently stops tracking after it. The content attribute is mirrored as well, which makes it the control's `defaultChecked`. The cost is that `form.reset()` moves nothing, and it is the deliberate half of the trade: the element is not form-associated (§3.2), so it never hears the reset, and without the mirror a reset would move the CONTROL to the authored default and leave the element's state where it was, with no event to reconcile them. A visible no-op is better than two answers to the same question. `jx-textfield` binds `value` the same way and for the same reason. `indeterminate` has no attribute to mirror, so a reset cannot restore it either way.

**Stepping is the control's own API.** `stepUp(n)` and `stepDown(n)` clamp to `min` and `max` and snap to the grid measured from `min`; `value ± step` diverges from that grid the moment the value is off it, so §2 principle 5 sanctions them by name. Shift with an arrow key moves ten steps and cancels the platform's own single step. The stepper buttons cancel `pointerdown`, or clicking one moves focus off the field and the blur fires a second `change` for the same edit; they carry real names and are never `aria-hidden`, because an unnamed button is a finding even when hidden from the tree.

**The platform's own events reach the host unchanged**, and the element synthesises `input` and `change` from itself only on the two paths where the platform fires nothing: a stepper press and a Shift-step. So `e.target` on the reader's own typing is the native control and `e.target.valueAsNumber`, `.validity` and `.form` are live. `<input type="number">` sanitizes what it cannot parse, so a half-typed `1e` and a cleared field both read as the empty string; the element mirrors `validity.badInput` into a `badInput` prop and a `data-bad-input` attribute on itself, so a host that deletes a key on empty can tell "still typing" from "cleared" by reading the ELEMENT, never an event detail.

**`jx-listbox` never takes DOM focus, and that is its contract rather than an omission.** It has no `tabindex`, no focus ring and no keyboard of its own, because it has TWO owners and neither can spare the caret. One is a field: a palette's search box owns every key, and the list is reached through `aria-controls` and `aria-activedescendant`, which is the arrangement the ARIA Authoring Practices sanction for exactly this. The other is NOTHING AT ALL — Studio's slash menu filters for a caret sitting in the canvas, often in another realm, and every character typed after the `/` has to keep landing there, which is why that surface is a listbox and not a `jx-menu`: a menu owns focus by contract. An element that could be focused would have to have a keyboard, and a keyboard here would be a second answer to a question its owner has already answered.

**The highlight is ONE id, written once, and closing that duplication is the whole reason the pair exists.** Studio's three palettes each carried `aria-selected="${$map.index === state.activeIndex ? 'true' : 'false'}"` beside a `data-selected` saying the same thing, in three files, with nothing keeping the three in agreement — and each of them re-decided the question once per row. A consumer now writes the listbox's `active`: the id of the row the caret is on, which is the SAME string its owning field puts in `aria-activedescendant`. `mountListbox` in `@jxsuite/ui/behaviors/listbox` turns it into each row's `selected` — the listbox is the single writer of that flag, exactly as `jx-tabs` is of every tab's, because the flag lives on a foreign element and §2 principle 5 forbids a sidecar writing an attribute on one — and scrolls the newly active row back into view with `block: "nearest"`, which is the half no consumer could do at all. The observer watches `childList` as well as the id, because a filter re-run makes the row carrying that id a DIFFERENT element and an implementation watching only the id would leave the list with no highlight; and only a row that was not already selected is scrolled to, so a re-sync provoked by a pointer never scrolls the list under the pointer.

**The active descendant and the selection are one row here, and a multi-select listbox is not offered.** Selection follows the caret in every consumer, so one flag says both things and `aria-selected` is what draws the highlight — the state a reader hears and the state a reader sees cannot come apart. A list where they must differ needs them as two props and is a different element.

**A `jx-option`'s words are its `label`, and it has no default slot**, which is `jx-tab`'s answer to the same question: `option` takes its name from its contents, so unnamed content in the row would join the name and a row whose only content was a badge would be announced as the badge. `description` is text for the same reason — a reader hears what a reader can see, which is what `jx-select`'s row description already does. `icon` and `end` are slots, and each unused channel draws no box because a `<slot>` leaves no node and its container asks its own `:empty` (§3.2). `face`, `swatch` and `line` are the same three drawing channels a `jx-select` row carries, under the same token names, which is what makes this pair the replacement for Studio's value selector rather than a plainer version of it. A press on a row is cancelled at `pointerdown`: a row is not focusable, so the press would otherwise move focus to the nearest focusable ancestor — off the field that owns the keyboard, and out of the canvas the slash menu is filtering for.

**`jx-combobox` filters NOTHING, and a keystroke highlights nothing.** `options` is the list that will be drawn, never a corpus to match against: every consumer already owns its matching — a fuzzy ranker that knows about modes, recents and chords, or a catalogue fetched from a provider — so an opinion here would be one more thing each of them had to defeat. The host re-answers `options` on the `input` the element lets bubble. And after a keystroke `activeIndex` is `-1`, so Enter commits what the READER typed until they arrow onto a row. That is what makes `allows-custom-value` mean something: the reported gap was a model id field whose catalogue is "a set of suggestions, never a whitelist", and `surfaces/ai-credentials-form.json` is now that field — one `jx-combobox` with `allows-custom-value` over the catalogue `ui/ai-credentials-form.ts` fetches, where a text field and a `jx-select` bound to one draft stood while the kit had no combobox — and the Style tab's keyword rows (`surfaces/style-panel.json`, the `keywords` case) are the same shape over a property's enum, because `text-transform: full-width` is a value whether or not the catalogue lists it. The unit row and the font row are NOT comboboxes, and the line between them is what a row of the list DOES: a keyword's row commits its value, which is the combobox contract, while a unit re-attaches to the number in the field and a font preset mints a token before the property is pointed at it, which are verbs, and a verb per row is the kit menu (§5.5, `jx-dimension-field` and `jx-token-field`). Home and End are left to the text caret, where the reader's cursor actually is; the APG gives them to the list only in the variant where the LISTBOX has focus, and this one never does.

**A list opened by a gesture lands on the row the field already holds, and an empty list is not shown.** Both are about a list that arrives LATE, which is what a fetched catalogue is. The chevron and `Alt`+ArrowDown put the caret on the row whose value the field holds — found through the same case-blind `rowFor` the commit uses, and never a disabled row — so a catalogue that arrived after the reader typed `gpt-4o` shows it as THEIR row when they open the list, rather than a list with nothing chosen beside a value it holds; a plain arrow still enters at an end, and a keystroke still lands on nothing. Tab closes the list whether or not a row was highlighted, because a Tab is not a press outside and light dismissal would leave the panel standing over the fields below. With no rows there is nothing to open: the host carries `data-empty`, the chevron is not drawn, and neither typing nor an arrow shows the panel, so a field whose catalogue has not arrived is a text field until it does and Escape reaches the dialog around it instead of closing a panel nobody could see. The cost is stated rather than hidden: a host that re-answers `options` on `input` and whose PREVIOUS answer was empty sees the list on the keystroke after the one that produced rows, because the element's own `input` handler runs before the host's; a host that wants it sooner calls `openList` itself once it has answered.

**A value a closed list does not hold is refused on the COMMIT, and the control's own `change` never escapes.** Reverting after letting the inner `change` bubble would deliver two committed edits for one gesture — two undo entries for one gesture, the same defect `jx-textfield` cancels a `pointerdown` to avoid — so the refusal stops the event at the control and the element dispatches ONE `change` of its own. A host reading `e.target.value` reads the value that stands either way. An accepted value commits in the ROW's spelling, so a picker normalises the case the reader typed; only `value` is compared, because `label` is what a row DRAWS and a list whose labels also committed would make two strings mean one row and neither of them what is stored. The empty string is emptying the field rather than a value no row holds, and is always accepted. The text judged is the CONTROL's, not the scope's: they agree whenever `input` preceded the `change`, which is every keystroke and every paste, but a `change` that arrives on its own — an engine or a host that set the control and reported only the commit — is still the reader's text, and an element that committed the value it last heard would contradict its own box. An accepted commit closes the list, and so does Enter with no row highlighted: a value that stands has nothing left to suggest, and a browser pass found the list standing over the rows below after the reader had pressed Enter, because the commit is `change`'s and `change` does not fire for text that is what it already was.

**Every id in a combobox is minted from one stem**, `uid`, and the element's own document derives the panel's, the listbox's, each row's and the two sentences' from it by one rule, so a consumer writes none of them and two comboboxes on one surface cannot collide. The list is a `jx-popover` the element owns, opened with `openAt(panel, host)` after the host's box is measured: naming the HOST as the source is what makes `match-width` measure the whole field rather than the text box inside it, and what keeps a press on the input or the chevron from light-dismissing the panel it just opened. `open` follows the panel's own toggle and is never written, so a light dismiss moves it as surely as the chevron does.

### 5.4 Containers

> **Status: Partial.** `jx-tabs`, `jx-tab`, `jx-tab-panel`, `jx-accordion-item` and `jx-action-group` are built, with the tab keyboard in `src/behaviors/tabs.ts` and the group's roving caret in `src/behaviors/action-group.ts`. `jx-accordion` is an element too (below). `jx-table` is not built: it has no consumer, and §3.5 records the shape it must take when one appears, along with the shape it must never take.

**`jx-tabs` closes the gap `studio-ui-guidelines.md` §14 logs**, which is that Studio's tab strips carry no tab semantics at all: the host IS the `tablist`, each `jx-tab` is a `tab` naming its panel through `aria-controls`, and exactly one holds `tabindex="0"` so Tab enters and leaves the strip in one step. The slot carries no `display`, so it stays `display: contents` and the tablist owns its tabs directly — a generic box between a container role and its required owned elements is the trap, and it is the same one §5.4's own `jx-action-group` has to avoid for `radiogroup`.

**The keyboard is the element's, because the platform gives a role-carrying custom element none of it**: arrows with wrap, Home and End, `activation="auto"` selecting as the caret moves against `"manual"` waiting for Enter or Space, and Delete closing a `closable` tab, which is the APG's answer and a path Studio's own × has never had. **A key pressed on a control INSIDE a tab belongs to that control**: the close button is a real button, and Enter or Space on it must close the tab rather than select it — a focusable control with no keyboard operation of its own is a failure of SC 2.1.1, not a rough edge.

**`jx-tab` takes slotted content in three named slots, and none of it can reach the tab's name.** `icon` draws before the label, `status` and `actions` after it and before the tab's own dirty dot and close button. The division is the CLICK rather than the position: `status` holds a mark ABOUT the document (a draft pill, a count, a sync state) and a click on a mark is a click on the tab, while `actions` holds a control (a pin, a lock) and a click inside it stops there — the same judgement the close button already makes, so activating a control never also moves the selection. There is deliberately no default slot: a tab's words are its `label` attribute, so unnamed content has nowhere to go, and a default slot would invite back the icon-only tabs one Studio panel removed along with three hover probes.

**The `label` attribute is what makes those slots safe, and it becomes REQUIRED once anything is slotted.** A `tab` names itself from its content, so a marker, a pill and a pin would all join the tab's own name; `aria-label` wins over name-from-content in accname's precedence order, so the name stays exactly the string the tab draws and each slotted control keeps announcing its own. With no `label` there is no `aria-label`, name-from-content comes back, and a tab whose only content is a pin button is announced "Pin". Nothing lints that either, for the same reason a missing tablist name is unlinted, so it is the element's own test that holds it. Two more consequences the element does not take on itself: a control in `actions` is in the tab order only while its tab is the current one — the consumer binds its `tabindex` the way the close button's is bound, and `jx-action-button` takes one as a property for exactly this, because a strip of ten tabs with ten tab stops is not a roving caret — and a slotted mark that says nothing to a reader is the consumer's to hide, because only the consumer knows whether it is decoration. Each of the three containers is `display: contents`, so an empty one generates no box and a tab that slotted nothing pays no gap for the ones it did not use.

**Nothing lints a missing `label` on a tablist**, because a bound role makes the naming rules stand down and `tablist` is in neither named-role set, so the element's own test asserts it. The same absence is why `jx-tabs` re-syncs when its tab set changes: a strip that loses the tab holding `tabindex="0"` drops out of the tab order entirely, and no gate would have said so.

**`jx-accordion` and `jx-accordion-item` are both elements, and they own different things.** The item earns its keep on the native `<details>` and `<summary>` beneath it and on `name`, which makes a group exclusive with no script. The container draws a stack: one hairline between sections and never above the first, which is a declaration and therefore belongs to a definition (§3.1). It was a recipe while the kit still had them, and the reason given — that a container "earns nothing" when every consumer allows more than one section open — measured behaviour rather than boxes; the kind is decided by how many definitions draw the box.

**The re-announced `toggle` stops at the element.** A native `toggle` does not bubble, but the element re-announces one so a host can bind `ontoggle` on the element it wrote — and that re-announcement DOES bubble, so an item nested inside a `jx-popover` closed the popover, and an inner section's toggle was read as its container's. One `stopPropagation` on the host closes both; it does not stop the other listeners on the host, so a consumer's own handler still runs.

**`jx-action-group` is the `radiogroup` case that forced two props onto `jx-action-button`.** Roving focus has to write a `tabindex`, and the focusable node is the inner control rather than the host; a radio segment has to carry `role="radio"` and `aria-checked` on that same control. Reaching in from the group's sidecar to write either is the foreign-attribute write §2 principle 5 forbids, so the button observes them and the group only sets props. **`checked` REFUSES `toggles`** rather than honouring both: a `role="radio"` that also announced `aria-pressed` is invalid ARIA, and a radio that flipped itself would fight the host that owns the value.

**A host may own the pressed state without the button flipping itself.** `selected` drives the visual whoever wrote it, `aria-pressed` stays gated on `toggles`, `aria-checked` on `checked`, and only the FLIP is gated on `toggles` — two Studio call sites need a segment that looks pressed and does not self-toggle, because clicking the selected one clears the property rather than re-setting it.

### 5.5 Builder

> **Status: Partial.** `jx-tree` and `jx-tree-item` are built, with the keyboard contract, the roving caret, typeahead (resolved locally, or dispatched for the host to resolve against the model when the tree is windowed), the multi-select anchor and the windowing contract in `src/behaviors/tree.ts`. `jx-toolbar` is built, with the roving caret and the mixed-row keyboard in `src/behaviors/toolbar.ts`, and Studio's two hand-rolled `role="toolbar"` rows — the grid's toolbar and the Project Styles chrome bar — are collapsed onto it. `jx-split` is built, with the pointer maths, the keyboard, the collapse toggle and the modifier report in `src/behaviors/split.ts`, and every handle in Studio — the pane grid's splitter, the three dock edges and the Edit column's two snapping handles — is collapsed onto it; the rail's was a hairline rather than a splitter and became `jx-divider`. The five entries the plan of record still carried — `jx-dimension-field`, `jx-box-editor`, `jx-token-field`, `jx-breakpoint-bar` and `jx-inline-edit` — were audited against the surfaces that would have consumed them, after every one of those surfaces had converted without them, and none is built: two are folded onto elements that exist and three are dropped, each for the reason its row gives.

**The tree takes a FLAT list of already-projected rows, and that is the decision every other one follows from.** Studio's two trees window: the Outline draws a screen of a document that may be five thousand nodes, and the Files tree draws eleven rows of a `node_modules` holding ten thousand. A nested structure cannot be windowed at all, because a subtree is a variable number of lines and a viewport is a fixed number of them, so both surfaces already project one flat row per drawn line and neither can go back. `jx-tree` therefore owns no model: its rows are `jx-tree-item` children, each carrying its own `level`, `posinset`, `setsize` and `expanded`, and the element derives none of them from the DOM it can see.

**`aria-setsize` and `aria-posinset` describe the FULL set, and they are props for exactly that reason.** A row that counted its own siblings would count the ones that happen to be drawn, and a reader would be told a directory holds eleven files when it holds ten thousand. Zero writes neither attribute, which is ARIA's own way of saying "ask the DOM" and is right for the one case where the DOM is the whole model; a windowed tree must supply both. `aria-selected` is the mirror image: it is written only when the row IS selected, because a `false` on every row is what tells assistive technology a tree supports multiple selection, and a row cannot see whether its tree does. `aria-multiselectable` on `jx-tree` is where that answer lives.

**Multi-select is an INTENT, and the host resolves it.** Shift extends from the anchor, `Ctrl`/`Cmd` toggles, a plain move replaces, and the element dispatches one `select` carrying `{ value, mode, anchor }`. It owns the anchor, because that is a fact about the reader's gesture rather than about the document; it does not own the selection set, because resolving a range means naming every row between two of them and the rows between are precisely the ones a drawn slice does not have. With `multiple` off every intent is `replace` however many modifiers are held, so a host that never asked for multi-select cannot be handed a `toggle` it has no code for.

**The windowing sidecar is not a second geometry engine, and saying so is the point.** What a windowed composite genuinely cannot do for itself is move the caret onto a row that has no element. `padtop` and `padbottom` are the element's only knowledge of what it cannot see: a caret move past one dispatches `move` and stops, leaving the host to scroll, repaint and write `current`; with both at zero the ends of the slice are the ends of the model and the same code clamps instead. That is also why the arrows do NOT wrap, which is the APG's rule for a tree and a deliberate difference from the kit's menu and tablist: in a list of actions wrapping is a convenience, and in a document outline it is a reader losing their place. Home and End consult the pad BEFORE the row set, or End in a windowed tree lands on the last row the viewport happens to show and calls it the bottom.

**What it hands over is the row, and never the keyboard.** A caret move is one act, and the element performs the whole of it whether it walked to the row itself or asked a host to reveal one: `jx-tree` focuses the row the caret lands on in both cases. The host cannot do that half, and the reason is a matter of ORDER rather than of division. It writes `current` while the row it names still has no element, and the element the repaint then draws is in the page — answering to its `value`, ready to be found by any selector — before its own `tabindex` has been written, so `focus()` on it moves nothing and reports nothing. The element is the only party that knows when the roving tab stop has actually reached the revealed row, so it keeps the request until the keyboard has MOVED rather than spending it on having asked. Two conditions bound that: the request is made only by a key, so a host writing `current` for its own reasons — a canvas selection moving an outline's caret — moves the caret alone; and it is abandoned the moment focus is somewhere the tree does not own, because a reader is not obliged to wait for a scroll.

**Typeahead is the second thing the pads decide, and it does not fail the way a move does.** A move off the end of the slice announces itself: there is no element to land on, so the element discovers it has run out and asks. A letter never does. The search over the drawn rows always answers, and over a five-thousand-node document the answer is whichever of the twenty painted rows happened to start with that letter, picked by wrapping inside a window the reader did not choose — indistinguishable, from in there, from a real hit. So the element does not try to tell them apart: a tree with a pad on EITHER side dispatches `typeahead` (`{ from, char }`) for every printable character and resolves none of them, and a tree with no pads resolves all of them itself. One pad is enough deliberately, because a tree scrolled to the top has nothing above it and the whole model below it, which is where a reader spends most of a session. The host answers it exactly as it answers `move`, and against the string the row DRAWS: `panels/layers-panel.ts` and `files/files.ts` each search their own row model, skip the rows that are drawn but are not tree items, and match the name the row shows — `jx-tree` matches a drawn row on its `label` because that is the row's accessible name, and a model-side search that named a row a second way would move the caret somewhere nothing on screen explains.

**`*` is not implemented, and that is a DEVIATION rather than a gap.** The APG's tree keyboard gives the asterisk one job: expand every closed sibling of the focused row, leaving focus where it is. `jx-tree` claims the key no more than it claims `Ctrl`/`Cmd`+`X`, so it reaches the host untouched. Two facts decide that and only the second would change. It is the one key in the pattern whose entire value is BULK, and bulk is what a windowed tree is least able to promise — the element owns no model, so it cannot name the focused row's siblings and could only dispatch, and the row set that came back might be ten thousand lines arriving in a viewport of eleven. And no Studio surface asks for it: neither the Outline nor the Files tree offers expand-siblings by any other route — no menu row, no chord, no verb in a row's cluster — so building it into the kit would be inventing a command rather than covering one, and §2 principle 4 puts the vocabulary of commands on the Studio side of that line. The shape is settled if a surface ever wants it, by everything around it: one more event carrying the focused row, resolved by the host against the model, exactly as `move` and `typeahead` are. It is written here rather than left as an absence because the silences in a keyboard contract are the part a reader cannot check.

**Drag and drop is an island, and cut and paste are the element's actual obligation.** Pragmatic-drag-and-drop attaches to the rows through the HOST (studio-ui-guidelines.md §9.4), so `data-dragging` and `data-drop` are styled by `jx-tree-item` and bound by nothing — a prop mirroring either would be a second writer, and the repaint that cleared it mid-drag is the stale affordance a cancelled drag used to leave on screen. What the element owes is the other half of SC 2.5.7: every row is addressable (`data-value`), every row is reachable by the roving caret, `cut` draws a row already lifted, and **every key the tree does not own reaches the host untouched**. That last one is not tidiness. Cut, paste, delete, rename and select-all are host commands with chords (guidelines §8.2), and a tree that swallowed `Ctrl`/`Cmd`+`X` would take the only pointer-free way to move a node with it.

**The pointer is delegated on the TREE, which is the one place the kit departs from its own idiom.** `jx-tab`, `jx-menu-item` and `jx-swatch` each dispatch their own `select` and let the container answer; a tree row does not. A selection intent IS the modifier state, and a row would have to copy three booleans out of the `MouseEvent` into a detail for the tree to read them back. One listener that reads the real event is one answer for the pointer and the keyboard both, and it is why a row needs no click handler at all beyond the two that STOP one: the twisty, so opening a row does not also select it, and the `actions` container, so pressing a control on a row does not either.

**`jx-toolbar` is not `jx-action-group` under another name, and a text field is the whole reason.** The question was asked before the element was built, because a second answer to a settled question is a defect: `selects="none"` already resolves to `role="toolbar"`, with a roving caret, an orientation, wrap, Home and End. What it does not have is a row it can hold. `jx-action-group` roves `jx-action-button` and nothing else — its member query is that one tag, its `compact` seam is a rule about that tag's own borders, and `selects="single"` clicks the child an arrow lands on — and both of the surfaces this element was built for hold a `jx-textfield` beside their buttons. A text field is not an action button, has no border to join, and an arrow key inside it is a caret move rather than a selection, so all three of the group's mechanisms are wrong for it at once. Put the group in that row and it finds two of the seven controls in Studio's grid toolbar and leaves the Save `jx-button`, the filter field and the pager as five more tab stops. So the two are separate elements with one sentence between them: **`jx-action-group` is a row of action buttons that may be joined into a segmented control or made a radiogroup; `jx-toolbar` is a container of arbitrary controls with one tab stop.** The widening that did happen is smaller and went the other way: `jx-button`, `jx-textfield`, `jx-checkbox` and `jx-switch` grew the property-only `tabindex` prop `jx-action-button` and `jx-swatch` already had (§5.1), which is the door a roving container writes through instead of reaching into another element's internals. A kit control that holds a focusable node it is not, and whose arrows are not already its own, owes that prop, and the toolbar's own test holds every kit document to it — because without it a toolbar can focus a control and cannot park it, the one tab stop silently absent. `jx-color-field` was the one that did not have it, and it does now; WHICH of its four controls the prop lands on was the colour family's question rather than the toolbar's, and §5.6 answers it.

**The arrows are the toolbar's, and a text control takes them back while its caret can still move.** This is the case the ARIA Authoring Practices raise for a toolbar and decline to answer: the arrow the row wants is the arrow that moves a caret. The contract is that **the field keeps the key while there is text left that way, and the toolbar takes it at the edge** — so the reader arrows in, types, and arrows out again with the same key, and no gesture is lost in either direction. A non-collapsed selection is a gesture in progress and is the control's; Home and End inside text are the control's unconditionally, because there they mean the ends of the line and the ends of the row are one arrow press away regardless. A control whose selection cannot be read at all — Chrome refuses `selectionStart` on `type="email"` — is treated as being at the edge, deliberately: ceding a key that cannot be reasoned about leaves a reader inside a control with no arrow key out of it, which is SC 2.1.2, and taking it costs a caret move Home and End can still make.

**Two kinds of control are not toolbar items at all, and each exclusion has a failure behind it rather than a taxonomy.** A composite that runs a roving caret of its own — a nested `jx-action-group`, a `jx-tabs` — is left alone entirely, because two carets over one set of children are two writers of the same `tabindex` and they disagree about which child is current; the composite keeps its own single tab stop and the toolbar's arrows do not reach into it. A control whose own arrows are already spoken for — a `<select>`, a range, a spin button, a `combobox` — is excluded for the opposite reason: a caret walking the row past a select or a spin button would rewrite what somebody chose, once per press, and past a combobox would open and walk its list. Both are deviations from the APG's one-tab-stop rule and both are stated rather than engineered around: nothing in Studio nests either, and the alternative is a second caret protocol negotiated between two elements. The element that needs one is the place to design it. For the composite case the shape is already known, and it is recorded here so it is not rediscovered: a `jx-action-group` or a `jx-tabs` inside a toolbar is a SECOND tab stop in the row today, and closing that is a property-only `tabindex` on the composite that forwards to whichever child holds its own roving caret — the same door every leaf control opens — so the toolbar parks the composite as one item and the composite's arrows still walk its children. Until an element declares it, the composite stays out of the toolbar's items and keeps its own stop.

**Overflow is the host's, and Studio already has one answer to it.** The plan of record gave this element "overflow into a `⋮` menu measured by a sidecar", and building it would have been the second answer to a question `surfaces/tab-strip.json` settled: the HOST measures what is out of view, projects the list, and opens the kit menu through `surfaces/menu.ts`. It could not have built the rows in any case — an overflow menu is a list of COMMANDS, and §2 principle 4 makes the host the only thing that may say what one is called, whether it can act, or what its chord reads, so a toolbar handed arbitrary children has nothing to name them with. And Studio's toolbars are budgeted rather than elastic: `scripts/check-chrome-budget.ts` caps what may stand in a chrome row (studio-ui-guidelines.md §12.2), which is why neither surface collapsed onto this element has an overflow control to move. Measurement stays in the allowed set (§2 principle 3); a toolbar that measured itself is simply not the design.

**A splitter's value is a FRACTION of the box it divides, and the element measures that box itself.** Pixels were the obvious unit and are the wrong one twice over: a splitter has no size of its own to report, so the only thing `aria-valuenow` can honestly carry is where it sits; and a stored pixel offset is wrong the moment the window moves, where a share survives it. The measurement is the other half of the same decision. A host that computed the fraction — Studio's did, as `1 / grid.clientWidth` re-read on every `pointermove` — has to keep reading a width belonging to a box it may not own, and its FLOOR is worse: `320 / width` as a prop is stale exactly when the window resizes, and stale in the direction that lets a pane go under its minimum. So `gap` is declared in PIXELS and converted at the start of every gesture, against the first ancestor that generates a box — `display: contents` wrappers walked past, which is not a nicety, because Studio's pane grid puts the splitter inside two of them precisely so it lands as a grid item between the two cells. A track too narrow for two gaps has no legal position at all, and the element answers with the middle of its crossed bounds rather than pinning to whichever end a naive clamp visited last.

**A splitter that can only be dragged fails two success criteria, and it takes two different answers to clear them.** The arrows answer SC 2.1.1: the pair of the splitter's own axis, `Shift` for the larger step, Home and End for the ends of the legal range — and they are NOT refused when the track cannot be measured, because a step is arithmetic on a number the element already has, and a layout-timing accident must not be allowed to take the keyboard away. SC 2.5.7 is a different question and the arrows do not answer it: it asks for a single-POINTER alternative that is not a dragging motion. That is the double click, and Enter is the same gesture through the other door — deliberately the same function, so the two cannot drift. `collapse` says where collapsed is, defaulting to `min` because that is what collapsing means for most splitters; a splitter whose two sides are both real panes points it at the position its double click already restored, and gets the return trip it never had. A splitter born at its collapse position still opens, to the middle of its range, because a control that visibly does nothing on its first press is one a reader cannot tell from a broken one.

**Every handle in Studio is `jx-split`, and the element still does not know what a breakpoint is.** `ui/panel-resize.ts` drives the Navigator, Inspector and Bottom-dock handles as `jx-split` elements in the frame — a tab stop, `role="separator"`, arrows and Home/End, Enter and a double click to reset — and keeps for itself only the TRANSLATION: a dock is stored in pixels with a pixel floor and a viewport ceiling, the element speaks in the leading side's share of the box it divides, and a dock sits behind fixed tracks (the rail's 56px, the status bar's 24px) that the share has to include. The Edit column's two handles were the last thing driven by pointer events alone, and the reason was a gap in the element: that column SNAPS to the document's breakpoints with Alt as the bypass, and a host's snap has to know what the hand was holding on each step. The element's answer is not a snap hook — a snap needs the host's units and the host's targets, and an element that took either would be doing a `ResizeTarget`'s job — but a REPORT: every `input` and `change` is a `CustomEvent` whose `detail` is `{ altKey, ctrlKey, metaKey, shiftKey }`, the modifiers of the pointer move or the key that caused it. On the event rather than in the state, because a modifier is a fact about one step and state is what is true between steps; a modifier the hand has released is not. `Shift` is reported even though the keyboard spent it on the large step, because what a host makes of a modifier is the host's business, and `splitModifiersOf(event)` reads a plain `input` a host dispatched itself as no modifiers. The snap then lives where the clamp already did: `bindSplit` bounds the pixels the element asked for, offers them to the target's snap with those modifiers, bounds the answer again, and writes the corrected share back so the announced position and the drawn column agree. `setupHandle` is deleted with the gap it survived for, and with it the last SC 2.1.1 debt this section recorded.

**A handle's track cannot be the thing the handle resizes, so the Edit column's handles stand beside the column rather than inside it.** `jx-split` measures the first boxed ancestor as the box it divides; inside the column, that would be the column, whose width is what the gesture changes — a share of a moving track means nothing. Beside it, as flex siblings pulled outside the column by a negative margin so their margin box is zero wide, the track is the canvas, and the doubling that keeps a centred edge under the pointer is not a special case but the share arithmetic with `scale` at 2 and `lead` at the centre line. Because that track moves for reasons the adapter cannot hear — a dock opening, a pane split, a scrollbar appearing — the four writes into the element are re-derived at the START of every gesture, on `pointerdown` and `keydown` in the capture phase so they land before the element records where the gesture began; the window-resize listener stays for the announced share between gestures. A browser pass found the one thing happy-dom could not: the element's rules are `[data-jx]` (0,1,0) and its hover `[data-jx]:hover` (0,2,0), the same weight as a surface's `[data-jx] [part]` rule, so a rest rule that sets `background: transparent` ties the element's hover fill and wins on source order. A surface that overrides the rest look restates the lit look one attribute heavier, as the frame does for the docks and the stage does for the column.

**Five builder elements were audited rather than built, and the bar was the one `jx-tree` cleared.** An element earns its place when the same contract is written in two surfaces with nothing holding them in agreement; a pattern implemented once, with a `$description` that argues each line of it, is a decision rather than a duplication. Every surface that would have consumed these five converted without them, so the question was what each surface does instead, and the answer was never "the same thing twice". Two are FOLDED, because an element that exists already answers them: the dimension field is the Style tab's composite of a `jx-textfield` and the kit menu over one grammar, and the token field's picker is `jx-color-field`'s own `tokens` slot, filled identically by two tabs from one projection. Three are DROPPED, because each was a bundle of things Studio had already decided to keep apart or a pattern with exactly one site: the box editor is the shorthand row, the breakpoint bar is three surfaces studio.md split on purpose, and inline editing has one consumer while every other name Studio collects is the prompt dialog by decision. The duplication the audit did find is on Studio's side and is a grammar, not a widget — `panels/style-panel.ts` parses `var()` with a private regex beside `style/token-ref.ts`, the module written for it — and a kit element is not how that is closed. The rows below say where each one lives and what, if anything, would move it.

### 5.6 Colour

> **Status: Implemented.** All five elements are built, in `packages/ui/components/`, with the pointer maths and the composition in `src/behaviors/color-area.ts`, `color-slider.ts`, `swatch-group.ts` and `color-field.ts`, and the colour maths in `src/color.ts`.

**A two-dimensional slider is not a role, so `jx-color-area` is two sliders.** ARIA has no `slider2d`, and the APG's answer for a saturation/brightness square is two one-dimensional sliders. The element is therefore two real `<input type="range">`s, one per axis, and everything a slider owes a reader comes from them rather than from an authored imitation: `role="slider"`, the tab stops, the focus, `aria-valuemin`, `aria-valuemax` and `aria-valuenow` derived from each control's own `min`, `max` and `value`, the announcement when a value moves, `:disabled`, and the along-axis arrow keys with their Home, End, PageUp and PageDown. They are `opacity: 0` and `pointer-events: none` rather than hidden: a control the platform has hidden is a control the accessibility tree does not have, and a square only a pointer can operate is an SC 2.1.1 failure with a thumb drawn on it. The element writes no ARIA of its own except the two `aria-valuetext` percentages and the group's name.

**What is left for a sidecar is exactly what a slider cannot know.** A range knows one dimension, so ArrowUp on the saturation control is the platform stepping saturation, which to a reader looking at one square with one thumb is the thumb moving sideways when they pressed up: the CROSS-axis arrows are cancelled and applied to the axis the reader meant. `Shift`+Arrow moves ten steps, the same coarse gesture `jx-number-field` adds and one the platform has on no range. And a square has no native drag, so pointerdown, move and up are read against the track's own box, snapped to the same grid the ranges hold. SC 2.5.7 is met by the ranges rather than by the drag: every value the pointer can reach is reachable with the arrow keys, and a single press with no movement sets the value outright, so no dragging motion is required for any of it. An unlaid-out track answers nothing rather than answering at its origin.

**`jx-color-slider` is one styled native range over a gradient, and almost nothing is left.** The platform owns the thumb, the drag, the along-axis arrows, Home, End and the Page keys; the kit adds `Shift`+Arrow and nothing else. Its `channel` chooses the track's drawing, the units the value is announced in, and the top of the range through a computed the inner control's own `max` is bound to, so the platform's clamp and the sidecar's cannot drift apart: a hue track runs to 360 and an alpha track to 100, and `max` is `0` for unset because a numeric prop coerces a removed attribute through the current value's type (§5.3).

**The colour family dispatches from the HOST and stops its controls' own events**, which is the one place in the kit that does so. `jx-number-field` lets a native `input` bubble because its control's value IS its value; here two ranges hold half a coordinate each, five controls stand around one value in `jx-color-field`, and a host that heard them would read `e.target.value` as `"64"` with no way to know which axis, or read a different node depending on which control the reader touched. So `e.target` is always the element and `e.target`'s own props are the whole answer. `jx-color-field` does it with ONE pair of listeners at its root, routing on a `data-jx-channel` attribute the document writes beside each `part`: it is the kit's own name because an element's root attributes win over the ones its instance is given, and `jx-color-slider` writes `data-channel` from its own `channel` prop, so the track the field called `opacity` arrived calling itself `alpha`. An event the routing does not claim is left to bubble as itself: an element may re-say what it routes and nothing else.

**One value, two representations, and a guard between them.** What `jx-color-field` holds is a string a stylesheet can read; what its picker moves is four numbers. Neither derives from the other for free, because a grey has no hue: a round trip through the string would send the hue track back to red every time the reader dragged the saturation to zero. So `value` is the truth, the channels are a working copy, and the sync rewrites the copy only when the two genuinely disagree, compared as hex. That guard is also what stops the loop, since composing writes `value`, the write moves `data-value`, and the observer's sync then finds nothing to do. `format` decides what is WRITTEN, never what may be read: hex, `rgb()` and `oklch()` are all accepted from the text field whatever it says, because refusing a colour the element itself could have produced would be a trap. A typed value is refused on the COMMIT and never on a keystroke, so a half-typed hex is neither taken nor reformatted under the caret. **A value the element cannot decompose is not a refusal either**: `invalid` means "what you typed is not a colour", and a host writing `var(--brand-accent)`, a named colour or a `color-mix()` is not the reader typing. The element keeps such a value verbatim, shows it in the text field, and still DRAWS it, because the preview chip's background is that string handed to CSS rather than anything computed; only the picker's channels are stale, and the first thing the reader moves replaces the token with a literal, which is what moving a picker means. That is what lets a project's own palette live in the same field as a colour.

**A colour field in a toolbar is one stop, and the stop is the swatch.** `jx-color-field` declares the property-only `tabindex` every leaf control has (§5.1), so `jx-toolbar` can park it as one item rather than finding four tab stops inside one element, and the question a composed control has to answer — which of its focusable nodes the prop lands on — is decided here rather than in the toolbar. It is the swatch button, for three reasons in order: it is the OPENER, so Enter from it reaches the whole picker and a reader parked on it can choose any colour, which is what keeps SC 2.1.1 whole; it is the one control the element always draws, where the eyedropper and the system well are optional by contract; and it is first in the row, so Tab lands where the eye does. The swatch wears `part="control"` for exactly this — the kit's name for the node a roving container focuses, which is how `jx-swatch` names its own button — and the rule that styles it is child-scoped, because in one cascade a bare `[part="control"]` would also dress the eyedropper's `jx-action-button`. **While the prop is set, the text field, the screen picker and the system door step out of the tab order** (`tabindex="-1"`): a container told that this element is one stop must find exactly one, and those three are then the pointer's. That is a stated trade rather than an oversight — in a toolbar a colour well is a quick pick, and typing a value or a token is the form's affordance, where the prop is unset and every control keeps its own named stop. The alternative, a caret of the field's own walking its four controls, is the second caret protocol §5.5 declines for every composite.

**The system picker is a door, never the control.** `<input type="color">` and `EyeDropper` reach what the page cannot draw, the operating system's picker and the pixels outside the document, and both are optional: the screen-picker button is drawn only where the engine has the API, so no control exists that does nothing when pressed, and the element is fully operable from the keyboard with neither. A colour well is opaque by construction, so the alpha the reader already chose is carried across rather than reset by a control that cannot express it.

**A swatch is named by its label and not by its colour**, and the fallback order is `label`, then `value`, then the colour, then the word "Colour": a hex read one character at a time is a name a reader cannot use, so it is the last resort rather than the first. `jx-swatch` works out its own ink through a pure `$src` computed over its own `color`, and draws the chip's boundary and its tick in whichever of black and white measures the greater contrast against it. That is SC 1.4.11 rather than decoration: a neutral border disappears against a neutral swatch, and a fixed ink or a luminance threshold both get the middle of the range wrong. A colour only the browser can resolve, `var(--jx-accent)` or a named colour, answers the empty string and falls back to the kit's border token rather than guessing. `jx-color-field` runs the same measurement for its own preview chip.

**`jx-swatch-group` is a radiogroup and its sidecar is the single writer of every child's `checked` and `tabindex`**, reached three ways that are all one call: at mount, because `applyAttributes` runs before `distributeSlots`; from a `sync` computed the host reads through `data-selection`, which is what makes a host write of `.value` re-sync with no method call; and from an observer, because the swatch SET moves too and a group whose caret-holder was filtered away has no tab stop left at all. Selection follows focus and it does so by CLICKING, exactly as `jx-action-group` does, so a pointer and a key take one path. Either arrow pair moves, because a palette wraps into rows; disabled members are stepped over; and a group in which nothing can be chosen has zero tab stops rather than one, so a reader cannot Tab into a control they then cannot operate.

**The colour maths is a module, not a document.** A cube root, an `atan2`, a piecewise transfer function and a regular expression are arithmetic the closed operator set cannot say, and the elements need them per keystroke. `src/color.ts` is pure, touches no DOM and holds no state: sRGB, HSV, OKLCH (Björn Ottosson's matrices, which CSS Color 4 §10 adopts verbatim), hex and `rgb()`/`oklch()` parsing, WCAG relative luminance and contrast ratio, and the step-snapping HTML's own range algorithm defines, including the rung-below rule that keeps the element and its inner ranges agreeing at the top of an uneven track. HSV is the geometry of the square and nothing else; sRGB is what a value is stored and transported as; OKLCH is what a colour is judged in and the second format the field writes.

## 6. Overlay Model

> **Status: Partial.** The dialog half is built: `jx-dialog` (§5.2) is a native modal dialog, so the platform owns inertness, focus restoration, Escape and `closedby`, and the kit adds nothing of its own around them. The popover half is built for menus: `jx-menu` is a native `auto` popover, a submenu is a child popover slotted into its row, and light dismissal, Escape one level and Tab-hides-root are verified in `packages/ui/tests/menu.test.ts` over a test shim of the popover API. Anchor positioning, `<dialog>`, invoker commands and discrete transitions are pending.

Menus, popovers and tooltips are native `popover` panels positioned with CSS anchor positioning (`anchor-name`, `position-anchor`, `position-area`, `position-try-fallbacks`) behind the mandatory `@supports` fallback the popover lint already requires. Dialogs are `<dialog>` opened with `showModal()`; openers use invoker commands (`command="show-modal" commandfor="…"`, `command="close"`), and a `--jx-*` custom command dispatches a `CommandEvent` a surface may answer declaratively. Entry and exit are `@starting-style` and `transition-behavior: allow-discrete`.

The top layer replaces a z-index ladder: whatever was shown later paints above what showed it. A modal `<dialog>` makes everything outside it inert, so a popover opened from a control inside one renders inside its `[part="overlay-slot"]`. A submenu is a child popover of its row and therefore in its parent's hierarchy: light dismissal closes the whole stack, Escape closes one level, and Tab hides the root.

In Studio, `layers.ts` keeps its exports (`getLayerSlot`, `isModalOpen`, and the three named dialog flows) as the façade over these primitives; how each maps is studio-ui-guidelines.md §8.7. `openModal`, `renderPopover` and `showDialog` are no longer among them: a persistent modal is a `jx-dialog` surface document mounted into the modal layer, a popover is `surfaces/menu.ts` or `getLayerSlot("popover", id)` plus a mounted document, and a bespoke dialog body is a named flow with an island — each helper went when its last caller did.

## 7. Keyboard and Focus

> **Status: Partial.** The menu's roving `tabindex`, typeahead and submenu keys are built, and so are the tablist's, the action group's, the swatch group's, the tree's, the toolbar's and the splitter's; the listbox's `aria-activedescendant` and the combobox's field keyboard are built too (§5.3). Every keyboard pattern in this section now has an element behind it.

Composite widgets use a roving `tabindex` (menu, toolbar, tabs, tree, action group) or `aria-activedescendant` where the ARIA Authoring Practices permit it (listbox, combobox). Focus moves are the one thing a behaviour sidecar is for; everything else about a key is a `$switch` on `event#/key`. Escape closes one level of an overlay stack; a hidden `auto` popover restores focus to what opened it, which is the platform's own behaviour. A status stack is the one surface a reader cannot reach in time by tabbing, because it is last in the document and its contents are on a clock, so `jx-toast-host` owns a key of its own and gives focus back on Escape (§5.2). Every move a drag performs is also reachable without one, which for a tree is cut and paste: `jx-tree` claims only the keys it owns and lets every other one — the chords those two commands are bound to included — reach the host untouched (§5.5). For a splitter it is the arrows, and SC 2.5.7 needs one thing a keyboard cannot supply: a single-pointer gesture that is not a drag, which is `jx-split`'s double click (§5.5).

**A composite is allowed to say no, and the toolbar is where that becomes a rule.** Every other roving container in the kit owns its axis outright, because every child in it is the same kind of control. A toolbar's children are not, so it asks each one whether the key is already spoken for and stands aside when it is: a text control keeps the arrows while its caret can still move that way and keeps Home and End always, a control that runs its own roving caret is not roved into, and a control whose arrows change its own value is not an item. The first is the APG's own unanswered case; the second and third are deviations from its one-tab-stop rule that §5.5 states, with the failure each one prevents.

## 8. Icons

> **Status: Implemented.** `jx-icon` and the manifest are built, and the Studio icon check reads the manifest: `packages/studio/scripts/check-icons.ts` holds every `jx-icon` name in a surface document and every `icon` on a command or panel record to `icons/manifest.json`, so the three spellings are one key space by gate rather than by convention.

The kit draws Phosphor (MIT). `packages/ui/icons/list.json` names the glyphs and weights the kit ships — an allow-list, so the bundle carries what the shell uses — and `bun run build:icons` lifts each glyph's path data out of `@phosphor-icons/core` into the committed `icons/manifest.json`, one `<path d>` per name and weight on a shared 256-unit viewBox. A name the package does not know fails the build.

`jx-icon` takes `name`, `weight` (`regular`, `bold`, or `fill` — the active drawing of the same glyph; a missing weight falls back to `regular`), `label` and `mirror`, and renders one `<svg part="svg" role="img">` whose `<path d>` is a computed over the manifest through a `$src` lookup, so the manifest is a plain import rather than reactive state. **A label is the accessible name; without one the icon is hidden from assistive technology.** A name the manifest lacks draws nothing and warns once. Size is `--jx-icon-size`; colour is `currentColor`.

The manifest is one key space: a `name` on `jx-icon`, an `icon` on a Studio command or panel record, and a name in a surface document all resolve through it, and a check over Studio's sources holds every literal to it.

## 9. Build and Distribution

> **Status: Partial.** `registerUi()`, the theme and the stylebook (one page per element under `stylebook/`, read by the conformance test) are built; the optional compiled distribution is pending.

`@jxsuite/ui` ships JSON sources and TypeScript, not compiled classes. `registerUi()` preloads every component document under `jx-ui:/components/<tag>.json` and every behaviour module under the `$src` specifier the documents spell, then defines each element through the runtime's `defineElement`, and adopts the theme (embedding.md §6). It is idempotent per realm and touches no network.

The theme sheet is wrapped in one cascade layer, `@layer jx-ui`. A site's or Studio's own rules are unlayered and therefore win over a kit token by cascade order, never by specificity; Jx's own style emitter stays unlayered (spec.md §9.6).

The kit is a Jx project (`packages/ui/project.json`): Studio opens it, the Library pane lists its components, and `stylebook/` holds one page per element showing every variant and state. A conformance test validates every document against the schema, runs the overlay lint over it, and refuses a raw colour or an internal node without a `part`.

## 10. Studio Integration

> **Status: Partial.** The shell's side is done: `packages/studio/src/ui/kit.ts` registers the kit at boot, `styles/tokens.json` aliases Studio's token names to the kit's, and every one of Studio's surfaces is a document mounted by an adapter — Spectrum is removed and banned, and `scripts/check-surface-purity.ts` keeps it so. What the kit promises the shell is what is short: §5 still carries `jx-menu-group` and `jx-table` on the plan of record, and §6's anchor positioning is pending, so the section is exactly as complete as those two — and as one more thing outside the kit: the canvas frame defines a project's elements from the project's own files and cannot load their `jx-ui:` behaviour modules, so a kit element with a sidecar does not mount on the canvas (measured on `stylebook/jx-combobox.json`: ten elements, none reaching its control). The shell's own realm has the lane the other way round — a saved component redefines the element and re-mounts every surface that used it (studio-ui-guidelines.md §9.3).

Studio registers the kit at boot, aliases its own token names to the kit's (§4.1), and re-authors each surface as a document mounted by an adapter that passes host records and functions as scope. The order, the per-surface contract and the gates are `studio-ui-guidelines.md` §6 and §9; this section records only what the kit promises the shell: every element in §5, the overlay model in §6, and one icon key space (§8).
