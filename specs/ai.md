> **Status: Partial.** This is a stub spec for a shipped subsystem that grew ahead of its specification. It records the contract as implemented today; sections will be expanded as the subsystem stabilizes. The authoritative user documentation is [`docs/studio/ai.md`](../docs/studio/ai.md).

## 1. Overview

`@jxsuite/ai` is the assistant that edits a Jx project from natural-language instructions inside Studio. It generates and edits pages and components on the canvas while the user watches. It ships **no account and no hosted model**: the user connects their own provider, and Studio talks to it through the dev/desktop server's AI proxy (`/__studio/ai/*`, see `@jxsuite/server` §4). The package itself (`@jxsuite/ai`) is a provider-agnostic streaming tool-call client. It depends on `@jxsuite/protocol`, and through it on `@jxsuite/schema`, for the wire's problem documents; only its reactive chat store uses `@vue/reactivity`. Its leaves — `./streaming-client`, `./tools`, `./messages` (§2.3), `./gateway` (§2.4) and `./harness` (§3.8) — are **Worker-safe**: they import no `node:*`, no `@vue/reactivity` and no DOM, and `packages/ai/tests/worker-safety.test.ts` and the `typecheck:ai-worker` gate hold them to it, because the platform's Worker imports them. The root entry is not Worker-safe, since it re-exports the chat store.

## 2. Provider Contract

> **Status: Partial.** The wire, the `usage` frame, the calls deciding rather than the finish, and Stop armed before the first wait ship. A model-listing failure is not always distinguished: Studio keeps `upstreamMessage` as the only witness of `upstreamError` (`proxyModelsError` in `packages/studio/src/services/ai-models.ts`), so a listing answered with `upstreamError` set and no message, or an empty one, fills the picker with the default catalogue and says nothing (`packages/studio/src/ui/ai-credentials-form.ts`). `upstreamMessage` is optional in `AiModelsResponse` (`packages/protocol/src/types.ts`), and the dev server's own fallback for a bodiless failure is the upstream's status text, which can be empty.

- The client speaks the **OpenAI chat-completions** wire format (streaming SSE, tool calls), whichever provider answers it. A backend reaches a provider of another family by translating that body and its stream, and the **Anthropic Messages API** is the one other family it reaches (§2.6).
- A **user-supplied key and base URL** are required; the server proxy attaches them per request and never persists them. The proxy refuses to forward a server-environment key to a user-supplied base URL, and blocks cloud-metadata/link-local hosts (see `@jxsuite/server` §4.2).
- Local and self-hosted OpenAI-compatible endpoints (e.g. LM Studio, Ollama's OpenAI shim) are supported by pointing the base URL at them.
- **The count travels with the stream.** A backend that holds the provider's token count for the request **SHOULD** send it as one `usage` frame (`inputTokens`, `outputTokens`, optional `cachedInputTokens` and `reasoningTokens`) immediately before `done`, because a reader stops at `done`. It is additive: a backend with no figure sends none and a reader that predates it ignores it. The client uses it as the context's size and estimates only the messages added after it, so the budget stops being a guess at four characters per token wherever a provider reports. With OpenAI's `include_usage` the count arrives in a chunk of its own after the finish, so a backend **MUST** keep reading past `finish_reason` until `[DONE]` or the end of the body.
- **The calls decide whether tools run, not the finish reason.** A round whose stream carried tool calls executes them whichever finish the provider reported (`stop`, `length` or `tool_calls`), because some OpenAI-compatible providers (Workers AI among them) end a tool-calling turn with `stop`, and gating on `tool_calls` left those calls unrun. **Cancellation is the exception, and it is not a finish reason:** a round that ends `cancelled`, or whose signal is aborted, runs nothing it streamed, including calls whose arguments were already complete, and a Stop that lands between two calls stops the ones after it. A Stop that lands during a round's last call opens no further round: nothing is streamed on the stopped signal, and no reply is begun after it. **Stop is armed before the send path's first wait.** The turn's signal exists from the moment the send begins, and the chat URL (an IPC round trip on desktop) is resolved inside the first request, on that signal, so a Stop pressed before anything streams sends nothing and runs nothing. Stop is the one control that must not be outrun.
- **Every error frame carries a problem.** An `error` frame has the human `message`, a `code` when the failure has one (the upstream's own status, or the backend's own reason for it, such as `cf_reconnect_required`), and an RFC 9457 `problem` naming the kind of failure, whether a backend's chat route wrote the frame or the client read the provider itself: both run one normalizer (§2.4). The message is the provider's own sentence with nothing prefixed to it. The types the chat route adds to the registry are `context-overflow` (the conversation is longer than the model's window), `rate-limited` (which an upstream `429` maps to, with `retryAfter` and `scope`) and `wire-unsupported` (with the `supported` versions). A client keys its recovery advice on the `code` first and reads the sentence only when the code decides nothing, because a provider's wording is the least stable thing about it.
- **A body that ends without a terminal marker finishes truncated.** An OpenAI-compatible stream is finished by `[DONE]` or by a finish reason. A body that closes having sent neither was cut off, and its `done` frame carries `truncated: true`; `stopReason` stays `"stop"`, so a reader that predates the member ends the round as it did. The calls it streamed still run (the rule below), and the turn engine records the round's message as incomplete (§3.8).
- **A tool call's fragments are joined by slot, and a repeated id continues the call.** The normalizer joins a call's argument fragments by the fragment's `index`, or by its place in the chunk when the provider sends no index, and a fragment that repeats the id of the call already open in its slot continues that call rather than starting it again. A host that knows an upstream needs the older reading, a single reasoning field, or another path to its cached-token count says so as that upstream's `quirks`.
- **The probe advertises the wire and the limits.** The models route's answer carries `wire`, the chat-route wire versions the backend accepts (absent means `[1]`), and `limits` (`maxMessages`, `maxBodyBytes`) when its chat route enforces any. A client trims a conversation to `limits.maxMessages` before it sends, leaving a note in place of what it dropped, rather than learning the ceiling from a `413`. A model's `contextWindow` is omitted when the backend has no positive figure for it.
- A **managed** platform may broker credentials instead, so a user-supplied key is required only where nothing else supplies one (§2.1).
- Model **listing** is best-effort per endpoint: a BYOK provider is not required to serve one (Cloudflare Workers AI's OpenAI-compatible surface, for instance, has no `/models` route at all). The proxy answers `200` with a default catalogue and `upstreamError` set either way, so this failure **MUST** be distinguished from an authentication failure rather than surfaced as a silent success — `upstreamMessage` carries the upstream's own reason (e.g. "No route for that URI") so a client can show it instead of a bare status code, and chat itself is unaffected: it is a separate endpoint from `/models` and a provider that cannot list models may still serve completions.

### 2.1 Managed providers

> **Status: Implemented.** Jx Cloud brokers Cloudflare Workers AI on the user's own Cloudflare account (`packages/studio/src/ui/ai-managed-connect.ts`, jx-platform `/api/v1/ai/*`).

A platform that can obtain credentials on the user's behalf declares it, and Studio offers that path **before** the key form rather than beside it: on such a platform, connecting an account is the recommended route and bring-your-own-key remains available beneath it.

The models endpoint is a **capability probe**, not merely a listing. Studio decides which paths to offer from its answer, so:

- It **MUST** answer `200` for every credential state, including "no credentials" and "credentials lapsed". A non-2xx makes the probe throw, and a client that cannot read the probe falls back to offering the key form alone — which withdraws the connect affordance from precisely the users who need it.
- `managed: true` declares that the backend can obtain credentials itself. `configured` reports whether it currently holds working ones.
- `code` explains a `configured: false`, and distinguishes the two states that need different words on screen: `cf_not_connected` (never connected — invite) and `cf_reconnect_required` (the grant lapsed — explain, and offer reconnection).
- `cf_upstream_error` is reported **with `configured: true`**. A provider that is briefly unreachable is not a credential problem, and prompting for re-authorization would send the user through a flow that cannot fix it.

Brokered credentials are the platform's to hold and refresh; the client never sees them. A backend that cannot refresh a lapsed grant **MUST** report `cf_reconnect_required` rather than continuing to present the expired credential to the provider.

**A row that exists is not a connection that works.** Two of the three managed states are a stored grant, and a client **MUST** distinguish them before calling a connect flow finished. A flow that settles on "is there a connection" is answered yes from the moment it starts, so it closes the provider's authorization window before the user has reached the login screen — the authorization can then never complete, and the lapsed state that needs re-authorization is precisely the state that prevents it. The proof a flow succeeded is the lapsed marker CLEARING, never the row's presence.

**`cf_account_required` is not `cf_not_connected`.** It reports a live grant with no account chosen, because the callback found more than one and could not choose for the user. Re-authorizing cannot fix it — the flow lands back in the same state — so the client owes the user a choice over the accounts endpoint instead of an invitation to connect something that already is.

**`action_required` is the fourth state, and no connection fixes it.** A backend that requires something of the user before the assistant will run (`desktop.md` §10.4) answers it — still `200`, still `managed: true` — with `detail` (the reason, in the backend's words) and `actions` (what the user can do). The client offers the primary action in that `detail` instead of a connect flow, on any platform that can perform actions whether or not it brokers Cloudflare, and re-runs the probe once the action is done; the send itself answers the `action-required` problem (HTTP 403). The chat and models routes are not under a project session, so a client with a project bound names it in the chat URL's `project` query, which the models route inherits: an access rule keyed on the repository needs to know which project asked.

**A capability probe expires with the grant it described.** A client **MUST** drop a settled probe when a send fails with `cf_reconnect_required`. A probe taken once at start-up otherwise keeps reporting a grant that lapsed mid-session, and every gate reading it keeps offering an assistant that cannot answer.

**Per-model capability facts travel with the listing.** `toolSupport` reports whether a model can make tool calls; `contextWindow` reports its usable budget in tokens. Both are optional — a bring-your-own-key provider need not report either — but a client that drops them on ingest cannot recover them later:

- A client that will send tools **SHOULD** warn when the chosen model reports `toolSupport: false`. Such a model answers and never edits, which reads as an assistant that has silently stopped working rather than one that was never able to act.
- A client **SHOULD** prefer a reported `contextWindow` over any local heuristic. A model-id prefix table only recognizes the families its author knew, so a brokered catalogue of unfamiliar ids is budgeted at the default — an amply-sized model trimmed to a fraction of its real window.

### 2.2 The request is the history the provider will accept

> **Status: Implemented.** `toOpenAIMessages` in `packages/ai/src/messages/openai.ts` (§2.3), which chat-state's `toMessagesArray` delegates to; the `reasoning` frame in `packages/ai/src/streaming-client.ts` and `packages/ai/src/gateway/normalize.ts` (the normalizer `packages/server/src/ai-api.ts` runs, §2.4). Anthropic's half of the rule is §2.6: `bindingOf` in `packages/ai/src/messages/binding.ts` and the replay rule in `packages/ai/src/providers/anthropic.ts`, held by `packages/ai/tests/providers-anthropic.test.ts`.

The conversation Studio displays and the array it puts on the wire are not the same object, and two of the differences are contractual rather than cosmetic:

- **An assistant turn carrying neither text nor tool calls MUST NOT be sent.** The store appends an empty assistant message the moment a turn begins, so that message is the answer being generated _by the request that would carry it_ — a turn which has not happened yet. Most providers read the trailing `{"role":"assistant","content":""}` as an empty prefill and ignore it; DeepSeek's thinking mode instead answers `400 The reasoning_content in the thinking mode must be passed back to the API`, because a thinking-mode assistant turn owes it one. That failed the FIRST request of every conversation, before any history existed to be malformed.
- **A turn's reasoning MUST be replayed when the provider streamed one.** Thinking models emit a chain-of-thought beside the answer (`reasoning_content`, or `reasoning` at OpenRouter). DeepSeek requires the reasoning of all previous turns back on any request carrying `tools` — which is every request the agent loop makes, including turns that called no tool — and ignores the field on requests carrying none. So a client MUST keep it on the message, persist it with the session, and echo it back; a provider that never sends one is never sent one, which is what makes replaying it safe everywhere.

**What is displayed is not always what was sent, and the transcript says so.** A conversation too long for its model is compacted before it is sent (§3.8): the earlier messages leave the transcript and one message stands in their place, saying what happened to them, either a note of how many were dropped or a summary the assistant wrote. That message is part of the conversation from then on: it is displayed, saved, and sent as a user message. Nothing is hidden from the provider that is shown to the author, and nothing is shown that the provider no longer has.

Both halves are one rule: **what the provider streamed is what it is owed back, and nothing else.** Every OpenAI-compatible request is built by one projection, `toOpenAIMessages(toChatMessages(messages))` (§2.3); no caller serializes a transcript into a request itself. A normalizing proxy is therefore not free to drop the frames it cannot render — `reasoning` is a member of the `StreamEvent` union precisely so a backend that only understands `delta` cannot silently strip the turn's other half and leave the next round unanswerable.

**A family that signs its thinking is owed it back unchanged, and only where it still binds.** Claude signs each thinking block and binds it to the request that produced it. The rule above then has a second half: such a block is replayed byte for byte, with its signature, on a request under which its binding still holds, and is not sent at all on any other (§2.6). A wire that cannot carry the signature carries none of that family's thinking: version 1 sends Claude no thinking (§2.6), and thinking one family produced is never sent to another.

`createAnthropicStreamingClient` in `./streaming-client` reaches no provider. It is kept so the export every earlier release had still resolves, and every round answers one `error` frame, with the code `NOT_IMPLEMENTED` and a `capability-unavailable` problem, saying where the direct path is: `createAnthropicProvider` in `@jxsuite/ai/providers` (§2.6, §2.7). The module that every page talking to a backend loads does not carry the Messages API projection.

### 2.3 The neutral conversation model

> **Status: Implemented.** `packages/ai/src/messages/` (`@jxsuite/ai/messages`); `packages/ai/tests/messages.test.ts` holds it to the frozen v1 corpus (`packages/ai/tests/fixtures/v1/transcripts/`), and `packages/studio/tests/ai-tool-specs.test.ts` round-trips every tool Studio offers.

A conversation is described in no provider's words. Each provider describes a turn differently: OpenAI's chat completions put a turn's text, its reasoning and its tool calls in three fields of one message, while Anthropic's thinking blocks carry a signature that must come back byte for byte and its tool results ride on a user message. A transcript stored in one provider's shape cannot be sent to another without guessing, so the conversation has one neutral shape and each provider's adapter projects it onto that provider's wire.

**A message is a list of blocks.** A `ChatMessage` has an `id`, a `role` (`user`, `assistant`, `tool` or `system`), its `blocks` in order, a `timestamp`, and optional `meta`. There are five kinds of block:

- `text`: what the model or the person wrote.
- `reasoning`: a thinking model's chain of thought (§2.2). Its `text` is empty when the provider sent only a redacted payload. It may carry an opaque `signature` and an opaque `redacted` payload, both replayed unchanged and never merged into the text, and a `provenance` naming the provider family and model that produced it.
- `tool_call`: an `id`, a `name` and `argumentsText`, the arguments exactly as streamed. That text is the only record of them: it may not parse (a call cut off mid-arguments), and nothing on the way to the wire repairs it.
- `tool_result`: the `callId` it answers, its `content` (for a Jx tool, the serialized result), and `isError`, true when the content parses as a result whose `success` is false and false otherwise, including when it does not parse.
- `opaque`: provider data with no neutral word, kept for the one `family` it came from.

**`meta` never reaches a provider.** It records what a message is (whether the harness, the model or the person wrote it, a synthetic message's kind, the model and family, whether it was cut off) and a host's own facts under reverse-DNS keys. What a request carries is each message's role and blocks alone (`toWireMessages`), without ids, timestamps, meta, or an assistant turn holding neither text nor a tool call (§2.2).

**The v1 shape stays readable and writable.** Chat-state and every saved session hold the v1 message (`LiveMessage`: `content`, `reasoningContent`, `toolCalls`, `toolCallId`), and `toChatMessages` and `toLiveMessages` convert between the two. The conversion keeps every field a message's role uses (its text for every role, its reasoning and tool calls for an assistant, the call id for a `tool` reply), with one exception: a tool call's `result` is the transcript's copy of an outcome its `tool` reply already carries, so it is rebuilt from the reply by a host that renders it rather than carried. An empty call list says nothing and is not kept. A saved session is restored without being checked, so a v1 value of the wrong type (a `null` reasoning field, a call list that is not a list, text that is not a string) is read as absent: it is never turned into text sent to the model, and it never stops the send. A v1 message gains a `blocks` field only when its v1 fields cannot describe its blocks exactly (signed, redacted or provider-bound reasoning, several reasoning or text blocks, opaque data, text and calls interleaved, or several results in one reply), and its v1 fields are still written beside them, so a reader that predates blocks keeps working.

**The OpenAI-compatible projection** (`toOpenAIMessages`) is the request every v1 client sent, stated once:

1. An assistant turn with no text and no tool call is not sent (§2.2).
2. An assistant turn's `content` is `null` when it made calls and wrote nothing, and otherwise its text.
3. `reasoning_content` is the concatenated text of the turn's replayable reasoning blocks, and is absent when that is empty. A block is replayable when it came from an OpenAI-compatible provider (its own provenance, else its message's `meta.family`, else the v1 default, which is OpenAI-compatible) and it is not redacted, so reasoning another family signed is never sent here.
4. `tool_calls` are the turn's `tool_call` blocks, in order, with their arguments as streamed.
5. A `tool` message is one `{ role: "tool", tool_call_id, content }` entry per result it carries.
6. A user message's text is sent byte for byte, attached context included.
7. A `system` message is `{ role: "system", content }`.

**Tools have a neutral form too.** A `ToolSpec` is a tool's `name`, optional `title`, `description`, `inputSchema` and optional `strict` flag. `toOpenAITools(fromOpenAITools(registry.listForLLM()))` serializes byte for byte as `listForLLM()` does: the same members in the same order, the schema kept by reference so one built with live getters still serializes as it stands that round, and the title left out, since OpenAI has no field for it.

`./messages` is Worker-safe (§1): it imports nothing at runtime outside itself.

### 2.4 One gateway implementation

> **Status: Implemented.** `packages/ai/src/gateway/` (`@jxsuite/ai/gateway`), adopted by `packages/server/src/ai-api.ts`; `packages/server/tests/ai-upstream-fixtures.test.ts` and `packages/ai/tests/gateway-*.test.ts`; the conformance kit is `packages/ai/src/testing/`, run by `packages/ai/tests/testing.test.ts` and `packages/server/tests/ai-api-conformance.test.ts`, and `packages/ai/tests/upstream-divergence.test.ts` holds the client's frames to the gateway's.

The server half of the `ai/chat` and `ai/models` routes is **one implementation**, `@jxsuite/ai/gateway`, which any backend serving them can run. Before it, the proxy's wire work lived inside `@jxsuite/server`, and a second backend had to write its own copy, which is how two normalizers came to disagree. The extraction changes no byte a client receives: the server's recorded upstream fixtures produce the same frames through the gateway as they did through the proxy before it.

The gateway owns the **wire**:

- `createChatHandler(options)` answers the chat route, taking each request through a fixed order, where the first step that refuses answers the request as `application/problem+json` and nothing later runs: the host's `admit` (before the body is read), the host's `resolveUpstream`, reading the body (a `413` once it passes `maxBodyBytes`, measured on the bytes actually read; a `400` when it is not JSON), the wire version (§2.7), the `messages` array (`400` when it is present and not an array), `maxMessages` (`413`, counted on the conversation's own messages for a version 2 body), the host's `onAccepted`, and then the stream. The version 1 body is forwarded as the OpenAI-compatible request it describes, and the response is always a `200 text/event-stream`: a failure after that point is an `error` frame, never a status (§2).
- `normalizeOpenAIStream(response, options?)` is the stream normalizer, including the `usage` frame and reading past the finish until `[DONE]` or the end of the body (§2). It is the **one** normalizer: `createOpenAIStreamingClient` runs it too, so a provider read by the client and one read by a backend yield the same frames for the same body, and the recorded upstream fixtures hold the two to no difference at all. Its options are the upstream's `quirks` and the host's `upstreamErrorCode`, the code an error frame carries for an upstream status when the host knows a better one than the status.
- `encodeSse(frames)` frames each event as one `data:` line and a blank line, and nothing else.
- `problemResponse(refusal)` renders a refusal. The body satisfies both kinds of reader: `error` accompanies `detail`, and a refusal's `code`, when it has one, is sent beside them.
- `modelsResponse(body, options?)` answers the models route, always with `200`, because it is a capability probe (§2.1), adding the `wire` versions and the `limits` the host declares (§2) and dropping a `contextWindow` that is not positive.
- `@jxsuite/ai/testing` is the **conformance kit**: `gatewayConformanceCases()` is the list of things a client expects of any backend serving the two routes, each a case that drives the routes through a scripted upstream (`fakeUpstream`) and throws naming the expectation it missed. It imports no test runner. `@jxsuite/ai` runs it against this gateway, and `@jxsuite/server` runs the same cases against the routes it mounts.

The **policy** stays with the host, and the gateway never second-guesses it. Whose key a request may use (the key provenance rule that keeps a server's environment key off a caller-supplied base URL), which base URLs are safe to reach (the link-local and metadata guard of §4), how requests are admitted, and what the model catalogue lists are the host's `resolveUpstream`, `admit` and models handler. `@jxsuite/server` keeps all four as its own functions (`@jxsuite/server` §4).

The gateway is Worker-safe (§1): its only runtime imports outside itself are `@jxsuite/protocol`'s two problem modules and `../cache-hints.ts` (the shared prompt-cache hint table of §2.5, which needs only `crypto.subtle` and `URL`), and the fetch it calls the upstream with is looked up per request unless the host supplies one.

### 2.5 Prompt caching

> **Status: Implemented.** `packages/ai/src/cache-hints.ts` (re-exported by `@jxsuite/ai`, `./streaming-client` and `./gateway`), applied by `createOpenAIStreamingClient` and `createChatHandler`; the session header in `createProxyStreamingClient` and `packages/studio/src/services/document-assistant.ts`; hashing in `packages/server/src/ai-api.ts`. Tests: `packages/ai/tests/cache-hints.test.ts`, `streaming-client.test.ts`, `gateway-chat.test.ts`, `packages/server/tests/ai-api.test.ts`.

A provider's prompt cache serves the longest prefix a request shares with one it has already seen, and only on the machine that saw it. Every round of an agent turn resends the system prompt, the tool schemas and the whole history, so the assistant is built to share a long prefix between rounds and to tell the providers that route by prefix which requests belong together.

**The client names the conversation; the backend names the cache.** `createProxyStreamingClient` sends the conversation's id, when it has one, as the `X-Jx-Ai-Session` request header (`AI_SESSION_HEADER`); Studio passes the persisted session's id. The raw id is for the client's own backend only and **MUST NOT** be forwarded to a provider. A backend that honours it checks it with `isAiSessionId` (1 to 128 characters of `[A-Za-z0-9_.:-]`), derives `affinityKey(scope, id)`, the first 32 hex characters of SHA-256 over `jx-ai-affinity/v1:<scope>:<id>`, and forwards only that, as the upstream's `sessionAffinity` (§2.4). `scope` is the backend's own namespace (`local` for `@jxsuite/server`), so two backends that see the same id never share a key. An absent or malformed header means no hint, never a refusal: the hint is an optimisation, and the request is valid without it.

**Each hint goes only where it is understood.** `upstreamCacheHints(baseUrl, affinity)` classifies the upstream by host. `api.openai.com` receives `prompt_cache_key` in the request body. Workers AI (an `api.cloudflare.com` URL with `/ai/` in its path) and AI Gateway (`gateway.ai.cloudflare.com`) receive the `x-session-affinity` header. Every other host receives nothing: an OpenAI-compatible server may reject an unknown body field, an unknown header on a browser's cross-origin request costs a preflight the endpoint may not answer, and an arbitrary endpoint a key was pointed at has no use for a stable identifier. The gateway and `createOpenAIStreamingClient` (which takes the key as `sessionAffinity`) apply the same function, so the rule has one definition.

> **Status: Implemented.** The prompt layout: `SYSTEM_PROMPT_STATIC_PREFIX` and `buildSystemPrompt` in `packages/studio/src/services/ai-system-prompt.ts`; `packages/studio/tests/ai-system-prompt.test.ts`.

**The system prompt is a stable prefix, then the state.** `buildSystemPrompt` opens with `SYSTEM_PROMPT_STATIC_PREFIX`, the same bytes in every state: the role, the Jx reference sections (document format, state-shape decision tree, real-world patterns, design principles, control flow, multi-page sites) and the error-recovery guidance, each followed by the section separator. Everything a state decides follows it: the `## Current Mode` section (the workflow for what is open and the tool list it is offered), then the current document, project context and project files when present, and the closing instructions last, where a long prompt's final words carry the most weight. Opening a document or a command tool coming into scope therefore changes bytes only after the reference material, which is most of the prompt.

### 2.6 Anthropic Messages

> **Status: Implemented.** The version 1 projection, the normalizer and the listing in `packages/ai/src/gateway/anthropic.ts`; the native projection, the replay rule and the provider adapter in `packages/ai/src/providers/anthropic.ts`; `bindingOf` and `stripOlderSignatures` in `packages/ai/src/messages/binding.ts`; the engine's binding of signed thinking in `packages/ai/src/harness/run.ts` and `appendReasoningBlock` in `packages/ai/src/chat-state.ts`. Adopted by `createChatHandler` and by `packages/server/src/ai-api.ts`; Studio's provider choice is `jx.ai.provider` (`packages/studio/src/services/ai-settings.ts`, `ui/ai-credentials-form.ts`), and its prompt split is `splitSystemPrompt` in `packages/studio/src/services/ai-system-prompt.ts`. Tests: `packages/ai/tests/gateway-anthropic.test.ts`, `providers-anthropic.test.ts`, `gateway-chat.test.ts`, `harness.test.ts`, `chat-state.test.ts`; `packages/server/tests/ai-api.test.ts`; `packages/studio/tests/ai-credentials-form.test.ts`.

A Claude key reaches Claude through Anthropic's own Messages API, never through an OpenAI-compatible shim, and the client does not change to do it: Studio sends the same body and reads the same frames whichever family answers. The backend translates. On wire version 1 it translates the OpenAI-shaped body, and sends Claude no thinking; on wire version 2 (§2.7) it projects the neutral conversation itself, and replays signed thinking where its binding holds. Both are described below.

**The family is named per request, and only where it can be honoured.** A client names its key's family in the `X-Api-Provider` request header (`AI_PROVIDER_HEADER`) on both AI routes: absent, empty or `openai-compat` is the default, and `anthropic` is the Messages API. A backend **MUST** refuse a family it does not reach rather than forward the key to another. The models route declares the families its chat route reaches in `providers`, and a client **MUST NOT** name any family a backend does not list: absent means `["openai-compat"]`, because a backend that predates the header forwards every key to an OpenAI-compatible endpoint, so a Claude key sent to it would reach OpenAI. Studio sends the header only for `anthropic`, so an OpenAI-compatible request is byte for byte the one it was before the header existed, and draws its provider picker only when the backend lists `anthropic` (or that family is already drafted or stored, so a reader can always switch back).

**Key provenance holds per family.** `@jxsuite/server` reads `ANTHROPIC_API_KEY` and `ANTHROPIC_BASE_URL` for this family as it reads `OPENAI_API_KEY` and `OPENAI_BASE_URL` for the other: an environment key is attached only to its own family's environment or default base URL, never to the other family's and never to one the caller supplied (`@jxsuite/server` §4.2), and the link-local guard of §4 applies unchanged. A client that keeps its key for an OpenAI-only path (Studio's site importer names components through one) **MUST** withhold a key of another family, and that family's endpoint, from that path.

**The upstream.** An `Upstream` of `family: "anthropic"` (§2.4) has the API's origin as its base URL (`https://api.anthropic.com`, written without `/v1`, as `ANTHROPIC_BASE_URL` is), and the gateway posts to `<baseUrl>/v1/messages` with the key as `x-api-key` and `anthropic-version: 2026-10-21`. No session-affinity hint is forwarded (§2.5): the Messages API's prompt cache routes without one.

**The version 1 projection** (`toAnthropicRequest`) is the version 1 body in the Messages API's words:

1. `max_tokens` is always sent (`ANTHROPIC_MAX_TOKENS`, 32,000), because the API requires it and the version 1 body has no member for it. `stream` is true. No `thinking`, `temperature` or `tool_choice` is sent, so each model runs its own default.
2. The system prompt is the top-level `system`, and a `system` message in the history is appended to it in order, because a mid-conversation system message is not accepted by every model.
3. An assistant message is its text, then one `tool_use` block per call in order; a call's `input` is its arguments parsed, or `{}` when they do not parse to an object (the call already carries an error result). Its reasoning is not sent (§2.2). A message left with neither text nor a call is not sent.
4. A run of `tool` messages is one user message of `tool_result` blocks, with `is_error` set when the result reports `success: false`, as the neutral model reads `isError` (§2.3).
5. A user message is its text, and an empty one is not sent, because the API refuses an empty text block.
6. The history starts at a user message that is not a tool reply, so a leading assistant turn and the replies to its calls are dropped together, and a trailing assistant turn is never sent, because the current models refuse an assistant prefill.
7. A tool-use id outside `^[a-zA-Z0-9_-]+$` (a provider's id from before the conversation moved to Claude) is rewritten deterministically, the same way on the call and its reply, and suffixed when the rewrite collides.
8. A tool is its name, description and parameters as `input_schema`, an empty object schema when it has none. Only to `api.anthropic.com` does the request carry automatic prompt caching (top-level `cache_control`) and `eager_input_streaming` on each tool, because an Anthropic-compatible endpoint elsewhere may refuse a member it does not know (the rule §2.5 applies to the OpenAI-compatible wire).

**The normalizer** (`normalizeAnthropicStream`) yields the frames of §2: a `text_delta` is `delta`; a non-empty `thinking_delta` is `reasoning`, while on version 1 signatures and redacted thinking are not forwarded; a `tool_use` block is `tool_call_start`, a `tool_call_delta` per non-empty `input_json_delta`, and `tool_call_end` at its stop. `usage` reports `inputTokens` as everything read (uncached, cache reads and cache writes) and `cachedInputTokens` as the cache reads, immediately before `done`. Stop reasons map `end_turn` and `stop_sequence` to `stop`, `max_tokens` and `model_context_window_exceeded` to `length`, and `tool_use` to `tool_calls`, and pass any other (`pause_turn`, `refusal`) through. A body that ends without `message_stop` still closes its open calls and ends with `usage` and `done`, which says `truncated` when no stop reason arrived either. An `error` event is an `error` frame carrying an `upstreamFailure` problem and the API's error type as `code`, and it ends the stream; a non-2xx response is the same frame the OpenAI-compatible normalizer gives one.

**The native projection** (`toAnthropicMessagesRequest`, wire version 2). A version 2 request to an `anthropic` upstream is projected from the neutral conversation rather than from its OpenAI form:

1. An assistant message is its blocks in the order they were produced: a signed thinking block as `thinking` with its `signature`, a redacted one as `redacted_thinking` with its payload, text, and a `tool_use` per call.
2. **The replay rule.** A signed block records, as `provenance.binding`, the digest of the request that produced it: the system prompt's text, the tools as the model is told of them (name, description and schema), and every message before it with its reasoning removed (`bindingOf`). On a later request the same digest is computed for the block's message. Blocks are sent only in the **trailing run** of assistant turns whose signed blocks all still bind; the thinking of every turn before that run is not sent, which the API accepts, because a leading run of thinking may always be removed. Reasoning is left out of the digest's prefix for that reason: removing earlier thinking must not unbind what follows. Thinking another family produced, or that carries neither a signature nor a redacted payload, is never sent.
3. **One retry, with nothing replayed.** A request that replays thinking and is refused with `400` as bound to a different conversation is sent once more with every thinking block removed, which is always accepted. Nothing else is retried. Where the platform offers binding controls (`thinking-binding-controls-2026-08-01`), a host may instead have the request say what the API does with a block that does not bind (`drop_block` or `error`); it is never the default.
4. A run of `tool` messages is one user message of `tool_result` blocks, placed first in it, and a person's message that follows rides on the same user turn after them.
5. A `system` message before the conversation begins joins the top-level `system`. One in the middle of it is a `system` message where the model accepts one (the Opus, Fable and Mythos lines), and otherwise a text block on the user message that follows, after any tool results.
6. The history starts where a person speaks, dropping a leading assistant turn together with the replies to its calls, and a trailing assistant message is never sent.
7. A tool-use id outside `^[a-zA-Z0-9_-]+$` is rewritten from the id and the index of the message that made the call (`anthropicToolId`), the same way on the call and its reply and on every request.
8. To `api.anthropic.com` alone, the request marks its cacheable prefixes with `cache_control`: the last system block the client flagged `cache`, the last tool, and the last user message, four at most. Studio flags the prefix of its system prompt that is the same for every request (`splitSystemPrompt`, §2.5), so the instructions and the tool list are read from the cache however the rest of the prompt changes.
9. `max_tokens` is the request's `maxTokens`, or 32,000; `temperature` is forwarded when given.

**Binding a block.** The turn engine closes each signed or redacted block at the end of its round with its provenance (the family and model the stream's `stream_start` named) and the binding of that round's request, reports it as a `reasoning_block` event before `round_end`, and keeps it on the round's message (§3.8). A host that keeps its own transcript records it there: chat-state's `appendReasoningBlock` rebuilds the streaming message's `blocks` as the signed thinking, then the text, then the calls, since the v1 members cannot carry a signature. A change to the system prompt, the tools or any earlier message therefore makes the bindings after it stale, and the next request simply sends that thinking no more. **A saved conversation keeps signatures only on its latest signed turn** (`stripOlderSignatures`): an earlier turn's are bound to a request a reloaded window will not send again, so only their text is kept.

**The normalizer on version 2.** Each `delta`, `reasoning` and `tool_call_start` names its content `block`; a signed thinking block ends with one `reasoning_signature` carrying the whole signature; a redacted block is one `reasoning_redacted`. `usage` adds `cacheWriteInputTokens`, the cache writes. On either wire, a body that ends having sent neither `message_stop` nor a stop reason finishes `truncated` (§2), and a failure whose sentence says the prompt is too long is the `context-overflow` problem with the code `context_overflow`, the one place the gateway reads a provider's wording.

**Reaching Claude directly.** `createAnthropicProvider` in `@jxsuite/ai/providers` is the same projection and normalizer behind the `Provider` shape of §2.7, for a host with no backend in between. Its capabilities are the family's: the system prompt and the tool list must stay fixed for thinking to stay bound (`promptLayout: "append"`, `toolListing: "stable"`), a token ceiling is required, and four cache breakpoints are allowed.

**The listing.** The models route lists the caller's own catalogue from `GET /v1/models` (`listAnthropicModels`), each model's `display_name` as its name and `max_input_tokens` as its `contextWindow`, following `has_more` for at most ten pages. It always declares a `defaultModel` (`claude-opus-5-5` on `@jxsuite/server`), and Studio falls back to that model for the Anthropic family when neither the user nor the backend chose one, because an OpenAI model id is never served there. A listing that fails answers a Claude default catalogue with `upstreamError` and `upstreamMessage`, as §2 requires.

### 2.7 Wire version 2

> **Status: Implemented.** The body, the frames, `negotiateWire` and `WIRE_HEADER` in `packages/ai/src/streaming-client.ts`; the gateway's check and projection in `packages/ai/src/gateway/wire.ts`, adopted by `createChatHandler`; the provider adapters in `packages/ai/src/providers/` (`@jxsuite/ai/providers`); the published schemas in `packages/ai/schemas/`, written by `packages/ai/scripts/generate-wire-schemas.ts` and held fresh by `bun run schema:verify`. Tests: `packages/ai/tests/gateway-wire.test.ts` (the hand check against the published schema, over one corpus), `gateway-chat.test.ts`, `streaming-client.test.ts`, `providers.test.ts`; Studio's send path in `packages/studio/tests/ai-loop-wire.test.ts`.

The version 1 chat body is the OpenAI chat-completions conversation: a backend that forwards to another family has to guess that conversation back out of one provider's words. **Version 2 sends the neutral conversation of §2.3 instead**, so the backend projects it onto whichever family it reaches.

- **The body.** `{ wire: 2, model?, system, messages, tools }`, with optional `maxTokens`, `temperature`, `toolChoice` (`auto`, `none`, `required`, or `{ name }`), `reasoning.effort` and `metadata`. `system` is the prompt's parts, joined in order with nothing between; a part may carry `cache: true` to mark the end of what stays the same across requests. `messages` are wire messages (a role and its blocks), with every tool call already beside its reply: a gateway never repairs a conversation (§3.4). `tools` are tool specs in the order the client lists them. `metadata` (`sessionId`, `turnId`, `round`) is for the backend's own audit and rate limiting and is **never forwarded** to a provider.
- **Version 1 is accepted forever, and is the default.** A client sends version 2 only to a backend whose models probe lists `2` in `wire` (§2); `negotiateWire(probe)` is that rule. A backend that advertises nothing is sent the version 1 body it has always read.
- **One transcript, one upstream request.** A gateway reads a version 2 body as the version 1 body it describes, through the projections a version 1 client applies before it sends, and forwards that. So the same transcript reaches an OpenAI-compatible upstream as the same bytes on either wire, which keeps a provider's prompt cache warm across a client upgrade. The members version 1 has no word for are forwarded as the family's own (`temperature`, `max_tokens`, `tool_choice`, `reasoning_effort`).
- **The answer names its wire.** Every chat stream carries an `X-Jx-AI-Wire` response header naming the version it was served on, and a version 2 client sends the same header beside its body. A version 2 stream opens with one `stream_start` frame (`wire: 2`, the upstream's `family`, the `model` the request was forwarded with, and optionally the provider's `requestId` and a `droppedThinking` count). Two more frames exist only on version 2, for a family that signs its thinking: `reasoning_signature` and `reasoning_redacted`, each naming the `block` it belongs to. The eight version 1 frames are unchanged, gain only optional members (`block` on `delta`, `reasoning` and `tool_call_start`; `signature` on `tool_call_end`), and **a version 2 frame is never sent to a version 1 request**.
- **A wire the backend does not accept is refused, saying which it does.** A body naming a version the gateway does not accept is a `400` `wire-unsupported` problem whose `supported` member lists the ones it accepts, sent before any upstream is contacted. A body that names `wire: 2` and is not a version 2 request is a `400` naming the JSON Pointer of the first member that fails. The proxy client answers `wire-unsupported` by sending the same round again as version 1, **once**, and speaks version 1 for the rest of its life: the probe said version 2 was accepted, so this is a backend that changed underneath the client, and the turn must not fail for it.
- **A host may hold its clients to version 1** by passing `wire: [1]` to `createChatHandler` and advertising the same list from its models route.
- **Provider adapters.** `@jxsuite/ai/providers` reaches a family directly behind one shape: a `Provider` takes a round's request in the neutral model and yields version 2 frames, opening with `stream_start`, and declares its family's `capabilities` (whether the system prompt may be rebuilt between rounds, whether the tool list may change, whether a token ceiling is required, and how many cache breakpoints a request may carry). `createOpenAICompatProvider` sends the chat-completions body the direct client sends, built by one module, and reads the answer with the one normalizer (§2.4). `providerModel(provider, model)` is the model function a turn engine calls (§3.8). Studio never imports it: the page talks to a backend, and the backend talks to the provider.
- **The schemas are published.** `@jxsuite/ai/schemas/wire-v2.request.schema.json` and `wire-v2.frame.schema.json` are JSON Schema 2020-12 documents of the body and of one frame, for a backend written in another language. They are build outputs. The gateway does not validate with them, because it runs in a Worker: `checkChatRequestV2` checks by hand and returns the pointer of the first failing member, and a test holds it to the request schema.

## 3. Tool Surface

The tool list this paragraph defers is still not enumerated here, although `AI_TOOL_TIERS` in `packages/studio/src/services/ai-system-prompt.ts` and the command records that declare `aiTool` are that list.

The tool schemas and the edit-application path live in `packages/ai/src`. This section is a placeholder; the concrete tool list will be enumerated here once it stabilizes.

### 3.0 The assistant is addressable by name

Every capability the chat surface offers is a command record in the `Assistant` category — Focus Composer (`⌘⇧A`), New Chat, Chat History, Retry, Attach Selection and Stop — so each one is in the palette, in the generated keyboard sheet, and rebindable, and the chat header's buttons RUN those records rather than calling module functions beside them. They are `level: "application"`, including Attach Selection: it READS the selection and WRITES a chip into the composer, and a record is filed by the level of the state it writes.

Two context keys gate them and had no readers before: `ai.configured` (a provider is connected) and `ai.streaming` (a turn is in flight, which is the only state in which Stop can act). **A turn is in flight from an accepted send until its loop ends**, its tools, questions and imports included: the chat's own status belongs to the token stream and reads idle while a round's tools run (§3.4), so it cannot answer the question. **One window runs one turn**: a send while one is in flight starts nothing, the composer offers Stop for the whole of it, and Retry is refused until it ends. A question the turn is waiting on outranks Stop in the composer, because a send while it waits is its answer. A turn that Stop, New Chat or Open Session ends still holds the window until its loop has unwound, which is as late as the call it was running allows; a hand-off that starts the next turn (the New Project Import and Agent prompts) waits for it to end rather than being refused. None carries an `aiTool` projection — the assistant does not get to end its own conversation.

### 3.1 Schema gate

Every tool that produces a document or `project.json` is gated on JSON-Schema validation, and failures are returned to the model as tool errors so the agent loop self-corrects. A call whose arguments do not parse to a JSON object never reaches its tool: it is answered as a parse failure that names what it got (`Failed to parse arguments: arguments must be a JSON object, got null`), so the model reads a malformed call and a call of the wrong shape as one kind of mistake. Canvas mutations validate AFTER applying (undo is the backstop, and only NEWLY introduced errors are reported); disk writes validate BEFORE writing, because a disk write has no undo. The same rule binds every host of the document tools (§3.9): a host that can take an edit back commits and then reports what it broke, and a host that cannot validates before it commits. `project.json` is gated against the project entry document, not the document one. **A document tool refuses an edit that would corrupt the tree or succeed without effect**, before it opens a transaction, so a refusal leaves the document, its history and the turn's ledger untouched and the sentence names the argument at fault: an index that is not a non-negative integer, a path that ends on a text child, a children array or a plain value where an element is needed, a move of a `$switch` case or a repeater's template (neither is a child in a children array), a move into the moved node's own subtree, and a nested style rule (`@…`, `:…`, `&…`, `[…]`) sent through `set_style`, which can only write a string. **An index written as a canonical numeric string is coerced** to the integer it names (`"2"` is 2, `"02"` and `"2.0"` are refused), in an index argument and in a path segment after `"children"`, because the argument validator admits a numeric string for an integer and a path admits strings as keys, and `["children", "1"]` resolves and then fails every splice test downstream. An index past the end is clamped, recorded at the slot the node actually lands in, and reported by its landing path, so the summary names the path the model's next call needs. Evidence: `packages/studio/tests/ai-tools-strictness.test.ts` and `packages/ai/tests/jx-tools.test.ts`.

**A render check follows the schema gate, and judges a page as the build would draw it.** A schema-valid document that throws when rendered is refused too, and a page that builds must not be refused for what only the build supplies. So the check awaits the data the document's class entries look up, for at most five seconds; draws a dynamic route with the first entry its `$paths` lists; and gives a page or a layout its `$page`, `$site` and project state. It reports only a template that still throws after that. Where it cannot supply what a template reads, because a lookup is still out or a route has no entry to draw, it does not refuse on template throws, since a live binding recovers on its own if the data was all that was missing; a render that throws outright is still refused. One entry is a sample: the build is what checks them all.

**A render check never calls a `timing: "server"` function, and never sends a document's `Request`.** The check runs without the author asking, on every write, against documents the model wrote. Calling the function would run project code with the project's secrets and arguments the model chose, and sending the request would reach a URL the model chose, with a method and body it chose. Nothing distinguishes a read from a write in either. Each entry reads as a placeholder instead: anything may be read from it or called on it and it prints as nothing, so templates over live data evaluate and every other template on the page is still judged. Whether a template reads live data correctly is what the editing canvas answers, which runs each such entry once and draws its answer (`studio.md` §4.5, "Remote data is fetched once").

**A lookup that fails is still a refusal, and says so.** A class entry that failed or came back empty leaves a template reading it with nothing to read, which is usually a mistake the model can fix. The refusal names the entry and its source rather than reporting a name missing from `state`, which it is not.

The gate uses the ACTIVE project's generated entry documents — the same payload and the same single fetch that drives the editor's diagnostics (studio.md §4.2.1), falling back to the bundled core schemas. Validating the loop against core alone under-checks it: the entry documents are what close the composition (`unevaluatedProperties: false`) and union in each enabled extension's shapes, so a model can otherwise ship an extension section its own tool call called clean and the editor flags the moment a human opens the file. The document-path convention the gate covers (`pages|layouts|components|elements`) tracks the editor's fileMatch globs for the same reason.

### 3.2 The turn is accountable

An assistant that edits documents must be able to say what it changed, and the author must be able to take it back. Four properties are normative.

**Every write is recorded, with whether it reached disk.** A tool that mutates the open document goes through the transaction path and is therefore reachable by undo; a tool that writes a file directly is not. That difference is a **fact recorded per write**, not a caveat in the system prompt, and the turn's summary states it: _"Changed 2 files · 1 written to disk — undo cannot reach it."_ **Restore to here** is offered only when every recorded change was transactional, and it re-checks at the moment it is clicked, because the ledger is bounded and may have been trimmed. **Restore undoes the turn, not the active tab.** The turn's batch lane (§3.3) returns a receipt for each step it closed, naming the history entry by identity rather than by index, which the history limit moves; the receipts are filed with the turn's writes. Restore takes back every step of the turn, in every document it wrote, newest first, and only while each is still the top of its tab's history. Every receipt is checked before anything is undone, and Restore refuses the whole turn with a sentence naming the document when any one fails: an edit made since the turn began sits on top (including a person's edit that split the turn's step), the step was already undone, the tab was closed, or the document is shared live and its undo belongs to the collaboration session, which Restore cannot inspect. Redo is offered with the confirmation only when the one tab restored is the active one, since redo reaches the active tab alone. Evidence: `packages/studio/tests/ai-restore.test.ts`, and the cross-tab case in `packages/studio/tests/ai-loop.test.ts`. A turn's writes are filed under the **last assistant message it drew**, the one the transcript renders the summary beneath, which is not always the last message: a turn can end on a tool reply (a Stop during the last call, or a cap reached with nothing applied, which draws no message), on a final round that said nothing, or after a stream error removed its round's partial. A turn capped after applying changes files under its cap message (below), which is drawn. A turn whose user message has left the transcript (another chat was opened while it ran) files under nothing, and writes nothing more into the transcript that replaced it. The ledger lasts as long as what it describes: New Chat drops it with the messages it is drawn under, and leaving a project (for another, or for none) drops it with the files it names, because a summary carried across would describe files the open project does not have. Adopting a project from none keeps it, since a bootstrap conversation follows the project it made.

**A tool chip states its outcome, not just its name.** A chip that cannot fail looks identical to one that did. The loop attaches each call's result to the call's own record, on the request that made it, as the call finishes, and the chip renders that record while the turn is still running; a restore backfills the same outcome from the `tool` reply (§3.4).

**A turn that stops working still answers.** Exhausting the tool-call budget does not end the turn on a canned sentence: the model gets one closing round to say what it found, what it changed and what is left (§3.8), so a turn that spent its budget reading still answers the question it was asked. What follows governs a turn whose closing round gave no reply.

**Partial success is not failure.** Exhausting the tool-call budget after applying changes ends the turn with an ordinary message describing what was applied. Rendering it as an error is wrong twice over: it misreports the turn, and the error path _deletes the streaming message_, destroying the only account of the edits that did land. A stream error is what that path is for: it removes the failed round's partial message, which may carry a tool call cut off mid-arguments and would otherwise go out on the next send, and keeps every round before it with the calls they ran. **Applied means a change was recorded**: a call counts as applied when it succeeded with a summary **and** the write ledger grew by an `ok` write while it ran. A summary alone is not enough, because a read (`list_files`, `search_files`, an answered question) reports in a sentence too. A change the tool itself reports back as a problem (one that introduced schema errors, say) is not applied either: it stays in the document, and it is the error the model is asked to fix. Creating or importing a project is a write, recorded as one to disk, since the project exists on disk from then on and no undo reaches it. A turn that only looked around and exhausted the budget applied nothing, so it ends as an error, and the message it would have written lists only the calls that changed something.

**A turn that drew nothing says so.** When the model answers with neither text nor a tool call, and nothing earlier in the turn was drawn either, the turn ends on an error row ("The model sent back an empty reply.") with Retry, rather than leaving the author's message without a reply. A stopped turn is never empty: the author ended it.

### 3.3 The batch follows the document, not the tab

A multi-tool turn may move between documents. The undo batch and the collaboration publish must follow the document each tool actually wrote — anchoring once, to whichever tab happened to be active when the turn opened, silently files one document's edits under another's history.

**The batch belongs to the assistant, one segment per document it writes, and a person's edit is never folded into it.** A turn opens a batch lane owned by its actor (`assistant:<sessionId|local>:<turnId>`, the id each call's context names), and every write the turn makes on a document joins that document's segment, opened on the turn's first write there. The segment becomes one history entry, tagged with the actor and the turn, when the turn ends; a document the turn never wrote gets no entry at all, so a turn that only answered leaves every history where it was. Anyone else's write to a document with an open segment (the person typing, an undo, another actor) closes the segment first: the assistant's step lands, then the other writer's after it, in the order they happened, and on a collaborative document the assistant's buffered ops reach the shared tree before the other writer's. Writes the assistant makes through a command (`delete_node`, `duplicate_node`, and every other projected record) are its own too; the attribution scope that carries the actor into them is synchronous, so a write made after an await is not attributed by accident. A loop with no document of its own (the evals) opens no lane, and each tool is its own entry. Project adoption closes every open segment before the project is replaced, against the document it was written into. Evidence: `packages/studio/src/tabs/transact.ts` (`openBatchLane`, `runAsActor`, `isBatched`, `flushOpenBatches`), `packages/studio/tests/transact-lanes.test.ts`, `tests/collab-transact.test.ts`, `tests/ai-loop.test.ts`, `tests/ai-command-tools.test.ts`.

### 3.4 A turn may stop and ask

An assistant that must guess, or apologise for not knowing, is worse than one that can ask. `ask_user` suspends the turn on the author and resumes with their reply. Five properties are normative.

**The mechanism is the invoker, not a new state.** `ask_user` declares the question it puts and what the answer means, and no tool body waits on the author: the invoker answers that the call needs a person before any tool code runs, the turn puts the question through the host's interaction strategy and waits on the answer, and the invoker settles the call with it (§3.11). Nothing in the chat state or the streaming protocol changes. `finishStream` has already run by the time tools execute, so a waiting turn is idle by construction — "waiting" is the presence of an outstanding question, not a fourth status. That idle is the token stream's, not the turn's: the turn is still in flight (`ai.streaming`, §3.0), so Stop stays on offer while the question waits, and a Stop settles the question as unanswered.

**A skip is a success, and only a stopped turn is a failure.** "You decide" is a real answer to a fair question. Reporting it as an error would have the model apologise for asking, and would end the turn on the error path — which deletes the streaming message (§3.2).

**The answer is a tool result, never a user message.** The wire format requires a `tool` reply to follow its `tool_calls` request; a user turn spliced between them is rejected. The reply is rendered into the question's own chip, so the exchange has one account in the transcript rather than two that can disagree.

**An interactive round does not spend the tool-call budget.** The round cap bounds AUTONOMOUS work, and a round that ends by blocking on a person cannot advance without them — which is the property the cap was ever a proxy for. A separate hard ceiling keeps the loop terminating regardless.

**A question does not survive a reload, and does not pretend to.** In Studio the wait is in memory and the transcript is not; a host that checkpoints a turn can do better, and §3.11 leaves the wait to the host. The conversation is saved as a question is put, as well as when a turn starts and ends, so a reload while it waits still finds it, and a restored question that was still open renders inert and says why. **A restored question that was answered shows its answer**, and every restored tool chip shows how its call ended. The outcome is persisted once, as the `tool` message that answered the call (the one the wire carries): a save strips `result` from every record so the payload never holds a second, disagreeing copy, and a restore backfills each call's `result` from the reply among the `tool` messages directly after its own request. Nothing is in flight after a restore, so an ordinary call nothing answered never completed and says so. A synthesized seal (below) is likewise an ordinary call's outcome, but it is not an answer to a question: a sealed or unanswered question restores as still open. The same reload — and ordinary history truncation, and a turn stopped mid-tool — can separate a `tool_calls` request from its reply, so the send path repairs the pairing, per request rather than by call id across the transcript, because a provider may number its calls afresh every round. A reply belongs to the closest earlier request that made its call and has no reply for it yet; a reply found later than that request, with other messages between, is moved back to directly after it; a reply with no such request is dropped. A request left with a call nothing answered gets a synthesised failure for it, directly after the request and before its other replies, and the failure says why: that the call was cut off before it finished, when its arguments do not parse, and otherwise that the session was reloaded or the history trimmed. Either one is a seal, not an answer. The repair is idempotent, and the turn engine runs the same one over a turn's history at its start (§3.8).

**What may be asked is bounded.** A question the model could have answered with another tool is waste, and a question about an option the answer cannot reach is worse than waste, because the reply cannot be honoured. Both are stated in the prompt as prohibitions.

### 3.5 Bootstrapping by import

`import_site` is `create_project`'s sibling: it clones a live site into a new project and adopts it into the window. Five properties are normative.

**Availability is a tier AND a capability.** "No project is open" is exactly as true on a backend with no import pipeline as on one with it, so a tier alone cannot express this; the tool declares the PAL member it needs, and one predicate answers for both the prompt's tool list and the execution gate. A tool the model is told about and then refused is a surprise to it; one refused without being told is invisible.

**The destination is the author's, not the model's.** When the run was started from the New Project wizard, the destination has already been chosen in front of the user, with a folder picker and a live preview. The tool takes it from there; a model-supplied path that disagrees is refused by name rather than silently preferred either way.

**Every create path initialises a repository.** The obligation in `specs/desktop.md` §4.5 is the create path's, not the wizard's — it belongs with whatever creates the project, and both bootstrap tools go through the same adoption sequence: version control, then the open flow, then a check that the workspace really moved. The adopter reports its failures rather than raising them, so a resolved promise is not proof.

**The project opens when it EXISTS, not when the run ends.** A crawl takes minutes, and adopting on the terminal line spent all of them with the author on the welcome screen — the only account of what was happening was a log in the sidebar. The pipeline announces the destination as soon as it holds an openable `project.json` (`specs/server.md`'s `ready` line), and adoption happens there, so pages, components and assets arrive in a file tree somebody is watching. Adoption runs at most once: a second one at the end would replace every tab the author opened while the crawl ran. A backend that sends no such signal is not broken — it is older — and the project opens at the end as before.

**The pipeline reports; the agent asks.** The import stream is one-way, so nothing pauses mid-crawl. What the run found — pages skipped by robots or by the node cap, the layout it did not detect, the components it may have split wrongly, per-page render fidelity — travels on the terminal line and becomes the material for §3.4, against real numbers rather than a guess made before the browser launched. The run's own account of itself outlives it: the transcript keeps the whole log under the tool call that produced it, scrollable and collapsed once the run is over, rather than showing a fixed tail of it and discarding the record on success. A Stop ends the run it interrupts and no other: once a run has finished or failed, a Stop later in the same turn leaves its outcome as it was.

### 3.6 Command tools

The assistant's tools are two kinds, and the difference is who wrote the tool.

**Hand tools** are registered in `packages/studio/src/services/ai-*.ts` and gated by tier: `AI_TOOL_TIERS` in `ai-system-prompt.ts` is the one table of them, carrying each tool's tier (`always`, `no-project`, `project`, `document`, `document-tree`) and its prompt blurb, and `document-assistant.ts` derives the gating predicates from the same rows. They exist for a write no person-verb makes: the seven tree writers address a node by path (the Inspector's job, not a command's), the file tools write arbitrary paths wholesale (`studio.md` §13.5's Remote Rule), and `create_project` / `import_site` re-key the conversation as a side effect a command must not know about. `ask_user` is a loop primitive, ungated. `open_document` is not a hand tool: it is the projection of the `document.open` record, whose `run` refuses by throwing when no tab holds the path and whose report names the document that IS active and whether the tree tools reach it.

**Command tools** are the command records that declare `aiTool` (`studio.md` §13.1), projected by `services/ai-command-tools.ts` as a view over the window's registry. Nothing registers them: each record IS its tool, `execute` is `registry.run`, `parameters` is the record's `args`, the gate is the record's own `when` / `enablement`, and `report` is what the model reads afterwards. The bridge's only additions are the two write witnesses, the ledger entry `undo` implies, and the schema verdict every document write already gets (`ai-write-report.ts`: new schema errors with fix hints, the render check, the token hints). The document witness holds an `undo: "document"` record to having written — an unchanged document root after `run` is "changed nothing", never success. The project witness is the same comparison over `project.json` for an `undo: "project"` record: every configuration write is a transaction on the configuration document (`tabs/project-config.ts`), so an unchanged configuration reference after `run` is a run that transacted nothing, and the ledger files nothing — `wrote: []`, mechanically, for every project record, whatever its report named. It is not a refusal: an idempotent verb asked for a state it already had is an ordinary answer, and a report that itself answered `wrote: []` keeps its sentence, because it says WHY nothing changed ("already enabled", "already one of this project's languages"), which the witness cannot; a report that claimed a write over an untouched file has its sentence replaced by "changed nothing". The per-record latches survive for that sentence alone, not for the ledger. A `report` that throws after `run` resolved is answered as a failure that says the run happened, with the ledger filed from the record's defaults, under the project witness too — the write must not vanish behind the sentence about it. A selection-level record takes `paths` and is run as `selection.setPaths` then the verb, both under their own gates.

**A tool with nothing it could be called with is withheld from the round.** A `derivedEnumProperty` on a REQUIRED argument serialises `enum: []` while the list behind it is empty — `enable_extension` with no catalogue, `disable_extension` with nothing enabled — and the record's gate cannot see its own argument list. So the bridge reads it: an enabled record whose required enum is empty is not advertised that round, in the prompt or on the wire, and returns the round the list does. An optional argument's empty enum withholds nothing, because the model can leave it out. The tool stays resolvable, so a call the model makes anyway meets the coercion's own refusal (`is not declared — declared: none`) rather than `Unknown tool`.

**Every projected tool is `strict: false`, deliberately.** `@jxsuite/ai`'s registry validator never checks `enum` and treats a required `null` as missing, which would refuse `select_node { path: null }` — a legal call. The registry's coercion (`coerceArgs`, applied inside `registry.run` for every caller) is the single validator, and its `RangeError` sentence is what the model reads.

**The loop sees one registry**, a catalog of both kinds (§3.10): its members are every hand tool and every record's projection, offered or not, and a name on both sides, or twice on one, refuses to build it rather than shadowing one tool with the other. What the model is offered each round is narrower than membership: a hand tool while its tier is active (`toolActive`, which the gate also refuses a call by, naming what the tier requires), a command tool while its record is advertised (its gate, and no empty required enum). A command tool's call is not refused by the catalog, because its record refuses it, in the person's own sentence. The prompt's tool list is the same two filters, so it advertises exactly what the gate will honour.

### 3.7 A tool call carries its context

> **Status: Implemented.**

A tool is handed everything it needs to know about the call it serves as its second argument, a `ToolContext` (`@jxsuite/ai/tools`), rather than reaching for it through module state. The same tool can then run in a Studio window, a Worker or an MCP server, and two turns cannot share a slot that belongs to one of them. Four properties are normative.

**The context carries per-call facts only.** It is `{ signal, callId, actor, ledger, session, progress }`: the call's own signal, the provider's id for the call, who the call acts for, the turn's write ledger, the conversation's session facts, and a sink for progress on a long call. A host service a tool needs (the adopter that opens a project, the store a wizard filled in) is bound when the tool is registered, not passed per call.

**The signal is the call's, not the turn's.** It aborts when the turn does, with the turn's reason, and the host unlinks it once the call settles (`linkCallSignal`). A Stop therefore reaches a call that is still running, a question waiting on the author or an import mid-crawl, and never a call that has already finished.

**A write is recorded on the call's ledger, and the ledger belongs to the turn.** Every call in a turn records into that turn's one ledger, and the host files it under the message the turn drew when the turn ends (§3.2). A tool run outside any turn, from a command or a test, gets a detached context: a signal that never aborts, an empty id, and a fresh ledger nothing files, so it records into no one's turn.

**What a conversation remembers is a session fact.** A fact a tool must keep across turns, such as an import having already run, is set on `ctx.session` and read back from it; the host decides how long the facts last. In Studio they last until New Chat: every turn of a chat sees the same set, and opening another chat from Chat History keeps them, which is how the one-import guard they replaced has always behaved. They are not saved with the conversation, so a reload starts with none.

A registry that wraps another (the availability gate, the union with the command tools) forwards the context unchanged, so the leaf tool always receives the one the host built. A definition declares `interactive` when its call suspends the turn on a person rather than doing work, which is how a host knows the round spends no work budget (§3.4).

### 3.8 The turn engine

> **Status: Implemented.** `packages/ai/src/harness/` (`@jxsuite/ai/harness`) and `invokeTool` in `packages/ai/src/tools.ts`; Studio's adapter is `packages/studio/src/services/tool-executor.ts` with `services/harness/`. `packages/ai/tests/harness.test.ts` holds the contract below, and Studio's recorded agent traces (`packages/studio/tests/fixtures/agent-traces/`) hold the adapter to the loop it replaced, call for call.

One turn of the assistant (stream a round, run the calls it made, feed the results back, until the model stops calling tools) is one engine, `runTurn`, that any host can run: a Studio window, a Worker, a headless test. The rules of §2 and §3.2 to §3.4 are the engine's, so a host cannot run a turn that breaks them. Nine properties are normative.

**A host hears every step, synchronously and in order.** `runTurn(input)` starts the turn at once and returns a `TurnRun`. Every step is a `HarnessEvent` carrying `v: 1`, the turn's id and a `seq` that increases by one from zero, and the host's `onEvent` is called with each before the engine takes its next step, so a host that keeps its own transcript applies the turn as it happens. The events of a turn follow one grammar:

- `turn_start`, then `transcript_repaired` when the turn's history needed the repair of §3.4, then rounds, then exactly one `turn_end`, after which nothing is emitted.
- A round is `round_start`; the streamed `text`, `reasoning`, `tool_call_start`, `tool_call_delta`, `tool_call_end` and `usage`; a `reasoning_block` for each thinking block the provider signed or redacted, closed with its binding (§2.6); then `round_end`.
- After a round that made calls, each call in stream order is `tool_start`, its `tool_progress` and `write`s, then exactly one `tool_result`. A call that never ran (the turn stopped first) has none. Calls run at once (see below) have their `tool_start`s and `tool_progress` before any of their `tool_result`s, which keep stream order.

The same events can also be iterated from the run, by any number of readers, each from the start of the turn whenever it begins.

**A turn ends one of six ways**, each a `TurnOutcome`:

- `complete`: the model stopped calling tools.
- `cap_partial`: the turn stopped working and ended on a message: the model's closing reply, or, when it gave none after something was applied, a message from the harness saying what (§3.2).
- `cap_failed`: the turn stopped working, nothing was applied, and the model gave no closing reply.
- `error`: the provider sent an error frame with a message. The round's message is dropped. A frame with no message is not a failure, as it never was.
- `cancelled`: the turn was stopped.
- `empty`: the model answered with neither text nor a tool call, and nothing earlier in the turn was drawn. The round's message is dropped.

Something the host supplied that throws is not a provider failure: when the model function, the registry's listing, a hook or `onEvent` throws, the turn ends by rejecting `outcome` rather than with an outcome, because the failure is the host's.

**A turn stopped between calls leaves calls unanswered, and the next turn seals them.** The calls after a Stop never run, so they have no reply in the messages the turn appended, and a provider refuses a request that repeats a call without its reply. The next turn seals them before it sends anything: it runs the repair of §3.4 over its history and reports it as one `transcript_repaired` event right after `turn_start`, carrying the ids of the calls it sealed and of the replies it dropped or moved. The event is emitted only when the repair changed something. A host that keeps its own transcript runs the same `repairToolPairs` over it, as Studio does before every send, and because the repair is deterministic both arrive at the same messages.

**The anchor is the last message the turn drew.** `anchorMessageId` is the last assistant message of the turn with text or a call, the cap message included (§3.2). The outcome also carries every message the turn appended in its final form, the writes the turn's ledger recorded, and the provider's last and total usage.

**The system prompt is fixed for the turn; the tools are listed each round.** A turn's `system` does not change between its rounds. The tools are read from the registry at the start of every round, so a call that opens a project makes the project's tools available in the very next round. The model function is called exactly once per round.

**One turn holds a lock at a time, and Stop is armed before anything else.** The run's signal exists before `runTurn` returns, aborted by `cancel` and by the host's signal with the host's reason, and each call's signal is linked to it only while the call runs (§3.7). A turn started on a `TurnLock` another turn holds throws `LaneBusyError` synchronously. The lock is released before `turn_end` is heard, so a host that starts its next turn on that event is not refused.

**A turn that stops working gets one closing round.** A turn stops working when it has spent its work budget (`maxWorkRounds`, 30 by default), when it has run `maxRounds` rounds of any kind (60 by default), or when a round has made the same calls and got the same results `maxIdenticalRounds` times (3 by default). A round whose calls were all interactive counts towards neither the work budget nor the repeats. The engine then runs one more round, marked `closing` on its `round_start`:

- The request ends on a harness note (`ModelRequest.closing`, already the last of `messages`) telling the model that no further call will run and to reply to the author. The note is a `user` message on no transcript: it is in neither the outcome's `appended` nor anything a host shows or saves, so a host projecting its request from its own transcript sends it from `closing`.
- The tools stay listed. A provider may refuse a history holding calls with no listing beside it, and an unchanged listing keeps the prompt cache for the last request.
- A call the model makes anyway is not run and not reported, so a transcript never holds a call this turn already decided to leave unanswered.
- A reply with text ends the turn `cap_partial` with no `cap` member, the model's message being the anchor. A round with no text, or a provider error (which `onStreamError` still hears), loses nothing: the turn ends as it would have without a closing round, with `policy.capText` as a `cap_partial` message when something was applied and a `cap_failed` error otherwise. A Stop is a Stop.

**Read-only calls may run at once.** With `parallelReadOnly` a run of neighbouring calls whose definition has `readOnlyHint` and is neither `interactive` nor an `interaction` runs concurrently, each with its own signal. Results are appended and reported in stream order, so the next request is byte for byte what a serial turn would send. A write or a question never joins such a run, so it still sees everything before it and everything after it sees its effects. It is off by default; Studio turns it on.

**A call reaches a registry one way.** `invokeTool` parses the call's arguments (an empty string is no arguments), executes it with its context, and returns the result as JSON would carry it. It never throws: arguments that do not parse, or parse to something other than an object, are answered `Failed to parse arguments: <reason>`, a result JSON cannot carry (a cycle, a `BigInt`) is answered as one that cannot be serialized, and the registry keeps its own texts for an unknown tool, failed validation, a gate and a tool that threw.

**A conversation that has outgrown its model is compacted between turns, never inside one.** What is displayed and what is sent part ways here (§2.2): the host replaces the earlier conversation with less, in its own transcript, before the turn's first request, so no tool call is separated from its reply and no request is cut mid-round. How it is replaced is a `CompactionPolicy` (`mode`, `thresholdRatio`, `keepRecent`), and `DEFAULT_COMPACTION` names each family's: **`keep-tail`** for an OpenAI-compatible provider, which drops the oldest messages and leaves a note saying how many, exactly as it always has; and **`summarize`** for Claude, which replaces everything before the new message with one summary message. The summary is the model's own: `summarizeForCompaction(model, request, signal)` sends the earlier conversation, under the system prompt and the tools it was held with, followed by a note from the system asking for a summary and nothing else, and answers the text the model wrote (a call it makes anyway is ignored). It costs a request, and it keeps what the conversation decided rather than what happened to be said last. It also replaces the whole prefix at once, which a provider that binds its thinking needs (§2.6): nothing that follows is bound to a history cut in the middle. An empty answer (the provider failed, the request was stopped, the model wrote nothing) means there is no summary, and the host keeps the tail instead; a turn the author stopped is left as it was. Both are triggered by the same measure: the context past 80% of the model's window, or more messages than the backend's `limits.maxMessages` (§2). Studio's are `trimContext` and `compactBySummary` in `packages/studio/src/services/context-manager.ts`, held by `packages/studio/tests/context-manager.test.ts` and `document-assistant-compaction.test.ts`; the helper is `packages/ai/src/harness/compaction.ts`.

**A long turn stays inside its window.** The engine does not budget a request's size, because only a host knows its window; a host that gives a turn many rounds keeps it inside. Studio's trim (§2.1) runs only when a message is sent, so before each round `shedToolResults` (`packages/studio/src/services/context-manager.ts`) checks the context against the trim's own budget, 80% of the window. Past it, the oldest tool results of 1 KiB or more are replaced in the transcript by what they ended as (`success`, `summary`, `error`) and a note saying to call the tool again, until the context is under 60%. The latest round's results are never shed, because the model has not read them, and a pair is never broken, because only a reply's content changes. A shed result stays shed: a later send measures what it will really send, a restored chip still has the call's outcome, and the prompt cache breaks once per batch rather than on every round past the budget.

### 3.9 Portable document tools

> **Status: Implemented.** `packages/ai/src/jx-tools/` (`@jxsuite/ai/jx-tools`); Studio's host is `packages/studio/src/services/harness/studio-documents.ts`, and `applyDocOpsAsUser` in `packages/studio/src/tabs/transact.ts` is the transaction it writes through. `packages/ai/tests/jx-tools.test.ts` holds the contract below; `packages/studio/tests/ai-doc-tool-ops.test.ts` holds the producers to the ops Studio's own mutators recorded for the same calls, op for op, and the tool listing to the bytes the model was sent before.

`read_document` and the seven tree tools (`set_property`, `add_child`, `set_style`, `set_text`, `add_state`, `update_state`, `move_node`) are one implementation that any host can run, so a Studio tab, a file on disk and a room's shared document are edited by the same code. Five properties are normative.

**A tree tool is a pure producer of doc ops.** Its `edit(doc, args)` reads the document and answers either the `@jxsuite/schema/doc-ops` ops the edit is, with the summary the model reads and the selection rule the edit carries, or the sentence refusing it (§3.1). It never writes the document and never throws for a refusal, so a host can run it once to check and again to commit. An accepted edit's ops apply to the document it was planned on without throwing, and their inverses, applied in reverse, restore it; the one residue is the empty `children` array an insertion into a childless node creates, which renders and validates as the absent key.

**A host resolves, snapshots and edits.** A `DocumentHost` answers which document a call addresses (or the sentence refusing the call when there is none), the document as plain data, and an `edit(ref, produce, meta)` that reads the document, calls `produce` and applies its ops synchronously, with nothing awaited between them, so nothing can change the document between the plan and the write. Its receipt is applied (and whether anything changed), or refused as `frozen` (structural edits are paused while a collaborator holds the source), `refused` (the producer refused the document as it stood at commit), `invalid` (a host that cannot undo would not commit an invalid result) or `not-open`. A host declares whether it can undo (`document`) or not (`none`), and §3.1's rule follows from that declaration.

**A refused call costs nothing.** The tool runs the producer against a snapshot first; a refusal is answered at once, with no validation, no transaction and no ledger entry. Only an accepted edit is bracketed by the host's write reporter (the standing before, the verdict after) and committed. The summary the model reads is the one the producer gave at commit, so it names where the edit landed in the document it actually ran on.

**An edit is an ordinary transaction.** Studio applies a producer's ops through `applyDocOpsAsUser`, which records each op with its real inverse, computed against the document just before the op lands, and applies the edit's selection rule inside the same transaction: replaced children drop the selection under them, and a moved node that was selected stays selected at the path it landed on. The gate, the turn's batch lane (§3.3), history, the canvas patch and the collab observer see it as they see the person's edit. No ops is no transaction at all: no new document root, no history entry, nothing published.

**The ledger says whether undo can reach the write.** Each committed edit records one entry, `disk: false` on a host that can undo and `disk: true` on one that cannot, which is what Restore and the transcript's undo caveat read (§3.2).

### 3.10 Catalog membership

> **Status: Implemented.** `packages/ai/src/catalog/` (`@jxsuite/ai/catalog`), with the argument check's seam in `catalog/validator.ts`, and `JX_TOOL_FACTS` in `packages/ai/src/jx-tools/facts.ts`; Studio's catalog is `packages/studio/src/services/harness/assistant-tools.ts` and its validator `packages/studio/src/services/harness/argument-validator.ts`. `packages/ai/tests/catalog.test.ts` holds the contract below, and `packages/studio/tests/ai-argument-validator.test.ts` the validator; `packages/studio/tests/ai-tool-availability.test.ts` holds Studio's catalog to the tools the registry it replaced offered and refused in seven states, by name and byte for byte, and `packages/studio/tests/ai-tool-specs.test.ts` holds every production tool to the facts table and the MCP projection.

A host's tools are one catalog, and the catalog separates two questions a registry used to answer together: which tools the host has, and which of them the model may use right now. Four properties are normative.

**Membership is decided once, and a bad member refuses the catalog.** `createCatalog(...groups)` keeps every tool in the order given and throws a `CatalogError` naming the tool when a name is not 1 to 64 letters, digits, `_` or `-` (what every provider and MCP accept), when two tools share a name, when a tool's parameters are not an object schema, or when a tool has no title or no behaviour hints. A plain registry only warns on a duplicate; a catalog never builds with one, because a duplicate is one tool silently shadowing another.

**Every member states what it does.** A member carries a person-facing `title` and all four of MCP's behaviour hints, none left to a default: `readOnlyHint` (it changes nothing), `destructiveHint` (it may destroy or overwrite something a person made), `idempotentHint` (a second identical call does what the first did) and `openWorldHint` (it reaches outside the project). The Jx assistant's tools take theirs from one table, `JX_TOOL_FACTS`, which also names each tool's effect: none, the host's view, the open document, the project's configuration, or disk. A tool missing from the table is refused by the catalog, so a new tool cannot ship without stating its facts.

**What the model is offered is the host's view, never membership.** `catalogRegistry(catalog, view)` lists every member as `list()` and offers the model, as `listForLLM()`, the members the view admits: a `gate` that answers what a member requires (or nothing) and an `advertise` that withholds a member from the listing without refusing its call. The gate is asked again at call time, and a call it refuses is answered `Tool "<name>" is not available right now — it requires <what>.`, so a refusal names what to do. A host whose membership follows its own state, as Studio's command records do, passes the catalog as a function read on every call. The listing is a plain registry's, byte for byte.

**A call's arguments are checked against the member's whole schema.** A registry's own check knows required keys and primitive types. A member's schema says more (an `enum`, a `pattern`, the shape of a nested argument), and checking that takes a JSON Schema 2020-12 validator, which this package does not carry into a Worker. So a host supplies one as the view's `validator`, in the shape MCP's SDK asks a host for (`getValidator(schema)` answering a check that returns the data or an `errorMessage`), and `cachedValidator(compile)` wraps a host's JSON Schema library so each schema object is compiled once. The catalog asks it about a strict member's call **after** the registry's own check has passed, so a call that check has always refused is refused in the words it always was, and a call the schema refuses is answered `Validation failed: <what the schema required>` and is not run. A schema built with live getters is checked as it reads at the call. Studio's validator is ajv for draft 2020-12, **coercing types as the registry does** on a copy of the arguments: a number written as a string is still accepted, because models write one and the tools that take an index coerce it themselves, and the tool receives exactly what the model sent. Until ajv has loaded, and for a schema it cannot compile, a call meets the registry's own check alone: a missing validator is never what refuses a call.

**A member projects to MCP as data.** `toMcpTool(entry, { undoable })` names a member as an MCP `tools/list` result does: name, title, description, its parameters as `inputSchema`, all four hints stated, and the serving host's undoability under `_meta["com.jxsuite/undoable"]`. `toCallToolResult(result)` returns a result as MCP's `tools/call` does: the summary, then the data as JSON, each its own text block, or a failure's error with `isError`. Neither imports an MCP SDK.

### 3.11 Interactions and approvals run before the tool body

> **Status: Implemented.** `invokeTool` in `packages/ai/src/tools.ts` and the turn engine's strategies in `packages/ai/src/harness/run.ts`; Studio's store is `packages/studio/src/services/harness/interaction-store.ts`, owned by the document assistant. `packages/ai/tests/invoke-interaction.test.ts` and `packages/ai/tests/harness.test.ts` hold the contract below, and Studio's recorded agent traces hold its questions to the turns the loop that awaited inside `ask_user` produced, call for call.

A call that needs a person, a question the model puts or an approval the host requires, is answered before any of the tool's own code runs, so no tool body ever awaits a person and a host decides how a person is reached. Four properties are normative.

**An interaction tool is asked and settled, never executed.** A tool that declares `interaction` and `settle` is not run by the invoker. Its arguments are validated, then `interaction(args)` names the question (or the sentence refusing the call), and the invoker answers `needs_input` with it. The caller invokes the call again with the person's response, and `settle(args, response)` is its result. A refusal and a failed validation are results the model reads, with nobody asked.

**An approval precedes the body.** For every other tool the host's approval policy decides first: proceed, deny with a sentence the model reads, or confirm with a reason (`destructive`, `not-undoable` or `open-world`) and a summary. A call to confirm answers `needs_input` with an approval request naming the tool and its title; invoked again, it runs only when the response approved it, and otherwise answers `The author declined this call.` The default policy proceeds, which is what Studio and the evals run.

**The turn reaches a person through the host's strategy.** `inline` hands the request to the host with the call's id and signal and waits on the answer within the turn; the turn reports `interaction_request` before and `interaction_settled` after. `none`, the default, answers the call `<tool> needs a person, and none is available here.` A host resolves a request when the call's signal aborts too, with the answer a stopped turn gives: a question unanswered and not skipped, an approval refused.

**The answer is the call's result.** What the person said reaches the model as the call's tool result (§3.4), so a question and its answer are one entry in the transcript, and the round that only asked spends no work budget.

**Studio confirms what undo cannot take back, and nothing else.** Studio's policy (`studioApprovalPolicy` in `packages/studio/src/services/harness/approval-policy.ts`, held by `packages/studio/tests/document-assistant-approval.test.ts`) puts two kinds of call to the author before they run:

- **A disk write that replaces a file.** `write_file`, `create_component` and `create_page` write straight to disk, which Studio's history cannot undo. A write to a path that already holds a file is confirmed (`not-undoable`), naming the path; a write that creates a file proceeds, because nothing is lost. A path the tool will refuse is left for the tool to refuse.
- **Enabling an extension** (`enable_extension`), which installs a package from the registry (`open-world`).

Every other call proceeds: an edit to the document tree is one keystroke from being undone, so asking about each would cost the author more than it protects. The request is drawn in the call's own chip, as a question is (§3.4): what would happen, why it is being asked, and three answers, **Allow**, **Allow for this chat** and **Decline**. There is no "you decide": an approval is the author's alone, and skipping one declines it. A typed answer is read as one of the three or as a plain yes, and anything else declines, so a call the author did not clearly allow does not run. A declined call answers `The author declined this call.` and the turn carries on. **Allow for this chat** is recorded per tool in the conversation's session facts (§3.7), so it lasts as long as the chat does and New Chat starts with none. A policy may answer asynchronously, since whether a write replaces a file is something a host has to look up. The eval runner approves every call.

### 3.12 A suspended turn resumes from a checkpoint

> **Status: Implemented.** The `suspend` strategy, `suspendOn`, `resume` and the checkpoint in `packages/ai/src/harness/run.ts` and `types.ts`; `checkResume`, `policyDigest` and `turnDigests` in `packages/ai/src/harness/checkpoint.ts`; `digest` and `canonicalJson` in `packages/ai/src/messages/digest.ts`; `createMemoryHarnessHost` and `scriptedModel` in `packages/ai/src/testing/`. `packages/ai/tests/harness-checkpoint.test.ts` holds the contract below, including the equivalence: a turn suspended and resumed at every call leaves the document an uninterrupted turn leaves.

A window can wait on a person inside a turn (§3.11). A host that cannot hold a turn open across the wait (a Worker answering one request, a headless run, a server whose client went away) needs the turn to **stop where it can be picked up**. A turn that suspends ends with the outcome `suspended` and a **checkpoint**, and a later turn resumes it.

- **Two things suspend a turn.** With the interaction strategy `suspend`, a call that needs a person (a question, or an approval the policy asks for) ends the turn instead of waiting: the request is reported as `interaction_request`, and nothing of that call has run. With `policy.suspendOn`, a provider `error` frame whose `code` is listed ends the turn suspended instead of failed, for a failure worth waiting out (a lapsed brokered credential, a rate limit). Neither is the default: the strategy defaults to `none` and `suspendOn` to nothing, so a host that asks for neither sees the outcomes it always has.
- **The checkpoint is plain JSON** (`TurnCheckpoint`, `v: 1`): the turn and session ids, the model, the round and work-round counts, every message the turn had added (`appended`), the writes it had recorded and the summaries and errors it had collected, the `reason` (`interaction`, `permission`, `credentials` or `rate_limit`), and where it stopped. `pending` names the round that was cut short: its message, its calls in order, and the index of the first one still to run. `awaiting` names the call that needs a person and the request it made. A turn suspended on a provider error stopped between rounds, so both are null and the failed round's partial message is not kept. It is reported as a `checkpoint` event immediately before `turn_end`, and is on the outcome. A host stores it **in the same write as the conversation**, because the two describe one moment.
- **Resuming.** A host starts a turn with `resume: { checkpoint, response }`, the same `history` the original turn was given, and the same tools, policy and system prompt. The turn keeps its id, reports `turn_start` with `resumed: true`, and first finishes the round it stopped in: the awaiting call is settled with `response` (reported as `interaction_settled`), the calls after it run, and **no call before it runs again**. Then the rounds continue as in any turn. A `response` of null with a request still awaiting puts the request to the turn's strategy again. A turn suspended between rounds asks the model again from the same conversation.
- **No side effect is repeated or anticipated.** The call a turn suspended on had not run, so approving it later runs it exactly once, and declining it answers it as any declined call (§3.11). The calls before it had run and their results are in `appended`. A call after it in the same parallel group (§3.8) may have run, and is run again on resume; such a group holds only read-only calls, so nothing is done twice.
- **A resume is held to the turn it continues.** A checkpoint records a digest of the tools as the model was told of them, of the policy (its numbers, its switches and the words it would say; not its approval decision, which the host makes afresh), and of the system prompt. `checkResume(checkpoint, input)` compares them, and the model when the input names one. A resume that does not match ends at once with the `error` outcome and the code `resume_refused`, naming what changed, before any call or request: a call planned under one set of tools is not run under another. `digest(value)` is the identity used, `f1:` and the 64-bit FNV-1a hash of the value's canonical JSON; it tells honest values apart and is not a security boundary.
- **The checkpoint never travels through a client.** It holds the conversation, so it stays in the host's own store.

### 3.13 A persisted conversation

> **Status: Implemented.** `migrateTranscript`, `persistWindow` and `sessionTitle` in `packages/ai/src/messages/persist.ts`; `SessionStore`, `SaveResult`, `createWriteQueue` and `createMemorySessionStore` in `packages/ai/src/sessions.ts` (`@jxsuite/ai/sessions`); Studio's store is `packages/studio/src/services/ai-session-store.ts`, written through by `packages/studio/src/services/document-assistant.ts`. Tests: `packages/ai/tests/sessions.test.ts`, `packages/studio/tests/ai-session-store.test.ts`, `packages/studio/tests/document-assistant-save.test.ts`, and the frozen payload corpus in `packages/studio/tests/ai-session-corpus.test.ts`, which holds what the current build saves to the bytes an older build loads.

A conversation outlives the window that held it. What is kept, how it is read back, and what happens when it cannot be kept are one contract, whatever store is behind it.

- **One contract for every store.** `SessionStore` is asynchronous and per root (a project, or the empty root for a conversation with no project yet): `list` (most recently updated first), `load`, `save`, `create` (which makes the new conversation the active one and evicts the oldest past the limit), `remove`, `move` (the bootstrap re-keying of §3.5, safe to repeat), `getActive` and `setActive`. `durable` says whether what it saves outlives the process. The limits are every store's: 20 conversations a root, 50 messages a conversation, a title of 60 characters. The stores that touch a browser or a disk live with their hosts, so `@jxsuite/ai` stays Worker-safe; it ships the contract and an in-memory store.
- **What is saved is a window that starts at a person's message.** `persistWindow` keeps the last 50 messages and moves the start forward to the first of them a person wrote. A conversation that began on a reply or a tool result is one no provider accepts, and its first message answers something the reader cannot see. A window with no message from a person is kept whole.
- **The payload is a bare array of v1 messages**, and stays one an older build loads: the members added since (`blocks`, `meta`) are optional, and no reader is required to know them. A tool call is saved without its outcome, which a restore reads back from the tool message that answered it (§3.4).
- **Every read is migrated.** `migrateTranscript` reads any generation of payload as the current shape, on every load, and running it over its own output changes nothing, so no payload carries a version marker. A message stored without an id is given one **once**: the store writes the payload back, so the id it was given is the id it keeps. A synthetic message is named by `meta.kind` rather than by its id's prefix. An assistant message holding a call whose arguments do not parse, with no reply after it, is marked `meta.incomplete: "error"`. An entry that is not a message is dropped, and a value that is not a list is no conversation at all.
- **A save says how it went.** `save` answers a `SaveResult` and never throws or stays silent: `quota` when the store is full, `unavailable` when there is no store, and `not_in_index` when the conversation is not listed. **A conversation that is not listed is not written**: it was deleted, and a payload that came back afterwards would have nothing to list it under. Studio shows a full or missing store to the author once, as a notice that does not interrupt the turn, and withdraws it at the next save that succeeds; a deleted conversation is said nothing about.
- **Writes keep their order.** A store's operations run through one queue (`createWriteQueue`), in the order they were asked for, so a save still in flight cannot land after the New Chat or the Delete that followed it. The queue starts an operation at once when nothing is waiting, so a store whose operations are synchronous behaves as if there were none.
- **A migration keeps the original until its copy is written.** The single-conversation store an early build wrote becomes the first session of the sessions store on first read, and its key is removed only once that session's payload and index entry are both written. A store too full to take the copy keeps the original, and the migration runs again on the next read.
- A conversation is titled by `sessionTitle`: the first non-empty line of the first thing a person wrote in it, whitespace collapsed, cut to the limit with an ellipsis.

### 3.14 Project tools over a ProjectHost

> **Status: Implemented.** `packages/ai/src/jx-tools/project.ts` (`projectToolEntries`, `ProjectHost`, `normalizeProjectPath`); Studio's host is `packages/studio/src/services/harness/studio-project.ts`, registered by `packages/studio/src/services/ai-project-tools.ts`; the in-memory host is `createMemoryHarnessHost` in `packages/ai/src/testing/memory-host.ts`. `packages/ai/tests/jx-project-tools.test.ts` holds the contract below, and Studio's tool listing and availability goldens (`packages/studio/tests/ai-tool-specs.test.ts`, `ai-tool-availability.test.ts`, `ai-project-tools.test.ts`) hold the moved tools to the bytes and the answers they gave before the move.

The four file tools are the same wherever the assistant runs. `projectToolEntries(host)` builds `list_files`, `read_file`, `write_file` and `search_files` over a `ProjectHost`, and what the model is told about them, the caps on what they answer and the containment check are theirs, not the host's.

- **The host is where the files are.** A `ProjectHost` lists a directory, reads a file, writes one and searches by file name, every path project-relative, each rejecting with a message the model can act on. Studio's is over its platform adapter; `createMemoryHarnessHost` is a flat map of files for a test.
- **Every tool contains its path first** (§4). `normalizeProjectPath` answers the project-relative path or refuses an absolute path, a `..` segment, a drive letter or a home directory, before the host is asked anything, and the refusal quotes what was sent. A host still enforces containment itself.
- **The answers are bounded.** `list_files` walks breadth-first, skips `node_modules`, `dist`, `.git`, `.jx-cache` and dotfiles, and stops at 200 entries, saying it was cut; a directory that cannot be listed is skipped. `read_file` returns the first 48 KiB of a larger file and says how large it was. `search_files` returns 100 paths. `write_file` refuses content past 256 KiB.
- **A write asks the host first.** A disk has no undo, so what must hold before a file is replaced is decided before it is: `write_file` asks the host's `beforeWrite(path, text)` and writes only when it allows. The host may refuse with the sentence the model reads, and may hand back advice to append to the answer and an `afterWrite` to run once the bytes are on disk, whose text joins the summary. Studio's host refuses a file open in the editor with unsaved changes, validates and render-checks a Jx document, checks a project file against the project's own entry schema less the errors it already had, and afterwards reloads an open editor or hands the written configuration to the configuration document. A host with none of that allows every write inside the project.
- **A write is on the ledger as a disk write** (§3.2), succeeded or failed, so a host can tell the person it cannot be undone.
- **The words are the ones the model has always read.** The descriptions, summaries and refusals moved from Studio's tools unchanged; changing any of them is a change to what a model is told.

> **Status: Future.** The tools Studio projects from its command records (`delete_node`, `duplicate_node`, `check_accessibility`, `check_popovers`, `validate_redirects`, `add_project_locale`, §3.6) have no portable twin yet. They act through Studio's command registry, and a host that is not Studio (a headless run, an MCP server) would need each as a `DocTool` producer or a check over a `DocumentHost`. They wait for the first such host, with the creation tools (`create_project`, `list_starters`), which stay Studio's because they bootstrap a window.

## 4. Security & Trust

> **Status: Partial.** The file/RPC surfaces, the Origin/Host gate and path containment hold (`packages/server/src/net-guard.ts`). The base-URL host block that §2 names and the two IANA rows in §5 describe is narrower than both: `isBlockedHost` in `packages/server/src/ai-api.ts` refuses a hostname whose text begins `fe80:`, so the rest of `fe80::/10` (`[fe90::1]`, `[febf::1]`) is forwarded, and it tests `169.254.` against the dotted IPv4 spelling alone, so the IPv4-mapped form of the metadata address (`[::ffff:169.254.169.254]`, which the URL parser serializes as `[::ffff:a9fe:a9fe]`) is forwarded too. `packages/server/tests/ai-api.test.ts` covers only `169.254.169.254` and `[fe80::1]`.

The assistant executes only through the same file/RPC surfaces a human uses, behind the server's Origin/Host gate and path containment (`@jxsuite/server` §4.2). It has no independent network or filesystem access beyond the connected provider endpoint.

A host can require the author's approval before a call runs (§3.11): the approval is decided from the call before any of the tool's code executes, so a declined call has done nothing. Studio asks before the two kinds of call undo cannot take back (§3.11): a disk write that replaces a file, and an extension being enabled. Undo remains its backstop for document edits.

The file tools contain the path themselves before they validate or write anything. `list_files`, `read_file`, `write_file`, `create_page` and `create_component` refuse an absolute path, a drive letter, a home directory and any `..` segment with an error that quotes the path, and otherwise use the normalized project-relative path for the read or write, the open-tab check and the ledger. The server's containment remains the second check rather than the only one, and a refusal from the tool is one the model can act on.
