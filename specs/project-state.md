# Jx Project State Specification

## One Backend-Owned Model of a Project, Served by Every Studio Host

**Version:** 0.1.19\
**Status:** Implemented\
**Updated:** 2026-11-27\
**License:** MIT

## 1. Overview

Studio has three backends: the desktop backend (an Electron utility process on Node, `desktop.md` §7.1), the dev server (`server.md`, Bun) and the cloud (a per-project Durable Object in the hosted platform, `desktop.md` §10). Before this contract none of them owned a model of the project. Each forwarded filesystem events (`FsEvent`, `server.md` §3.1), Studio folded them into its listings (`studio.md` §9.2), and every cache Studio kept (the version map, component discovery, the usage index, the format registry, the open tabs) decided for itself what an event meant. A gap in the stream was repaired by re-listing (the `"open"`, `"reconnect"` and `"commit"` resync reasons, retired by §3.3), Studio's own writes were told apart from foreign ones by a 1.5 second window, and a write overwrote whatever was on disk.

This specification defines **one contract**, the project state service, that every host implements and one conformance suite tests:

- the host owns a file index with a stable document identity and a content hash per file, a revision counter with a replay log, a dependency graph, a readiness state and a git monitor;
- a client subscribes with the last revision it applied and receives either exactly the events it missed or a snapshot, on every connect;
- every event names its revision and its origin, so a client recognises its own writes by the bytes they wrote rather than by when they happened;
- a write or delete names the bytes it replaces, so a stale writer gets a conflict instead of silently overwriting (§5 states the one window a filesystem host cannot close);
- a client keeps one content store keyed by document and hash, and every cache it holds derives from it.

The contract is written in TypeScript first (`packages/protocol/src/project-state.ts`). A native core and durable persistence on the desktop are deferred until measurements ask for them (§13).

### 1.1 Scope

In scope: the wire types, the meaning of each event, revision and replay semantics, write preconditions, the two dirty notions, the readiness machine, the dependency graph's edge kinds, the rename cascade as one operation, what each host must implement, and what a client must derive from the stream.

Out of scope: the collaboration protocol (`collab.md`), which this contract hosts but does not redefine (§11.3); the Studio Backend Protocol's request routes (`server.md` §4.1), which remain the way a client reads a file's bytes; and the layout of any persisted store beyond the dialect rule in §13.1.

### 1.2 Terms

- **Host**: the process that implements this contract for one project (a desktop window's project session, the dev server's active project, a cloud project's Durable Object).
- **Client**: one Studio window or tab subscribed to a host.
- **Document**: any file in the project's index, whatever its format.
- **Revision**: a positive integer the host assigns to each event, strictly increasing within an epoch.
- **Epoch**: an opaque string naming one revision sequence. A host starts a new epoch whenever its revisions restart.

The key words MUST, MUST NOT, SHOULD and MAY are to be read as in `standards.md` §12.

## 2. Identity, Hashes and Revisions

> **Status: Implemented.** The types and the pure helpers ship in `packages/protocol/src/project-state.ts` (`contentHash`, `createEchoLedger`, `createMemoryEventLog`, tested by `packages/protocol/tests/project-state.test.ts`), and the conformance suite (§10.4), which an in-memory reference host passes, has a case for every rule below with one exception: the ledger clearing a path's entries on an external removal is pinned by `createEchoLedger`'s own tests, because no driver action can make a watcher lose an own write's observation, which is the only time the clearing shows. An identity kept across a rename through §9 is asserted by the §9 cases. Which hosts mint document ids, hash their files, keep a log and attribute events by hash is each host's own item (§10.1 to §10.3).

### 2.1 Content hashes

A content hash is the SHA-256 digest of a file's bytes, spelled `sha256-` followed by the standard base64 encoding of the 32-byte digest, padding included (`ContentHash`). A host computes it over the exact bytes on disk; a client computes it over the exact bytes it would write. Text is hashed as its UTF-8 encoding, so a host that reads a file as text and one that reads it as bytes agree. Equal hashes mean identical bytes for every purpose in this contract. A directory has no hash.

The hash is not the listing `version` of `studio.md` §3.4: a version is a token a host MAY issue for immutable caching, while a hash is computed by every host for every file and is never used as a cache lifetime.

### 2.2 Document identity

The host assigns every indexed file a `DocId`: an opaque string, unique within the project, that survives a rename performed through §9, a rename the watcher reports as one move, and an atomic-rename save (§2.4). A file removed and a file later added at the same path get different ids. Clients compare ids for equality only. The host also classifies each document into a `DocKind` (`page`, `layout`, `component`, `content`, `data`, `media`, `style`, `project-config`, `other`) from the project configuration and the file's location; a document whose kind the host cannot decide is `other`. A document in a format an extension registers is classified only once the host reaches `extensions-resolved` (§7), and is `other` until then.

> **Status: Implemented.** The conformance suite asserts the conventional locations' kinds, the index scope (a `build.outDir` other than `dist/` included), that a symlink is followed only inside the root, and that a document in a format an extension registers is `other` until `extensions-resolved`: the fixture's extension (`extensions/notes/`) registers the `.note` format, and a host held below `extensions-resolved` with it enabled reports a `.note` document, one on disk and one written while held, as `other` and classifies both once released. The reference host and the desktop host (`packages/server/tests/project-state-host.test.ts`, which loads the extension through the editor's registry) pass it.

**Index scope.** The index holds every file and directory under the project root except `.git/`, `node_modules/`, `dist/` (and the directory `build.outDir` names when it is another, `site-architecture.md` §3.1), `.jx/`, `.cache/`, `.devenv/`, `.direnv/`, and Bun's lockfiles (`bun.lock`, `bun.lockb`), at any depth. A symlink is followed only when it resolves inside the root. This is the ignore set the existing watchers apply (`packages/server/src/watch.ts`, `packages/server/src/watch-policy.ts`), and every host applies the same one, so two hosts serving the same tree produce the same snapshot. Paths outside the scope that a host still reads (the lockfile and installed packages for readiness, §7; `.git/` for the git monitor, §4.5) produce no file events.

### 2.3 Revisions, epochs and the replay log

Every change the host observes or performs produces one event, and every event gets the next revision. Revisions start at 1 within an epoch and never repeat or go backwards in it. The host keeps a **replay log**: a window of its most recent events, so that a client that missed some can receive exactly those. The window's size is the host's choice; the in-memory log (`createMemoryEventLog`) keeps 1024 by default. A log answers "the events after revision N" with all of them, oldest first, or with nothing at all: it MUST NOT answer with a subset, because a client cannot tell a partial replay from a complete one.

A host starts a new epoch whenever it cannot continue the old sequence: on process start for an in-memory log, and whenever a persisted log is discarded. An epoch SHOULD be unguessable enough not to collide across restarts (a random UUID suffices).

### 2.4 Origin and echo suppression

Every event carries `origin`: `{ writeId, writeHash }` when the change was caused by a write or delete through §5, whichever client issued it, or `"external"` for any change the host did not perform (another program, a `git checkout`). `writeHash` is `null` for a delete. Origin is **host-global**: the log and the snapshot are shared by every subscriber (§2.3, §3.1), so every subscriber sees the same origin for the same event, and each client decides which writes are its own with `isOwnOrigin` against the write ids it issued.

**A host records its own writes when it performs them.** A write or delete through §5 appends its file event, with its `WriteOrigin`, and updates the index's hash in the same step that changes the disk, before the host replies (§5). The watcher's later report of those bytes then carries the hash the index already holds, and the host emits nothing for an observation whose hash equals the indexed one (§4.2). That rule, not a time window, is what suppresses an echo, and it replaces the 1.5 second window of `studio.md` §9.2, which misattributes a foreign write landing inside it and an echo arriving after it.

**The echo ledger covers the one case the equal-hash rule cannot: an observation that is stale by the time the host compares it.** Before it writes, the host notes `(path, writeHash, writeId)` in an echo ledger (`createEchoLedger`), and it passes every observation at that path to the ledger before comparing it with the index. When the watcher read the file after write A and the host compares after write B, the bytes are A's: they differ from the index, and without the ledger they would be reported as an external change back to A. A hash matching a pending write is that write's echo, whose event is already in the log, so the host drops it; the match consumes that entry and every older one for the path, because a watcher may coalesce several writes into one observation that shows only the last. A hash the ledger does not hold is external: it clears every pending entry for the path, so a later external change that restores an own write's bytes (a `git checkout` of an earlier version) is never attributed to that stale write, and when it differs from the index the host emits it with origin `"external"`. A removal the host did not perform is external and clears the path's entries too. A host processes the observations of one path in the order the watcher reported them.

A watcher event that names a file costs a read and a hash; a host MAY skip it when the file's size and modification time equal the ones it recorded with its last hash. It records them only from a stat taken before the read they describe, and only when that modification time is older than the coarsest timestamp tick the project's filesystem may have (two seconds, FAT's), since an edit landing in the same tick can leave both unchanged; a host does not record them for its own write at all, so the first observation after it is always read.

**Atomic-rename saves.** An editor that saves by writing a temporary file and renaming it over the target is observed as a change at the target path, or as a removal followed by an add. A host holds an observed removal at a path for a pairing bound (`atomicSaveMs`, configurable per host, default 100 ms, the bound chokidar's `atomic` option applies); when a file reappears at the same path within it, the host reports one `fileChanged` for the existing `DocId`, or nothing when the bytes equal the indexed ones, attributed by hash like any other change. The bound decides identity only, never origin: a save slower than the bound is reported as a `fileRemoved` and a `fileAdded` with a new `DocId`, both still attributed by hash.

## 3. Subscription

> **Status: Implemented.** The exchange's types and the host's answer (`SubscribeRequest`, `SubscribeResponse`, `answerSubscribe`) ship in `packages/protocol/src/project-state.ts`, the wire codecs and the client's cursor (`createSubscriptionCursor`) in `packages/protocol/src/project-state-frames.ts`, and the conformance suite asserts §3.1 (§10.4). Which hosts accept a subscription is each host's own item (§10.1 to §10.3).

### 3.1 The subscribe exchange

A client sends a `SubscribeRequest` on **every** connect, the first one included: `{}` when it holds no state, otherwise `{ epoch, sinceRev }` naming the epoch and the last revision it applied. Every request MAY also carry `clientId`, a string naming the client (one Studio window or tab) that it keeps across reconnects, which scopes per-client state on the host (§11.3). The host answers with one `SubscribeResponse` and then streams every later event in revision order:

- `{ kind: "events", epoch, rev, events }` when the epochs match and the log holds every event after `sinceRev`. `events` is exactly those events, oldest first, and may be empty.
- `{ kind: "snapshot", epoch, rev, snapshot }` otherwise: a first connect, an epoch the host no longer serves, a revision outside the window or ahead of the host. The snapshot is the whole state at `rev`: every file in the index scope (`IndexedFile`: path, id, kind, whether it is a directory, hash, and `indexed`, whether the host has extracted its references, §8.2), the readiness state, the git summary when there is a repository, the set of discoverable component tags (`components`, §4.3), and the format-set token (`formats`, §4.4).

The host MUST take the snapshot and read `rev` without an event intervening, so that the first streamed event is `rev + 1`. A client applies a snapshot by replacing its state, not by merging: everything not in it is gone. The snapshot carries the component set and the format token so that a client never has to rediscover either after applying one.

**A host answers a subscribe in every readiness state**, so a client opening a project is never left without state. Below `indexed` (§7) a snapshot may list a file without a hash, with a provisional kind (§2.2), and with `indexed: false`. As the host hashes, classifies and extracts each file it emits `docChanged` with the filled-in fields (§4.3), and a client draws what it has and refines it on those events.

### 3.2 Transport bindings

> **Status: Implemented.** The three bindings' codecs, the `Last-Event-ID` parser and the gap detector (`checkContinuity`) ship in `packages/protocol/src/project-state-frames.ts`, tested by `packages/protocol/tests/project-state-frames.test.ts`. A host's use of its binding is that host's §10 item.

The exchange rides each host's existing push channel, with one frame per message:

- **Desktop**: the window's RPC WebSocket (`desktop.md` §7.2). The client sends the request `projectSubscribe` (`{ id, method, params }`) with a `SubscribeRequest` as its `params`; its reply (`{ id, result }`) is the `SubscribeResponse`, and later events arrive as unprompted `projectEvents` frames whose `params` is `{ epoch, events }`, sent to the socket that subscribed and never before its reply. A socket holds one subscription: a second `projectSubscribe` on it (a client repairing a gap) ends the first, which sends nothing more. When the host ends the subscription (§4.8, the window opening another project, or the socket holding more unsent bytes than the host buffers for one reader), the socket receives an unprompted `projectEnded` frame whose `params` is `{ epoch }`, naming the epoch that ended, and the client subscribes again, catching up from the log or a snapshot. A reconnect is a new `projectSubscribe`, and the old socket's subscription ended with it, unannounced, since a closed socket can be told nothing. A write or delete through §5 is the request `projectWrite` (a `WriteRequest` whose `contents` is a `WireContents`) or `projectDelete` (a `DeleteRequest`), answered `{ rev, hash }` or `{ rev }`; a refusal is the reply's `error` with the `412` problem document of §5 beside it as `problem`.
- **Dev server**: a dedicated Server-Sent Events stream at `GET /__studio/project/events`, separate from the reload stream of `server.md` §3.1. Every frame carries `id: <epoch>:<rev>`, naming the last revision the frame carries, so a browser's automatic reconnection sends `Last-Event-ID` and the server reads it as `{ epoch, sinceRev }`. The epoch and the revision travel in the one header because an `EventSource` cannot change its URL after construction, so a query parameter could not follow a reconnect. The epoch is everything before the last colon, and an absent or malformed `Last-Event-ID` reads as `{}`, a first connect. The first frame on every connection is the `SubscribeResponse` as an `event: subscribe` frame; each later frame is an `event: project` frame whose data is `{ epoch, events }`. A request's `clientId` travels as the `clientId` query parameter, which a reconnecting `EventSource` keeps, since a client keeps one for its lifetime. When the host ends the subscription, or the reader falls further behind than the host buffers, the stream closes and the client subscribes again. Unlike the reload stream, this one replays. A write's `writeId` travels as the `Jx-Write-Id` request header and its `bufferRev` as `Jx-Buffer-Rev`, beside the base of §5, and a write answers `{ ok, rev, hash, path }` with the hash as its `ETag`.
- **Cloud**: the session's `/events` WebSocket (`desktop.md` §10.1), beside three HTTP routes under the session base `/api/v1/p/:owner/:repo/:branch/studio`. Both halves of the binding ship in `packages/protocol/src/project-state-cloud.ts`. A client first asks `GET /project-state`: a session that serves the binding answers `{ version: 1 }`, and one that predates it answers `404`, after which the client follows no other writer on that session (§3.3). Any other answer (a `5xx` while the session hydrates, an expired sign-in) says nothing about the binding, so the client asks again on its next subscribe rather than going without live updates for the life of the page. A session that answers serves all of the binding: the subscription, the writes and deletes, and the rename. The subscription rides an `/events` socket. The client's first message after open is `{ kind: "subscribe", clientId?, epoch?, sinceRev? }`; the host's first message of the exchange is `{ kind: "project-subscribe", response }`, with the `SubscribeResponse` nested because it has a `kind` of its own; later events arrive as `{ kind: "project", epoch, events }`; and when the host ends the subscription it sends `{ kind: "project-ended", epoch }`, naming the epoch that ended, and the client subscribes again, catching up from the log or a snapshot. The cursor travels in the subscribe message rather than in `Last-Event-ID`: a browser's WebSocket cannot set a request header, but unlike an `EventSource` its client chooses every message it sends, so the `{ epoch, sinceRev }` the dev server reads from `<epoch>:<rev>` travels as members. A socket holds at most one subscription: a second subscribe on it ends the first, and a socket that closes ends its own, unannounced. Messages of any other `kind` on the socket (`fs` batches, git notices) are not part of the exchange, and no message of the exchange precedes its answer. A write is `PUT /project-state/file?path=<path>` and a delete `DELETE` on the same route, with the dev server's headers (`If-Match` or `If-None-Match: *`, `Jx-Write-Id`, `Jx-Buffer-Rev`) and a directory delete's `{ files }` base as its JSON body; a write's body is the file's bytes and its answer `{ ok, rev, hash, path }` with the hash as its `ETag`, a delete's answer `{ ok, rev, path }`, and a stale base is refused with `412` as §5 describes. A rename is `POST /project-state/rename`, whose body is the operation with each rewrite's contents as a `WireContents` and whose `200` answer is its `RenameOperationResult`, a refusal included. A malformed request on any of the three routes is `400`, and a path that is not project-relative is malformed. The session's older `PUT /file`, `DELETE /file` and `POST /file/rename` keep their behaviour, unconditional and last-writer-wins (§5).

Every frame is JSON. File bytes inside a frame are a `WireContents`: a JSON string for text (hashed as its UTF-8 encoding, §2.1), or `{ encoding: "base64", data }` for anything else. On the dev server, writes and deletes are HTTP requests rather than stream frames (§5), and their body is the raw bytes. A host MAY batch several events into one frame on every binding, the desktop socket included, since a client already applies a multi-event `events` answer; a client MUST apply them in revision order and MUST treat a frame from another epoch, or one whose first revision is not its last revision plus one, as a gap, which it repairs by subscribing again.

### 3.3 Retiring the resync reasons

> **Status: Implemented.** No adapter reports a resync reason: `onResync` and `FsResyncReason` are gone from `StudioPlatform.subscribeFileEvents` (`packages/studio/src/types.ts`), the desktop backend no longer pushes `onFileResync`, and Studio's re-list pass and its 1.5 second echo window are deleted from `packages/studio/src/files/fs-events.ts`. A reconnect on every platform is the subscription's own resubscribe with `{ epoch, sinceRev }` (`packages/studio/src/project-state/subscription.ts`), tested per adapter by `packages/desktop/tests/webview-project-state.test.ts`, `packages/studio/tests/devserver-project-state.test.ts` and `cloud-project-state.test.ts`, and through Studio's file sync by `fs-events-project-state.test.ts`.

A host that serves §3.1 replaces the resync reasons Studio's adapters used to report: a reconnect is a subscribe with `sinceRev`, a first open is a snapshot, and a commit is `gitChanged` plus whatever file events the checkout produced. A client MUST NOT run a resync pass in response to a subscription answer: it applies the answer, and a snapshot that replaced earlier state stands for every event it summarises, the files it added and removed included. The platform's file events (`subscribeFileEvents`) keep reaching the client's file tree, idempotently beside the subscription's own file events, and carry no gap repair of their own.

**A client whose host does not serve the subscription has no live account of other writers.** A platform without the member, or whose host has refused every subscribe so far (a dev server or a cloud session that predates its binding answers `404`), gives the client nothing to tell its own writes from another's and nothing that says when a stream had a gap. Such a client keeps its file tree and the caches of the file set current from the platform's file events when it has them, re-reads no open document and redefines no component on a change on disk, writes unconditionally (§5), and takes no content version from a listing (`studio.md` §3.4). It subscribes again with a growing delay, as after a dropped subscription, since only an answer says what the host serves, and the first answer makes the host served from then on. Git status follows each of the platform's file-event batches, and a platform whose host learns of a commit with no file event (another client of a shared session committed) reports it as an empty batch, which re-reads git status and changes nothing else. The same client, while a served subscription is down after answering, is in this position too: the platform's file events drop the caches of the file set until the subscription answers again, and a reconnect whose answer replays or replaces anything re-reads git status, since a change the watcher's missed batches carried can move a file's comparison without moving the summary.

## 4. Events

> **Status: Implemented.** Every event type below is declared in `packages/protocol/src/project-state.ts` (`ProjectEvent`), and the conformance suite asserts what each means (§10.4); the events §8 and §9 produce are asserted by those sections' cases. Which hosts emit them is each host's own item (§10.1 to §10.3).

### 4.1 Common fields and ordering

Every event carries `type`, `rev` and `origin` (§2.4). Events are delivered in revision order and a host MUST NOT reorder or drop one within an epoch. An event that names a file carries its project-relative path, spelled as the Studio Backend Protocol spells paths (`server.md` §4.1), and its `DocId`. Where an event carries `hash`, it is the hash of the bytes the event left on disk.

### 4.2 File events

- `fileAdded { path, docId, isDir, hash? }`: a file or directory appeared. `hash` is absent for a directory, and for a file the host has not hashed yet (§3.1).
- `fileChanged { path, docId, hash }`: a file's bytes changed. A host MUST NOT emit it when the new hash equals the indexed one (a touch that rewrote identical bytes, or the watcher's echo of a write the host already recorded, §2.4).
- `fileRemoved { path, docId, isDir }`: a file or directory disappeared. A directory removal is one event; the host does not also emit one per contained file.
- `fileRenamed { from, to, docId, isDir }`: a file or directory moved, keeping its id. A host emits it for a rename performed through §9 and MAY emit it for a watcher-observed move it can pair by hash; an unpaired move is a removal and an add. A host never pairs a move to or from the configuration document or a dependency input (§7), because its arrival or departure changes the configuration or the fingerprint, and a rename carries neither.

### 4.3 Document and dependency events

- `docChanged { docId, path, kind, hash, indexed }`: what the host knows about a document changed: its bytes, its kind, or whether its references are extracted (`indexed`, §8.2). Emitted after the file event that caused it for every `fileAdded` or `fileChanged` of a file, carrying that event's origin, and on its own, with origin `"external"`, when indexing fills a document in (§3.1) or a configuration change reclassifies it. A client re-reads or re-parses on `docChanged`, never on a bare file event.
- `dependentsInvalidated { cause, docIds, tags, complete }`: documents whose rendering depends on `cause.docId` along an edge of kind `cause.kind` (§8.1), emitted for the file events §8 lists. `tags` names custom-element tags whose definition changed, for caches keyed by tag. `complete` is `false` when the host's graph is partial for this cause (§8.2), in which case the list is a lower bound.
- `componentsChanged { tags }`: the set of discoverable components changed (a definition added, removed or retagged). `tags` is the whole set after the change, not a delta, and replaces the snapshot's `components`. It replaces a client's own re-discovery.

### 4.4 Project-level events

- `projectConfigChanged { path, hash }`: the project configuration document changed.
- `formatsChanged { formats }`: the set of document formats the project can open changed, because the configuration's extensions or the installed packages changed (`extensions.md` §7). `formats` is the new token, replacing the snapshot's. A client rebuilds its format registry.

### 4.5 Git

`gitChanged { status }` reports the repository's state (`GitSummary`: `branch`, `head`, and `changed`, a map from every path whose working state is not `unmodified` to its `WorkingState`). The host's git monitor watches `.git/HEAD`, `.git/index` and `.git/refs`, runs the git CLI after a debounce, and emits the event only when the summary differs from the last one it emitted. A commit, checkout, stage or pull is observed this way whoever ran it.

### 4.6 Readiness

`readiness { state }` reports a transition of the readiness machine (§7).

### 4.7 Conflicts and operations

- `conflict { path, docId, diskHash, writeId, bufferRev? }`: a write or delete through §5 was refused because its base was not what is on disk. `docId` and `diskHash` name what is at the path now, both `null` when nothing is. `writeId` names the refused request, and `bufferRev` echoes the request's own when it carried one; only the request's issuer can interpret it. Its origin is `"external"`, because it records no change. The refused writer already has the conflict in its reply; the event is in the log, and so reaches every subscriber, because any other client holding the same document learns from it that its own base is stale before it tries to save.
- `operationApplied { opId, files }`: a multi-file operation (§9) finished; `files` lists every path it wrote, renamed or removed, in the order it applied them. The individual file events precede it and carry the operation's writes as their origin.

### 4.8 Watcher degradation

`watcherDegraded { reason }`: the host can no longer guarantee that it observes every change (a watch limit reached, a watch error, a network filesystem without events). Clients SHOULD tell the author that changes made outside Studio may not appear until reload. A host that recovers starts a new epoch and ends every open subscription, so each client subscribes again and receives a snapshot. The new epoch's state replaces the old one in one step that also ends the old subscriptions: a subscribe while the host restarts is answered from the old epoch and then ended, and one after it, including one made from inside the ending, is answered from the new epoch with its scan complete.

## 5. Writes and Preconditions

> **Status: Implemented.** `WriteRequest`, `WriteResult`, `DeleteRequest`, the precondition checks (`checkWritePrecondition`, `checkDeletePrecondition`) and the refusal's event (`conflictEvent`) ship in `packages/protocol/src/project-state.ts`, the HTTP binding's headers and refusal (`writePreconditionHeaders`, `parseWritePrecondition`, `parseDeletePrecondition`, `preconditionFailedProblem`) in `packages/protocol/src/project-state-frames.ts`, and the conformance suite asserts every rule below that a driver can reach (§10.4). Two are pinned elsewhere: refusing a request with no base, or with a base this contract does not read, is the binding's, asserted by the frame tests (`packages/protocol/tests/project-state-frames.test.ts`), since a driver's `WriteRequest` always carries one; and a collaboration room writing with a base is §11.3's. Which hosts take a base hash is each host's own item (§10.1 to §10.3).

A write names the bytes it replaces. A `WriteRequest` carries `path`, `contents`, `baseHash` (the hash the writer last read, or `null` to assert the file does not exist), `writeId` (chosen by the writer, unique per write) and optionally `bufferRev` (the writer's buffer revision, §6.1, echoed in a refusal and otherwise ignored). The host:

1. reads the current hash of `path` and the `DocId` there (`null` for both when absent);
2. refuses the write when the hash differs from `baseHash`, answering `{ ok: false, conflict: { path, docId, diskHash } }` and emitting `conflict` (§4.7); the disk is untouched;
3. answers `{ ok: true, rev, hash }` with the host's current revision, writing nothing and emitting nothing, when the new bytes hash to what is on disk (an unchanged buffer saved, or a format that round-trips to identical bytes);
4. otherwise notes the write in its echo ledger (§2.4), writes the bytes, and in the same step updates the index to the new hash and appends the `fileAdded` or `fileChanged` event with origin `{ writeId, writeHash }`, followed by its `docChanged` and any `dependentsInvalidated` (§8). It answers `{ ok: true, rev, hash }`, where `rev` is the revision of that file event. The reply never waits for the watcher.

Steps 1 to 4 MUST be atomic with respect to every other write through the host and to the host's processing of watcher observations at the same path.

Against a program outside the host the steps cannot be atomic: it can change the file between the check and the write. A watcher-backed host narrows that window by writing the bytes to a temporary file in the target's directory, re-hashing the target, and renaming the temporary file over it only when the re-hash still equals the base, refusing as in step 2 otherwise. That also means the watcher never observes a half-written file. The temporary file is the host's own and never enters the index or the event stream, and a write that fails after creating it (a full disk, a rename refused) removes it and leaves no echo pending. A write to a path that is a link resolving inside the root writes the link's target, keeping the link, and a write over an existing file keeps its permissions. A file that exists but cannot be read is never taken for an absent one: a write or delete over it fails rather than proceeding with no base. What remains is the interval between the re-hash and the rename: a change landing there and replaced before the watcher reads it is lost without an event. It is the one silent overwrite this contract admits, bounded by one rename, and a host that observes a hash matching neither its index nor a pending ledger entry reports it as an external change (§2.4) rather than dropping it. The cloud host, which has no writer outside it, has no such window.

**Deletes.** A delete names what it removes. A `DeleteRequest` carries `path`, `base` and `writeId`. A file's base is `{ hash }`, the hash the writer last read; a directory's base is `{ files }`, every file beneath it by path relative to the directory with the hash the writer last read, and any file added, removed or changed since is a conflict (`checkDeletePrecondition`). The host refuses a stale base exactly as step 2 refuses a write, and otherwise removes the path and, in the same step, drops it from the index and appends `fileRemoved` with origin `{ writeId, writeHash: null }`, answering `{ ok: true, rev }`. So a client's own delete carries its origin, and a delete never discards a change made just before it. Creating a directory can overwrite nothing and takes no base, but carries a `writeId` so its `fileAdded` carries the writer's origin. Moving a file or a directory is a rename (§9).

**Collaboration rooms.** A room's persistence (`collab.md`; `packages/server/src/collab.ts` writes on an explicit save and as a flush on shutdown) goes through this section like any other writer: the room holds the hash it hydrated from or last saved, every save is a write with that base and its own `writeId`, and a refusal is delivered to the room, whose participants resolve it as §6.1 describes. A shutdown flush that is refused leaves the disk untouched; nothing persists a room beyond its process, so the bytes the refusal kept off the disk end with it.

A write or delete MUST NOT be accepted without a base once a host serves this contract; a host that also serves the Studio Backend Protocol's unconditional `writeFile` keeps it only for clients that have not subscribed, and documents it as last-writer-wins. A binding whose requests cannot be tied to a subscription (an HTTP binding, whose writes arrive on requests of their own, §10.2) cannot tell those clients apart: there the unconditional form is kept for every request that names neither a base nor a `writeId`, and a client that subscribes MUST send a base with every write and delete it makes. On an HTTP binding the base hash travels as `If-Match: "<hash>"` (or `If-None-Match: *` for `null`), a file's delete is `DELETE` with the same `If-Match`, a directory's carries its `{ files }` base in the body, and a refusal is `412 Precondition Failed` with the conflict as a problem document of type `precondition-failed` whose extension members are `path`, `docId` and `diskHash` (`server.md` §4.3). The content hash is a strong entity tag, quoted; a request whose precondition is absent, weak, a list, `If-Match: *`, or both headers at once is refused before the disk is read, because each of those either names no bytes or names more than one.

## 6. Two Dirty Notions

> **Status: Implemented.** The unsaved-buffer derivation (`bufferStatus`, `isBehindDisk`) and `WorkingState` ship in `packages/protocol/src/project-state.ts`. Every Studio tab carries a `BufferState` (`tab.doc.buffer`, `packages/studio/src/tabs/tab.ts`), whose `dirty` flag is the derivation's `bufferRev ≠ savedRev`: an edit moves `bufferRev`, and a read or a save that reached disk moves `savedRev` and sets `baseHash` to the hash of the bytes read or written (`packages/studio/src/project-state/buffer.ts`). While the platform's host serves §3 (the desktop and the dev server, `studio.md` §3.4), every `docChanged` sets `diskHash` on the open tabs of its path: a clean tab behind the disk is re-read, a tab that already holds those bytes is not, and an edited tab becomes `conflicted` and the author is told. A save is a write with the tab's `baseHash` and a `writeId` of its own (`packages/studio/src/files/based-writes.ts`); a refusal marks the tab conflicted, and a conflicted tab's save asks the author before anything is written: Keep Mine writes against the current `diskHash`, Take Disk Copy re-reads the file, and Compare writes nothing and compares the copy on disk with the unsaved version (`studio.md` §21). A delete names the hash the host last reported, or every file beneath a directory, and a refused one deletes nothing. Every other write and delete Studio makes while the host serves §3 names a base too (§5), through the route `based-writes.ts` installs on the platform layer: the store's account of the path, the hash the host last reported or that of Studio's own write still on its way. A tab is held against its base from the first read, whichever door opened it, and a host restart's snapshot starts the revisions it compares again. The Problems entry for a conflict goes when the tab closes or the disk returns to its base. A co-edited tab reads its room's state: it is conflicted while the room's last save stands refused, or while its file has changed under the room's unsaved edits (the provider's `doc-conflict`, `collab.md` §2), until the room saves or the session ends, and it stays dirty throughout. Its save asks the same question before the room writes anything: Keep Mine saves the room against the `diskHash` the conflict named, Take Disk Copy reverts the room for every participant and re-reads the file before rejoining, and Compare shows the bytes the room would write beside the copy on disk (`saveCoEdited` in `based-writes.ts`, `saveRoom`, `revertRoom` and `roomSource` in `packages/studio/src/collab/collab-session.ts`). A host that does not serve §3 leaves the tab's base unchecked and its saves unconditional, as before. Tested by `packages/studio/tests/project-state-buffer.test.ts`, `based-writes.test.ts` (the conflict question through the harness, and the route), `fs-events-project-state.test.ts`, `studio-shell-project-state.test.ts`, `collab-session.test.ts` and `project-state-edited-conflict.test.ts` (an edited tab, solo or co-edited, whose file another program changes, through the file sync and the save).

Studio has used one word for two different facts. This contract names them separately, and a client MUST NOT conflate them in state or in the interface.

### 6.1 The unsaved buffer

A client's open copy of a file is a `BufferState`: `diskHash` (what the host last reported on disk), `baseHash` (the disk hash the buffer was loaded from or last saved as), `bufferRev` (bumped on every edit) and `savedRev` (the buffer revision that equals `baseHash`'s bytes). Its status is derived, never stored:

| Condition                                        | Status       | The client                                                  |
| ------------------------------------------------ | ------------ | ----------------------------------------------------------- |
| `bufferRev = savedRev`                           | `clean`      | re-reads silently when `baseHash ≠ diskHash` (behind disk)  |
| `bufferRev ≠ savedRev` and `baseHash = diskHash` | `dirty`      | saves with `baseHash` as the write's base                   |
| `bufferRev ≠ savedRev` and `baseHash ≠ diskHash` | `conflicted` | asks the author to keep theirs, take the disk's, or compare |

A conflicted buffer is never saved without the author's choice. Keeping theirs is a write whose base is the current `diskHash`; taking the disk's discards the buffer.

A co-edited document (`collab.md`) has one buffer, the room's, shared by its participants. The host keeps that buffer's `BufferState` (§11.3): `bufferRev` is the room's document revision, and `baseHash` the hash the room hydrated from or last saved (§5). The table applies to the room as a whole, and a participant's client keeps no buffer state of its own for that document while the room is open.

### 6.2 Saved but uncommitted

A saved file whose bytes differ from the repository's `HEAD` has a `WorkingState` other than `unmodified`, reported by §4.5. This is the source-control notion (`studio.md` §5.5), and it says nothing about buffers. On the cloud a save writes to the project's Durable Object, which is the working tree there; a commit is a separate action.

## 7. Readiness

> **Status: Implemented.** The states and their order (`READINESS_ORDER`, `readinessAtLeast`) ship in `packages/protocol/src/project-state.ts`, and the conformance suite asserts the machine: a host held below `indexed` still answers, readiness advances one state at a time, an install's own lockfile write moves nothing, and only a dependency or extension-set change moves it back (§10.4). Which hosts track readiness is each host's own item (§10.1 to §10.3).

A host reports how far it has prepared the project, as one of five ordered states:

| State                 | Means                                                                                                                   |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| `scaffolded`          | the project's files exist; its dependencies may not be installed                                                        |
| `installed`           | the dependencies the manifest declares are installed (or, on a host with no `node_modules`, the lockfile is consistent) |
| `extensions-resolved` | every extension the configuration names is loaded and the format registry is known                                      |
| `indexed`             | every file is hashed and classified and the dependency graph is built                                                   |
| `ready`               | the host serves every part of this contract for the project                                                             |

The host advances one state at a time and emits `readiness` for each. A change to an input moves it back to the first state that input invalidates, and only a change that alters what the state was computed from does:

- **Dependencies.** The host records, with each completed install, a fingerprint of what it installed: the hash of the lockfile it ran against, together with the manifest's dependency fields (`dependencies`, `devDependencies`, `optionalDependencies`, `peerDependencies`). It moves back to `scaffolded` only when the current fingerprint differs from the recorded one. A manifest edit that leaves the dependency fields alone (a script, a version bump of the project itself) moves nothing, and neither does the lockfile an install rewrites: the install records its fingerprint after it writes, and its writes carry the install operation's `writeId` (§2.4).
- **Extensions.** A configuration change moves the host back to `installed` only when the set of extensions it names changes; any other configuration change is a `projectConfigChanged` (§4.4) and leaves readiness where it was.

A snapshot carries the current state. A client MUST NOT draw a view that needs a later state as empty or failed while the host is below it. A view that has never had the state it needs shows that the project is still being prepared; a view that had it keeps showing what it last derived while readiness moves back and forward again, and refreshes on the events that follow, so a dependency change never blanks the interface.

## 8. Dependency Graph

> **Status: Implemented.** `createDependencyGraph` in `packages/server/src/project-state/graph.ts`, exported as `@jxsuite/server/project-state/graph`, keeps the graph from `extractRefs` (built on `walkDocRefs` and the walk behind `countTagUses`, §12) and answers each change's invalidations, transitive and deduplicated, with `invalidationEvents` turning them into `dependentsInvalidated` events; its module graph has no I/O import, so every host bundles the same graph (`packages/server/tests/refs-export.test.ts`), and `packages/server/tests/project-state-graph.test.ts` covers each edge kind. The §10.4 cases for a host that serves this section are in the published suite, and the reference host passes them. Each host's own use of the graph is its §10 item: the desktop and dev-server hosts still walk every file per request (`packages/server/src/refactor/`), and Studio still invalidates its caches by path.

The host keeps a directed graph from each document to the documents whose rendering depends on it, built from the references §12 extracts. It recomputes a document's outgoing edges whenever its bytes change, and recomputes the edges that depend on the configuration on every `projectConfigChanged`. An edge whose target path does not exist yet is kept, so a file arriving there reaches the documents that already name it.

The trigger is a file event, not `docChanged`: the host emits dependents for every `fileChanged`, `fileRemoved` and `fileRenamed` of a document that has any, media included, and for every `fileAdded` at a path some document references. For each such event it emits one `dependentsInvalidated` per edge kind that reaches at least one dependent, after the file event and after its `docChanged` when there is one. A removed or renamed document's dependents are invalidated because their references now dangle (unless a rename cascade rewrote them, §9, whose own writes invalidate in turn).

### 8.1 Edge kinds

| Kind                 | From → to                                                                      | Built from                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            |
| -------------------- | ------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `component-instance` | a component definition → each document that instantiates its tag               | tag uses (`countTagUses`) against the component's declared tag, and `$ref` and `$elements` paths to the definition                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| `layout-page`        | a layout → each page it wraps                                                  | the page's resolved layout (below)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| `content-collection` | a content entry → each collection that includes it, and each page listing it   | the collection loader's resolved entry list (`site-architecture.md` §6.1), not the `source` alone, since a `{locale}` source is not a glob and `exclude` and `where` leave files out; a document lists a collection through `ContentCollection` and `ContentEntry` state in any scope (`site-architecture.md` §6.4, `spec.md` §23.3) and through each `contentType` its `$paths` names, `each` included (`site-architecture.md` §4.3); between configuration changes the host re-resolves the loader for every file event under a collection's source |
| `media-referrer`     | a media file → each document that references it                                | every other file reference `walkDocRefs` offers                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |
| `data-consumer`      | a data or class document → each document whose `$src` or `$prototype` reads it | `$src` references, the document's own `imports`, and the configuration's `imports` for each `$prototype` name the document uses and does not map itself (`imports.md` §1.1)                                                                                                                                                                                                                                                                                                                                                                           |
| `project-config`     | the project configuration or the installed packages → every document           | always; it also emits `formatsChanged` when the format set changes                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |

The configuration's own references (`defaults.layout`, `imports`, `copy`, a collection's `source`) are not edges: the host reads them on `projectConfigChanged`, resolving each against the project root as authored, and an edge from the configuration would make every layout it names invalidate every document through it.

Edges are transitive for invalidation: a document invalidated through one edge invalidates its own dependents, and each document appears at most once per emitted event.

A page's **resolved layout** is its `$layout` when it has one, otherwise the configuration's `defaults.layout` (`site-architecture.md` §3.1, §5.2); a page whose `$layout` is `false` has no `layout-page` edge. Most pages name no layout, so the implicit edges are the common case: they are recomputed on every `projectConfigChanged`, and editing the default layout invalidates every page that falls back to it.

A component's **samples** (the definition's own `examples`, drawn by the Site panel's component cards and by Project Styles, `studio.md` §5.7 and §7.2) are not graph dependents: they derive from the definition alone. A client keys its sample and stylebook caches by the component's tag and the definition's hash, and redraws them on that definition's `docChanged`, not when its component registry is replaced (§11.1).

### 8.2 Partial graphs

> **Status: Implemented.** The cloud host reports a partial graph: the session Durable Object, in the platform repository, holds a document in a format an extension registers as `indexed: false` in its snapshot and its `docChanged` events, marks every invalidation `complete: false` while any document is unindexed, announces a change no document it can name depends on as an invalidation naming none, and refuses a rename without client `rewrites` while its graph is partial (§9.1); it passes the conformance suite with its driver's `graph: { complete: false }` (§10.3). The desktop and dev-server hosts read every format the project registers, so their graphs are complete. The client half: Studio's store keeps `indexed` from the snapshot and every `docChanged` (`packages/studio/src/project-state/store.ts`), a `dependentsInvalidated` whose `complete` is `false` invalidates every document the store holds as unindexed besides the ones it lists (`packages/studio/src/project-state/derive.ts`), and a rename carries Studio's own rewrites of those documents (`packages/studio/src/files/client-rewrites.ts`, §9.1), all tested by `packages/studio/tests/project-state-derive.test.ts`, `client-rewrites.test.ts` and `rename-operation.test.ts`.

A host that cannot extract a document's references leaves it `indexed: false`, in its snapshot entry (`IndexedFile`) and in every `docChanged` for it; the host's graph is partial while any document is. Every `dependentsInvalidated` whose dependents could include an unindexed document carries `complete: false`. The cloud host is the expected case: extracting references from a document in a registered format other than JSON (Markdown, CSV, a parser extension's format) runs the project's parser code, which a Durable Object cannot execute.

Because `indexed` travels on the snapshot's files and on `docChanged`, and a removed file leaves with its `fileRemoved`, a client keeps its set of unindexed documents current from the stream alone: a page added after the snapshot arrives as `fileAdded` followed by `docChanged { indexed: false }`. On `complete: false` a client MUST treat every document it holds as unindexed as invalidated too, in addition to `docIds`. A host whose graph is partial still reports every edge it can extract; partial means a lower bound, never a guess. For the same reason, while its graph is partial a host announces a change to a document or asset that no document it can name depends on as one `dependentsInvalidated` with `complete: false` and an empty `docIds`, since an unindexed document may depend on it; a change to the configuration or the manifest already reaches every document and needs no such event, and a host whose graph is complete emits nothing for a change nobody depends on.

## 9. Rename Cascade

> **Status: Implemented.** `runRenameCascade` (`packages/server/src/project-state/rename.ts`) plans each operation over the refactor engine's planning half (`planRename` in `packages/server/src/refactor/apply.ts`, which `applyRename` also runs) and applies it from an in-memory outbox; the desktop and dev-server host serves it as `rename` (`packages/server/src/project-state/host.ts`), the desktop binding as `projectRename` (`packages/desktop/src/backend/project-state.ts`) and the dev server as `POST /__studio/project/rename` (`packages/server/src/project-events.ts`). `RenameOperation`, its answer `RenameOperationResult` and the wire codec are in `packages/protocol/src/project-state.ts` and `project-state-frames.ts`. `packages/server/tests/project-state-rename.test.ts` covers rollback at each step (the directories a move created included), an undo that fails, a referrer changed between plan and apply, both policies (a dirty document's client rewrite included), a partial graph with and without `rewrites`, a project whose dependencies are not installed, a file too large to index, a rename that changes only the case of a name, and the usage query's cache (§12) dropped by every rename, and both hosts pass §10.4's §9 cases. Studio renames through it while the host serves §3 (`packages/studio/src/files/rename-operation.ts`, `studio.md` §9.1.1), and while its store holds documents the host could not index it sends its own rewrites of them, parsed with the formats Studio has loaded and rewritten with the walk of §12 (`packages/studio/src/files/client-rewrites.ts`). The outbox is in memory: a crash mid-operation leaves the steps already applied, and the host's next start reports them as external changes; a durable outbox waits for §13.

### 9.1 One operation

A rename is one `RenameOperation { opId, from, to, policy, dirtyReferrers, rewrites? }`. The host plans it before touching the disk: the move, and for every referrer it can parse (found through §8) the rewritten bytes and the hash they replace. It then applies the plan from an **outbox**: each step is recorded before it runs, and a failure undoes the completed steps in reverse, restoring each file's prior bytes, so the project ends either fully renamed or exactly as it was. Every write in the plan carries the operation's write ids, so its events are attributed to it (§2.4), and `operationApplied` follows the last of them. A referrer whose hash changed between planning and applying fails the operation and rolls it back.

The move is the outbox's first step and every rewrite follows it, at the path its file has after the move; step `n` writes as `<opId>:<n>` and its undo as `<opId>:rollback:<n>`, and `operationApplied` lists the move by its destination, then every path it rewrote. The host answers a `RenameOperationResult`: either what it applied (the revision of `operationApplied`, the referrers it rewrote and how many references in each, the documents it found and could not rewrite, the component tag it renamed with a component's file, and the dirty referrers it left for their buffers, §9.2), or a refusal naming its reason and the paths concerned (`dirty-referrers`, `rewrites-required`, `conflict` for a referrer that changed or a destination that is taken, `failed` for any other failed step), after which every file is as it was. A refusal is an answer on every binding, not an error. A rename onto an existing path, into itself, or of the project configuration, the package manifest or a lockfile is refused before any step runs; on a filesystem that ignores case, the entry's own name in another case is not an existing path, so a rename that changes only the case of a name is a rename. The undo of the move also removes, while they are empty, the directories the move created for its destination. When an undo itself fails, the refusal still answers, and lists in `unrestored` the paths of the steps it could not undo, each left as its step made it (the move by its destination); a refusal without `unrestored` left every file as it was.

**Documents the host cannot parse.** Where the graph is partial (§8.2) the host can neither find nor rewrite references in its unindexed documents, and on the cloud no full walk can either, since it needs the same parser code. A client that can parse them computes those rewrites and sends them as the operation's `rewrites`, each naming the base hash it read; the host applies them as steps of the same outbox, checked and rolled back like every other step. A host whose graph is partial refuses a rename that does not carry `rewrites` (an empty list asserts that the client searched every unindexed document and found no reference), so a rename never quietly leaves references unrewritten. A client rewrite replaces the host's own plan for its document, and the report counts its file among the referrers it rewrote with a count of 0, since the host did not count its references. Only a document whose format is not known yet can make a host refuse: once the formats are loaded, a file no format parses is not a document (§2.2), and an unindexed file a format does parse (one too large to index, say) is planned, read whole. A desktop or dev-server host loads the project's parsers before it plans, so it leaves no document unindexed for this reason and plans every rewrite itself; where the project's dependencies are not installed no format is registered, and no host or client can parse a document in one, so it renames as if none were.

### 9.2 Dirty referrers

A referrer the client holds unsaved is listed in `dirtyReferrers` with its buffer revision. With policy `refuse` the operation is refused before any step runs, naming those referrers. With `rewrite-buffer` the host leaves those files on disk untouched and the client applies the same rewrite to each buffer, which stays dirty for the author to save; the operation's report names them, each as a `BufferRewrite` carrying the buffer revision it was named with, every reference value the rewrite replaced with its replacement, and the renamed component tag when there is one. A client rewrite (§9.1) of a document listed in `dirtyReferrers` is never written: under `refuse` it refuses the operation like any dirty referrer, and under `rewrite-buffer` the report names it as a `BufferRewrite` with no changes, since the client computed that rewrite and applies it to its buffer itself. A client MUST NOT send a rename that omits a dirty referrer it holds, and a document whose collaboration room holds unsaved edits is held by every client that has it open (§11.3), which applies its rewrite as an edit through the room; it may list a dirty document that refers to nothing, which the host ignores. The rewrite maps reference values to their replacements, so a client applies it to whatever its buffer holds when the answer arrives, edits made while the operation was in flight included.

### 10.3 Cloud

> **Status: Implemented.** The binding is specified (§3.2) and both its halves ship in `@jxsuite/protocol/project-state-cloud`: `answerCloudProjectRequest` answers its HTTP routes for a host, and `createCloudProjectStateClient` is its client, which the Cloud adapter exposes as `subscribeProjectState`, `writeProjectState`, `deleteProjectState` and `renameProjectState` (`packages/studio/src/platforms/cloud.ts`, tested by `packages/studio/tests/cloud-project-state.test.ts`). `packages/protocol/tests/project-state-cloud-binding.test.ts` runs the conformance suite through the binding, its socket and its routes, against the reference host shaped as the cloud's: no watcher and no links, a log that survives a restart, and a partial graph whose renames take the client's rewrites. The Durable Object host is in the platform repository: the session object (`src/do/project-session.ts`) runs `ProjectStateHost` (`src/lib/project-state/host.ts`) over its SQLite storage and its working tree, answers the binding's routes with `answerCloudProjectRequest`, keeps each subscription on its socket's attachment, reads committed files in from GitHub as its indexing pass and as each write, delete and rename needs them, and imports the reference walk from `@jxsuite/protocol/refs`. It passes the published conformance suite through the binding, with the §8 and §9 cases on and a partial graph, under Bun (`tests/project-state-conformance.test.ts` there): subscriptions over the subscribe exchange, writes, deletes and renames over the HTTP routes, changes behind its back over the session's older unconditional routes, and a restart as a new object over the same storage and sockets, which is what a wake from hibernation is. Its collaboration rooms save through it (§11.3).

The cloud host is the project's Durable Object. Hibernation drops memory, so its revision counter and replay log are persisted in the object's SQLite storage (§13.1), and an epoch survives hibernation; a new epoch starts only when the log is discarded. Its replay window is the most recent 4096 events or those of the last 24 hours, whichever is fewer (§13.1): a day covers a tab left open overnight or a laptop asleep until morning, and 4096 events bound what one resubscribe replays; a client away longer is answered with a snapshot, which the host builds from its index without reading the repository. A subscription survives hibernation with its socket: the host records it on the socket (its epoch and `clientId`) and streams to it after waking as before, and a socket the host can no longer serve from its log is sent `project-ended`. Its index and hashes come from the object's own file store, and every write goes through it, so it has no watcher and no echo ledger: every event's origin is known at the moment of the write, and a change that reaches the store another way (a pull, the session's unconditional `PUT /file`) is recorded with origin `"external"` in the same step. Its dependency graph is partial (§8.2), so its renames rely on the client's rewrites for the documents it cannot parse (§9.1). It serves §3.2's cloud binding.

### 10.4 Conformance suite

> **Status: Implemented.** `runProjectStateConformance` and the `ProjectStateDriver` interface ship in `packages/protocol/src/project-state-conformance.ts`, exported as `@jxsuite/protocol/project-state-conformance`. The suite takes `describe`, `test` and `expect` as a parameter rather than importing a runner, so it runs under `bun:test` here and under Vitest in a Worker. An in-memory reference host (`packages/protocol/tests/reference-host.ts`) passes every case below that applies to all hosts, and `packages/protocol/tests/project-state-conformance.test.ts` turns the suite on deliberately broken variants of it to show each rule fails a host that breaks it. A host that serves neither §8 nor §9 runs a negative case for each (it emits no `dependentsInvalidated`, no `operationApplied`); a driver that declares the `graph` hook runs the §8 cases in its place, and one that declares the `rename` hook (`rename`, and `failStep`, which makes the next operation's step fail, counted from 0) runs the §9 cases, so declaring a hook can never switch a check off. The reference host passes the §9 cases with a complete graph and with a partial one, and the desktop and dev-server host passes them on the host and over the HTTP binding. A driver that reaches its host over a wire records each subscription with `observeSubscription`, through a client of the host's binding (`ProjectStateClient`), and its `settle` waits for the frames in flight; the reference host passes the suite that way through the cloud binding (`packages/protocol/tests/project-state-cloud-binding.test.ts`). Once a host is ready every fixture file must be `indexed: true`, unless its driver declares the graph partial (`graph: { complete: false }`, §8.2).

One suite tests every host through the same driver interface: create a project from fixture files, write through the contract, change a file behind the host's back, restart the host, and observe the subscription. The suite covers at least:

- a first subscribe gets a snapshot, also while the host is below `indexed`, and the `docChanged` events that fill it in follow;
- a document in a format an extension registers is `other` until `extensions-resolved`;
- a resubscribe within the window gets exactly the missed events, and one after a restart that started a new epoch, or outside the window, gets a snapshot (a host whose log survives a restart, §10.3, replays instead);
- revisions are strictly increasing and gap-free;
- a write's reply carries the revision of its own file event, and no second event follows when the watcher reports the same bytes;
- a write of the bytes already on disk answers the current revision and emits nothing;
- a write or delete with a stale base is refused and leaves the disk untouched, and an own delete's `fileRemoved` carries its origin;
- an external change carries `"external"`, including one that restores the bytes of an earlier own write;
- an atomic-rename save inside the pairing bound keeps its `DocId`, and one slower than the bound is a removal and an add;
- a coalesced burst of writes emits one event per write and nothing for the watcher's observation;
- readiness advances in order, and an install's own lockfile write does not move it back;
- `gitChanged` follows a commit made outside Studio.

A host that serves §8 also passes: deleting a component invalidates its instances; renaming a media file outside Studio invalidates the documents that reference it; editing the default layout invalidates the pages that name no layout. A host that serves §9 also passes: a rename with one referrer either completes or leaves every file as it was, at a failure of each of its two steps; a rename that completes moves the file with one `fileRenamed` that keeps its `DocId`, rewrites its referrer, and then emits `operationApplied` listing the move first, by its destination; and a dirty referrer is refused under `refuse` before any step and left on disk under `rewrite-buffer`, its own client rewrite included. The suite is published with the protocol package, so the cloud repository runs it against its own host.

## 11. Clients

### 11.1 One content store

> **Status: Implemented.** The store and its subscription ship: `packages/studio/src/project-state/store.ts` holds the documents a host's snapshot and events describe, keyed by `DocId` with the path as a relabelable attribute, and the contents Studio has in hand keyed by `(docId, hash)`, so a rename moves no bytes and a change drops exactly the bytes it replaced; it is one per window and reset when a project is left. `packages/studio/src/project-state/subscription.ts` subscribes through the platform's `subscribeProjectState` (`studio.md` §3.4) on every platform, applies the answer and every later frame in revision order, and subscribes again with its cursor on a gap or an end (§3.1, §3.2). Studio recognises its own writes by the hash of the bytes it noted before writing them, or by a write id it issued (§2.4), and an open tab is held against its buffer's base on every `docChanged` (§6.1). Every cache is a derivation of the store, invalidated only by its events (`packages/studio/src/project-state/derive.ts`, `studio.md` §9.2): the version map is the store's hashes (`files/asset-versions.ts`, `studio.md` §3.4); the caches keyed on the file set drop on the file events and the caches keyed on contents on `docChanged`; git status follows `gitChanged`; a component another writer changed, or one a `dependentsInvalidated` names by tag, is redefined on the canvas (`services/live-components.ts`); and Project Styles' component samples are keyed by tag and definition hash (`style/stylebook-specimens.ts`, `studio.md` §7.2). The caches that read documents are keyed by what they read: the store's `keyAt(path)` names a document's `DocId` and the hash of its bytes (`DerivationKey`), and its `generation` moves whenever any document's bytes or the set of documents changes. The component registry (`files/components.ts`) remembers each entry's key, so a changed definition is re-read alone, a moved one is relabelled without a read and a removed one leaves, and a full scan runs only on `componentsChanged`; a snapshot of a new epoch re-keys the entries whose bytes it names unchanged, a registry scanned before the subscription answered is keyed by the first snapshot, and an entry the store held no hash for is read once a hash arrives and rescanned for if its path leaves the store; the Site panel's index (`panels/site-panel.ts`) keeps its file set across a change to contents alone and re-reads only the dynamic pages whose key moved; the format registry (`format/format-host.ts`) is keyed by the format-set token and fetched again only under another; and the usage counts (`services/references.ts`), which read every document, are keyed by the store's `generation`. The watcher's file events then update the file tree alone, beside the subscription's file events, which also repair the tree after a gap (§3.3). Tested by `packages/studio/tests/project-state-store.test.ts`, `project-state-subscription.test.ts` (against a host built on `answerSubscribe`), `project-state-derive.test.ts`, `project-state-keyed-caches.test.ts`, `asset-versions-derived.test.ts`, `site-panel.test.ts` and `fs-events-project-state.test.ts`. An open tab's parsed document is keyed by the hash of the bytes it was read from, its buffer's `baseHash` (§6.1), and the bytes a tab reads and the bytes Studio saves fill the store under the document at the path and that hash (`packages/studio/src/project-state/buffer.ts`, tested by `project-state-buffer.test.ts`).

A client keeps one store of file contents keyed by `(docId, hash)`, filled by reads and by its own writes, with the path of each document as a relabelable attribute. Every cache it keeps (parsed documents, the version map of `studio.md` §3.4, component metadata and samples, usage counts, previews) is a function of entries in that store and of the graph events, keyed by the document and hash it was derived from. A `fileChanged` or `docChanged` invalidates exactly the derivations keyed by the old hash; a `fileRenamed` relabels the document's path and invalidates nothing by itself, since the bytes are the same; `dependentsInvalidated` invalidates the derivations of the listed documents; a snapshot invalidates every derivation whose key it does not contain. A snapshot that names the same bytes at the same path under a new `DocId` (every snapshot of a new epoch mints its ids again) re-keys the derivations of that path rather than dropping them, and changes no bytes a reader holds; a path it names without a hash keeps what was known of its bytes until the `docChanged` that names them. A `docChanged` that names the bytes the client last accounted for at its path (the host filling in what it learned, §4.3) is no other writer's change. No cache subscribes to file events on its own.

### 11.2 The preview realm

> **Status: Implemented.** `packages/studio/src/preview-realm/`: the frame is `canvas.html?realm=preview` (`frame.ts`, booted by `canvas/iframe-entry.ts`'s `bootFrame`), the shell's handle and its replacement `host.ts`, the window's one realm and the store reads `client.ts`, and the requests a surface makes `ask.ts`. The Content home and the Site panel (`browse/library-preview.ts`), the palette's component cards (`panels/dnd.ts`) and Project Styles' samples (`style/stylebook-specimens.ts`) all ask it; `browse/preview-root.ts` shows its answers. Tested by `packages/studio/tests/preview-realm.test.ts`, `library-preview.test.ts`, `preview-root.test.ts` and `live-components.test.ts`.

Previews of project documents outside the canvas (the Library, the Site panel, component cards) render in one realm of their own: a same-origin `<iframe>` with its own custom-element registry, fed from the content store (§11.1) by message. A project component's definition is registered in the realm's registry and never in Studio's, a previewed document's stylesheets and scripts load and run in the realm's window and never in Studio's, and a changed definition is redefined there by replacing the realm rather than by the registry, which cannot redefine a tag. The separation is of registries and documents, not a security boundary: the frame is same-origin, as the canvas frame is, so code running in it can reach the window that holds it.

**One realm, made on the first request.** Its document is the canvas's own (`canvas.html` with `?realm=preview`), so every host that serves the canvas serves the realm at the same origin and with the same dev-proxy token, and its channel is the canvas's token- and origin-gated `postMessage` channel under a token of its own. A surface asks by `DocId` (the path while the host indexes no document there) and hands the realm the document as the store holds it, parsed: a page or layout to draw, a component instance to draw with its sample props after checking its definition renders with them, a package's element to draw if the realm has it, or a definition to try. A package element whose tag Studio's own window defines (the `@jxsuite/ui` kit Studio is drawn with) is not asked of the realm, which never imports a package: the shell answers one element of that tag, and its own registry draws it once the card mounts it. The bytes come from the store when it holds them and from the platform otherwise, and a read of a document the store indexes is held in the store under its hash. The realm fetches only what a document names by URL (an `$elements` definition, a `$src` class), as the canvas does, and never imports a package to draw a preview.

**The realm answers with a snapshot, and the shell shows it.** The realm draws each request into a container of its own, waits for it to settle (the lookups in flight, then a few quiet ticks, all within a bound, so a lookup that never settles cannot hold the realm), and answers its markup, shadow roots included as declarative shadow DOM (`getHTML`), relative media URLs made absolute against the realm's address, and the text of the rules its runtime wrote; then it stops the draw's effects and lets the drawn tree go. The realm answers requests concurrently but makes definitions one at a time, so two requests that define one component at once both draw it. The shell parses the markup in a document with no browsing context, removes every element that runs, embeds or redirects something (`script`, `iframe`, `object`, `embed`, `base`, `meta`), every event-handler attribute, every `srcdoc` and every `javascript:` URL, and only then moves it into the card's own shadow root beside one sheet per realm holding those rules, so a card stays in its surface's layout, its text stays text, and nothing in a snapshot runs in Studio's window. A project's custom elements in a snapshot are names Studio's window never defines; a tag of the kit Studio is drawn with is upgraded by Studio's own definition, as it was when previews were drawn in Studio's window.

**Replaced when a definition it holds changes.** Each answer carries the custom element names the realm's registry holds. When a component's definition changes (Studio saves it, another writer's `docChanged` reaches it, or `dependentsInvalidated` names its tag), a realm holding that tag is disposed and the next request makes a new one; a `componentsChanged` replaces a realm that holds any project tag, because the tag may now be defined by another file or by none. The realm names the tags it holds only in its replies, so a change to a tag it does not yet name while requests are in flight is remembered until each of them has answered, and a reply that names the tag replaces the realm then: the request in flight may have defined it from the old definition. A request in flight is answered as failed and marked as the realm's failure rather than the document's (as is a realm that did not start, did not answer in time, or is not installed), so no surface remembers it as "does not render" or reports it as the document's failure; the previews that failed are asked again, and the snapshots already on screen stay, since a snapshot outlives the realm that drew it. A palette card is asked again once its realm has been replaced, so it does not keep a stale definition's snapshot. A definition read while Studio's own write to it has not echoed is read through the platform, not from the store, whose bytes there are still the ones the write replaced. Opening another project replaces the realm too. Requests not yet answered are an idle source (`studio.md` §13.5).

### 11.3 Collaboration rooms and the preview overlay

> **Status: Implemented.** The overlay: on the desktop and on the dev server it is keyed by `DocId` and the setting client (`createOverlayRegistry` in `packages/server/src/project-state/overlays.ts`, run beside the host by `packages/desktop/src/backend/project-state.ts` and by `packages/server/src/project-events.ts`), follows a rename, drops on a removal (matched by path as well as by `DocId`, so an overlay keyed before the host knew its document, or in an earlier epoch, is dropped too), and outlives its client's subscriptions by `overlayGraceMs` (tested by `packages/server/tests/project-state-overlays.test.ts`, `packages/desktop/tests/project-state.test.ts` and `packages/server/tests/project-events.test.ts`). A resubscribe the host answers with a snapshot (§4.8) drops the overlays of documents it no longer holds, and re-rooting the window or activating another project unpublishes the overlays of the one before. An overlay set by a client that never subscribed keeps the behaviour it had before it had owners: any such client of the project clears it. On the desktop, one set with no `clientId` on a socket that has subscribed belongs to that socket, which takes over what it set before it subscribed, and is dropped when the socket closes. The dev server's `/__studio/preview/overlay` is a request of its own, tied to no stream, so an overlay it sets with a `clientId` in its body belongs to that client, kept while a stream naming it (`?clientId=`) is open and for the grace after, and one set without belongs to every client that names none, as before. The dev server's rooms: inside the project its host serves (§10.2), its registry (`packages/server/src/collab.ts`) keys a room by the `DocId` the host gives its document, or by its path when the host has not indexed it yet, and follows the host's events by path, so a room keyed either way moves with a `fileRenamed`, closes on a `fileRemoved` of it or a directory above it, and reseeds on a change it did not save unless the change left the bytes it holds or the room holds unsaved edits: then it keeps them and its base, tells every participant with `doc-conflict` (§6.1), and its next save is refused until a participant saves against the new bytes (a `flush` naming them) or reverts the room (`collab.md` §2). A room is still addressed by path on the wire: `createCollabHost` (`packages/collab/src/ws-room.ts`) takes the key from a `keyOf` the embedder supplies and answers each peer under the path it opened, so a peer that opened the old path and one that opens the new one share the room. A room loads the hash of the bytes it seeds from, saves through the host's `write` with that base and a `writeId` of its own, and a refusal reaches every participant as the `doc-conflict` control message (`collab.md` §2), leaving the room dirty. Two saves of one room run one after the other, so the second names the hash the first wrote. A room is recorded when it loads, so a path that fails to load, or a frame for a path a peer never opened, leaves nothing behind, and a path whose room changes key never goes back to a lower epoch. Activating another project saves each of its rooms with unsaved edits through its host, with its base, and then closes them; a room keyed by its path that the new project covers is saved, unconditionally, and closed too, so one file never has two rooms. A resubscribe the host answers with a snapshot reaches each room as the removal or change it missed. A room outside the active project is keyed by its path and saves unconditionally, as before. Tested by `packages/server/tests/collab-rooms.test.ts`, `collab-api.test.ts` (a rename through the dev server keeps the room), `packages/collab/tests/ws-room-host.test.ts` and `ws-wire.test.ts`. The cloud's rooms (§10.3) are in the platform repository: the session object's registry (`src/lib/collab/rooms.ts`, its SQLite tables in `src/lib/collab/store.ts`) keys every room by the `DocId` its host gives the document, or by its path when the host has not indexed it, starting the host with the first room, and keeps each room's key, the path its document is at and its base in the object's storage, so they survive hibernation with the room's update log. A room loads the hash of the bytes it seeds from and saves through the host's `write` with that base and a `writeId` of its own (`src/do/project-session.ts`), so the change is recorded with the room's origin rather than as external; the session's operation lock runs one save at a time. A refusal reaches every participant as `doc-conflict` and leaves the room dirty, a `flush` naming a base saves against it, and a writer's `revert` resets the room; a read-only participant's `flush` and `revert` change nothing and are acknowledged. The rooms follow the host's events by path as the dev server's do: a `fileRenamed`, from the contract's rename or the session's older route, moves a room, a removal of it or of a directory above it closes it unless the tree still holds a file at its path (a pull reports bytes the session has not read as a removal and an add), which settles it as a change instead, and a change it did not save (a based write, the older unconditional routes, a pull, a discard) reseeds a clean room and leaves a dirty one its edits, told of the conflict once per change; a tree that returns to the room's base ends the conflict, so a participant who joins then is not told of it. A change to bytes the session has not read yet is reported with a `diskHash` of `null`; taking the disk's copy still works, and keeping the room's edits waits until the host has read them, when the room is told their hash. The collab socket carries no token, so the reading is done by the next request that does: a commit reads in the files of the dirty rooms waiting on it before it saves them, and any other request starts the indexing pass, those files first, whether or not a client has subscribed. A commit saves every dirty room with its own base first, and leaves a refused one out. A new epoch over a replaced tree settles every room against it. Tested there by `tests/collab-rooms.test.ts` and the "collab rooms through the project state host" cases of `tests/project-session.test.ts`.

The host owns both by `DocId`. A room follows its document across a rename and is closed when the document is removed; it holds the document's shared buffer state (§6.1) and saves through §5. A host that stops serving the project closes its rooms, saving each one's unsaved edits through §5 first; a save it refuses keeps those bytes off the disk, and they end with the room. An overlay is keyed by the document and the `clientId` of the client that set it (§3.1), not by a connection: the socket drops for ordinary reasons (an idle timeout, a suspended window, `desktop.md` §10.1) and a host ends every subscription when its watcher recovers (§4.8), and none of those may unpublish an author's preview. The host drops a client's overlays once no subscription with that `clientId` has been open for a grace period (`overlayGraceMs`, configurable per host, default 30 seconds), so a closed window never leaves unsaved bytes published for longer than that. A client that sent no `clientId` has its overlays dropped when its subscription ends.

## 12. Reference Extraction

> **Status: Implemented.** The walk lives in `@jxsuite/protocol/refs` (`walkDocRefs`, `countTagUses`, `rewriteDocRefs`, `rewriteTagName`, `packages/protocol/src/refs.ts`) and its path arithmetic in `@jxsuite/protocol/ref-paths` (`packages/protocol/src/ref-paths.ts`), beside the contract, so Studio, which must not depend on a backend (`studio.md` §3), walks with the same code when it rewrites the documents a host could not index (§9.1); both are tested by `packages/protocol/tests/refs.test.ts`, `ref-paths.test.ts` and `refs-walk.test.ts`. `@jxsuite/server/refactor/refs` re-exports the walk for the hosts that import it from the server, and its module graph (the walk, its path arithmetic, plus `@jxsuite/schema`'s guards and asset paths) has no filesystem, process or watcher import; `packages/server/tests/refs-export.test.ts` imports the entry under Bun, bundles it for the browser, and fails on any `node:`, builtin or `chokidar` import in its graph and on any `process` or `Bun` global in the bundled code. Node does not load the TypeScript sources directly (extensionless relative imports, and no type stripping under `node_modules`), so a Node host reaches the walk through a bundle, as the desktop backend already does (`desktop.md` §7.1).

What counts as a reference in a Jx document has one definition: `walkDocRefs`, which takes a parsed document and a visitor and performs no I/O. A host whose graph is built answers the usage query from the references it already holds (`findReferences` with its `graph` option, `packages/server/src/refactor/find-refs.ts`), and a host below `indexed`, one whose watcher is degraded (§4.8), one that has not settled the changes it has been told of, or no host, walks the tree; both give one answer (`packages/server/tests/refactor-find-refs-graph.test.ts`). It is published as a subpath export of `@jxsuite/protocol`, and re-exported by `@jxsuite/server`, whose module graph contains no filesystem, process or watcher import, so Bun imports it as source and every other host bundles it unchanged (a Durable Object's Worker, a browser, the desktop backend's Node bundle), and the dependency graph (§8) of every host is built from the same walk as the rename refactor and the usage query.

## 13. Persistence and the Native Core

### 13.1 Persistence dialect

> **Status: Implemented.** The cloud host persists its log in the session Durable Object's SQLite storage with exactly this table (`src/lib/project-state/log.ts` in the platform repository), the epoch and revision in a key-value table beside it and its index in a table of its own, all in the subset, written in the same synchronous run as the change each records, which a Durable Object commits as one unit. Its tests pin the window's two bounds, the all-or-nothing answer of a trimmed log, and a sequence that continues from storage after a restart. No other host persists its log.

Any persisted form of this contract's state (the cloud's replay log first; the desktop's, if measurement ever asks for one) uses the common subset of SQLite: plain tables, `INTEGER`, `TEXT` and `BLOB` columns, no extension functions, no dialect-specific pragmas in the schema. That keeps one schema valid in a Durable Object's SQLite storage and in an embedded SQLite-compatible engine (Turso) on the desktop. A persisted log stores events as JSON text keyed by `(epoch, rev)`, and trims from the oldest revision.

The log is one table:

```sql
CREATE TABLE IF NOT EXISTS events (
  epoch TEXT NOT NULL,
  rev INTEGER NOT NULL,
  at INTEGER NOT NULL,
  event TEXT NOT NULL,
  PRIMARY KEY (epoch, rev)
);
```

`event` is the `ProjectEvent` as JSON text, exactly as a frame carries it, and `at` is when it was appended, in milliseconds since the Unix epoch. A host appends an event's row in the same transaction as the change it records, so a log never holds an event whose change was lost, nor a change without its event. The current epoch and revision are recorded beside the log, in the same transaction, so a log trimmed to nothing still continues its sequence. A host keeps rows of its current epoch only: starting a new epoch (§2.3) deletes the old one's rows in the step that starts it. The window is the most recent 4096 events or those of the last 24 hours, whichever is fewer, trimmed after each append: a row goes when 4096 newer rows exist or when it is older than 24 hours. A subscribe whose `sinceRev` is below the oldest kept row's revision minus one is answered with a snapshot (§3.1), so a trimmed log still answers all or nothing (§2.3).

### 13.2 Native core

> **Status: Implemented.** The host logic (index, hashing, graph, log) is TypeScript: `packages/protocol/src/project-state.ts` and `packages/server/src/project-state/`, which the desktop session and the dev server both run (§10.1, §10.2). `bench/project-state/run.ts` measures it, indexing a 10,000-file project and replaying a 1,000-event burst under Node (the desktop backend's runtime) and Bun (the dev server's).

> **Status: Future.** The host logic may later move into one Rust core, compiled natively for the desktop backend and to WebAssembly for the Durable Object, with storage behind a trait so the same core runs on either persistence. That waits on a measurement of the TypeScript hosts that shows them too slow on a large project; the contract does not change if it happens.
