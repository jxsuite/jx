# Jx Monorepo — Desktop

Subsystem notes for `packages/desktop`: how the Electron application is packaged and what keeps a packaged build honest, and how Jx Studio reaches the Microsoft Store and the Snap Store. The root `AGENTS.md` holds the rest of the agent notes, and everything in it applies here too.

## The Electron application, and packaging it

The application is Electron as the root process with the backend as its utility process, on the Node inside Electron (`specs/desktop.md` §9.7 is the architecture, §7 the packaging). No channel ships a Bun: the Mac App Store's automated review rejected 6.1.0 for the system ICU symbols Bun's JavaScriptCore imports, and Bun is now only the repository's tool. The Nix package, the snap, a checkout (`bun run dev`) and every installer run it, and it is the only desktop host: the per-window Bun launcher (`bun run chromium`) was removed (`specs/desktop.md` §9.2). `src/webview/` is the adapter every window loads, `src/main/` the main process, `src/backend/` the backend.

- **`bun run stage` assembles, `electron-builder.yml` places, `bun run package` does both.** `scripts/stage-app.ts` writes `build/app` (becomes `app.asar`: the main process, the preload, a `package.json`) and `build/resources` (stays real files: the backend bundle with its data and its staged `node_modules`, and the studio assets). `src/main/layout.ts` is the one place the app learns where those are, and `tests/` hold it to the config. `build/` and `artifacts/` are generated and gitignored.
- **One function bundles the backend, and the bundle holds no Bun code.** `bundleBackend` in `scripts/lib/backend-bundle.ts` builds `src/backend/main.ts` for `target: "node"` with the default export conditions, so `#serve` and `#bundler-backend` resolve to their Node side. `stage-app.ts`, `run-electron-app.ts` (a checkout bundles into `build/dev-backend-*`, because Electron's Node cannot run the TypeScript sources) and `package.nix` (`scripts/bundle-backend.ts`) all call it. `tests/backend-bundle.test.ts` bundles exactly the same way and fails naming each source file that put a `Bun.` call in; a Bun API belongs behind an `imports` condition with a Node side, as `#serve` is.
- **A bundle is a different program from its sources, and only starting it proves anything.** Inlined modules find their data and their dependencies by path (`import.meta.dirname`, `createRequire`), and no unit test running the sources can see a file nobody staged. `bun run smoke` (`scripts/smoke-backend.ts`) starts the STAGED backend under Node (the `node` on `PATH`, Node 24 in `desktop-bundle`; the release lanes pass `--electron packaged`, which runs the PACKAGED backend and studio assets, not the staged ones, under the packaged Electron with `ELECTRON_RUN_AS_NODE=1`), with the messages the Electron main process sends, loads the native packages, and calls the RPCs that reach those paths, a package add and remove included. It runs on every pull request that reaches this package (`desktop-bundle` in `test.yml`) and in every release lane. When you inline a module that reads its own files, add the file to `BACKEND_DATA` (or the package to `BACKEND_MODULES`) and a check to the smoke test, in the same change. That list was found empirically: `catalog.json` was the first thing the smoke test caught. **The app ships no extension, first-party ones included**: a project resolves `@jxsuite/parser` from its own install, exactly as it would a third-party extension, so the smoke test installs the new project's dependencies before any check that loads one. That install takes its `@jxsuite` packages from this checkout, packed with `bun pm pack` (`scripts/lib/workspace-tarballs.ts`), and only third-party ones from the registry: a starter pins the versions it is released beside, which on the release pull request and in the release lanes are not on npm yet (the release PR's install failed with `ETARGET` on `@jxsuite/compiler@^8.0.0`). Never stage an extension into `backend/node_modules` to make a check pass; that would hide the case where a project's own dependencies are missing.
- **Native packages are staged as real files, for the host only.** `esbuild`, `sharp` and `@npmcli/arborist` find files of their own by path at run time (a platform binary, libvips, Arborist's helpers), so they stay external (`BACKEND_NATIVES`) and `moduleClosure` copies each with its installed dependency closure into `backend/node_modules`. The binaries are this host's, so `stage-app.ts` refuses another `--platform`/`--arch`, and every release lane builds on a native runner. 6.1.0 inlined sharp with nothing staged, and its loader cannot find `@img/sharp-*/sharp.node` from a bundle: image optimization never worked in the packaged app. On NixOS the prebuilt sharp (the addon and the libvips it links) needs `libstdc++`, which has no global location there: `package.nix` adds the compiler's runtime library to those binaries' RPATH and its install check loads sharp under the packaged Electron, and the flake's dev shell puts it on `LD_LIBRARY_PATH`, which the backend's utility process inherits.
- **Bun's bundler (which still makes both bundles) folds module-identity globals at build time, so a bundle cannot ask for its own path.** `__filename`, `module.filename` and `import.meta.filename` become the SOURCE file's name, and `require.main` is Electron's own internal module. The app finds its directory with `app.getAppPath()`, and `tests/electron-shell-bundle.test.ts` fails if the bundle ever relies on one of them.
- **electron-updater is bundled into the main process and reads `latest*.yml` from the latest release.** `publish.url` in `electron-builder.yml` is the same `releases/latest/download/` feed the old updater read, which is why the desktop release must be GitHub's "latest" (the release lanes force it). The updater is enabled only where it can replace the app: not in a checkout, not a Store install, and on Linux only the AppImage. Installed ElectroBun builds cannot update into this application, since that updater applies archives of its own format; users reinstall once.
- **Electron is pinned, not installed.** `electronVersion` in `electron-builder.yml` equals nixpkgs' `electron`, and the npm `electron` package stays out of the dependency graph because its postinstall downloads ~100 MB. Bump both together.
- **Unverified until a release has run them:** macOS signing and notarization (`CSC_LINK`, `APPLE_API_KEY*` in `bundle-desktop-macos.yml`), the Windows lane's smoke test and its appx, and the AppImage wrapper itself (the Linux arm64 unpacked app was built and run on Ubuntu 24.04 under Xvfb, with its staged backend passing the smoke test, but only a release builds the AppImage). The snap has not been packed: the container used for the Linux checks has no squashfs, so snapd cannot run there. The macOS DMG and zip, the unpacked app, and the staged backend were built and run on a Mac without a signing identity. Read the first release's lanes before trusting them.
- **The Windows installer changed.** The old lane shipped a WiX `.msi`; the new one ships an NSIS `JxStudio-Setup.exe` (what electron-updater replaces in place) and the Store's appx. `release-assets.json` and the download pages say so, and `scripts/desktop-build-lanes.test.ts` holds those names equal to `electron-builder.yml`'s `artifactName` patterns.

## Microsoft Store Publishing

`desktop-v5.2.0` was submitted to the Microsoft Store by hand — someone signed into Partner Center, uploaded the MSIX that had already been attached to the GitHub release, filled in the listing, and clicked "Submit for certification." `store-publish.yml` (called from `release-please.yml`, gated on the Windows lane that builds the package — `needs.release-please.outputs.desktop_released == 'true'`) is the automation that does that from then on, and manual publishing is retired: the release pipeline owns the Store package.

- **It is Microsoft's own path, not ours.** The lane follows [Microsoft's GitHub Actions guide](https://learn.microsoft.com/en-us/windows/apps/publish/msstore-dev-cli/github-actions): `microsoft/microsoft-store-apppublisher` installs the Microsoft Store Developer CLI, `msstore reconfigure` signs it in, and `msstore publish <msix> --appId` creates the submission, uploads, swaps the package, commits and waits for the commit to be accepted. There is no script of ours in between. `desktop-v5.3.0` ran a hand-rolled REST client instead and failed on a contract the CLI already gets right: the update call REPLACES the whole submission, so sending the package list alone came back `400: The size of Listings must be 1 or more`.
- **It runs on `windows-latest`, and that is load-bearing.** `msstore reconfigure` keeps the client secret in the OS credential store; on Linux that is libsecret, which needs a Secret Service a hosted runner does not run.
- **The CLI version is pinned** (`version:` on the installer action). A re-run must behave like the run it repeats, and the CLI has shipped regressions (a v0.4.0 crash, microsoft/msstore-cli#154; an upload timeout that defaulted to zero, #162). Dependabot bumps the action's tag but cannot see that input, so moving the CLI is a deliberate edit.
- **Free products only.** Microsoft supports CI publishing for free products only, and Jx Studio is one, so the price the Store clones from the last published submission round-trips unchanged. A paid listing would need `--priceId` and a re-read of the guide.
- **Creating a submission clones the last PUBLISHED one.** Listing text, screenshots, age ratings and pricing come from there; only the package changes. A listing edited in Partner Center survives into the next automated release, but edit it on the published submission, never on a pending draft (next bullet).
- **A pending submission is REPLACED, by decision.** The Store allows one open submission per app, and `msstore publish` deletes whatever is pending before it creates its own. That includes a draft a human is mid-edit on in Partner Center, and it is accepted: the release pipeline is the only publisher, so a pending draft is either debris from a failed run or work that belongs in the next release. The previous rule (refuse, and require a `force_replace_pending` dispatch to delete) is gone, along with the input. It existed to protect hand-made submissions, and there are no more of those.
- **Soft no-op until five secrets exist.** `STORE_TENANT_ID` / `STORE_CLIENT_ID` / `STORE_CLIENT_SECRET` come from a Microsoft Entra app registration added under **Partner Center → Account settings → User management → Microsoft Entra applications** with the **Manager** role. `STORE_SELLER_ID` is the Seller (publisher) ID in Partner Center's account settings. `STORE_APP_ID` is the Store ID from the app's Partner Center URL (`9P7DQL3T4NJ6` for Jx Studio): identifying, not sensitive, but kept beside the other four for one less place to look. Until all five are set, the job skips with a `::warning::` naming the missing ones and stays green.
- **The workflow does not wait for certification.** `msstore publish` returns once the commit leaves `CommitStarted`; certification legitimately takes hours to days (see the `store-publish` job comment in `release-please.yml`). It polls `CommitStarted` without a bound, and the Store has been reported to sit there for hours (microsoft/msstore-cli#29), so the job carries `timeout-minutes: 45`. A `CommitFailed` exits non-zero with the Store's own error details in the log.
- **`workflow_dispatch` is the backfill/retry entry point**, the same pattern `publish.yml` uses: point `tag_name` at a specific `desktop-v*` release to resubmit it. A retry needs no special flag, because whatever the failed run left pending is replaced.

## Mac App Store Publishing

The Mac App Store is a second macOS channel, built and uploaded by `mas-publish.yml` (called from `release-please.yml`; `workflow_dispatch` runs it from any branch, which is how the first run is made). `specs/desktop.md` §7.7 is the contract and `plans/desktop/mac-app-store.md` is what is still open.

- **It is a separate build, not a flag on the DMG.** `bun run package --target mas` asks electron-builder for `--mac mas`: Apple Distribution identity, a Mac Installer Distribution identity for the `.pkg`, an embedded provisioning profile, no hardened runtime and no notarization. The artifact is `mas-arm64-JxStudio.pkg`. `tests/mas-config.test.ts` holds the `mas` block and the two entitlements files to these facts.
- **The App Sandbox is on, and what it breaks is the open work.** `entitlements.mas.inherit.plist` is what Electron's helpers are signed with, and the backend is one of them: a utility process (`utilityProcess.fork`), not a foreign binary. The backend is started before any folder is picked, so whether it can read a picked project is unmeasured. Site import is absent (its browser is only set by the Nix package and the snap), and `git` runs Apple's developer-tools shim, which cannot read the user's Git configuration. Read §7.7 before changing any of it.
- **A picked folder reaches the backend only because the backend starts after the pick.** The sandbox grants exactly what the user picked, to the Electron main process and to children it starts afterwards, so the Mac App Store build asks for the project **folder** (a picked `project.json` grants only that file), stores a security-scoped bookmark per folder (`main/folder-grants.ts`, `folder-grants.json` in the user-data directory), restores them all before spawning the backend, and replaces the backend when a pick is not inside a granted folder (`restartBackend` in `main/app.ts`). Test it for real, not only through the fakes: `bun run package --target mas --arch arm64 -- --dir -c.mac.identity=null -c.mas.identity=null` produces the MAS-flavor app (the signing step then fails, which is expected without certificates), then sign it ad hoc with `entitlements.mas.plist` (minus the two identifier keys) and `entitlements.mas.inherit.plist` on every nested binary, add `ElectronTeamID` to each `Info.plist` (osx-sign does this when it signs with an identity), and launch it. A copy made from the regular macOS build crashes under the sandbox, because it is the wrong Electron flavor.
- **The store updates the app.** `process.mas` makes `updatesEnabled` return false, so `electron-updater` never starts.
- **Soft no-op until eight secrets exist.** `MAS_CERTIFICATE_BASE64` and `MAS_CERTIFICATE_PASSWORD` (the Apple Distribution `.p12`), `MAS_INSTALLER_CERTIFICATE_BASE64` and `MAS_INSTALLER_CERTIFICATE_PASSWORD` (the Mac Installer Distribution `.p12`), `MAS_PROVISIONING_PROFILE_BASE64` (the Mac App Store profile for `com.jxsuite.studio`), and the existing `APPLE_API_KEY_BASE64`, `APPLE_API_KEY_ID` and `APPLE_API_ISSUER_ID`. The API key needs the App Manager role. Until all are set the job skips with a `::warning::` naming the missing ones and stays green.
- **A `.p12` must use legacy algorithms.** macOS's `security import` rejects OpenSSL 3's default PKCS#12 (SHA-256 MAC, AES-256) with "MAC verification failed during PKCS12 import (wrong password?)", which is a misleading message and not a wrong password. Re-encode with `openssl pkcs12 -export -legacy` before base64-encoding a secret. This cost the Developer ID lane two failed runs.
- **The `.pkg` is in `artifacts/mas-arm64/`, not `artifacts/`.** electron-builder puts the package beside the unpacked app and names it by `artifactName`, so the lane finds it with `find` and prints the directory when it is missing. A missing file shows up as the upload step's failure, since the build step succeeds without one.
- **No binary may import the system ICU.** App Review rejected 6.1.0 for 129 non-public symbols, all imported from `libicucore` by the Bun it shipped. The lane lists every Mach-O in the `.app` with `otool -L` and `nm -u -m` before the upload and fails naming any that imports `libicucore`, which is the check App Review runs, run first.
- **The upload goes to TestFlight only.** `xcrun altool --upload-app` with the API key. Nothing submits a build to App Review. Each upload needs a higher build number than the last, which `-c.mac.bundleVersion=${{ github.run_number }}` supplies.
- **One-time setup, by a person in Apple's consoles:** the bundle ID `com.jxsuite.studio` is registered in the developer portal and is the `appId` of every channel (the DMG, the Store appx and the AppImage share it with the Mac App Store build). Confirm its the sandbox-compatible capabilities, create the app record in App Store Connect, create the two distribution certificates, and create the Mac App Store provisioning profile.

## Snap Store Publishing

Ubuntu gets Jx Studio from the Snap Store as `jx-studio`, through the same shape of lane as the Microsoft Store: `build-snap.yml` attaches `jx-studio_<version>_<arch>.snap` (amd64 and arm64) to the desktop release, and `snap-publish.yml` uploads them with `scripts/snap-publish.ts` (`bun run snap:publish`). Both are called from `release-please.yml` and gate nothing; `snap-publish.yml`'s `workflow_dispatch` is the retry/backfill entry point and can target `candidate`, `beta` or `edge`.

- **The snap runs the same unpacked Electron application as every other channel.** `build-snap.yml` runs `bun run --cwd packages/desktop package --target linux --arch <x64|arm64> -- --dir --publish never`, copies the unpacked build to `packages/desktop/snap-stage` (with a `version.txt`), and `snapcraft.yaml` dumps it under `$SNAP/app/`. The executable is `jx-studio`, and it brings its own Electron (whose Node runs the backend) and its layout (`main/layout.ts`), so the snap has no Bun part, no Nix tree and no `ELECTRON_BIN`. `snap/local/jx-studio` is the command (`exec "$SNAP/app/jx-studio" --no-sandbox --class=jx-studio "$@"`) and `snap/gui/jx-studio.desktop` the launcher entry. `snapcraft-config.test.ts` holds the config to these facts.
- **The snap still uses the `gnome` extension (GTK, and `gpu-2404` Mesa) and `core24`.** `stage-packages` carries the libraries Electron links against that neither the runtime nor Chromium's staged set provides. Electron's setuid `chrome-sandbox` is removed in `override-build`, because the store refuses a setuid file and the sandbox it serves is not started.
- **Canonical's Chromium is in the snap only as the site import's browser.** It is copied from the `chromium` snap (`build-snaps`) and found through `CHROME_PATH`, because puppeteer cannot open a page in Electron. A snap cannot use the user's installed Chromium snap instead: strict confinement cannot execute another snap's binaries, and the chromium snap has no slots. **Chromium updates reach users only when Jx Studio is released**; accepted, because it loads only the sites a user imports.
- **Hardware acceleration under `gpu-2404` is unmeasured for the Electron prebuilt, and the first store build is where it shows.** Canonical's Chromium was the proven renderer there, which is why the snap was a Chromium launcher until it moved. This is an open verification item, not a blocker: if the first build renders in software, record that in `specs/desktop.md` §9.6 rather than reintroducing a second shell. The Nix history stays relevant to one decision: nixpkgs Chromium looks for drivers only where NixOS installs them, and a pure-Nix snap (a same-length `/nix/store` rewrite, 655 MB) rendered in software, so the snap never carries a Nix-built binary that has to find a driver.
- **Locally, build it in LXD**: stage the unpacked build into `snap-stage/` as the workflow does, then `snapcraft pack --use-lxd` from `packages/desktop`. CI uses `--destructive-mode`, which needs a 24.04 host, which is why build-snap.yml pins `ubuntu-24.04` rather than `ubuntu-latest`.
- **Soft no-op until the secret exists.** One-time setup: `snapcraft register jx-studio`, then `snapcraft export-login --snaps=jx-studio --acls=package_access,package_push,package_update,package_release creds` and store the file's content as the `SNAPCRAFT_STORE_CREDENTIALS` repository secret. **An exported login expires (at most a year)**; the script warns 30 days ahead on every run, and the fix is the same two commands.
- **The snap runs with `--no-sandbox`** (`snap/local/jx-studio`). Chromium's sandbox needs `browser-support` `allow-sandbox: true`, which the store grants only to trusted publishers after a forum request. Once granted: declare the plug with `allow-sandbox: true` in `snapcraft.yaml`, drop `--no-sandbox` from the command, and delete the `chrome-sandbox` removal.
- **The Nix package ships a production install, not the workspace's `node_modules`.** `package.nix` reinstalls with `--production --filter '@jxsuite/desktop'` after building, prunes `monaco-editor`/`tabulator-tables` (bundled into the studio assets) and `tests/`, and its `installCheckPhase` proves that the backend bundle (made in the build phase, by `scripts/bundle-backend.ts`) holds no Bun code and that its native packages (`backendNatives`, equal to `BACKEND_NATIVES`) resolve from it through the result, and checks the Electron application's bundle. So **a package the bundle leaves external must be declared by the package that imports it**, or the production install drops it and `nix build` fails. Packages the app reaches without importing them must be declared too. No extension is one of them: a project resolves every extension it enables from its own install, so no `extensions/*` package is a dependency of `@jxsuite/desktop` and `package.nix` does not copy `extensions/`; `nix-bundle-completeness.test.ts` asserts both.
- **A manual-review hold is success, not failure** (the first upload, and any upload that changes plugs, is held). So is a byte-identical re-upload, which is what makes re-running `snap-publish.yml` safe.
