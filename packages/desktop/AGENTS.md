# Jx Monorepo — Desktop

Subsystem notes for `packages/desktop`: how the Electrobun SDK reaches a checkout, and how Jx Studio reaches the Microsoft Store and the Snap Store. The root `AGENTS.md` holds the rest of the agent notes, and everything in it applies here too.

## The Electrobun SDK is vendored, and typechecking depends on it

Electrobun 2 publishes **no SDK to npm**: `node_modules/electrobun` is a command bootstrap whose `exports` map sends every specifier — `electrobun`, `electrobun/main`, `electrobun/view`, types included — to `lib/moved.cjs`, a module whose entire body is `throw new Error(...)`. The real SDK reaches a project only when Hutch downloads that release's core archive and copies it into a gitignored `.hutch/devkit`. That is a network step, so a clone could not typecheck `packages/desktop` at all and CI had to run `bunx electrobun prepare` before it could reach `tsc`.

So the SDK's TypeScript sources are vendored: **`vendor/electrobun`, a git submodule pinned to the exact release the `electrobun` devDependency names.** `packages/desktop/tsconfig.json` maps `electrobun/*` straight into `vendor/electrobun/package/src`.

- **`bun run electrobun:verify` is the gate; `bun run electrobun:sync` is the fixer** (`scripts/check-electrobun-vendor.ts`). The root `postinstall` runs the fixer softly, so an ordinary `bun install` leaves a working tree that typechecks. CI runs `--init`, which materialises and narrows the submodule but deliberately **does not move the gitlink** — moving it is exactly how a Dependabot bump would stop looking like a mismatch. `packages/desktop/scripts/pre-build.ts` runs `--init` too, as does every desktop bundle lane before it builds, because the launcher's init bundle is compiled by plain `bun build` through the same tsconfig `paths`. The root `postinstall` skips the fixer under `CI`, and the release lanes used a bare checkout, so **desktop 5.0.0 through 5.1.3 shipped an `init.js` that threw on import**: with the submodule empty the bundler fell back to `node_modules/electrobun`, inlined the throwing stub, and exited 0. `scripts/desktop-build-lanes.test.ts` fails any lane that builds the app without the `--init` in front of it, and pre-build and post-build both judge the bundle's content (`packages/desktop/scripts/init-bundle.ts`), not just its existence.
- **The version has two writers**, the pin and the gitlink, and the gate is what keeps them together. A Dependabot `electrobun` bump moves the pin alone and goes red here, and `.github/workflows/electrobun-vendor.yml` is the second writer: it runs `bun run electrobun:sync` on the pull request, commits the moved gitlink to the branch and approves the runs its push queued, the same shape as `schemas.yml`. **The gate itself stays strict** — test.yml runs `--init`, which never moves the gitlink, so the head a bump arrived on is red, the lane fixes it, and the pushed head re-runs green; `scripts/electrobun-vendor-lane.test.ts` holds every other workflow to never running `--fix`. A fork's pull request, which the token cannot push to, keeps the red X and `bun run electrobun:sync` is its patch. The lane terminates on a fixed point (once the gitlink names the pinned tag there is nothing left to move), so it carries no actor refusal, and its push survives losing a race to `schemas.yml` on the same branch by re-applying the gitlink onto the new tip.
- **Hutch still owns the main-process build.** `.hutch/devkit` is the sysroot for Hutch's own bundling of the main process; the submodule is the typecheck sysroot **and** the build sysroot for the webview init bundle, which Hutch never compiles. They are one release rather than two sources of truth — the projection is a verbatim copy of the same directories (196 of 197 files byte-identical at 2.0.1). The gate compares VERSIONS, not bytes, on purpose: upstream's release artifact and its git tag legitimately differ, and `--init` reports those byte differences without failing on them.
- **The checkout is sparse**, and that is load-bearing rather than thrift. Upstream interleaves ~40 `*.test.ts` with its sources and ships a `.md` among them; at a tracked path those would be collected by a root-level `bun test`, rewritten by `bun run format:md`, and globbed by `check-coverage-manifest.ts`. Narrowed to the five directories the entry points reach, it is 1 MB instead of 26 MB and none of that happens.
- **A tracked path is not ignored by anything implicitly.** oxlint walks the tree honouring `.gitignore` — which is what actually excludes `node_modules`, `dist` and the old `.hutch/devkit`, and why `.oxlintignore` is inert (oxlint's ignore file is `.eslintignore`, via `--ignore-path`, and the lint script passes neither). `vendor` therefore needs an explicit entry in **both** `.oxlintrc.json` and `.oxlintrc.typecheck.json`, plus `.oxfmtrc.json` and root `bunfig.toml`.
- **The Nix derivation is the fifth of those, and the one that cost a release.** `package.nix` takes the whole repository as `src`, so a tracked path is part of the tree whose NAR hash IS the store path `nix run github:jxsuite/jx/release` resolves — and `vendor/electrobun` is the one tracked path whose PRESENCE depends on how the tree was fetched. GitHub's tarball materialises the gitlink as an empty directory; nix's git-tree source for a checkout omits it. The submodule is uninitialised either way, so no build phase notices — but two empty directories are two NAR entries, and `desktop-v5.0.0` had two store paths for one commit. CI published `sq57vgab…` and every consumer asked for `671d1spz…`: the push succeeded, the closure was complete, and the cache was useless (#250). `src` now filters `vendor` so the two agree by construction, asserted in `electrobun-config.test.ts` and re-checked against a live `nix eval` on nix.yml's publish leg.
- **`.d.ts` remains impossible.** `TS4094` in the SDK's own `index.ts` blocks declaration emit, so `skipLibCheck` cannot help and `packages/desktop` keeps its own tsconfig. That carve-out is asserted, not just written down, in `packages/desktop/tests/electrobun-config.test.ts`.

## Microsoft Store Publishing

`desktop-v5.2.0` was submitted to the Microsoft Store by hand — someone signed into Partner Center, uploaded the MSIX `build-msix.yml` had already attached to the GitHub release, filled in the listing, and clicked "Submit for certification." `store-publish.yml` (called from `release-please.yml`, gated the same way as `build-msix` — `needs.release-please.outputs.desktop_released == 'true'`) is the automation that does that from then on, and manual publishing is retired: the release pipeline owns the Store package.

- **It is Microsoft's own path, not ours.** The lane follows [Microsoft's GitHub Actions guide](https://learn.microsoft.com/en-us/windows/apps/publish/msstore-dev-cli/github-actions): `microsoft/microsoft-store-apppublisher` installs the Microsoft Store Developer CLI, `msstore reconfigure` signs it in, and `msstore publish <msix> --appId` creates the submission, uploads, swaps the package, commits and waits for the commit to be accepted. There is no script of ours in between. `desktop-v5.3.0` ran a hand-rolled REST client instead and failed on a contract the CLI already gets right: the update call REPLACES the whole submission, so sending the package list alone came back `400: The size of Listings must be 1 or more`.
- **It runs on `windows-latest`, and that is load-bearing.** `msstore reconfigure` keeps the client secret in the OS credential store; on Linux that is libsecret, which needs a Secret Service a hosted runner does not run.
- **The CLI version is pinned** (`version:` on the installer action). A re-run must behave like the run it repeats, and the CLI has shipped regressions (a v0.4.0 crash, microsoft/msstore-cli#154; an upload timeout that defaulted to zero, #162). Dependabot bumps the action's tag but cannot see that input, so moving the CLI is a deliberate edit.
- **Free products only.** Microsoft supports CI publishing for free products only, and Jx Studio is one, so the price the Store clones from the last published submission round-trips unchanged. A paid listing would need `--priceId` and a re-read of the guide.
- **Creating a submission clones the last PUBLISHED one.** Listing text, screenshots, age ratings and pricing come from there; only the package changes. A listing edited in Partner Center survives into the next automated release, but edit it on the published submission, never on a pending draft (next bullet).
- **A pending submission is REPLACED, by decision.** The Store allows one open submission per app, and `msstore publish` deletes whatever is pending before it creates its own. That includes a draft a human is mid-edit on in Partner Center, and it is accepted: the release pipeline is the only publisher, so a pending draft is either debris from a failed run or work that belongs in the next release. The previous rule (refuse, and require a `force_replace_pending` dispatch to delete) is gone, along with the input. It existed to protect hand-made submissions, and there are no more of those.
- **Soft no-op until five secrets exist.** `STORE_TENANT_ID` / `STORE_CLIENT_ID` / `STORE_CLIENT_SECRET` come from a Microsoft Entra app registration added under **Partner Center → Account settings → User management → Microsoft Entra applications** with the **Manager** role. `STORE_SELLER_ID` is the Seller (publisher) ID in Partner Center's account settings. `STORE_APP_ID` is the Store ID from the app's Partner Center URL (`9P7DQL3T4NJ6` for Jx Studio): identifying, not sensitive, but kept beside the other four for one less place to look. Until all five are set, the job skips with a `::warning::` naming the missing ones and stays green.
- **The workflow does not wait for certification.** `msstore publish` returns once the commit leaves `CommitStarted`; certification legitimately takes hours to days (see the `build-msix` job comment for what that looks like in practice). It polls `CommitStarted` without a bound, and the Store has been reported to sit there for hours (microsoft/msstore-cli#29), so the job carries `timeout-minutes: 45`. A `CommitFailed` exits non-zero with the Store's own error details in the log.
- **`workflow_dispatch` is the backfill/retry entry point**, the same pattern `publish.yml` uses: point `tag_name` at a specific `desktop-v*` release to resubmit it. A retry needs no special flag, because whatever the failed run left pending is replaced.

## Snap Store Publishing

Ubuntu gets Jx Studio from the Snap Store as `jx-studio`, through the same shape of lane as the Microsoft Store: `build-snap.yml` attaches `jx-studio_<version>_<arch>.snap` (amd64 and arm64) to the desktop release, and `snap-publish.yml` uploads them with `scripts/snap-publish.ts` (`bun run snap:publish`). Both are called from `release-please.yml` and gate nothing; `snap-publish.yml`'s `workflow_dispatch` is the retry/backfill entry point and can target `candidate`, `beta` or `edge`.

- **The snap runs the Chromium app-mode launcher, not the Electrobun bundle, and that was measured.** Electrobun's Linux `libNativeWrapper.so` imports `XOpenDisplay` and `gdk_x11_window_get_xid`: it embeds CEF in GTK by X11 window id, and with `DISPLAY` unset it exits on "cannot open display". So the CEF bundle only ever runs under XWayland. Re-test that before proposing a snap of the Electrobun build.
- **`packages/desktop/snap/snapcraft.yaml` is a hybrid, on purpose.** The app tree is the Nix package's `lib/jx-studio` (`nix build .#default`, staged into `snap-stage/` by the workflow); Chromium is Canonical's build, copied from the `chromium` snap (`build-snaps`); Bun is the official binary, pinned by checksum (`snapcraft-config.test.ts` holds its series to CI's). The reason is graphics: Canonical's Chromium links against the same Ubuntu userspace as the `gnome` extension's `gpu-2404` Mesa, which gives hardware acceleration. nixpkgs Chromium looks for drivers only where NixOS installs them, so a pure-Nix snap rendered in software. A snap cannot use the user's installed Chromium snap instead: strict confinement cannot execute another snap's binaries, and the chromium snap has no slots. **Chromium updates reach users only when Jx Studio is released**; accepted, because it loads only the user's own projects from loopback.
- **Do not go back to a pure-Nix snap without a plan for both of these.** nixpkgs no longer has `snapTools.makeSnap` (it broke on snapd >= 2.36, which rejects a layout creating `/nix`, NixOS/nixpkgs#100618), and a working replacement (a same-length `/nix/store` → `/opt/nixst` rewrite bound with a layout) was built, passed `snap-review`, and still rendered in software. It was also 655 MB.
- **Locally, build it in LXD**: `snapcraft pack --use-lxd` from `packages/desktop` after staging `snap-stage/lib/jx-studio`. CI uses `--destructive-mode`, which needs a 24.04 host, which is why build-snap.yml pins `ubuntu-24.04` rather than `ubuntu-latest`.
- **Soft no-op until the secret exists.** One-time setup: `snapcraft register jx-studio`, then `snapcraft export-login --snaps=jx-studio --acls=package_access,package_push,package_update,package_release creds` and store the file's content as the `SNAPCRAFT_STORE_CREDENTIALS` repository secret. **An exported login expires (at most a year)**; the script warns 30 days ahead on every run, and the fix is the same two commands.
- **Chromium runs with `--no-sandbox` inside the snap** (`chromiumPlatformArgs`, only when `$SNAP` is set). Its sandbox needs `browser-support` `allow-sandbox: true`, which the store grants only to trusted publishers after a forum request. Once granted: declare the plug with `allow-sandbox: true` in `snapcraft.yaml` and drop `--no-sandbox` from the `SNAP` branch.
- **The Nix package (and so the snap) ships a production install, not the workspace's `node_modules`.** `package.nix` reinstalls with `--production --filter '@jxsuite/desktop'` after building, prunes `monaco-editor`/`tabulator-tables` (bundled into the studio assets) and `tests/`, and its `installCheckPhase` bundles `chromium/index.ts` against the result. So **a runtime import must be declared by the package that makes it**: an undeclared one used to be satisfied by the root's dev tooling (`@jxsuite/server` imported `oxfmt` that way) and now fails `nix build`. Packages the app reaches without importing them must be declared too, which is why every `extensions/*` package is a `dependencies` entry of `@jxsuite/desktop` (the schema loader resolves first-party schemas from the app, never the project); `nix-bundle-completeness.test.ts` asserts it.
- **A manual-review hold is success, not failure** (the first upload, and any upload that changes plugs, is held). So is a byte-identical re-upload, which is what makes re-running `snap-publish.yml` safe.
