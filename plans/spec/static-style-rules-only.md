# Built output writes every style declaration as a rule and carries each reactive value through a custom property the element sets, so a nested block can always override it

## Context

`specs/spec.md` §9.1, line 875:

> **Status: Partial.** The runtime conforms (§9.6). The static compiler does not: a `${…}` base declaration it can resolve against a build-time scope, and a component definition's resolved host style, are written into an inline `style` attribute (`inlineStyleDeclarations` and the `hostStyle` argument of `buildAttrs` in `packages/compiler/src/shared.ts`), so in prerendered HTML a `:hover` or `@media` block cannot override those declarations.

§9.1 says every declaration becomes a rule, a `${…}` template and a `{ $ref }` mean the same thing, and a reactive custom property on the element itself is written inline under the author's own name. §9.6 gives the runtime's mechanism: the rule says `property: var(--jx-r<n>-<m>)` and the element sets the variable inline (`applyStyleInto` in `packages/runtime/src/runtime.ts`).

**What the build does today** (read against the code and a scratch `compileClient`/`emitElementModule` run, 2026-09-27)

- **Prerender.** `buildAttrs` writes `inlineStyleDeclarations(def.style, scope)`, the base `${…}` entries resolved against the scope, as `style="color: red"`. `renderStaticNode` reaches it for every element of a component definition with the instance's scope, so a definition's children carry their resolved templates inline per instance. `renderComponentInstance` appends a nested instance's host style (`resolveHostStyle`) to the same attribute. On a site page `resolveDocTemplates` (`packages/compiler/src/site/site-build.ts`) has already turned a page element's resolvable base templates into literals, so the page case is the direct `compile()` route (`compileStaticPage`, and `compileClient`'s static attributes) and templates the build leaves for the client.
- **Page-level instance.** `expandComponents` merges `resolveHostStyle(...)` into `node.style` as `{ ...node.style, ...resolvedStyle }`. That is a rule, but it gives the definition's resolved host value precedence over the instance's own, the reverse of §9.6, and `compiler.md` §8.1 documents that order. A definition's static host declarations already lose to the instance's own (a `tag` rule against the instance's class rule), so the build disagrees with itself as well.
- **Nothing binds a nested or `$ref` value.** `pushStyleRules` passes `recordDroppedReactive` as the resolver, so every reactive value leaves the stylesheet. Only base `${…}` strings are written back anywhere; a template under `:hover` or a breakpoint, and any `{ $ref }`, is absent from built output.
- **Correction: the compiled targets write inline too, which the census marker omits.** `buildClientNode` (`compile-client.ts`) emits `style="color: red" :style.color="_s0"` and the hydration script writes `el.style[parts[1]] = …`. `compile-element.ts` writes the host through `this.style['color'] = …` and children through `emitStyleString` (`style="color: ${s.c}"`).
- **Correction: a repeater row has no rules.** `collectStyles` never walks a mapped array's `map`. `emitLitMapTemplate` (client: rows, `$switch` cases and mixed children) writes every base declaration inline, static ones included (`<li style="font-size: 1rem; color: ${item.c}">`), and drops nested blocks; `emitMappedArray` (element) writes only the reactive ones, so a row's static declarations and nested blocks are lost.
- **Correction: a reactive custom property is renamed and not set.** The client target kebab-cases it (`--rowFace` became `:style.--row-face` and `style="--row-face: red"`), and `el.style[name] = v` or `this.style['--k'] = …` sets no custom property at all.

The three corrections match the defects `plan:spec/report-dropped-reactive-styles` found while detailing and routed here in its second Open decision.

**The handle.** `plan:spec/style-handle-assignment` (an enabling plan both this plan and `plan:_shared/static-style-handle-and-descriptions` require) gives every styled element a handle that selects it alone. This plan needs that: a rule reading a variable only the declaring element sets would leave every other element sharing an author's class with an unset property, and the stub's scratch case (two page-level instances sharing `className: "icon"` both render the second `mask-image`) is a handle defect. The stub left open whether a definition rendered more than once needs a per-instance handle or the indirection; this plan decides the indirection (see Decisions), so the handle plan needs no rule sink for the prerender path.

**Found while detailing, not this plan's.** An island in `compileStaticPage` is emitted as a bare `<jx-island-N>`, which carries none of its root's `id`, `className` or handle, so the page rule for that root matches nothing. That is a lost element, not an inline declaration; the island's module otherwise follows the element target's rules below.

**Related.** §9.2 and §9.6; §9.3 (`plan:spec/report-dropped-reactive-styles`); `compiler.md` §4.3 (the binding table's style row, `plan:compiler/element-binding-table`) and §8.1 (component expansion); `plan:spec/shadow-dom-parity`, which also rewrites `buildComponentCSS` and `pushStyleRules`.

## Outcome

- `spec.md` §9.1 → Implemented. In prerendered HTML, a compiled page and a component module alike, no element carries a style declaration inline except custom properties: a reactive value at any depth, as a template or a `$ref`, is read by its rule through a variable the element sets, a repeater row's declarations are rules, and a custom property keeps its name.
- `spec.md` §9.3 (Implemented by its prerequisite) is narrowed to what still has no element to carry it. `compiler.md` §8.1 and the §4.3 style row describe the new output. Neither spec graduates.

## Decisions

- **Open:** precedence between an instance's own style and its definition's reactive host style. Recommendation: the instance wins, as §9.6 says and the interpreter does. After this plan the definition's value is read in the component sheet's `tag` (or `:host`) rule and the instance's own style is a rule on the instance's handle, so the instance wins by specificity with no extra work, matching how the definition's static declarations already behave. Keeping today's order (`compiler.md` §8.1: "the definition's over the instance's own") would need a per-instance rule that outranks the instance's own, which is the per-instance handle and sink this plan declines. Accepting it makes the `compiler.md` fragment `major`.
- **Open:** whether §9.1 closes only when the compiled targets conform. Recommendation: yes, one pull request for every writer, because the audit record's spec-wide decision gives each plan its section's gap in every tier, a hydrated page is where `:hover` over a live value matters, and a rule that reads a variable only the prerender sets would lose the value when a module re-renders. The alternative is a `defer` that marks the client and element targets `Future`.
- **Decided:** a reactive value is carried by the static form of §9.6's indirection, not a per-instance handle. The definition's one rule serves every instance and every row, and only the variable varies, which is the property §9.1 already relies on to make a repeater affordable. A per-instance handle would need a rule sink on every prerender path and cannot serve a row a module creates at runtime.
- **Decided:** the variable is `--jx-s` plus `hashCss(key + "\u0000" + source)` (`hashCss` from `@jxsuite/runtime`), where `key` is the element's handle selector, or the tag name for a definition's host in either shadow mode, and `source` is the template text or the `$ref` pointer. Four emitters must agree on the name (the component sheet from `buildComponentCSS`, the prerender, the element module's own stamping pass and the client module), and they run separately over separately parsed copies of a document. A name built from what each one sees needs no shared state, and with no counter in it, call order, `$media` and the scheme-query twin cannot shift it. `s` keeps it apart from the runtime's `--jx-r`, and the hash is a valid name for any literal id. One source used twice on an element reads one variable.
- **Decided:** a reactive custom property in a rule targeting the element itself is set under the author's own name and adds no declaration, and a descendant rule's keeps the indirection, mirroring `applyStyleInto` and §9.1. Every emitter carries the name as data (a JavaScript string or an attribute value), never as an attribute name, which the HTML parser lowercases.
- **Decided:** a value in a declaration-body at-rule (target `unscoped`) is dropped and recorded, since a document-global rule has no element to set a variable on (descriptors such as `src` take no `var()` either). Slot content keeps being dropped and recorded (`origin: "slot"`): `expandComponents` renders it once with an empty scope after `resolveDocTemplates` resolved what it could, and nothing hydrates it. Keyframe stops are unchanged.
- **Decided:** a page-level instance's host values are merged into `node.style` as literal declarations of those variables, spread before the instance's own keys, so they land in the page's rule on the instance's handle and an author-named custom property the instance also writes stays the instance's. A nested instance's are set inline, because the definition walk has no stylesheet to write to and §9.6 sanctions an inline variable.
- **Decided:** a static emitter resolves each value with `resolveStaticValue`, which reads a `$ref` as well as a template, and sets nothing for `null`. The declaration then reads an unset property, as it does in the runtime before a source has a value; no `var()` fallback is added, because the runtime writes none.
- **Decided:** the client target binds `:style="_sN"` to `() => ["<name>", value]`, and hydration calls `el.style.setProperty(n, v == null ? "" : String(v))`. The element target calls `this.style.setProperty` in the host effect and writes `name: ${expr}` in a template's `style` attribute. A `$ref` goes through each target's existing lowering (`refToBindingKey`, `refAccessor`, `mapRefToExpr`, `mapRefToClientExpr`).
- **Decided:** `collectStyles` walks a mapped array's `map` template once, so every row shares one handle and one rule set, and the row emitters write only variables inline. `emitLitMapTemplate` stops writing static declarations inline for rows, `$switch` cases and mixed children alike, since `collectStyles` emits rules for all three.
- **Decided:** the helpers live in `packages/compiler/src/shared.ts` beside `pushStyleRules`, because they call `resolveStaticValue` and `recordDroppedReactive`, which live there, and a separate module would import back into it.
- **Decided:** `plan:spec/report-dropped-reactive-styles` lands first. Its integration contract is written for a later plan that makes the resolver return a value and binds new shapes, and this plan's §9.3, remedy-text and test edits are edits to what it lands. Its `origin` option on `pushStyleRules` and `collectStyles` is reused here rather than a second flag.

## Implementation

The handle accessor `plan:spec/style-handle-assignment` provides is written `styleHandle(node)` below; use the name its integration contract gives. It returns the selector the style pass keyed a node's rules on, or `null` for a node the pass never styled.

1. **`packages/compiler/src/shared.ts`**
   - New block "Style variables (spec.md §9.1)" above `pushStyleRules`, tagged `@docs framework/concepts/styling`:
     - `export interface InlineStyleSource { name: string; value: string | JxRef }`.
     - `export function styleVariable(key: string, value: string | JxRef): string`, per the naming decision.
     - `function styleVariableResolver(key, sink: InlineStyleSource[], onDrop)` returning a `CssBuildOptions["resolveValue"]`: target `unscoped` → `onDrop(...)`, `null`; target `self` and a `--` property → push `{ name: property, value }`, `null`; otherwise push `{ name: styleVariable(key, value), value }` unless that name is already in the sink, and return `var(<name>)`.
     - `export function inlineStyleSources(style, key): InlineStyleSource[]`: runs `buildStyleRules(style, { scope: key, resolveValue: styleVariableResolver(key, sink, () => null) })`, discards the rules, returns the sink. Empty for no style or a `null` key.
     - `export function resolveInlineStyle(style, key, scope): [string, string][]`: each source through `resolveStaticValue(value, scope)`, skipping `null`/`undefined`, `String()` otherwise.
   - `pushStyleRules`: its options gain `key?: string` (default: the selector). The resolver: `origin: null` (the element module's stamping pass) returns the variable and records nothing; `origin: "slot"` and an `unscoped` target record and return `null`; every other value on an element returns the variable and is carried. This replaces the prerequisite's "carried" test (base, string, element). Rewrite the comment above the resolver.
   - `collectStyles`: pass `{ key: selector, origin }` to `pushStyleRules`. When `def` is a mapped array, walk `def.map` and return; when `def.children` is one, walk its `map`. The handle is assigned the way `plan:spec/style-handle-assignment` assigns any other.
   - `inlineStyleDeclarations(style, scope, key)`: `resolveInlineStyle(...)` as `name: value` joined by `; `, or `""` without a style, scope or key. `buildAttrs` passes `styleHandle(def)`; update both doc comments ("custom properties, never a declaration").
   - `resolveHostStyle(style, tagName, scope)`: `Object.fromEntries(resolveInlineStyle(style, tagName, scope))`. `renderComponentInstance` passes `tag` and joins the entries as `name: value`; rewrite its "Host style" doc bullet.
   - `buildComponentCSS`: every host call to `pushStyleRules` (the own block, an `@` block, a selector block) passes `{ key: tagName }`, so `:host(.wide)`'s values share the host's names. If `plan:spec/shadow-dom-parity` has already folded these into one call, pass it there.
   - `droppedReactiveStyleMessage` (from the prerequisite): the `element` remedy becomes "A declaration-body at-rule (`@font-face`, `@property`, `@counter-style`, `@position-try`) belongs to the whole document, so it has no element to carry a value that changes. Give it a static value."
2. **`packages/compiler/src/site/site-build.ts`**, `expandComponents`: `const hostVars = resolveHostStyle(def.style, node.tagName, buildInstanceScope(def, props))`; when non-empty, `node.style = { ...hostVars, ...node.style }`. Rewrite the comment above it.
3. **`packages/compiler/src/targets/compile-client.ts`**
   - `buildClientNode`, "Dynamic style properties": iterate `inlineStyleSources(def.style, styleHandle(def))`. Each source gets a key `_sN` whose binding returns a pair, the name as a JSON string and the value: the template as a template literal, or `state.<refToBindingKey(ref)>` for a `$ref`. Push `:style="_sN"`.
   - `emitClientModule`: the style branch tests `parts[0] === 'style'` and runs `effect(() => { const [n, v] = bind[key](); el.style.setProperty(n, v == null ? '' : String(v)); })`.
   - `emitLitMapTemplate`: replace "Style → inline CSS" with the sources of `styleHandle(def)`, a template as `name: <mapRefsToLit(value)>` and a `$ref` as `name: ${<mapRefToClientExpr(ref)>}`, written only when there is one. The class attribute carries the handle as every other emitter does.
4. **`packages/compiler/src/targets/compile-element.ts`**
   - Host effect in `emitElementModule`: iterate `inlineStyleSources(doc.style, doc.tagName)`, emitting one `this.style.setProperty(<name>, <value>)` per source. A template's value is the template literal with the existing `state.` to `this.state.` rewrite; a `$ref`'s is `String(<refAccessor("this.state", …)> ?? '')`.
   - `emitStyleString(styleDef, key, inMap)`: sources of `key`, a template as `name: <toLitExpr(value)>`, a `$ref` as `name: ${<refToExpr or mapRefToExpr>}`. `emitLitNode` passes `styleHandle(def)`; `emitMappedArray` passes `styleHandle(mapDef)` and `inMap`.

No change to `packages/runtime` or `packages/site`.

**Integration contract.** Once this lands, `styleVariable`, `inlineStyleSources`, `resolveInlineStyle` and `resolveHostStyle(style, tagName, scope)` are exported from `packages/compiler/src/shared.ts`, and they are the only way an emitter learns what to set on an element. No emitter writes a style declaration inline except a custom property. A host's variables are keyed on its tag name in both shadow modes, so `plan:spec/shadow-dom-parity`'s move of the `:host` translation into `css.ts` keeps every name. `pushStyleRules` records only an `unscoped` value and slot content, and its options take `key`. A comment `plan:_shared/static-style-handle-and-descriptions` writes rides on the same rules. `spec.md` §9.1 states the build's indirection.
