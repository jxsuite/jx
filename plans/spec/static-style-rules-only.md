# Built output writes every style declaration as a rule and carries each reactive value through a custom property the element sets, so a nested block can always override it

## Context

`specs/spec.md` §9.1, line 875:

> **Status: Partial.** The runtime conforms (§9.6). The static compiler does not: a `${…}` base declaration it can resolve against a build-time scope, and a component definition's resolved host style, are written into an inline `style` attribute (`inlineStyleDeclarations` and the `hostStyle` argument of `buildAttrs` in `packages/compiler/src/shared.ts`), so in prerendered HTML a `:hover` or `@media` block cannot override those declarations.

§9.1 says every declaration becomes a rule, a `${…}` template and a `{ $ref }` mean the same thing, and a reactive custom property on the element itself is written inline under the author's own name. §9.6 gives the runtime's mechanism: the rule says `property: var(--jx-r<n>-<m>)` and the element sets the variable inline (`applyStyleInto` in `packages/runtime/src/runtime.ts`).

**What the build does today** (read against the code and a scratch `compileClient`/`emitElementModule` run, 2026-09-27)

- **Prerender.** `buildAttrs` writes `inlineStyleDeclarations(def.style, scope)`, the base `${…}` entries resolved against the scope, as `style="color: red"`. `renderStaticNode` reaches it for every element of a component definition with the instance's scope, so a definition's children carry their resolved templates inline per instance. `renderComponentInstance` appends a nested instance's host style (`resolveHostStyle`) to the same attribute. On a site page `resolveDocTemplates` (`packages/compiler/src/site/site-build.ts`) has already turned a page element's resolvable base templates into literals, so the page case is the direct `compile()` route (`compileStaticPage`, and `compileClient`'s static attributes) and templates the build leaves for the client.
- **Page-level instance.** `expandComponents` merges `resolveHostStyle(...)` into `node.style` as `{ ...node.style, ...resolvedStyle }`. That is a rule, but it gives the definition's resolved host value precedence over the instance's own, the reverse of §9.6, and `compiler.md` §8.1 documents that order. A definition's static host declarations already lose to the instance's own (a `tag` rule against the instance's class rule), so the build disagrees with itself as well.
- **Nothing binds a nested or `$ref` value.** `pushStyleRules` passes `recordDroppedReactive` as the resolver, so every reactive value leaves the stylesheet. Only base `${…}` strings are written back anywhere; a template under `:hover` or a breakpoint, and any `{ $ref }`, is absent from built output.
- **A statically expanded repeater loses the same values for good.** `expandMappedArrayStatic` clones each row through `expandMapTemplate` (`site-build.ts`), whose `style` branch resolves only top-level `${…}` strings against the row's `$map` scope. A nested-block template and every `$ref` survive as source, and the row's scope is gone by the time the page renders, so no emitter can resolve them later.
- **Correction: the compiled targets write inline too, which the census marker omits.** `buildClientNode` (`compile-client.ts`) emits `style="color: red" :style.color="_s0"` and the hydration script writes `el.style[parts[1]] = …`. `compile-element.ts` writes the host through `this.style['color'] = …` and children through `emitStyleString` (`style="color: ${s.c}"`).
- **Correction: a repeater row has no rules.** `collectStyles` never walks a mapped array's `map`, so a row's static declarations and nested blocks reach no sheet; `emitLitMapTemplate` (client: rows, `$switch` cases and mixed children) writes every base declaration inline, and `emitMappedArray` (element) writes only the reactive ones. `plan:spec/style-handle-assignment` fixes the static half (its `walkStyleScopes` visits the `map` template and it deletes `emitLitMapTemplate`'s literal branch); the templated declarations it leaves inline are this plan's.
- **Correction: a reactive custom property is renamed and not set.** The client target kebab-cases it (`--rowFace` became `:style.--row-face` and `style="--row-face: red"`), and `el.style[name] = v` or `this.style['--k'] = …` sets no custom property at all.
- **`buildComponentCSS` reports the wrong target for a descendant block.** It hands each top-level selector block of a definition's style to `pushStyleRules` as its own scope (`resolveSelector`), so `buildStyleRules` sees `x-card .inner` as `self`, where a whole-object walk (the runtime's, and any emitter's) sees `"& .inner"` as `descendant`.

The three corrections match the defects `plan:spec/report-dropped-reactive-styles` found while detailing and routed here.

**The handle.** `plan:spec/style-handle-assignment` (an enabling plan both this plan and `plan:_shared/static-style-handle-and-descriptions` require) gives every styled element, a repeater's item template included, a class that selects it alone, read back with `styleHandleOf(node)` (the class without its dot, or `undefined`). This plan needs that: a rule reading a variable only the declaring element sets would leave every other element sharing an author's class with an unset property, and the stub's scratch case (two page-level instances sharing `className: "icon"` both render the second `mask-image`) is a handle defect. That plan declines a per-render handle because this plan carries per-instance values through the indirection (see Decisions).

**Found while detailing, not this plan's.** An island in `compileStaticPage` is emitted as a bare `<jx-island-N>`, which carries none of its root's `id`, `className` or handle, so the page rule for that root matches nothing. That is a lost element, not an inline declaration; the island's module otherwise follows the element target's rules below.

**Related.** §9.2 and §9.6; §9.3 (`plan:spec/report-dropped-reactive-styles`); `compiler.md` §4.3 (the binding table's style row, `plan:compiler/element-binding-table`) and §8.1 (component expansion); `plan:spec/shadow-dom-parity`, which also rewrites `buildComponentCSS` and `pushStyleRules`.

## Outcome

- `spec.md` §9.1 → Implemented. In prerendered HTML, a compiled page and a component module alike, no element carries a style declaration inline except custom properties: a reactive value at any depth, as a template or a `$ref`, is read by its rule through a variable the element sets (or, in a statically expanded row, resolved into the row's own rule), a repeater row's declarations are rules, and a custom property keeps its name.
- `spec.md` §9.3 (Implemented by its prerequisite) is narrowed to what still has no element to carry it. `compiler.md` §8.1 and the §4.3 style row describe the new output. Neither spec graduates.

## Decisions

- **Open:** precedence between an instance's own style and its definition's reactive host style. Recommendation: the instance wins, as §9.6 says and the interpreter does. After this plan the definition's value is read in the component sheet's `tag` (or `:host`) rule and the instance's own style is a rule on the instance's handle, so the instance wins by specificity with no extra work, matching how the definition's static declarations already behave. Keeping today's order (`compiler.md` §8.1: "the definition's over the instance's own") would need a per-instance rule that outranks the instance's own, which is the per-instance handle and sink this plan declines. Accepting it makes the `compiler.md` fragment `major`.
- **Decided:** §9.1 closes only when the compiled client and element targets conform too, in one pull request for every writer. The audit record's first spec-wide decision gives each plan its section's gap in every tier, a hydrated page is where `:hover` over a live value matters, and a rule that reads a variable only the prerender sets would lose the value when a module re-renders.
- **Decided:** a reactive value is carried by the static form of §9.6's indirection, not a per-instance handle. The definition's one rule serves every instance and every row, and only the variable varies, which is the property §9.1 already relies on to make a repeater affordable. A per-instance handle would need a rule sink on every prerender path and cannot serve a row a module creates at runtime.
- **Decided:** the variable is `--jx-s` plus `hashCss(key + "\u0000" + source)` (`hashCss` from `@jxsuite/runtime`), where `key` is the element's handle class (`styleHandleOf`), or the tag name for a definition's host in either shadow mode, and `source` is the template text or the `$ref` pointer. Four emitters must agree on the name (the component sheet from `buildComponentCSS`, the prerender, the element module's templates and the client module), and they run separately over separately parsed copies of a document. A name built from what each one sees needs no shared state, and with no counter in it, call order, `$media` and the scheme-query twin cannot shift it. `s` keeps it apart from the runtime's `--jx-r`, and the hash is a valid name for any handle. One source used twice on an element reads one variable.
- **Decided:** a reactive custom property in a rule targeting the element itself is set under the author's own name and adds no declaration, and a descendant rule's keeps the indirection, mirroring `applyStyleInto` and §9.1. The sheet and the emitters must classify a value alike, so `buildComponentCSS`, while it still splits a definition's top-level selector blocks, tells the resolver a descendant block's real target. Every emitter carries the name as data (a JavaScript string or an attribute value), never as an attribute name, which the HTML parser lowercases.
- **Decided:** a value in a declaration-body at-rule (target `unscoped`) is dropped and recorded, since a document-global rule has no element to set a variable on (descriptors such as `src` take no `var()` either). Slot content keeps being dropped and recorded (`origin: "slot"`): `expandComponents` renders it once with an empty scope after `resolveDocTemplates` resolved what it could, and nothing hydrates it. Keyframe stops are unchanged.
- **Decided:** a page-level instance's host values are merged into `node.style` as literal declarations of those variables, spread before the instance's own keys, so they land in the page's rule on the instance's handle and an author-named custom property the instance also writes stays the instance's. A nested instance's are set inline, because the definition walk has no stylesheet to write to and §9.6 sanctions an inline variable.
- **Decided:** a statically expanded row resolves its reactive style values when it is cloned, at every depth and as a template or a `$ref`, into literals in its own style. The row's `$map` scope exists only inside `expandMappedArrayStatic`, and each expanded row is already its own page node with its own handle and rule, as its resolved top-level values are today.
- **Decided:** a static emitter resolves each value with `resolveStaticValue`, which reads a `$ref` as well as a template, and sets nothing for `null`. The declaration then reads an unset property, as it does in the runtime before a source has a value; no `var()` fallback is added, because the runtime writes none. Because instances share a name, an instance that sets nothing inherits what an enclosing instance of the same definition set, which only a recursive definition can produce; accepted.
- **Decided:** the client target gives an element ONE `:style="_sN"` binding, returning every `[name, value]` pair the element sets, and hydration runs `for (const [n, v] of bind[key]()) el.style.setProperty(n, v == null ? "" : String(v))` in one effect. One attribute per element, because two `:style` attributes on one tag are a duplicate the HTML parser discards. The element target calls `this.style.setProperty` in the host effect and writes `name: ${expr}` in a template's `style` attribute. A `$ref` goes through each target's existing lowering (`mapRefToClientExpr` or the `refAccessor("state", …)` read `addRefBinding` builds, `refToExpr`/`mapRefToExpr`, `refAccessor("this.state", …)`), never `state.<refToBindingKey(ref)>`, which flattens `/` into `_`.
- **Decided:** the helpers live in `packages/compiler/src/shared.ts` beside `pushStyleRules`, because they call `resolveStaticValue` and `recordDroppedReactive`, which live there, and a separate module would import back into it.
- **Decided:** `plan:spec/report-dropped-reactive-styles` lands first. Its integration contract is written for a later plan that makes the resolver return a value and binds new shapes, and this plan's §9.3, remedy-text and test edits are edits to what it lands. Its `origin` option on `pushStyleRules` and `collectStyles` is reused here rather than a second flag; its `null` origin loses its only caller when `plan:spec/style-handle-assignment` replaces the element module's stamping pass with `assignStyleHandles`, so this plan deletes that value.

## Implementation

`styleHandleOf(node)` and `styleChildren(def)` are `plan:spec/style-handle-assignment`'s exports. An element's `key` below is `styleHandleOf(node)`; a host's is its tag name.

1. **`packages/runtime/src/css.ts`**: export `compoundsOntoScope` (module-private today) and add it to `runtime.ts`'s re-export list beside `isNestedSelectorKey`, so the compiler asks the builder's own question.
2. **`packages/compiler/src/shared.ts`**
   - New block "Style variables (spec.md §9.1)" above `pushStyleRules`, tagged `@docs framework/concepts/styling`:
     - `export interface InlineStyleSource { name: string; value: string | JxRef }`.
     - `export function styleVariable(key: string, value: string | JxRef): string`, per the naming decision.
     - `function styleVariableResolver(key, sink: InlineStyleSource[], onDrop, descendant = false)` returning a `CssBuildOptions["resolveValue"]`: target `unscoped` → `onDrop(...)`, `null`; target `self`, `descendant` false and a `--` property → push `{ name: property, value }`, `null`; otherwise push `{ name: styleVariable(key, value), value }` unless that name is already in the sink, and return `var(<name>)`.
     - `export function inlineStyleSources(style, key): InlineStyleSource[]`: runs `buildStyleRules(style, { scope: key, resolveValue: styleVariableResolver(key, sink, () => null) })` over the whole object, discards the rules, returns the sink. Empty for no style or no key.
     - `export function resolveInlineStyle(style, key, scope): [string, string][]`: each source through `resolveStaticValue(value, scope)`, skipping `null`/`undefined`, `String()` otherwise.
   - `pushStyleRules`: its options gain `key?: string` (default: the selector) and `descendant?: boolean`. For `origin: "element"` its resolver is `styleVariableResolver(key, [], onDrop, descendant)` with an `onDrop` that builds the prerequisite's entry (origin, property, source, selector, path) and calls `recordDroppedReactive`, so only an `unscoped` value is recorded and every other value returns its variable (or `null` for a custom property set under its own name); `origin: "slot"` records every value and returns `null`. That replaces the prerequisite's "carried" test (base, string, element). Delete the `null` origin. Rewrite the comment above the resolver.
   - `collectStyles`: the visitor passes `{ key: styleHandleOf(node), origin }` to `pushStyleRules`.
   - `inlineStyleDeclarations(style, scope, key)`: `resolveInlineStyle(...)` as `name: value` joined by `; `, or `""` without a style, scope or key. `buildAttrs` passes `styleHandleOf(def)`; update both doc comments ("custom properties, never a declaration").
   - `resolveHostStyle(style, tagName, scope)`: `Object.fromEntries(resolveInlineStyle(style, tagName, scope))`. `renderComponentInstance` passes `tag` and joins the entries as `name: value`; rewrite its "Host style" doc bullet.
   - `buildComponentCSS`: every host call to `pushStyleRules` passes `key: tagName`, so `:host(.wide)`'s values share the host's names; the selector-block call also passes `descendant: !compoundsOntoScope(prop)`. If `plan:spec/shadow-dom-parity` has already folded the three calls into one, pass `key` there and add no `descendant`: the builder then sees the authored keys and reports the right target itself.
   - `droppedReactiveStyleMessage` (from the prerequisite): the `element` remedy becomes "A declaration-body at-rule (`@font-face`, `@property`, `@counter-style`, `@position-try`) belongs to the whole document, so it has no element to carry a value that changes. Give it a static value."
3. **`packages/compiler/src/site/site-build.ts`**
   - `expandComponents`: `const hostVars = resolveHostStyle(def.style, node.tagName, buildInstanceScope(def, props))`; when non-empty, `node.style = { ...hostVars, ...node.style }`. Rewrite the comment above it.
   - `expandMapTemplate`'s `style` branch: copy the object recursively and resolve every value against the row's scope, a `${…}` through `evaluateMapTemplate` and a `{ $ref }` through `resolveRefValue`, descending into nested selector and conditional blocks but not into a declaration-body at-rule or `@keyframes` (`isDeclarationAtRule`, `isKeyframesAtRule`). A value that does not resolve keeps its source, as today.
4. **`packages/compiler/src/targets/compile-client.ts`**
   - `buildClientNode`, "Dynamic style properties": when `inlineStyleSources(def.style, styleHandleOf(def))` is non-empty, register one key `_sN` whose binding returns an array of `[name, value]` pairs, the name as a JSON string and the value as the template literal, or `refAccessor("state", …)` for a `$ref`. Push one `:style="_sN"`.
   - `emitClientModule`: the style branch tests `parts[0] === 'style'` and runs `effect(() => { for (const [n, v] of bind[key]()) el.style.setProperty(n, v == null ? '' : String(v)); })`.
   - `emitLitMapTemplate`: replace the template branch the prerequisite keeps with the sources of `styleHandleOf(def)`, a template as `name: <mapRefsToLit(value)>` and a `$ref` as `name: ${<mapRefToClientExpr(ref)>}`, and write `style` only when there is one.
5. **`packages/compiler/src/targets/compile-element.ts`**
   - Host effect in `emitElementModule`: iterate `inlineStyleSources(doc.style, doc.tagName)`, emitting one `this.style.setProperty(<name>, <value>)` per source. A template's value is the template literal with the existing `state.` to `this.state.` rewrite; a `$ref`'s is `String(<refAccessor("this.state", …)> ?? '')`.
   - `emitStyleString(styleDef, key, inMap)`: sources of `key`, a template as `name: <toLitExpr(value)>`, a `$ref` as `name: ${<refToExpr or mapRefToExpr>}`. `emitLitNode` passes `styleHandleOf(def)`; `emitMappedArray` passes `styleHandleOf(mapDef)` and `inMap`.

No change to `packages/site`.

**Integration contract.** Once this lands, `styleVariable`, `inlineStyleSources`, `resolveInlineStyle` and `resolveHostStyle(style, tagName, scope)` are exported from `packages/compiler/src/shared.ts`, and they are the only way an emitter learns what to set on an element. No emitter writes a style declaration inline except a custom property. A host's variables are keyed on its tag name in both shadow modes, so `plan:spec/shadow-dom-parity`'s move of the `:host` translation into `css.ts` keeps every name, and its fold of `buildComponentCSS`'s calls deletes `descendant`. `pushStyleRules` records only an `unscoped` value and slot content, and its options take `key`. `compoundsOntoScope` is exported from `@jxsuite/runtime`. A comment `plan:_shared/static-style-handle-and-descriptions` writes rides on the same rules. `spec.md` §9.1 states the build's indirection.
