# Type errors in document code show up in the terminal, Studio and VS Code, and `.jxn` becomes the recommended format

## Context

`specs/spec.md` §23.3 is Partial: Studio's function editor checks a body (`studio.md` §16.7, landed with JTC.1), and `tsc` and a language server check a `.jxn` document's bodies and scripts through `@jxsuite/content-mapper` (landed with JTC.2). JTC.3's first part typed events, `$map` rows and nested scopes in both readers, its second has the mapper read every `${}` template and every `$ref` into `state` or a row, its third holds each prop a document gives a `.jxn` component against that component's `State`, and its fourth reads a typed entry's schema and the document's `$defs` in both readers. What is missing is the rest of what the mapper reads (`$type`, class methods), an editor extension, and a scaffold set up for any of it. TypeScript is the default language (`spec.md` §23.1), so this plan is what makes that default worth having.

**TypeScript 7.1 content mappers** (`7.1.0-beta` on npm on 2026-11-05, `latest` is 7.0.2, and the repository pins `7.1.0-beta` exactly since JTC.2). A mapper is a process speaking JSON-RPC over stdio (`initialize`, `openProject`, `transform`, `closeProject`), declared under `contentMappers` in a tsconfig. `tsc` refuses it without `--runExternalCode`, and VS Code requires workspace trust. Rename, completion and formatting edits write back only through `Verbatim` spans. Design source: microsoft/typescript-go#4712.

**Not tested:** VS Code, `node` on the desktop app's PATH (it appears not to be there), and Monaco's worker on generated text. Tested since, under the real language server: a running session reads a page again when told (`workspace/didChangeWatchedFiles`) that its project file changed, beside the `tsconfig` or in a folder under it, and reads nothing again when it is not told, so the editor's report is what it relies on.

**The gaps this leaves for users.** No scaffold has a `tsconfig` or `typescript` dependency (`packages/create/generate.ts`), and no starter manifest has a `typecheck` script. Desktop is the only end-user path to Studio, and it has no `tsc`. `.json` gets completion from `$schema` with no tooling, in Studio (`services/monaco-setup.ts:155`) and in VS Code, and `.jxn` would have none.

## Outcome

- spec.md §23.3 → Implemented.
- Studio marks type errors in bodies without `tsc` or Node (landed). Scripts join them: a document carries `$script` now (`spec.md` §23.2), and Studio edits one on the same surface with syntax errors only.
- `tsc --runExternalCode` reports them at real positions, and scaffolded projects are set up for it.
- VS Code gives squiggles, hover, rename, and schema-driven completion.
- `.jxn` is what starters, scaffolds and docs teach. `.json` remains fully supported.

## Decisions

- **Decided (owner):** Studio type errors are part of v1, or TypeScript by default goes unchecked in the only end-user path to the visual editor.
- **Decided (owner):** a `(fn)` body cannot reach a script's private scope, and the checker enforces it, by giving bodies their own virtual file that sees only `State` and globals.
- **Decided (owner):** a `${}` template stays JavaScript, and the checker reports TypeScript syntax inside one, since it would render `""`.
- **Decided (JTC.3):** a template is a supplemental `.js` unit opening `// @ts-check`, which is what makes the compiler report TypeScript syntax in one (TS8016) with no rule of ours. Its quotes stand for the backticks, so an unclosed `${` is reported on the string. One syntax error anywhere silences every semantic error of the run, as it does in any `tsc` run.
- **Decided (JTC.3):** a `$ref` is a line of one `.ts` unit per document, its path read off the scope's `State` with `?.` after the first name, because a token that matches nothing reads as `undefined` at run time (`spec.md` §7.1). A one-name state ref on an element's `on*` member is checked as that binding's handler, since the runtime binds nothing where it is not a function. A longer path there is a plain read. Not read: `parent#/`, `window#/`, `document#/`, `event#/`, files and `$defs`.
- **Decided (JTC.3):** the reader keeps a token for every value, and a tagged argument's token is the string alone. The parser's location for `(ref)"#/state/a"` starts at the tag, so the token is measured back from its end by the length of what was written.
- **Decided (JTC.3):** a component's props are checked against its `State`, with no second declaration. Every main module ends with an `$elements` interface naming what the document defines (its root tag, where that is a custom element name, against its `State`), and the references unit joins the document's own, each relative `.jxn` file its `$elements` list names, and the project component a tag resolves to. Each prop is then one call of its own, `props<"tag">({ key: value })`, so one mistake does not hide the next and the compiler's error lands on the prop's name. A prop is optional and may be `null` or `undefined`. A tag nothing declares takes anything, as an open `State` does. A file `$elements` names that is not there is TS2307 at its entry, and the document's props go unchecked until it is fixed.
- **Decided (JTC.3):** the mapper lists the project's `components/` folder on each transform and passes tag and relative specifier. Nothing watches the folder, so a component added while an editor runs is seen when a document is next mapped. A `.json` component, a package's and a non-relative `$elements` entry are not read.
- **Known (JTC.3):** a one-line `$elements` holding a single value parses as that value, not a list of one, so the reader takes a list only. A private `#` entry given as a prop is not refused. A template, a compound value and `null` are passed unchecked.
- **Decided (JTC.3):** `$defs` is a namespace in the main module and not an interface, so a message and a hover say `$defs.TodoItem` as the author named it, a `.ts` module can import it, and a definition's name is an identifier a rename reaches. A type is written as parts, each either text or a name the author wrote with its pointer, which is what lets one reader map names to tokens and the other join them.
- **Decided (JTC.3):** a schema is read conservatively. No `type` is `any` (so `properties` alone makes no object, and a naked object that happens to hold `items` is not misread), an absent `additionalProperties` adds no index signature (a misspelled property is the error worth having, against JSON Schema's open default), and a vague type (`any`, `any[]`, a bare map) gives way to a non-null `default`. `$ref` is read only as `#/$defs/<identifier>` in a document that has `$defs`.
- **Known (JTC.3):** `required` is a list of strings joined to nothing, so renaming a property leaves it, and in Jx Notation `required id` alone is a string and requires nothing (`(array)required id`). A `default` of `null` beside a declared type does not make the entry nullable, as before. A `$defs` of another file, and a definition whose name is no identifier, are `any`.
- **Decided (JTC.3):** a parameter's `type` is checked inside its body and nowhere else. `{ text }` is TypeScript written in brackets and joined to its token as one verbatim span, so an error and a rename inside the text land in the file, and any other `type` is a schema read by `declaredParts`, as a typed entry's is. A body's module imports `$defs` only where a parameter's type names a definition and the document has some, so a body with no typed parameter still sees `State` and nothing else. A declared type on the first parameter after `state` replaces the event's, since the author said what they wanted there.
- **Decided (JTC.3):** class methods are a limit and not a part of this item. A class is a `.class.json` file and has no Jx Notation form, and the mapper claims `.jxn`, so there is nothing for it to read until classes are written in the notation, which is its own design. The docs' limits say a class's methods are not checked, and JTC.5 moves the clause out of the `spec.md` §23.3 marker's "not yet" and into the section's stated limits when it deletes the marker, beside `$defs` of another file and a component that is not `.jxn`.
- **Known (JTC.3):** a call is not held against a function's parameters. The entry stays `(...args: any[]) => any` in `State`, because the runtime binds `state` first and an event binding passes the event whatever is declared, and a signature built from `parameters` would report calls that work. The entry's own `type` (its return, `spec.md` §5.3) is not read for the same reason. `text` is closed on a line of its own, because one that ended in a `//` comment took the rest of the signature with it and the compiler printed syntax errors in code the author never wrote. And `paramNames` in `guards.ts` throws on a `null` in `parameters`, which the schema refuses but the reader meets before validation does.
- **Known (JTC.3):** a state entry that is itself a template is `any` in `State`, and one written `held { $ref … }` is `{ $ref: string }`. Both are what `state-types.ts` says today and neither reports a false error.
- **Decided (owner):** the stated goal is readability and making hand-written and agent-written code practical, and removing sidecars is a result of that. JTC.5 says so where the old premise is written down.
- **Decided:** one generator, two consumers. `generateVirtualTypes(source)` is pure and returns virtual text plus a span map, with no Node dependency. The mapper and Monaco both call it, so the two surfaces cannot disagree about a document's types.
- **Decided:** Studio diagnostics do not wait for TypeScript 7.1. Monaco's TypeScript worker carries its own compiler, so JTC.1 can ship on its own. It also reaches the cloud host with no change there, since `ts.worker.js` is already staged with its Studio tree. That host runs no `tsc`, so Studio is its only checker until a project's own CI runs one. JTC.2 onward was to wait for 7.1 stable, since the mapper protocol is still being tested with partner tools.
- **Decided (owner, revised 2026-11-11):** JTC.2 adopts `typescript@7.1.0-beta` rather than waiting for stable. The mapping pieces need it and the owner does not expect the protocol to change. The version is pinned exactly while it is a prerelease, and it moves to the stable release when there is one.
- **Decided:** virtual layout. The main file holds `$script.client` line by line as `Verbatim` spans, because dedent breaks a single span, and an exported `State` interface. A `supplemental` file holds each body, with `import type { State }`. Another holds `$script.server`, so its imports stay apart. KDL names in `(export)` and `(server)` are `Verbatim` too, so rename reaches them.
- **Decided:** what `State` says. `(export)` entries are `typeof import` of the script's export. Server entries are `Awaited<ReturnType<…>> | null`. An empty array is `any[]`, not `never[]`. Anything the document cannot determine (`Request`, `ContentEntry`, `$expression`, inherited layout state) is `any`, not an error. A false error in code the author can't fix would teach people to ignore the checker.
- **Decided (JTC.1):** the options are `strict` without `noImplicitAny`, because a body is as often JavaScript as TypeScript and an untyped callback parameter is not a mistake in one. `event` is `any` where an entry does not name it, `this` is `any`, and an empty object is `Record<string, any>`. Measured over the repository's own bodies with the real `tsc` (`virtual-types-corpus.test.ts`): 42 bodies, five errors in two site components, all genuine TypeScript objections to JavaScript idioms (`document.__jxSearchHotkeys`, `ev.target.tagName`, `e.detail`), none a gap in what `State` says.
- **Decided:** event types come from the `on*` binding, including `event.target` typed from the element carrying the handler where that is unambiguous.
- **Decided (JTC.3):** unambiguous means the event can only have started on the handler's element: it holds no element and no `innerHTML`, or the event does not bubble, or it is a `select` reporting `change` or `input`. The last was added because the corpus check flagged `event.target.value` in a `select`'s `onchange` (`examples/components/fetch-demo.json`), which is correct code. Everywhere else `target` is the platform's `EventTarget | null`. Every lookup answers `any` when it finds nothing, so a project without the DOM `lib`, a custom element and an event the platform does not name report nothing.
- **Decided (JTC.3):** a state function bound only by `on*` `$ref`s is given the union of its bindings' events. One whose name appears as a whole word in any other string of the document is given `any`. Accepted cost: a function another document calls is still typed with the event, and `$type` (below) is the author's way out once it lands.
- **Decided (JTC.3):** each nested scope is an interface of the main module named `State$n`, numbered in document order, and a body imports its own as `State`. The numbers show in a hover and move when a scope is added above; a stable name would need one from the author, and nothing imports an inner scope. A scope that redeclares a parent's key extends the one around it less that key (`$except<State, "key">`, a mapped type over `keyof State`), since an `extends` would refuse the changed type. It was first written closed, listing what it kept by reference (`count: State["count"]`), and each listed member was then a second name to the language server: a rename from the root missed every body in such a scope. `Omit` was tried and loses the declared members of a `State` with an open index signature; the mapped type keeps them and the index both.
- **Decided (JTC.3):** `document-scopes.ts` holds where a body stands (scope chain, map row, event) for both readers, as `state-types.ts` holds what an entry is.
- **Decided:** the mapper config is never in the root `tsconfig.json`. tsgolint fails on the unknown option, and `lint:typecheck` would go red. It goes in a separate `tsconfig.jxn.json`, here and in scaffolds, and the root `include` is unchanged. Inline code stays outside the lint gates until tsgolint supports mappers, and docs say so.
- **Decided:** a mapper claims every `.jxn`, so the generator answers a project file with empty virtual text, using `classifyJxn` from `spec.md` §22. Reading one as a document would report grammar errors on every project in `tsc`. Studio does not need this, since a project file has no Code-view type check.
- **Decided:** Studio's limits are stated, not hidden. It checks one document's bodies and client script against its own state. An import it cannot resolve in the worker is `any` and suppresses TS2307. Whole-project checking is `tsc`'s job. This is a real limit, and §16.7 says so.
- **Decided:** two new workspaces, created by their slices: `packages/content-mapper` (`@jxsuite/content-mapper`, run with `node`, `dynamicConfig: true` so it watches the project file) and `packages/vscode`. Each needs a `bunfig.toml`. The mapper needs a release-config entry (`scripts/release-config.test.ts:67`), a npm trusted publisher and template version pins. VS Code needs a marketplace lane. The publisher and marketplace accounts are owner actions.
- **Decided (revised 2026-11-09):** the documents flipped ahead of this plan, at the owner's call. Starters, the `create-jxsuite` layouts, Studio's Add new, New File and Convert to Component write `.jxn` now, because every published host a starter pins reads it. What still flips last is the premise and the teaching (the AI prompts, `AGENTS.md`, the spec subtitle, `README.md`, marketing), and the `tsconfig.jxn.json`, mapper and `typecheck` scaffolding, which need this plan's tooling. Until then a `.jxn` document has no schema completion in VS Code, which is the cost this accepted.
- **Decided (JTC.4):** one formatter for a body, in the server, asked by Studio's Format and by `jx format`, so neither undoes the other. It indents with two spaces (Studio's endpoint wrote tabs, which Monaco then showed against its own two spaces) and breaks at 100 columns counted from where the body starts. A body is formatted inside a function at two depths, and a line is unindented only where the deeper reading moved it one level: taking a leading tab off every line, as the endpoint did, took one off a template literal's own text. Where the two readings cannot be told apart line by line the body is left as written, with no error.
- **Decided (JTC.4):** `jx format` writes a comment-free file in its canonical form and merges a commented one with what was on disk (`spec.md` §22.4), which is what Studio's save does. It reads `.jxn` only. Code that does not parse is named with its pointer and line and left, the rest of the file is formatted, and the run exits 1.
- **Known (JTC.4):** no `.oxfmtrc.json` is read, so a project's own quote or width preference does not reach a body; a body is in a document and belongs to no file a configuration is scoped to, and whether to read the project's is the owner's to want. Double quotes are oxfmt's default and cost a one-line body a raw string (`#"return "hi";"#`). Studio does not format a document's script, though `formatScript` now could. A `.json` document is not formatted. The starters and examples were not reformatted here; that is a diff for JTC.5, which touches them anyway.
- **Open:** whether a document's function body may `await`. The interpreter compiles one with `new Function` (`compileBody` in `packages/runtime/src/body-eraser.ts`) and the compiler emits it as a plain arrow, so `await` in one is a `SyntaxError` when the page runs. The checker says otherwise: both readers wrap a body in an `async function`, so `tsc` and Studio pass it, and `docs/framework/concepts/statements.md` recommends a string body for `await` chains. A class method that awaits is emitted `async` and works. The formatter formats an awaiting body (a class method's goes through the same editor) and Studio's lint still reports it. Recommendation: make the runtime and the compiler agree with the checker (an `async` function where the body awaits, as `isMethodAsync` does for a class), since the docs already promise it and a computed that awaits has no meaning either way; until then the checker passes code that does not run.
- **Open:** should the grammar and schema completion of JTC.4 leave this plan? Neither needs a mapper, and `project.jxn` loses `project.json`'s no-tooling completion in VS Code (`site-architecture.md` §2.3). Document scripts have landed and 7.1 is adopted as a beta, so that half no longer waits for anything but the marketplace account. Recommendation: split it into its own plan requiring only `spec.md` §22, leaving `registerContentMappers` here, once someone is ready to take on the marketplace account.
- **Open:** how an author types what the checker cannot derive. Recommendation: a `$type` key on a state entry holding a TypeScript type, such as `"Task[]"`, resolved against the client script and globals, and ignored by every tier but the checker. The 47 measured errors include real cases that need this. Parameters no longer wait on it: a parameter object's CEM `type` is read (JTC.3), which the schema already had, so the `name: Type` string in a `(fn)` node this item once proposed would only be a shorter spelling of it, and is the owner's to want or not.
- **Open:** whether `tsc` checks bodies in `.json` documents. A mapper claims files by extension, and claiming `.json` would capture every data file and has not been tried. Recommendation: not in this plan. Studio checks both formats through the generator, and `jx convert` moves a file into `tsc`'s reach. A `jx typecheck` that writes the generator's output to temporary `.ts` files could cover `.json` later, with no design change.
- **Decided (JTC.2, by test):** `--runExternalCode` trusts every mapper a `tsconfig` declares, not the named one. `spec.md` §23.3 and `docs/framework/concepts/type-checking.md` say so, and it is the second reason the mapper has a `tsconfig.jxn.json` of its own: the flag then covers one short file. A scaffold's `typecheck` script (JTC.5) makes that decision for the user, so the scaffold's `tsconfig.jxn.json` names this mapper and no other.
- **Decided (JTC.2):** whether `State` is open is read from the project. A page's `State` takes any name when its project file has `state`, or when the page is wrapped by a layout (its own `$layout`, or the project's default where the page names none and is not itself in `layouts/`). A component is always exact. The mapper finds the project file at or above the document and no higher than the `tsconfig`'s folder. A project file it cannot read, or a folder holding both names, opens `State`, so the project's own error is the one reported.
- **Decided (JTC.3):** a `tsconfig` above several projects watches all of them. The protocol takes watched files only from `openProject`, before any file is read, so the mapper walks the `tsconfig`'s folder for project files (outside `node_modules` and dot-folders, through no link; this repository is 664 folders and under 20 ms), watches both names in each folder that holds one and beside the `tsconfig`, and gives what each project gives as `configIdentity`. A project above the `tsconfig`'s folder stays not looked for: that is the bound the spec and the docs state, and it is what keeps a document's types from depending on a folder the `tsconfig` does not own. A project file created in a folder that had none is not watched, and is a stated limit.
- **Decided (JTC.3):** a layout's `State` is open. `resolveLayout` merges the page's state over the layout's before anything runs, so a layout body that reads a name only its pages declare works, and calling it an error would be a false one. A layout is a document in the project's `layouts` folder (`OutsideState.wraps`); one kept elsewhere and named by a page's `$layout` is still read as alone. Both readers and both hosts ask one place (`givenByProject` and `outsideAt` in `state-types.ts`): the mapper from the project file on disk, Studio's function editor from the project open in it, read at each check. Before this Studio read every document as alone unless it named a `$layout`, so a page body reading project state, or state of the default layout, was reported there.
- **Decided (JTC.2):** the generator for a whole document is `generateVirtualDocument` (`@jxsuite/schema/virtual-document`), beside JTC.1's `generateBodyTypes`. Both read an entry's type from `state-types.ts`, which is what keeps the two from disagreeing.

## Implementation

1. **Generator** (landed in JTC.1). `packages/schema/src/jxn/virtual-types.ts` (`@jxsuite/schema/virtual-types`): `generateBodyTypes(doc, target, body)` writes the function around one body from a `JxDocument`, whichever format the file is in, and `bodyOffsetOf` maps a position back by one shift. It handles root `state` functions and inline `on*` handlers, with `State` built from the element chain. It does not yet read `$script` (which a document can carry now, `spec.md` §23.2: `(export)` entries are the import itself on `state`, and a server export takes `(args, env)`), `$defs` or class methods, and it does not read `.jxn` text for a whole-file span map: a `.jxn` body is checked through its parsed document. JTC.2 added the whole-document reader beside it: `virtual-document.ts` (`generateVirtualDocument`) writes the main, server and per-body modules from `.jxn` text with a span for every stretch, `string-pieces.ts` maps a position through each KDL string form, and `state-types.ts` holds what an entry's type is for both readers.
2. **Studio** (landed in JTC.1). `services/type-check.ts` checks the wrapped body in a hidden Monaco model through Monaco's TypeScript worker and draws the findings as `jx-types` markers on the function editor, and files them as Problems (source **Type check**, keyed by tab and body, kept after the editor closes because the Problems tab shares the dock). The editor's own model stays syntax-only. Not done: the `.jxn` Code view (source mode) is a whole-file editor, and its bodies are `.jxn` strings whose offsets need the span map above, and JTC.2 wrote that span map (`generateVirtualDocument`), so the Code view's checking lands with item 5, beside its completion provider.
3. **Mapper** (landed in JTC.2). `packages/content-mapper`: `src/mapper.ts` is `ts-content-mapper` 0.1.1 as a thin layer over `generateVirtualDocument`, adding only what a project gives a document, and `src/server.ts` is the process `tsc` starts with `node`. A syntax error is reported as `error jx1` at its position, and `tsc` then reports only syntax errors for that run. TypeScript is `7.1.0-beta`, pinned exactly. The repository checks its own documents with `bun run typecheck:jxn` over `tsconfig.jxn.json`, in `checks` and in `all-the-things`. **Owner action before the first release:** `@jxsuite/content-mapper` needs an npm trusted publisher, or the release that first publishes it fails.
4. **Mapper depth.** Landed in its first part, in both readers through `packages/schema/src/jxn/document-scopes.ts`: event types by binding and element, `state.$map` typed from what the array maps, an interface for each nested scope with its entries spanned (so rename and definition reach them), and a state function typed by its bindings. Landed in its second part, in the whole-document reader only: a JavaScript module for each `${}` template and one module for the document's `$ref`s, with the reader keeping value tokens and the mapper passing each unit's extension. Studio checks neither, and gets both with the Code view's checking in item 5. Landed in its third part, in the whole-document reader only: what a document defines as an `$elements` interface, and each `$props` entry held against the `.jxn` component its tag names, with the mapper passing the project's components. Landed in its fourth part, in both readers through `packages/schema/src/jxn/schema-types.ts`: the type a JSON Schema says, a typed entry read by it, and `$defs` as a namespace whose names are spanned in the whole-document reader. Landed in its fifth part, in both readers through `declaredParameters` in `state-types.ts`: the type a parameter declares, as CEM `text` or as a schema, with the name of an object parameter spanned so rename reaches it.
