# A malformed reference value is reported on both sides, and a table write naming a row or entry that does not exist is refused

## Context

`specs/relationships.md` §4, line 65:

> **Status: Partial.** The connector enforces the value shape on every `/_jx/data` write (`validateRow` in `extensions/connector/src/validate.ts`, called from `insertRow` and `updateRow` in `extensions/connector/src/worker.ts`), and the parser checks content existence at load time (`resolveContentTypeRefs`), but it reports a dangling id as a warning naming the entry, field and target and leaves the id in place, which is what site-architecture.md §6.4 specifies rather than the validation error the second bullet names. Not built: the parser's `validateEntries` never judges a reference field's value, so a non-string to-one value or a non-string to-many element passes silently, and those writes check the shape only, never that the referenced row or content entry exists.

Verified against the code at `84735a9f`:

- **Connector shape.** `coerceField` in `extensions/connector/src/validate.ts` requires a to-one value to be a non-empty string and a to-many value an array of them (`parseRefPointer`, `extensions/connector/src/columns.ts`, recognises the pointer). `insertRow` and `updateRow` (`worker.ts`) answer a failure with `fail(400, "Validation failed", errors)` and otherwise write straight away: the row, then `writeJunctions` for table to-manys, with no lookup of any target. Covered by `extensions/connector/tests/validate.test.ts` and `tests/worker.test.ts`, whose ref writes all name rows that exist.
- **Parser shape.** `validateEntries` (`extensions/parser/src/content-loader.ts`, run by `loadContentType` on all three load paths) warns through `console.warn` on required fields, dates and `string`/`number`/`boolean`/`array` mismatches. A to-one `{ "$ref" }` field has no `type`, so none of its branches fire; a to-many is checked only for being an array. `resolveContentTypeRefs` then resolves `#/content/` refs, warns on an unknown target type and on each missing id, and skips a non-string value or element without a word (its test, "leaves unresolved ids and non-string values untouched", pins that).
- **Second bullet.** The parser's dangling-id warning agrees with site-architecture.md §6.3 ("ids that match no entry in the target collection log a warning and are **left unresolved**") and §6.4 ("left as the bare string, with a build warning"), and with `docs/framework/site/relationships.md`. Only relationships.md §4 calls it an error.
- **No content view on the mount.** `DataMountOptions.sections` (`worker.ts`) is the raw `project.json` section values, filled by `buildRuntime` (`packages/server/src/jx-mounts.ts`) and `buildMountSpecs` (`packages/compiler/src/site/site-build.ts`); the loaded content never reaches the mount. `plan:relationships/cross-domain-references` adds that view for `?include=`.
- **Every site write goes through the mount.** `TableInsert`, `TableUpdate` and `TableDelete` fetch `/_jx/data` in the browser and in compiled output (`extensions/connector/src/table-actions.ts`); the node path (`table-node.ts`) only reads.
- **The owner console.** `insertDataRow` and `updateDataRow` (`packages/server/src/data-api.ts`, `POST` and `PUT /__studio/data/rows`, reached from the grid through `packages/studio/src/services/data-service.ts`) write physical columns keyed on introspected types through `coerceValues`, never `validateRow`, and bypass table rules by design (extensions.md §13). `packages/server` may not import `@jxsuite/connector` (the module header states the dep rule).

## Outcome

- relationships.md §4 → Implemented. Bullet one holds on both sides: the parser warns on a reference value that is not an entry id, and the connector refuses one with a 400 (as today). Bullet two is reworded to the warning the parser gives. Bullet three is built: every `/_jx/data` insert and update refuses a to-one id, to-many id or junction id that names no row of the target table or no entry of the target content type. Bullet four is unchanged.
- The owner console stays outside the check (Decisions), and the spec and the data grid page say so.
- If relationships.md §5 is already Implemented when this lands, relationships.md graduates in the same pull request (Specs & docs).

## Decisions

- **Open:** does a dangling content id stay a build warning, or become a load error as §4's second bullet says? Recommendation: stay a warning and reword the bullet, because the parser has no error channel (every content validation finding is a `console.warn`, and site-architecture.md §6.3 says so), two specs and the user docs already promise the warning, and failing builds on a stale id would be a breaking change for every author with one. `jx validate` reporting dangling ids as errors can be a later, separate change.
- **Open:** is the Studio owner console exempt from the existence check? Recommendation: exempt, because extensions.md §13 defines it as the owner's raw admin surface that bypasses table rules, it writes physical columns (`author_id`, junction and system tables) rather than schema fields, and checking it would need a new connector capability dispatched through the registry, since `packages/server` may not import the connector. The foreign keys `plan:relationships/table-foreign-keys` adds still bind it wherever the dialect enforces them, and `plan:relationships/studio-reference-picker` gives the grid an entry picker for reference cells. The cost, a grid that can store a dangling id, is stated in the spec and on the data grid page.
- **Decided:** the parser judges any field whose `$ref`, or whose array `items.$ref`, matches the `RelationshipRef` grammar (`^#/[A-Za-z][A-Za-z0-9_-]*/[A-Za-z0-9._-]+$`, relationships.md §1), whatever the section, and a value passes only as a non-empty string, because that is exactly the set `validateRow` accepts, so one value is judged the same on both sides, and the grammar keeps a non-relationship `$ref` such as `#/$defs/Thing` out. The finding goes through `validateEntries`' existing `console.warn` channel, in its message form. A to-many value that is not an array keeps the existing "expected array" warning.
- **Decided:** the existence check is a separate async step in a new module, `extensions/connector/src/references.ts`, run by `insertRow` and `updateRow` after `validateRow` and before any write, because `validateRow` is synchronous and database-free (and Workers-safe by design), and checking first means a refused write changes nothing: no row, no half-replaced junction links. A failure is the same 400 `{ error: "Validation failed", issues: [{ field, message }] }` shape `validateRow` produces, so every client already handles it. It runs on the payload after schema defaults and before grant-forced `setColumns` are merged, because those come from the auth mount rather than the caller.
- **Decided:** a row lookup reads the target table through its own connection's memoised database (`getDb`) with a plain `SELECT id … WHERE id IN (…)`, ignoring the target's `read` rule and owner scoping, because referential integrity asks whether the row exists, not whether this caller may see it, a database foreign key answers the same question the same way, and the 400 names only the id the caller sent. A target on another connection is therefore checked too, which no foreign key can do. Each id is converted by the target's id kind before the query, with the typing `plan:relationships/table-foreign-keys` fixes for include (an `integer` target takes only an integral numeral, so `"1"` finds row 1 and `"abc"` is missing without a query, never a Postgres cast error), and found ids are keyed back the same way. One query per distinct target per write.
- **Decided:** only `data` and `content` targets are checked, because §4's third bullet names rows and content entries and those are the two referenceable sections that ship; a pointer into any other section passes unchecked, and `plan:extensions/referenceable-sections` refuses it in the entry schema. A `data` pointer naming no declared table, or a `content` pointer naming a type the mount's content view does not hold, is an issue ("References unknown table", "References unknown content type"), because the write cannot be judged and silence would hide a config error. A host that supplies no content view is treated as supplying an empty one.
- **Decided:** check-then-write is not atomic, and that is accepted: where the dialect enforces the foreign key it closes the race for table to-one refs, content targets are fixed for the life of a mount, and a concurrent delete of a junction target is the same gap a delete of any target leaves (§4 governs the referencing write, not deletes).

## Implementation

1. **`extensions/parser/src/content-loader.ts`**, in the Schema Validation block:
   - Add `const RELATIONSHIP_REF = /^#\/[A-Za-z][A-Za-z0-9_-]*\/[A-Za-z0-9._-]+$/;` with a comment citing relationships.md §1 (the `RelationshipRef` grammar in `@jxsuite/schema`), and three small helpers: `isRelationshipRef(ref: unknown): boolean`, `isEntryId(value: unknown): value is string` (`typeof value === "string" && value !== ""`), and `describeValue(value: unknown): string` (`"an empty string"`, `"null"`, `"array"`, else `typeof value`).
   - `validateEntries`: inside the per-field loop, after the `value == null` skip and before the date branch, compute `toOne = isRelationshipRef(def.$ref)` and `toMany = !toOne && def.type === "array" && isRelationshipRef(def.items?.$ref)`. For `toOne`, when `!isEntryId(value)` warn `Content validation: "<type>/<id>" field "<field>" expected an entry id string, got <describeValue>` and `continue`. For `toMany` with an array value, warn once per bad element: `… field "<field>" element <i> expected an entry id string, got <describeValue>`, then `continue`. A non-array to-many falls through to the existing array branch. Extend the JSDoc: reference values are judged here (relationships.md §4), existence in `resolveContentTypeRefs`.
   - `resolveContentTypeRefs`: resolve only when `isEntryId(value)` (to-one) and `isEntryId(id)` (each to-many element), so an empty string is not reported a second time as a missing entry `""`; update its JSDoc sentence to "values that are not entry ids are left as they are; `validateEntries` reports them".
2. **`extensions/connector/src/references.ts`** (new, Workers-safe: no node imports), module header citing relationships.md §4 and `@docs framework/site/relationships`:
   - `export interface ReferenceLookup { missingRows(table: string, ids: string[]): Promise<string[] | undefined>; contentIds(type: string): ReadonlySet<string> | undefined; }`. `missingRows` returns the subset of `ids` naming no row, or `undefined` when `table` is not a declared table; `contentIds` returns a content type's entry ids, or `undefined` when the view has no such type.
   - `export async function checkReferences(plan: TablePlan, value: Record<string, unknown>, lookup: ReferenceLookup): Promise<ValidationIssue[]>`. Collect, for fields present in `value` with a non-null value: each `plan.columns` entry with `ref !== null` (one id when `!manyRef`, the array when `manyRef`) and each `plan.junctions` entry (the array, target `{ section: "data", name: junction.targetTable }`). Group by target, de-duplicating ids. For `data` call `missingRows` once per target; for `content` read `contentIds` once; skip every other section. Issues, in payload field order, one per field and missing id: `References missing "<table>" row "<id>"` or `References missing "<type>" entry "<id>"` (the parser's wording), and one per field for an undeclared target: `References unknown table "<name>"` or `References unknown content type "<name>"`. Reuse `ValidationIssue` from `validate.ts` and `TablePlan` from `columns.ts`.
3. **`extensions/connector/src/worker.ts`**:
   - In `handleDataRequest`, for `insert` and `update`, build a `ReferenceLookup` over `state`, `options`, `env` and `tables`. `missingRows(name, ids)`: `undefined` when `tables[name]` is absent; otherwise `getDb(state, options, env, def.connection)`, `planTable(name, def, tables, kind)`, convert each id with the target id-typing helper that `plan:relationships/table-foreign-keys` lands for include (today's `parseId` rule), query `db.selectFrom(name).select("id").where("id", "in", typed)` only when `typed` is non-empty, key the found ids the same way, and return the ids with no match. `contentIds(type)`: the entry ids of `type` in the content view `plan:relationships/cross-domain-references` adds to `DataMountOptions`, as a `Set`; with no view, `undefined`.
   - `insertRow(…, lookup)`: after the defaults loop and before `Object.assign(value, decision.setColumns ?? {})`, `const missing = await checkReferences(plan, value, lookup); if (missing.length > 0) return fail(400, "Validation failed", missing);`. `updateRow(…, lookup)`: the same, right after `validateRow` passes. Lookup errors (an unknown target connection) reach the existing `catch` and are a 500, as for the table's own connection.
   - Module header: one sentence that writes check reference targets exist (relationships.md §4).
4. Specs, docs and tests as below. Delete this file in the landing pull request (and `plans/relationships/` if the spec graduates).

**Integration contract.** Once this lands: every `/_jx/data` `POST` and `PATCH` refuses, before writing anything, a reference whose target row or content entry does not exist, with `400 { error: "Validation failed", issues: [{ field, message }] }`, where `field` is the schema field name and `message` names the target and the id; `checkReferences` and `ReferenceLookup` are exported from `extensions/connector/src/references.ts` (not a package subpath). The parser reports a reference value that is not a non-empty string, or a to-many element that is not one, as a `Content validation:` warning naming the entry and field, and `resolveContentTypeRefs` still leaves dangling ids in place with its warning. The owner console routes (`/__studio/data/rows`) are unchanged.
