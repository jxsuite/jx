# A malformed reference value is reported on both sides, and a table write naming a row or entry that does not exist is refused

## Context

`specs/relationships.md` §4, line 65:

> **Status: Partial.** The connector enforces the value shape on every `/_jx/data` write (`validateRow` in `extensions/connector/src/validate.ts`, called from `insertRow` and `updateRow` in `extensions/connector/src/worker.ts`), and the parser checks content existence at load time (`resolveContentTypeRefs`), but it reports a dangling id as a warning naming the entry, field and target and leaves the id in place, which is what site-architecture.md §6.4 specifies rather than the validation error the second bullet names. Not built: the parser's `validateEntries` never judges a reference field's value, so a non-string to-one value or a non-string to-many element passes silently, and those writes check the shape only, never that the referenced row or content entry exists.

Verified against the code at `84735a9f`, and re-read on 2026-09-27 against the two prerequisites' drafted designs:

- **Connector shape.** `coerceField` in `extensions/connector/src/validate.ts` requires a to-one value to be a non-empty string and a to-many value an array of them (`parseRefPointer`, `extensions/connector/src/columns.ts`, recognises the pointer). `insertRow` and `updateRow` (`worker.ts`) answer a failure with `fail(400, "Validation failed", errors)` and otherwise write straight away: the row, then `writeJunctions` for table to-manys, with no lookup of any target. Covered by `extensions/connector/tests/validate.test.ts` and `tests/worker.test.ts`, whose ref writes all name rows that exist; no other suite writes a reference through the mount.
- **Parser shape.** `validateEntries` (`extensions/parser/src/content-loader.ts`, run by `loadContentType` on all three load paths) warns through `console.warn` on required fields, uncoerced dates (a branch `plan:parser/uniform-entry-dates` deletes) and `string`/`number`/`boolean`/`array` mismatches. A to-one `{ "$ref" }` field has no `type`, so none of its branches fire; a to-many is checked only for being an array. `resolveContentTypeRefs` then resolves `#/content/` refs, warns on an unknown target type and on each missing id, and skips a non-string value or element without a word (its test, "leaves unresolved ids and non-string values untouched", pins that). An empty string is looked up and reported as a missing entry `""`.
- **Second bullet.** The parser's dangling-id warning agrees with site-architecture.md §6.3 ("ids that match no entry in the target collection log a warning and are **left unresolved**") and §6.4 ("left as the bare string, with a build warning"), and with `docs/framework/site/relationships.md`. Only relationships.md §4 calls it an error.
- **What the prerequisites land.** `plan:relationships/table-foreign-keys` adds `typedId(idType, value)` and `idKey(value)` to `columns.ts` (the one id conversion and the one id comparison), keys same-connection to-one columns in the database, makes `validateRow` refuse a malformed id into a same-connection integer-id table as a shape error, and makes a to-many into another connection's table a JSON id column rather than a junction. `plan:relationships/cross-domain-references` adds `parseRelationshipPointer` and `findReferencedEntry` (`@jxsuite/schema/reference-view`), replaces the parser's `refTargetName` with the former, and hands the data mount a `references` option (`ReferenceSource` in `extensions/connector/src/include.ts`: a `ReferenceView`, or a function returning one, possibly a promise) holding every entry the `data` section points at. Its integration contract names this plan as the one that checks table → content existence with that source.
- **The dev server's view is as fresh as `project.json`.** The dev server builds `references` from the resolve proxy's project context (`loadProjectEntry`, `packages/server/src/resolve.ts`), which is cached against `project.json`'s mtime and nothing else. A content entry created since (Studio writes entries as files, never touching `project.json`) is absent from it. For `?include=` that is a `null`; for a write-time check it would be a false 400, in `jx dev`, Studio's live preview (`packages/server/src/live-preview.ts`) and the desktop, which reaches the same `handleJxMounts`.
- **Every site write goes through the mount.** `TableInsert`, `TableUpdate` and `TableDelete` fetch `/_jx/data` in the browser and in compiled output (`extensions/connector/src/table-actions.ts`); the node path (`table-node.ts`) only reads.
- **The owner console.** `insertDataRow` and `updateDataRow` (`packages/server/src/data-api.ts`, `POST` and `PUT /__studio/data/rows`, reached from the grid through `packages/studio/src/services/data-service.ts`) write physical columns keyed on introspected types through `coerceValues`, never `validateRow`, and bypass table rules by design (extensions.md §13). `packages/server` may not import `@jxsuite/connector` (the module header states the dep rule).
- **Grant-forced fields.** `insertRow` merges `decision.setColumns` after validation, and `docs/framework/concepts/security.md` promises that for an `ownerField` "the value in the request body is not consulted".

## Outcome

- relationships.md §4 → Implemented. Bullet one holds on both sides: the parser warns on a reference value that is not an entry id, and the connector refuses one with a 400 (as today). Bullet two is reworded to the warning the parser gives. Bullet three is built: every `/_jx/data` insert and update refuses a to-one id, to-many id or junction id that names no row of the target table or no entry of the target content type, judged in the dev server against the content on disk. Bullet four is unchanged.
- The owner console stays outside the check (Decisions), and the spec and the data grid page say so.
- If relationships.md §5 is already Implemented when this lands, relationships.md graduates in the same pull request (Specs & docs).

## Decisions

- **Open:** does a dangling content id stay a build warning, or become a load error as §4's second bullet says? Recommendation: stay a warning and reword the bullet, because the parser has no error channel (every content validation finding is a `console.warn`, and site-architecture.md §6.3 says so), two specs and the user docs already promise the warning, and failing builds on a stale id would be a breaking change for every author with one. `jx validate` reporting dangling ids as errors can be a later, separate change.
- **Open:** is the Studio owner console exempt from the existence check? Recommendation: exempt, because extensions.md §13 defines it as the owner's raw admin surface that bypasses table rules, it writes physical columns (`author_id`, junction and system tables) rather than schema fields, and checking it would need a new connector capability dispatched through the registry, since `packages/server` may not import the connector. The foreign keys `plan:relationships/table-foreign-keys` adds still bind it wherever the dialect enforces them, and `plan:relationships/studio-reference-picker` gives the grid an entry picker for reference cells. The cost, a grid that can store a dangling id, is stated in the spec and on the data grid page.
- **Decided:** the parser judges any field whose `$ref`, or whose array `items.$ref`, parses under `parseRelationshipPointer` (the `RelationshipRef` grammar, relationships.md §1), whatever the section, and a value passes only as a non-empty string, because that is exactly the set `validateRow` accepts, so one value is judged the same on both sides, and the grammar keeps a non-relationship `$ref` such as `#/$defs/Thing` out. Reusing the prerequisite's parser rather than a second regex keeps the parser, the connector and the schema on one grammar. The finding goes through `validateEntries`' existing `console.warn` channel, in its message form. A to-many value that is not an array keeps the existing "expected array" warning.
- **Decided:** the existence check is a separate async step in a new module, `extensions/connector/src/references.ts`, run by `insertRow` and `updateRow` after `validateRow` and before any write, because `validateRow` is synchronous and database-free (and Workers-safe by design), and checking first means a refused write changes nothing: no row, no half-replaced junction links. A failure is the same 400 `{ error: "Validation failed", issues: [{ field, message }] }` shape `validateRow` produces, so every client already handles it. It runs on the payload after schema defaults and before grant-forced `setColumns` are merged, and skips every field `setColumns` sets, because those values come from the auth mount rather than the caller, and security.md promises the body's value for them is not consulted.
- **Decided:** a row lookup reads the target table through its own connection's memoised database (`getDb`) with a plain `SELECT id … WHERE id IN (…)`, ignoring the target's `read` rule and owner scoping, because referential integrity asks whether the row exists, not whether this caller may see it, a database foreign key answers the same question the same way, and the 400 names only the id the caller sent. It does tell a caller who may write whether an id exists in a table it cannot read, as the foreign key already does for a same-connection target; the default `uuid` ids make that unguessable, and security.md says so. A target on another connection is checked too, which no foreign key can do. Each id is converted with `typedId(targetIdType, id)` and matched with `idKey`, the prerequisite's helpers: a same-connection integer target never sees `"abc"` (`validateRow` refuses it first), and a cross-connection one reports it missing without a query, never a Postgres cast error. One query per distinct target per write.
- **Decided:** only `data` and `content` targets are checked, because §4's third bullet names rows and content entries and those are the two referenceable sections that ship; a pointer into any other section passes unchecked, and `plan:extensions/referenceable-sections` refuses it in the entry schema. A `data` pointer naming no declared table, or a `content` pointer naming a type the mount's `references` view does not hold, is an issue ("References unknown table", "References unknown content type"), because the write cannot be judged and silence would hide a config error. A mount with no `references` option is treated as holding an empty view; in-repo hosts supply one whenever the section points at loaded content.
- **Decided:** a content miss is judged against fresh content before it is refused. When `references` is a function, the mount calls it once per write, and on any miss or unknown type calls it once more with `{ reload: true }`; the dev server's function passes that to the resolve proxy's context loader, which then rereads the project past its mtime cache. A hit costs nothing extra, and only a write that is about to be refused pays for a reload, which is a dev-server cost: the generated worker's view is a snapshot of the content that deployment serves and is never reloaded. Refusing against the cached context would reject a valid write naming any entry created since `project.json` last changed, and skipping content targets in dev would leave the check unbuilt where authors test it.
- **Decided:** check-then-write is not atomic, and that is accepted: where the dialect enforces the foreign key it closes the race for same-connection to-one refs, content targets are fixed for the life of a deployment, and a concurrent delete of a junction target is the same gap a delete of any target leaves (§4 governs the referencing write, not deletes).
- **Decided:** edges. Both are hard. `plan:relationships/cross-domain-references` supplies everything the content half stands on (`ReferenceSource` and `include.ts`, the `references` mount option in both hosts, `findReferencedEntry`, `parseRelationshipPointer` in the parser, `projectContext` in `resolve.ts`), and §4's third bullet cannot read Implemented without a view to judge content ids against. `plan:relationships/table-foreign-keys` supplies `typedId` and `idKey`, the shape rule that keeps `"abc"` from a same-connection integer column, the cross-connection storage rule `checkReferences` walks (a JSON id column, not a junction), and the foreign keys the owner-console exemption and the race note lean on. The second edge is implied by the first; it stays because this plan calls that plan's helpers directly and that plan's integration contract asks for it. `plan:relationships/studio-reference-picker` is not required: the exemption stands on its own, and the grid's pickers only make a dangling id harder to type.
- **Decided:** merge adjacency only, with no ordering: `plan:parser/uniform-entry-dates` (the date branch in `validateEntries`, see step 1), `plan:site-architecture/build-excludes-drafts` (it rewords the miss-branch warnings in `resolveContentTypeRefs` that step 1 guards; and since a build then leaves drafts out of the view the worker inlines while `jx dev` keeps them, a write naming a draft entry is accepted in dev and refused by a deployed site, which is what §4's "the entries built into a deployed site" means), and `plan:extensions/connector-table-paths` and `plan:extensions/declared-media-type-responses` (the `loadProjectEntry` cache entry, see step 5). Whichever lands second rebases.

## Implementation

1. **`extensions/parser/src/content-loader.ts`**, in the Schema Validation block:
   - Two small helpers: `isEntryId(value: unknown): value is string` (`typeof value === "string" && value !== ""`) and `describeValue(value: unknown): string` (`"an empty string"`, `"null"`, `"array"`, else `typeof value`).
   - `validateEntries`: inside the per-field loop, first after the `value == null` skip (ahead of the date branch today; `plan:parser/uniform-entry-dates` deletes that branch, and the check keeps its first place in either order of landing), compute `toOne = parseRelationshipPointer(def.$ref) !== null` and `toMany = !toOne && def.type === "array" && parseRelationshipPointer(def.items?.$ref) !== null` (the function `plan:relationships/cross-domain-references` imports into this module). For `toOne`, when `!isEntryId(value)` warn `Content validation: "<type>/<id>" field "<field>" expected an entry id string, got <describeValue>` and `continue`. For `toMany` with an array value, warn once per bad element: `… field "<field>" element <i> expected an entry id string, got <describeValue>`, then `continue`. A non-array to-many falls through to the existing array branch. Extend the JSDoc: reference values are judged here (relationships.md §4), existence in `resolveContentTypeRefs`.
   - `resolveContentTypeRefs`: the to-one branch resolves only when `isEntryId(value)`, and the to-many map passes through any element that is not `isEntryId(id)`, so an empty string is not reported a second time as a missing entry `""`; its JSDoc gains "values that are not entry ids are left as they are; `validateEntries` reports them".
2. **`extensions/connector/src/references.ts`** (new, Workers-safe: no node imports), module header citing relationships.md §4 and `@docs framework/site/relationships`:
   - `export interface ReferenceLookup { missingRows(table: string, ids: unknown[]): Promise<unknown[] | undefined>; missingEntries(type: string, ids: unknown[]): Promise<unknown[] | undefined>; }`. Each returns the subset of `ids` naming nothing, or `undefined` when the table is not declared or the view holds no such content type.
   - `export async function checkReferences(plan: TablePlan, value: Record<string, unknown>, lookup: ReferenceLookup): Promise<ValidationIssue[]>`. Collect, for fields present in `value` with a non-null value: each `plan.columns` entry with `ref !== null` (one id when `!manyRef`, the array when `manyRef`) and each `plan.junctions` entry (the array, target `{ section: "data", name: junction.targetTable }`). Group by target, de-duplicating ids by `idKey`. Call `missingRows` once per `data` target and `missingEntries` once per `content` target; skip every other section. Issues, in payload field order, one per field and missing id: `References missing "<table>" row "<id>"` or `References missing "<type>" entry "<id>"` (the parser's wording), and one per field for an undeclared target: `References unknown table "<name>"` or `References unknown content type "<name>"`. Reuse `ValidationIssue` (`validate.ts`), `TablePlan` and `idKey` (`columns.ts`).
3. **`extensions/connector/src/include.ts`** (landed by the prerequisite): `ReferenceSource`'s function form widens to `(options?: { reload?: boolean }) => ReferenceView | Promise<ReferenceView>`, documented as "`reload` asks the host to reread its content first; a snapshot ignores it". The one expression that resolves a source (`typeof references === "function" ? await references() : (references ?? {})`) becomes an exported `resolveReferences(source, options?)` if it is still inline, so the include path and the check share it.
4. **`extensions/connector/src/worker.ts`**:
   - In `handleDataRequest`, for `insert` and `update`, build one `ReferenceLookup` per request over `state`, `options`, `env` and `tables`. `missingRows(name, ids)`: `undefined` when `tables[name]` is absent; otherwise `getDb(state, options, env, def.connection)`, `typed = ids.map((id) => typedId(def.id ?? "uuid", id))`, a query `db.selectFrom(name).select("id").where("id", "in", defined)` only when some are defined, and the ids whose `idKey` matches no returned `idKey(row.id)`. `missingEntries(type, ids)`: resolve the view with `resolveReferences(options.references)` (at most once per request), judge each id with `findReferencedEntry(view, { section: "content", name: type }, id)` and `view.content?.[type]` for an unknown type; when that finds a miss or an unknown type and `options.references` is a function, resolve once more with `{ reload: true }` (at most once per request) and judge again.
   - `insertRow(…, lookup)`: after the defaults loop and before `Object.assign(value, decision.setColumns ?? {})`, check `value` without the keys `decision.setColumns` sets: `const missing = await checkReferences(plan, checked, lookup); if (missing.length > 0) return fail(400, "Validation failed", missing);`. `updateRow(…, lookup)`: the same, right after `validateRow` passes. Lookup errors (an unknown target connection) reach the existing `catch` and are a 500, as for the table's own connection.
   - Module header: one sentence that writes check reference targets exist (relationships.md §4).
5. **`packages/server/src/resolve.ts`**: `projectContext(projectRoot, options?: { reload?: boolean })` (the export the prerequisite adds) passes `reload` to `loadProjectEntry`, which then skips the mtime match and replaces the cache entry, so the resolve proxy and asset mounts see the fresher context too. A reload runs the same body that builds the entry on an mtime miss, so the fields `plan:extensions/connector-table-paths` (`config`, `registry`, `sections`) and `plan:extensions/declared-media-type-responses` (`formats`) add to that entry are rebuilt with it; neither is a prerequisite, and whichever lands second keeps the others' fields.
6. **`packages/server/src/jx-mounts.ts`**, `buildRuntime`: the `references` function the prerequisite adds takes `options` and awaits `projectContext(projectRoot, options)`; its `WeakMap` memo is keyed by the context object, so a reload rebuilds the view by construction. Header bullet: a refused content reference is judged after rereading the project.
7. Specs, docs and tests as below. Delete this file in the landing pull request (and `plans/relationships/` if the spec graduates).

**Integration contract.** Once this lands: every `/_jx/data` `POST` and `PATCH` refuses, before writing anything, a reference whose target row or content entry does not exist, with `400 { error: "Validation failed", issues: [{ field, message }] }`, where `field` is the schema field name and `message` names the target and the id; fields a grant's `setColumns` sets are not checked. A function-valued `references` source may be called with `{ reload: true }` and must then answer from current content. `checkReferences` and `ReferenceLookup` are exported from `extensions/connector/src/references.ts` (not a package subpath). The parser reports a reference value that is not a non-empty string, or a to-many element that is not one, as a `Content validation:` warning naming the entry and field, and `resolveContentTypeRefs` still leaves dangling ids in place with its warning. The owner console routes (`/__studio/data/rows`) are unchanged.
