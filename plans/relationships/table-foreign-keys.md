# A to-one table reference is typed like its target's id, so it resolves on include and carries a real foreign key

## Context

This plan claims nothing. It enables `plan:relationships/cross-domain-references`, which owns relationships.md §2 and requires it: this plan closes the table → table half of that section's marker, and the owner flips the marker. `specs/relationships.md` §2, line 39, the parts this plan answers:

> **Status: Partial.** … the connector's `/_jx/data` mount stores `<field>_id` text columns and expands `?include=` for junction to-manys and for to-one refs into uuid-id tables (`expandIncludes` in `extensions/connector/src/worker.ts`, by a second `SELECT … WHERE id IN` rather than a join). Not built: a to-one `?include=` onto an `integer`-id table resolves to `null`, because the text column's `"1"` misses the numeric key the target rows come back with; … `buildCreateTable` and the additive `ADD COLUMN` path (`extensions/connector/src/ddl.ts`) emit no foreign-key constraint on any dialect; …

The contract is the matrix's table → table row (line 47): "FK column `<field>_id`; real FK constraint where the dialect allows". It is one decision in one workspace (how a to-one column is typed, and what that means for rows and databases that already exist), which is why it was split from the owner. `plan:relationships/reference-validation` (relationships.md §4) compares ids under the typing decided here.

**What exists** (verified at the working tree on 2026-09-27)

- `planTable` (`extensions/connector/src/columns.ts`) gives every to-one `<field>_id` column `dataType: "text"`, `storage: "text"`, whatever the target's `id`. Junction columns are typed by `idDataType` from each side's id kind. Covered by `extensions/connector/tests/columns.test.ts`.
- `validateRow` (`extensions/connector/src/validate.ts`) accepts only a non-empty string for a to-one value and only strings as to-many elements, so `"abc"` reaches an integer junction column today and would reach an integer to-one column.
- `expandIncludes` (`worker.ts`) keys its target map by `t.id` as the driver returns it and looks it up with the stored column value. Measured on bun:sqlite: `select id from users where id in ('1')` returns `{ id: 1 }`, so the `SELECT` finds the row and the `Map` lookup with `"1"` misses. Junction to-manys resolve because the junction column is typed `integer`, both engines store `"1"` as `1`, and the link rows come back numeric.
- `syncTables` and `buildCreateTable` (`extensions/connector/src/ddl.ts`), covered by `extensions/connector/tests/ddl.test.ts`: plain columns, no `REFERENCES`, never a retype; type drift is `current.dataType.toLowerCase() !== col.dataType.toLowerCase()`.
- The DDL plan and the runtime plan see different table sets. Every `syncTables` caller passes one connection's tables (`tablesForConnection` in `getDb` and `table-node.ts`, `tablesFor` in `pushDataSchema` in `packages/server/src/data-api.ts`, and the per-connection loop in `packages/compiler/src/site/db-push.ts`), while the mount calls `planTable` with the whole `data` section. A to-many into another connection's table is therefore a JSON id column in the database and a junction at request time, and `expandIncludes` queries the source connection for a target table it does not hold.
- bun:sqlite opens with `foreign_keys = 0` (measured), and `extensions/connector/src/dialects/bun-sqlite.ts` never sets it, so a declared key would go unenforced in local dev and in every connector test. D1 enforces foreign keys by default; Postgres always does. The Sqlite provider's dialect also backs the auth extension's local Better Auth database (`extensions/auth/src/server.ts`, exercised by `extensions/auth/tests/server.test.ts` and `worker.test.ts`).
- Kysely's `PostgresIntrospector` reports `typname` (`int4`, `float8`, `bool`), so the drift comparison already misreports every scalar `integer`, `number` and `boolean` column as drift on Supabase, and would do the same for every integer reference column.

**Corrections to the stub**

- A self-reference needs no ordering: an inline `references "tree" ("id")` inside `create table "tree"` is legal on SQLite and Postgres (checked by compiling through Kysely). Ordering matters only on Postgres, only between distinct tables, and a mutual reference needs one constraint added after both tables exist.
- SQLite accepts `ALTER TABLE … ADD COLUMN … REFERENCES` whenever the new column's default is `NULL`, which it always is here, and pragma `foreign_keys = ON` enforces it (measured, including `ON DELETE SET NULL` and a text child column against an integer parent).

## Outcome

- A to-one reference into a table on the same connection gets a `<field>_id` column typed like the target's id and a foreign key, on `CREATE TABLE` and on `ADD COLUMN`, on SQLite, D1 and Postgres, created in an order Postgres accepts.
- `?include=` resolves a to-one reference onto a uuid-id or integer-id table, including through a column an older push created as `text`.
- An existing reference column whose type or key disagrees with the schema is reported once as drift and never altered.
- The local SQLite stand-in enforces foreign keys as D1 does, and a write the database refuses for a missing referenced row is a 400, not a 500.
- relationships.md §2's marker loses its two table → table sentences and stays `Partial`, owned by `plan:relationships/cross-domain-references`. No claim changes state here.

## Decisions

- **Open:** what is a reference value into an integer-id table on the wire? Recommendation: the id's decimal string (`"1"`), as today, with the integer column a storage detail converted at the boundary the way booleans already are: `toStorage` binds a number, `fromStorage` returns a string, and a JSON number in a payload stays a validation error. Because relationships.md §1 ("the target section's entry `id` (string)"), §4's first bullet ("must hold a string"), `docs/framework/site/relationships.md` and every writer (forms posting `FormData`, `TableInsert`, Studio's pickers) already speak strings, and one value shape across content, uuid and integer targets is what the §4 existence check and the §5 pickers have to handle. The cost a maintainer signs: `comment.author_id` reads `"1"` beside `user.id` reading `1`, which is today's behaviour. The alternative (the value takes the target's id type: a number is accepted, `"1"` is coerced, reads return `1`) changes §1's sentence and §4's first bullet, which `plan:relationships/reference-validation` owns.
- **Open:** what does deleting a referenced row do? Recommendation: `ON DELETE SET NULL`. `RESTRICT` would make `DELETE /_jx/data/users/:id` fail on any referenced row, with a status the wire contract does not have and often with no way for the deleting user to delete the referencing rows first; `CASCADE` deletes rows nobody named. `SET NULL` gives the answer `?include=` already gives a dangling id (`null`). It does write referencing rows the deleting user may have no `update` permission on, and it can leave a `required` reference null; `required` is a payload rule on writes, and the read side already tolerates null.
- **Open:** what is a reference into a table on another connection? Recommendation: stored like a content reference (a `text` column, no key), not expanded by `?include=`, and a to-many into one is a JSON id column rather than a junction, because one database can hold neither a key nor a join into another, each push plans one connection alone, and today the same field is a junction at request time and a JSON column in the database. §2 gains one sentence saying so; resolving across connections, if ever wanted, belongs to the owner of §2's `?include=` paths.
- **Decided:** one predicate, `foreignKeyTarget(ref, source, allTables)` in `columns.ts`, decides "a table → table reference this database can key": the pointer's section is `data`, the target is declared, and it names the source's `connection`. `planTable` uses it for to-one typing and for the junction choice, so the per-connection DDL plan and the whole-section runtime plan derive the same columns.
- **Decided:** ids are compared through one helper, `idKey(value)` (`null` for nullish, otherwise `String(value)`), and converted for a query or a bind by one, `typedId(idType, value)` (the mount's `parseId` rule, moved: for `integer` a safe integer from a number or a non-blank numeral, for `uuid` a non-empty string, otherwise `undefined`). Both `expandIncludes` branches, `toStorage`, `parseId` and `validateRow` use them, because additive sync never retypes, so a pre-existing `text` column must keep resolving against an integer key forever, and the §4 existence check needs the same conversion and comparison.
- **Decided:** additive sync never alters an existing column: a reference column whose type or foreign-key target differs from the plan is one drift warning naming both sides. Adding a constraint to an existing column would validate every stored row and fail on the first dangling one, and SQLite has no `ADD CONSTRAINT`, so drift keeps the dialects uniform. The type comparison normalises Postgres's catalog names (`int4`, `float8`, `bool`), which fixes the existing false drift on Supabase in the same line.
- **Decided:** creation order is a stable topological sort of the plans on their to-one key edges (declaration order breaks ties and cycles). SQLite and D1 always declare the key inline. Postgres declares it inline when the target already exists, was created earlier in the run, or is the table itself, and otherwise adds it after the loop as `alter table … add constraint "<table>_<column>_fkey" foreign key …`, Postgres's own default name. Only a reference cycle reaches that form, so the push plan's step classifier (`classifyStatement`, `packages/server/src/data-api.ts`) keeps reading nearly every key as "Create table" or "Add column" and shows the rare cycle step as a generic statement, with no server change.
- **Decided:** the bun-sqlite dialect runs `pragma foreign_keys = on` in `init()` on every database it opens or is given, because the local SQLite file stands in for D1 (extensions.md §12's `local`) and a stand-in that ignores keys lets a write pass in dev that D1 refuses. Better Auth's own keys become enforced locally too, as they already are on D1 and Postgres; the auth suite is the regression check.
- **Decided:** the data mount maps a foreign-key violation (`code` `SQLITE_CONSTRAINT_FOREIGNKEY` or Postgres `23503`, or a message containing `FOREIGN KEY constraint failed`, which is D1's) to `400 "A reference names a row that does not exist"`, because enforcing the key turns a dangling write that used to succeed into a thrown error, and a 500 says the server broke. The field-named 400 from a pre-write check is §4's, not this plan's; the mapping stays as that check's backstop against races.
- **Decided:** `validateRow`, given the table set, requires a to-one value or to-many element into an integer-id table to pass `typedId("integer", value)`, because once the column is `integer`, Postgres answers `"abc"` with a cast error (a 500) where SQLite answers with a key violation. This is a shape rule on the value, not the existence check.
- **Decided:** junction tables keep relationships.md §3's shape (composite primary key and target index, no foreign keys), because §3 asks for none and `deleteRow` already removes a deleted row's own links. The owner console (`packages/server/src/data-api.ts`) is not changed: it coerces `"1"` to `1` for an integer column already, and the database's keys now bind it where they are enforced, surfacing the engine's message.
- **Decided:** this PR rewrites §2's marker to drop its two table → table sentences, because the PR that makes a sentence false is the one whose reviewer can confirm it. The marker stays `Partial`, owned by `plan:relationships/cross-domain-references`.

## Implementation

1. **`extensions/connector/src/columns.ts`**
   - `export interface ForeignKeyTarget { table: string; idType: "uuid" | "integer" }`, and `ColumnSpec` gains `references: ForeignKeyTarget | null` (set only on a keyed to-one column; `null` everywhere else, the owner column included).
   - `export function foreignKeyTarget(ref: RefTarget | null, source: TableDef, allTables: Record<string, TableDef>): ForeignKeyTarget | null`: non-null when `ref?.section === "data"`, `allTables[ref.name]` exists and its `connection === source.connection`; `idType` is the target's `id ?? "uuid"`.
   - `export function idKey(value: unknown): string | null`: `value == null ? null : String(value)`.
   - `export function typedId(idType: "uuid" | "integer", value: unknown): string | number | undefined`, the rule decided above; `parseId` in `worker.ts` becomes `typedId(plan.idType, rawId)`.
   - `planTable`: the to-one branch computes `const target = foreignKeyTarget(toOne, table, allTables)` and pushes `dataType: target ? idDataType(target.idType) : "text"`, `references: target`, `storage: "text"`. The junction branch's condition becomes `itemsRef && foreignKeyTarget(itemsRef, table, allTables)`, reusing `target.idType` for `targetIdType`; anything else with `itemsRef` stays the JSON id column.
   - `toStorage`: a string value on a column with `references?.idType === "integer"` is returned as `typedId("integer", value)`. `fromStorage`: a number on such a column is returned as `String(value)`. (Under the alternative wire form, both lines invert.)
   - The module comment's storage model: a to-one reference is a `<field>_id` column typed like a same-connection target's id with a foreign key, else `text`; a cross-connection to-many is a JSON id list.
2. **`extensions/connector/src/ddl.ts`**
   - `const ON_DELETE = "set null"`.
   - `function orderPlans(plans: TablePlan[]): TablePlan[]`: repeatedly take the first remaining plan (declaration order) whose `references` targets, other than itself and other than tables outside the set, are already placed; when none qualifies (a cycle), take the first remaining.
   - `async function foreignKeys(db, dialect, tables: string[]): Promise<Map<string, Map<string, string>> | null>` (table → column → target table), shaped like `indexNames`: SQLite runs `select "from" as col, "table" as target from pragma_foreign_key_list(${sql.lit(t)})` per existing table; Postgres runs one query over `information_schema.table_constraints` joined to `key_column_usage` and `constraint_column_usage` on `(constraint_schema, constraint_name)`, filtered to `constraint_type = 'FOREIGN KEY'` and `table_schema = current_schema()`. Any failure returns `null`, meaning "unknown": key drift is then not reported.
   - `function sameDataType(have: string, want: string): boolean`: lower-cases both and maps `int4` and `int` to `integer`, `float8` to `double precision`, `bool` to `boolean`.
   - `syncTables`: iterate `orderPlans(plans)`; keep `ready`, seeded with the introspected table names and extended after each create; `const keyInline = (plan, col) => dialect === "sqlite" || col.references!.table === plan.table || ready.has(col.references!.table)`; a keyed column that is not inline is pushed to `deferred`. `buildCreateTable(db, plan, dialect, keyInline)` and the `ADD COLUMN` path pass `(c) => c.references(`${target}.id`).onDelete(ON_DELETE)` for an inline keyed column. After the plan loop, before the orphan scan, each deferred column runs `db.schema.alterTable(t).addForeignKeyConstraint(`${t}_${col}_fkey`, [col], target, ["id"], (cb) => cb.onDelete(ON_DELETE))`.
   - Drift on an existing table: for a to-one reference column (`col.ref && !col.manyRef`), compare `sameDataType` and, when the catalog answered, the foreign-key target (`null` for none) with `col.references?.table ?? null`; any difference is one warning, `` `${t}.${c}: reference column is ${have}${haveKey}; the schema wants ${want}${wantKey} — additive-only sync never alters an existing column` ``, where each key part reads ` referencing "users"` or ` with no foreign key`. Every other column keeps today's type-drift message, now through `sameDataType`.
3. **`extensions/connector/src/dialects/bun-sqlite.ts`**: `init()` runs `db.prepare("pragma foreign_keys = on").run()` after `openDatabase`, for owned and injected databases alike; the module comment says why (the D1 stand-in).
4. **`extensions/connector/src/validate.ts`**: `validateRow`'s options gain `tables?: Record<string, TableDef>`, threaded into `coerceField`. After today's string checks, which still run first (so a JSON number stays an error), when `foreignKeyTarget(ref, table, tables ?? {})?.idType === "integer"`, a to-one value that `typedId("integer", raw)` refuses fails with `"Reference value must be an integer id"`, and a to-many list with such an element fails with `"Reference list must be an array of integer ids"`. Without `tables` the behaviour is today's.
5. **`extensions/connector/src/worker.ts`**
   - `insertRow` and `updateRow` pass `{ tables }` (and `partial` for the patch) to `validateRow`; `handleDataRequest` hands `tables` to both.
   - `expandIncludes`, to-one branch: the guard becomes `spec?.references`; the target plan comes from `spec.references.table`; the `IN` list is the distinct keys mapped through `typedId(target.idType, …)` with refusals dropped (a legacy `text` column may hold anything the old validator took, and Postgres would answer `"abc"` with a cast error); the map is keyed `idKey(t.id)` and read with `idKey(row[spec.column])`. Junction branch: `byId` and the `mine` filter compare through `idKey`. A to-one whose `references` is `null` (content, unknown or cross-connection) is left unexpanded, as content refs are today.
   - `function isForeignKeyViolation(error: unknown): boolean`, one expression over `code` and `message` as decided; the `catch` in `handleDataRequest` returns `fail(400, "A reference names a row that does not exist")` for it, and 500 otherwise.
6. Spec and docs edits, as listed below.
7. In the landing PR: delete this file; remove `relationships/table-foreign-keys` from `requires` in `plans/relationships/cross-domain-references.md` (and in `plans/relationships/reference-validation.md` if its detail added the edge), and reword their paragraphs that say this work is still to come.

**Integration contract.** Once this lands, `@jxsuite/connector/columns` exports `foreignKeyTarget` (the only test for a keyable table → table reference), `idKey` (the only id comparison, under which `1` and `"1"` are equal), `typedId` (the only conversion of an id to its target's kind, `undefined` for a malformed one) and `ColumnSpec.references`. `planTable` gives the same columns to the DDL and the mount. A to-one reference into a same-connection table carries `ON DELETE SET NULL` on every table this sync creates or extends, enforced on D1, Postgres and every database the bun-sqlite dialect opens, so a dangling table → table write is refused by the database (the mount answers 400 without a field name). `validateRow(table, payload, { partial, tables })` refuses a malformed id into an integer-id table as a shape error (`"Reference value must be an integer id"`), so `"abc"` never reaches an existence lookup. `expandIncludes` resolves same-connection to-one and junction includes for both id kinds and leaves every other to-one unexpanded. For `plan:relationships/cross-domain-references`: the node-path `include` and table → content expansion reuse `expandIncludes`'s branches and `idKey`, and §2's marker names only the node path, content includes and the content → table warning. For `plan:relationships/reference-validation`: the table-side check converts with `typedId` and compares with `idKey`, may leave same-connection targets to the key and still owes the field-named 400, content targets and cross-connection targets; it should require this plan.
