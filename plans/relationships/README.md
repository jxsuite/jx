## Dispositioned without a plan

- §2, §4 and §5, unmarked before the census, gained leading Partial markers for what the auditors found and this census confirmed: `expandIncludes` skips content refs and misses a to-one row on an integer-id target, `table-node.ts` drops `include` under node, and `ddl.ts` emits no foreign key (extensions/connector/src/worker.ts, table-node.ts, ddl.ts, columns.ts); the parser ignores `#/data/...` refs and never judges a reference value's shape (extensions/parser/src/content-loader.ts); the `/_jx/data` writes check no referenced row exists (extensions/connector/src/validate.ts, worker.ts); and the studio pickers know only to-one `#/content/` targets (packages/studio/src/ui/form-controls.ts, ui/schema-form.ts, settings/defs-editor.ts, grid/schema-columns.ts, grid/cell-popovers.ts).
- §4's second bullet diverges from the code and from site-architecture.md §6.4, which both treat a dangling content id as a warning that leaves the id in place; the §4 marker states it and the owning stub reconciles the wording.
- §1's `referenceable` scoping: see Verified. Owned under extensions.md §9, not here.
- The whole-spec header stays `Partial`; there is no preamble marker, so it is not an item of its own. No roadmap, status ledger or stale status cell.

## Spec-wide decisions

- The connector's mount receives the raw `sections` config (`DataMountOptions.sections`, extensions/connector/src/worker.ts), filled by `buildRuntime` (packages/server/src/jx-mounts.ts) in the dev server and by `buildMountSpecs` (packages/compiler/src/site/site-build.ts) for a deployed worker, and never the loaded `_project.content`. So table → content `?include=` (§2) and table → content existence on write (§4) both need the same content-entry view at request time. That view is decided once, in `plan:relationships/cross-domain-references`, and `plan:relationships/reference-validation` builds on it rather than loading content a second way. The node path (`TableQuery` and `TableEntry` at server and compiler timing) already carries `_project.content` (packages/server/src/resolve.ts, packages/compiler/src/site/prototype-resolver.ts).
- How a to-one `<field>_id` column is typed against its target's id is decided once, in the enabling `plan:relationships/table-foreign-keys`: it fixes the integer-id include miss (§2), carries the foreign keys (§2), and is the comparison §4's table-side existence check uses. `plan:relationships/cross-domain-references` requires it.
- Studio's reference controls (§5) read the `referenceable` flag the extensions payload already carries (`contributions[].project`, packages/compiler/src/site/format-host.ts), so no payload change is needed. `plan:extensions/referenceable-sections` owns only the registry view of the referenceable sections and the validation that refuses a pointer into a non-referenceable section; `plan:relationships/studio-reference-picker` owns every Studio control change and requires that plan at detail.
