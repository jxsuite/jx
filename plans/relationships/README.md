- §1's `referenceable` scoping: see Verified. Owned under extensions.md §9, not here.
- The whole-spec header stays `Partial`; there is no preamble marker, so it is not an item of its own. No roadmap, status ledger or stale status cell.

## Spec-wide decisions

- **Order.** `plan:relationships/table-foreign-keys` → `plan:relationships/cross-domain-references` → `plan:relationships/reference-validation`, each a hard prerequisite of the next (reference-validation also requires table-foreign-keys directly, for `typedId` and `idKey`). `plan:relationships/studio-reference-picker` requires only `plan:extensions/referenceable-sections` and may land at any point. No cycle.
- **The content view.** The connector's mount receives the raw `sections` config (`DataMountOptions.sections`, extensions/connector/src/worker.ts), filled by `buildRuntime` (packages/server/src/jx-mounts.ts) in the dev server and by `buildMountSpecs` (packages/compiler/src/site/site-build.ts) for a deployed worker, and never the loaded `_project.content`. So table → content `?include=` (§2) and table → content existence on write (§4) both need the same content-entry view at request time. That view (`@jxsuite/schema/reference-view`, handed over as the `references` mount option) is decided once, in `plan:relationships/cross-domain-references`, and `plan:relationships/reference-validation` builds on it rather than loading content a second way, widening only its function form with `{ reload: true }`. The node path (`TableQuery` and `TableEntry` at server and compiler timing) already carries `_project.content` (packages/server/src/resolve.ts, packages/compiler/src/site/prototype-resolver.ts).
- **Id typing and comparison.** How a to-one `<field>_id` column is typed against its target's id is decided once, in the enabling `plan:relationships/table-foreign-keys`: it fixes the integer-id include miss (§2), carries the foreign keys (§2), and its `typedId` and `idKey` (extensions/connector/src/columns.ts) are the only id conversion and comparison the other two connector plans use. Its first Open decision, the wire form of an id into an integer-id table (recommended: the decimal string), owns §1's "Stored values" sentence; §4's first bullet (`plan:relationships/reference-validation`) and Studio's pickers (strings in, a numeric id read as its string) follow whatever it decides.
- **Cross-connection references.** Whether a reference into another connection's table is keyed, expanded or a junction is `plan:relationships/table-foreign-keys`' question (recommended: stored as an id, never expanded, a to-many being a JSON id list). `plan:relationships/cross-domain-references` owns §2's `include` paths, so a different answer is implemented there; its §2 cells say "on the same connection". The per-connection rule lives in `foreignKeyTarget` and, because `packages/server` may not import the connector, once more in `plan:relationships/studio-reference-picker`'s `declaredReferenceColumns`.
- **One pointer grammar.** `plan:extensions/referenceable-sections` exports it as `RELATIONSHIP_SECTION_KEY_PATTERN` and `RELATIONSHIP_ENTRY_NAME_PATTERN` (`@jxsuite/schema/defs`) and builds `relationshipRefSchema`'s pattern from them; `parseRelationshipPointer` (`plan:relationships/cross-domain-references`) reads that pattern for the connector and the parser, and Studio's `referenceOf` (`plan:relationships/studio-reference-picker`) builds its regex from the constants. No plan hand-copies the regex.
- **Referenceable sections in Studio.** Studio's reference controls (§5) read the `referenceable` flag the extensions payload already carries (`contributions[].project`, packages/compiler/src/site/format-host.ts), so no payload change is needed. `plan:extensions/referenceable-sections` owns only the registry view of the referenceable sections and the entry-schema constraint that refuses a pointer into a non-referenceable section; `plan:relationships/studio-reference-picker` owns every Studio control change and requires that plan. The connector and the parser do not consult the flag (`plan:relationships/cross-domain-references` qualifies a view target by shape; `plan:relationships/reference-validation` checks only `data` and `content` targets).
- **Who writes which spec text.** §1: "Stored values" is `plan:relationships/table-foreign-keys`'; the entry-schema sentence is `plan:extensions/referenceable-sections`'. §2: table-foreign-keys shortens the marker, rewrites the table → table Storage cell and adds the first paragraph after the matrix; `plan:relationships/cross-domain-references` flips the marker, owns every Resolution cell and the content → table row, and adds its paragraph after the prerequisite's. §3's lead ("on the same connection") is table-foreign-keys'. §4 is `plan:relationships/reference-validation`'s alone, §5 `plan:relationships/studio-reference-picker`'s alone.
- **Shared docs pages.** `docs/studio/data/tables.md`: the reference paragraph's picker clause is studio-reference-picker's, its storage and `include` clause cross-domain-references', the doc-note's sentence on what a to-one and a to-many reference become table-foreign-keys', and its last sentence (on the Target picker, deleted) studio-reference-picker's. `docs/studio/data/grid.md`: reference-validation's no-check sentence closes the save paragraph and is worded to hold with or without the pickers; studio-reference-picker's reference-cell paragraph follows it. `docs/framework/site/relationships.md`, "Beyond content": insertions land in plan order, reference-validation's last.
- **Graduation.** `plan:relationships/cross-domain-references` never graduates the spec (§4 is still open when it lands). Whichever of `plan:relationships/reference-validation` and `plan:relationships/studio-reference-picker` (its SRP1.4) lands second closes the last open item: it sets `**Status:** Implemented`, runs `bun run spec:bump relationships.md minor -m "…"` in place of its fragment, and deletes `plans/relationships/`.
