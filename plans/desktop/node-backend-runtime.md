# The packaged backend runs on Electron's Node, and every Studio installs packages with Arborist

## Context

App Review rejected the Mac App Store build `6.1.0 (443)` with two automated findings:

1. **Non-public API use, 129 symbols** (`_ubrk_*`, `_ucal_*`, `_ucol_*`, `_udat_*`, `_unum*`, `_ures_*` and others). Every one is an undefined import of the pinned Bun binary (`resources/bun/bun`) from `/usr/lib/libicucore.A.dylib`: `nm -u` finds them there and in no other Mach-O in the package. JavaScriptCore links the system ICU on Apple platforms, so every macOS Bun build imports it. A version bump cannot fix this; only removing Bun from the package can.
2. **`com.apple.security.network.server` without matching functionality.** The entitlement is needed: each window's backend server listens on loopback (desktop.md §9.7). This is a reply to App Review, not a code change, and the same reply goes in the App Review Information notes.

`specs/desktop.md` §7.1 states why the backend is Bun ("The backend's module graph is Bun-native throughout") and §7.4 ships the binary in `resources/bun`. The graph is less Bun-native than that sentence says. The metafile of a `Bun.build` of `src/hub/main.ts` with `BACKEND_EXTERNALS` reaches 28 first-party files that use Bun: 12 APIs and about 100 call sites, measured on 2026-10-27 against `a410caf4`:

| API                       | Uses | Where                                                                                                                                                                         |
| ------------------------- | ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Bun.serve` + WebSocket   | 17   | `server/src/project-server.ts`, `collab.ts`, `site-preview.ts`, `live-preview.ts`, `oauth-loopback.ts`, `desktop/src/github-signin.ts`, `import/src/{verify,pipeline,run}.ts` |
| `Bun.Glob`                | 16   | `server/src/studio-api.ts`, `refactor/scan.ts`, `live-preview.ts`, `desktop/src/project-session.ts`                                                                           |
| `Bun.build`               | 14   | `compiler/src/site/bundler.ts` (already has an esbuild branch), `server/src/build.ts`, `project-server.ts`, `live-preview.ts`                                                 |
| `Bun.file` / `Bun.write`  | 17   | `studio-api.ts`, `net-guard.ts`, `project-session.ts`, `code-api.ts`, `import/src/{io,run,verify}.ts`                                                                         |
| `Bun.spawn` / `Bun.which` | 15   | `studio-api.ts` (git, `bun add`/`remove`), `server/src/packages.ts`, `desktop/src/git.ts`, `chromium/shell-command.ts`, `import/browser-local.ts`                             |
| the rest                  | 11   | `import.meta.dir` ×5, `Bun.resolveSync` ×3, `Bun.Transpiler` ×2 (`code-api.ts` minify), `Bun.hash` ×1 (`site-build.ts`)                                                       |

The server surface those `Bun.serve` calls rely on is small: a Fetch-API `fetch(req, server)` handler, `port`, `url`, `stop()`, `idleTimeout`, `upgrade(req, { data })`, and a socket's `send`, `close` and `data`. No `publish`/`subscribe`, no `routes`.

Bun also does a second job in the shipped application: it is the **package manager**. `server/src/packages.ts` runs `bun install`, `bun add [-d]` and `bun remove` as children (`process.execPath`), and `studio-api.ts` does the same for the dev server's `/__studio/packages*` routes. The registry lookups (`fetchLatestVersion`) are plain `fetch` already.

Electron 43.7.7, the pinned `electronVersion`, embeds Node 24.21.0 with its own ICU (78.2, symbols internal to Electron Framework), and has `fs.promises.glob`, `import.meta.dirname` and the Fetch globals. Bun implements the same `node:` APIs, so most of the port is a move to APIs both runtimes share.

## Outcome

- The packaged application, in every channel (DMG, Mac App Store, NSIS, appx, AppImage, snap, Nix), runs its backend on the Node inside Electron. `resources/bun` and `bun-runtime.json` are gone.
- Studio's package operations (install, add, remove, set versions) run `@npmcli/arborist` in-process against the public npm registry. Registry metadata stays the plain `fetch` it is today. No package manager binary ships.
- Bun stays the monorepo's tool: `bun install`, `bun test --isolate`, the build scripts and `jx dev`'s dev server (`createDevServer`, server.md §2).
- The per-window development launcher (`bun run chromium`, `src/chromium/index.ts`) is deleted. The Electron shell is the only desktop host, in development and in every channel.
- Cloud Studio runs the same package operations. The platform's `ProjectSession` sends the manifest and lockfile to a Cloudflare container that runs this plan's Arborist code in lockfile-only mode, and writes the result back into the shared working tree. Cloud's add, remove and set versions stop being manifest-only edits that leave the lockfile stale, and a cloud commit carries a lockfile Pages CI can install from frozen.
- A Mac App Store build passes the automated review and `plan:desktop/mac-app-store` can close desktop.md §7.7.

This plan claims nothing. It is the enabling plan for `plan:desktop/mac-app-store`, which owns §7.7 and requires it. It rewrites what §7.1, §7.4, §7.6, §9.3 and §9.7 say about the runtime, and server.md's statements about `project-server.ts`, `code-api.ts` and `packages.ts`.

## Decisions

- **Decided:** every channel moves, not only the Mac App Store. A Node backend in one channel and a Bun backend in the others would be two programs from one source, each needing its own smoke test, and the other channels gain from it too (27 MB less per installer, one runtime to patch, one less binary to sign).
- **Decided:** the backend is started with Electron's `utilityProcess.fork()`, not `child_process.spawn` of a Bun. It runs as an Electron helper, so it is signed with `entitlements.mas.inherit.plist` and inherits the sandbox and the folder grants exactly as the Bun child does now, and the restart-after-grant logic of §7.7 is unchanged. The protocol of §9.7 is unchanged; only its transport changes, from `process.send` to `process.parentPort` on the backend side. `scripts/run-electron-app.ts` forks the backend the same way, so `hub/main.ts` keeps the `process.send` branch only if that script still needs it once NB1.4 lands, and the slice decides which.
- **Decided:** the `bun run chromium` launcher is deleted rather than ported. It is a second host for the same hub (one process per window, the hub's handlers bound to module globals) that no channel ships, and keeping it would mean keeping a Bun path through `hub/main.ts` and the legacy handler surface for it alone. What it shares with the Electron shell stays and moves out of `src/chromium/`: the webview adapter (`platform.ts`, `init.ts`) that every Electron window loads, and `app-id.ts`, `app-info.ts`, `shell-command.ts` and `window-registry.ts`, which `hub/` and `electron-shell/` import.
- **Decided:** runtime-specific code is selected at **resolution time** through package `exports` conditions (`"bun"` then `"default"`), not by `typeof Bun` at run time. The Node bundle then contains no Bun code at all, which is what makes the gate below a plain text check rather than a judgement. This follows Node's conditional exports and the WinterCG runtime keys.
- **Decided:** primitives move to APIs both runtimes implement, and only the server needs two implementations. `Bun.Glob` → `fs.promises.glob`; `Bun.file`/`Bun.write` → `node:fs/promises` with the media type from `@jxsuite/schema/media-type`; `Bun.spawn` → `node:child_process`; `Bun.which` → a small `which()` in `@jxsuite/schema` (or the `which` package); `Bun.hash` → `node:crypto`; `import.meta.dir` → `import.meta.dirname`; `Bun.resolveSync` → `createRequire(...).resolve` (the compiler's fallback already); `Bun.Transpiler` minify → `esbuild.transform` (esbuild is already a compiler dependency). Each replacement lands with a parity test that runs under `bun test` and compares the new answer to Bun's own on the same input (glob results, media types), because "Bun gave the same answer" is the property being preserved.
- **Decided:** all bundling in the backend goes through the compiler's existing bundler abstraction (`compiler/src/site/bundler.ts`), whose esbuild branch is already the Node path (compiler.md's "Backends"). `server/src/build.ts`, `project-server.ts` and `live-preview.ts` stop calling `Bun.build` directly.
- **Decided:** Arborist runs with `ignoreScripts: true`. Lifecycle scripts would run arbitrary code from the registry inside the sandbox with the user's folder grants, and neither `esbuild` nor `sharp` (the native packages a Jx project pulls in through `@jxsuite/compiler`) needs one: both ship their binary in a platform `optionalDependencies` package. Its cache is the user-data directory (`npm-cache`), which the sandbox maps into the container.
- **Decided:** Arborist, not npm's command-line package run as a child. npm is Arborist plus config loading, `ci`, `audit` and log formatting, and none of those is worth about 10 MB, a second process and a dependency on Electron's `RunAsNode` fuse staying enabled. `pacote` is not a direct dependency: Arborist uses it internally, and `fetchLatestVersion` already reads the registry with `fetch` (its comment records why it asks for `application/json` rather than the abbreviated format).
- **Decided:** no `.npmrc` in this plan. Arborist runs with `registry: "https://registry.npmjs.org/"` and no auth, the same registry `fetchLatestVersion` already names. A project that depends on a private scope, GitHub Packages or a mirror cannot install from Studio, and the operation fails with an error naming the package, the registry and the status (`401`, `403`, `404`) instead of Arborist's raw log alone. Deployment secrets belong to the deployment platform, and the install-time case is rare for a starter-based project. Supporting it later is additive: `@npmcli/config` loads the same options npm passes Arborist, so it needs no change of tool.
- **Decided:** Arborist runs strict, and nothing is relaxed to make an install pass. No `force`, no `legacyPeerDeps`: a peer conflict (`ERESOLVE`) fails the operation and reports the conflict. `addPackage` accepts only a registry spec (a name, optionally with a version, range or tag), checked with `npm-package-arg` before Arborist runs; a git, file, URL or `workspace:` spec already in `package.json` fails the install with Arborist's `EUNSUPPORTEDPROTOCOL` (or git's absence in the sandbox) reported by name. The lockfile is `lockfileVersion: 3`.
- **Decided:** every operation is all-or-nothing on the manifest and the lockfile. A failed operation leaves `package.json` and `package-lock.json` byte-identical to before it ran. Arborist saves both only after a successful reify, which covers add, remove and install. `setPackageVersions` writes `package.json` first and then installs today, so a failed install leaves the new ranges behind; it moves to the same rule, by passing the new specs to `reify({ add })` or restoring the manifest on failure, whichever the tests prove.
- **Decided:** operations on one project root are serialized by a per-root queue in `packages.ts`. Two Arborist reifies in one `node_modules` race on the same files, and Studio can start one from the Packages panel while install-on-open or pull sync is running.
- **Decided:** Arborist and its dependency tree are staged as real files beside the bundle, not inlined into it. Arborist and its dependencies resolve files at run time (`@npmcli/run-script` finds `node-gyp` by `require.resolve`, `@npmcli/git` spawns `git`), which a bundler cannot see. `scripts/stage-app.ts` adds it to the backend's externals and copies its production closure, as it does for `BACKEND_MODULES`, and the smoke test's add and remove are the proof.
- **Decided:** cloud package operations run the **same Arborist code** as desktop, in a Cloudflare container, not npm's command-line package and not a reimplementation in the Worker. One implementation means one set of strictness rules, error texts and tests, and a lockfile cloud writes is byte-for-byte the one desktop would write. A Worker cannot host it (no `child_process`, no persistent filesystem, 128 MB), and a Worker-side resolver would have to match npm's hoisting exactly or `npm ci` rejects the lock.
- **Decided:** the container runs Arborist with `packageLockOnly: true`. It reads registry metadata and writes `package.json` and `package-lock.json`; it never downloads a tarball or builds a `node_modules`, so no package code reaches it and the platform's rule that no project code runs (its README's security posture) still holds. Combined with `ignoreScripts`, nothing from the registry executes. It is also fast: an operation costs the metadata requests and nothing else.
- **Decided:** the container is a plain Cloudflare Container (`@cloudflare/containers`) serving one fixed HTTP endpoint, not the Sandbox SDK. Sandbox exists to run arbitrary commands, and this needs exactly one function with a typed request and reply. The request is `{ op, args, files }` (`files` holds `package.json` and, when present, `package-lock.json` and `bun.lock`); the reply is `{ result: PackageOpResult, files, deleted }`. The service is stateless: it writes the files into a fresh temporary directory, runs the operation, reads the two files back and deletes the directory. Being stateless, instances are a small shared pool picked per request, not one per project, with a short `sleepAfter`.
- **Decided:** the service is published from this repository and the platform only deploys it. `@jxsuite/server` gains a `packages-service` entry and bin (a `node:http` handler over `packages.ts`), so the code under test here is the code in the image. The platform's Dockerfile installs a pinned `@jxsuite/server` on a Node 24 image and runs the bin. Release order: this repository publishes first, then the platform bumps the pin.
- **Decided:** the platform's `ProjectSession` owns the operation, not the Worker or the browser. It is already the one place per (repository, branch) that every collaborator's write passes through, so it serializes operations for a project for free (the per-root queue of desktop, with the same guarantee). It reads the files from the working tree, calls the container, and on success writes `package.json` and `package-lock.json` (and deletes `bun.lock`) through the same path as a file save, in one change, so open collaboration rooms and the dirty state see it like any other edit. On failure it writes nothing. Writes need write permission, gated like every other tree mutation.
- **Decided:** cloud implements `addPackage`, `removePackage`, `setPackageVersions` and `packageVersions`, and still omits `installDependencies` and `dependenciesNeedInstall`. There is no `node_modules` in a cloud session to be missing or reinstalled; every mutation brings the lockfile in step as a side effect. `packageVersions` is the existing `fetchLatestVersion` run in the Worker, with no container. The current adapter's `addPackage` writes the literal range `latest` into `package.json`; Arborist saves `^<resolved>` instead, as desktop does.
- **Decided:** no silent fallback. When the container cannot be reached (including `wrangler dev` without Docker), the operation fails with an error saying so and the manifest is untouched. A manifest-only edit behind the user's back would recreate the stale lockfile this decision exists to remove.
- **Decided:** the `jx dev` dev server stays Bun-only. It is contributor and CLI tooling (server.md §2, "spawns it under Bun"), so `createDevServer` keeps returning the `Bun.serve` object and server.md's contract for it does not change. Only the modules the desktop backend reaches become neutral.
- **Decided:** the Node server is our own `serve()` over `node:http` and the `ws` package, exposing exactly the surface listed in Context, with `Bun.serve` behind the `"bun"` condition. `srvx` with `crossws` was the alternative: maintained and good at streaming bodies, but its WebSocket hooks are a different shape from `upgrade(req, { data })`, so every call site would change instead of one module. Owning the Node side means owning the request conversion and response streaming, which the tests below hold.
- **Decided:** Studio's projects move to `package-lock.json`. Arborist reads and writes it, and on the first install in a project that has a `bun.lock` and no `package-lock.json`, Studio writes `package-lock.json` and deletes `bun.lock`, saying so in the operation's log. One lockfile is the only state in which Studio and a command-line install cannot disagree. Keeping both was refused because they drift; installing without a lockfile was refused because it is not reproducible. No starter or template commits a lockfile, so this reaches only projects an earlier Studio installed with Bun, and a user who runs `bun install` afterwards gets Bun's own migration from `package-lock.json`.
- **Decided:** the dev server's `/__studio/packages*` routes move to Arborist as well, because `server/src/packages.ts` exists so that both backends behave identically and one implementation is one thing to test. The cost is that a contributor iterating a starter in browser Studio gets Arborist's installs there, so the slice re-checks the shadowed-core cleanup (root AGENTS.md, "Starter Roots and the Shadowed Core"), which removes `node_modules/@jxsuite/*` and the stray lockfile from starter roots and must now treat `package-lock.json` as that lockfile.

## Implementation

**NB1.7 Drop the Chromium launcher.** Lands first, so no later slice ports code that is about to go. Delete `src/chromium/index.ts` and `utils.ts`, the `chromium` script in `packages/desktop/package.json` and `desktop:chromium` at the root, and their tests (`chromium-index`, `chromium-utils-*`). Delete the legacy handler surface it was kept for (`src/handlers.ts` and the module-global delegates in `project-session.ts` and `git.ts`), moving the tests that import `../src/handlers` (`packages`, `git`, `content-collection`, `handlers-gaps`, `_rpc-server`, `_studio-schema`) onto `hub/handlers.ts`. Move the shared modules out of `src/chromium/` (the webview adapter to `src/webview/`, the rest beside their importers in `hub/` or `electron-shell/`) and update `pre-build-rpc.ts`, the `check-coverage-manifest.ts` shim allowlist and `scripts/screenshots/lib/browser.ts`'s comment. `bun run docs:sync` names the pages and spec sections that describe the launcher.

**NB1.1 Neutral primitives.** Replace the Bun primitives listed in Decisions across `server/src`, `import/src`, `compiler/src/site` and `desktop/src` with the shared `node:` APIs. `Bun.file`'s type inference is replaced by `@jxsuite/schema/media-type`'s table, extended until a parity test over every extension the routes serve agrees with `Bun.file(...).type`. Nothing changes behaviour under Bun, so this slice is safe to land alone.

**NB1.2 The server seam.** Add `serve()` (and the socket type replacing `ServerWebSocket`) to `@jxsuite/server` behind an `exports` entry with a `"bun"` condition (`serve.bun.ts`, a pass-through to `Bun.serve`) and a default (`serve.node.ts`). Move `project-server.ts`, `collab.ts`, `site-preview.ts`, `live-preview.ts`, `oauth-loopback.ts`, `github-signin.ts` and the import package's three servers onto it. The Node implementation must stream response bodies (SSE heartbeats and AI streams depend on it, which is why `idleTimeout: 120` exists) and honour `idleTimeout` on the socket. Route `Bun.build` calls in `server/src` through `@jxsuite/compiler`'s bundler.

**NB1.3 Packages through Arborist.** Reimplement `installDependencies`, `addPackage`, `removePackage` and `setPackageVersions` in `server/src/packages.ts` over `@npmcli/arborist` (`reify()`, `reify({ add, saveType })`, `reify({ rm })`) with the options in Decisions, behind the per-root queue. `fetchLatestVersion` and `packageVersions` are unchanged. `PackageOpResult.log` carries Arborist's log output, led by the error summary the Decisions name for a refused registry request or a peer conflict. The first install in a project with `bun.lock` and no `package-lock.json` deletes `bun.lock` after a successful reify, never before. `studio-api.ts`'s `/__studio/packages*` routes call the same functions instead of spawning `bun`, and `scripts/check-shadowed-core.ts` treats a starter root's `package-lock.json` as the stray lockfile it removes. `bunExecutable()` is deleted. Add `@npmcli/arborist` and `npm-package-arg` as `@jxsuite/server` dependencies.

The user-visible strings and comments that name Bun as the installer move with it: `ensure-deps.ts` and `pull-package-sync.ts` ("Running bun install…" and the `"bun install failed"` fallbacks become "Installing dependencies…" and "Install failed"), `desktop/src/packages.ts`'s `"bun add failed"`/`"bun remove failed"`, the `PackageOpResult` and `PackageInfo` comments in `@jxsuite/protocol`, and the `installDependencies`/`setPackageVersions` comments on `StudioPlatform`.

**NB1.4 The application.** `scripts/stage-app.ts` bundles `hub/main.ts` for `target: "node"` with the default conditions. Native packages the backend reaches by `import()` (`esbuild`'s platform binary, `sharp` and its `@img/*` libvips, `oxfmt`'s binding) are staged as real files beside the bundle, like `BACKEND_MODULES`, because the packaged app of `6.1.0` carries no `.node` file at all and what that means for formatting and image optimization today is unmeasured: measure it first, with the smoke test. `electron-shell/backend-process.ts` forks with `utilityProcess`; `layout.ts` loses `bun`; `bun-runtime.json`, its test and the download step of the release lanes are deleted. `package.nix` and the snap stop carrying a Bun for the backend. `bun run smoke` starts the staged backend under Node 24 (the major of Electron's Node, from `setup-node` in the pull-request job) and, in each release lane, under the packaged Electron with `ELECTRON_RUN_AS_NODE=1`.

**NB1.5 The gates.** A desktop test bundles `hub/main.ts` exactly as staging does and fails if the output contains `Bun.` or an import of `bun`/`bun:*`. It derives the file set from the metafile, so a new Bun call anywhere the backend reaches fails in the pull request that adds it. `mas-publish.yml` gains a step before the upload: `nm -u` over every Mach-O in the `.app`, failing on any symbol imported from `libicucore` and printing the binary that imports it. This is the check App Review ran, run first.

**NB1.8 Cloud package operations.** In this repository: `packages.ts` takes a `lockfileOnly` option that passes `packageLockOnly: true` to every reify, and `packages-service.ts` (entry and bin in `@jxsuite/server`) serves the request and reply in Decisions, refusing any `op` outside add, remove and set versions and any file outside the three names. `cloud.ts` replaces its manifest-only `addPackage`/`removePackage` with calls to new session routes, adds `setPackageVersions` and `packageVersions`, and drops `dependencyBlock`'s write path; `@jxsuite/protocol`'s route table updates the degradation notes for `packages/add`, `packages/remove`, `packages/versions` and `packages/set-versions`. Release `@jxsuite/server` and `@jxsuite/studio`.

In the platform repository, once those are published: the Dockerfile and the container class with its binding and migration in both wrangler environments; `ProjectSession` routes for the three mutations, calling the container and writing back as Decisions describe; a Worker route for `packages/versions`; the gateway's read-only path set leaves all three mutations out; the README's security posture names the container and why it is not project code; and the platform's own tests mock the container binding. Re-vendor the Studio bundle (`bun run build:assets`).

**NB1.6 Resubmit.** Reply to the network.server finding (the backend's per-window servers listen on loopback for the Studio window and its canvas iframe), add the same text to App Review Information, upload through the lane, test from TestFlight (pick, edit, save, relaunch, Recent, add a package), and submit. This slice belongs to `plan:desktop/mac-app-store` and is listed so the order is visible.

Integration contract for `plan:desktop/mac-app-store`: once this lands, nothing in `Resources/` imports `libicucore`, the backend is an Electron utility process that inherits the main process's sandbox and grants, and package operations need only `network.client`.

## Tests

- **Parity tests, under `bun test --isolate`:** glob, media type and minify against Bun's answers (NB1.1); the Node `serve()` driven by `fetch` and a WebSocket client, imported directly from `serve.node.ts` so `bun test` covers it (`node:http` runs under Bun), including a streamed SSE body and an upgrade carrying `data` (NB1.2).
- **Arborist against a local registry fixture:** `tests/packages.test.ts` gains cases over a temporary project with a tarball registry served from a fixture, so nothing reaches npm: add, add `-d`, remove, set versions, the `bun.lock` switch (deleted only after a successful install, kept when the install fails), and that `ignoreScripts` holds (a fixture package whose `postinstall` writes a marker file must not write it).
- **Arborist strictness, same fixture:** a registry answering `401` and `404` fails with the package, the registry and the status in the log; two fixture packages with conflicting peer ranges fail with `ERESOLVE` and install nothing; `addPackage` refuses a git, file and `workspace:` spec before Arborist runs; every failing case, `setPackageVersions` included, leaves `package.json` and `package-lock.json` byte-identical; two operations started together on one root run one after the other (the second sees the first's lockfile); the written lockfile is `lockfileVersion: 3`.
- **Lockfile-only and the service, same fixture:** with `lockfileOnly`, add, remove and set versions write `package.json` and `package-lock.json`, create no `node_modules`, and request no tarball from the fixture registry (the fixture fails the test if one is asked for). `packages-service` is driven over HTTP: each op returns the files Arborist wrote and `deleted: ["bun.lock"]` on the switch, a refused op or file name answers `400`, a failed op returns the original files untouched, and no temporary directory survives a request, failed or not.
- **Cloud adapter:** `cloud.ts`'s package members call the session routes with the right bodies, surface the service's `PackageOpResult.log` as the error, and never write `package.json` themselves.
- **The smoke test under Node** is the proof that the bundle is a Node program. Extend it to add and remove a package through the RPC, since that is new code reached only in the bundle.
- **The Bun-free bundle test** and the Mach-O scan of NB1.5.
- Coverage: `packages/server`, `packages/desktop` and `packages/import` keep their thresholds; new files ship with tests, and the manifest check holds them. `serve.bun.ts` is a pass-through tested through the routes that already use it.

## Acceptance

- `nm -u` over every Mach-O in a Mac App Store build finds no `libicucore` import, and the lane's step proves it on every upload.
- `bun run smoke` passes under Node 24 on all three lanes, including a package add and remove.
- The Bun-free bundle test passes, and fails when a `Bun.` call is added to any file the backend reaches.
- A TestFlight build opens a picked project, edits and saves it, adds a package, and reopens from Recent after a relaunch.
- App Review accepts the build past the automated stage.
