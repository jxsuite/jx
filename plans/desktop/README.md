## Spec-wide decisions

- §6's Active set is built once. `extractReferences` and the active/global partition belong to `plan:desktop/component-scope-sections`; single-file mode (§4.3, §6.1) renders that same set as its flat list rather than deriving its own. `plan:desktop/single-file-mode` requires it, fills the registry from the file's own `$ref`s, and owns the one palette change it makes: in single file mode `componentSections` draws the Active section alone, so an unsaved edit that drops a reference never surfaces the component under Global.
- The palette's scoping has one owner per half (decided at detail). studio.md §5.4 is claimed by `plan:_shared/component-discovery`, which states discovery (what the palette can list, site-architecture.md §10.3) and, per its second Open's recommendation, defers sectioning to desktop.md §6.2–§6.5. `plan:desktop/component-scope-sections` requires it, because §5.4's marker cites the `componentViews` that plan removes, and writes the sectioning here. If that Open resolves the other way, `plan:desktop/component-scope-sections` moves to `plans/_shared/` and is redrafted before it can be `ready`.
- Editorial drift in sections whose status holds (stale paths, counts and names, with no marker to carry them) is owned by `plan:desktop/app-structure-tree` as riders, so that it survives this record's deletion at graduation.
- §7.4's source tree lists files by kind: the launcher's entry, windowing, session, RPC, adapter, boot and build files whose role desktop.md states (`plan:desktop/app-structure-tree`). Of the other plans, `plan:desktop/packaged-window-boot-ci` (`src/boot-probe.ts`) and `plan:_shared/desktop-code-services` (`scripts/code-tools.ts`, and the staged tools in the packaged tree) add lines, whichever of each pair lands second; a store, GitHub or utility module gets none, so `plan:desktop/settings-patch-cross-process-lock` and `plan:desktop/github-token-stays-in-launcher` add nothing to it.
- The only `requires` edges are `plan:desktop/single-file-mode` → `plan:desktop/component-scope-sections` → `plan:_shared/component-discovery`. Every other overlap is a shared file or paragraph, and the plan here says what to do in either landing order: desktop.md §3.1 (the lock's marker and paragraph, the riders' count and extras, single file mode's table rows), the launcher's handler maps, `rpc-schema.ts` and `src/index.ts` (the GitHub request, the boot probe, single file mode), `cloud.ts`'s header (`plan:desktop/cloud-storage-mapping` and `plan:imports/cem-discovery-on-every-backend`), `panel-elements.json` (`plan:ui/surface-classes-to-parts`), and the welcome screen's Start list (`plan:studio-ui-guidelines/git-panel-action-list` owns its shape). `plan:desktop/github-token-stays-in-launcher` → `plan:studio-ui-guidelines/git-panel-action-list`, proposed by the cross-spec review, is not drawn: the first rewrites the inside of `createGithubRepository`, the second only how the panel reaches it, and each keeps what the other relies on.
- No plan graduates desktop.md unconditionally. It has thirteen open items across nine plans (these eight and `plan:_shared/desktop-code-services`, which owns §5.3). Whichever pull request closes the last one (check `bun run plans:status --spec desktop` there) sets the header to Implemented, runs `bun run spec:bump desktop.md <level> -m "…"` in place instead of writing its fragment (patch, or minor when it rides on an execution, per plans/README.md), and deletes this directory; each plan's "does not graduate" sentence holds only while another item is open.
