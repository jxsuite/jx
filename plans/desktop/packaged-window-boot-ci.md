# CI boots a packaged Jx Studio window on Linux, macOS and Windows and fails unless the desktop adapter registers and Studio runs on it

## Context

`specs/desktop.md` §3.3:

> **Status: Partial.** Registration and all three rules below ship: `registerPlatform` in `packages/studio/src/platform.ts`, the launcher signal in `packages/desktop/src/boot.ts`, the build's refusal in `packages/desktop/scripts/pre-build-rpc.ts`, and `resolveDefaultPlatform` with `PlatformUnavailableError` in `packages/studio/src/platforms/default-platform.ts`. The packaged BACKEND is started and exercised in CI (`bun run smoke`, §7.2), but nothing boots a packaged WINDOW on any OS to observe the desktop adapter register.

The section's last paragraph says the same: what holds the rules without a window is the build refusal, the resolver's unit tests, each shim's tests, the end-to-end test, and now the staged-backend smoke. This is the retired §11 roadmap row. Desktop 5.0.0 through 5.1.3 shipped an `init.js` that threw on import, and every check that holds the line is static, runs in happy-dom, or starts the backend alone. The next failure of a kind nobody has written a rule for, in the part between the page and the backend, still reaches a release.

**What exists**

- The boot sequence. `src/chromium/init.ts` imports `../boot` first (`announceLauncher()` publishes `globalThis.__jxLauncher`, `watchBootErrors` records the first page error), then `bootLauncher({ create: createDesktopPlatform, … })` constructs the one adapter (`src/chromium/platform.ts`, a WebSocket RPC to the window's own server), calls `registerPlatform` synchronously, then asks `platform.githubAuth.status()`, i.e. the `githubToken` request. The Electron application and the development launcher both serve this same bundle, so there is one boot to observe.
- Studio's entry (`packages/studio/src/studio.ts`) refuses the fallback at the gate and otherwise, at module level and unconditionally, calls `platform.activate()` (a no-op on this adapter) and `void hydrateSettings()`, which calls `platform.getSettings()` (`services/settings/kernel.ts`). The adapter answers `getSettings` over its transport.
- The Bun side of each window. In the Electron application `buildWindowHandlers(window, hub)` in `src/hub/handlers.ts` returns the one RPC map for a window, which `src/hub/window-hub.ts` hands to that window's `createProjectServer`; in the development launcher, `defaultSession.handlers` in `src/chromium/index.ts` is the exported map its project server dispatches into. `src/hub/backend.ts` `startBackend({ env, onMessage, send })` is the backend's composition root and receives the process environment.
- The Electron shell: `src/electron-shell/app.ts` takes the single-instance lock, spawns the backend under the Bun in `resources/bun`, and opens a `BrowserWindow` per `open-window` message; the backend's `quit` message (`hub/protocol.ts`) ends the application. A packaged application is `bun run --cwd packages/desktop package --target <os> --arch <arch> -- --dir`, which leaves an unpacked tree under `packages/desktop/artifacts/` that is directly runnable and needs no signing identity.
- CI. `bundle-desktop-{linux,macos,windows}.yml` are `workflow_call` from `release-please.yml`, run after the tag exists, build with `bun run --cwd packages/desktop package … -- --publish never`, run `bun run smoke` against the staged backend, and launch no window. The `desktop-bundle` job in test.yml stages and smokes the backend on every pull request that reaches `packages/desktop`. test.yml already has a release-PR-only job: `nix`, `if: startsWith(github.head_ref, 'release-please--')`, required through `ci`. `scripts/desktop-build-lanes.test.ts` holds the lane files to the build pipeline's shape, and `scripts/ci/affected.test.ts` pins `ci`'s `needs:` line verbatim.
- Tests: `packages/desktop/tests/boot.test.ts`, `chromium-init-shim.test.ts`, `electron-app.test.ts`, `electron-shell-bundle.test.ts`, `hub-backend.test.ts`, `hub-handlers.test.ts`, `hub-window-hub.test.ts`, `chromium-index.test.ts`; `packages/studio/tests/studio-boot-refusal.test.ts`.

**What is missing**: a launched packaged window anywhere in CI, a way to read its boot outcome out of a process CI does not control, and a decision on which pipeline stage runs it.

## Outcome

With the recommendations below taken:

- desktop.md §3.3 → Implemented: the release pull request packages the Electron application (unpacked, unsigned) on Linux x64, macOS arm64 and Windows x64, launches it, and fails `ci` unless the window's adapter registered and Studio's entry called it; the development chromium launcher gets the same check on Linux.
- Any pull request can opt in with the `desktop-boot` label, and `desktop-boot.yml` can be dispatched on `main`.
- `JX_STUDIO_BOOT_PROBE` is a stated launcher contract, usable locally and in support.

## Decisions

- **Open:** where the check runs. Recommendation: on the **release pull request** (a `desktop-boot` job in test.yml, same gate as `nix`, required through `ci`), plus any pull request labelled `desktop-boot`; the release lanes gain no boot step. Because: the release PR is the last point before the tag, so a red boot stops the release rather than shipping a release with missing installers; gating on a diff would fire on nearly every PR (desktop's dependency closure is almost the whole graph, and Studio's entry is in scope) at three OS runners each, which is the trade `.github/AGENTS.md` already refused for Nix; and a step inside a release-only lane is first executed at a release and can only act after the tag. The price: the signed and notarized artifact is not what gets booted. Alternative if a maintainer wants the shipped bytes covered too: add the same probe step to each `bundle-desktop-*` lane after its smoke step and before "Attach to release", launching the unpacked tree electron-builder leaves beside the installers, and change that step's `if: !cancelled()` to require the boot step's success; it composes with this plan and changes nothing below. It is cheaper than it was, because those lanes now build the same unpacked tree this job needs.
- **Open:** whether the development chromium launcher (§9.2) gets the check. Recommendation: yes, on the Linux leg, launched from the source tree (`pre-build-rpc.ts`, then `bun src/chromium/index.ts` with `CHROMIUM_BIN` set to the runner's Chrome), because that is what a checkout runs, and what a machine with no Electron falls back to, its init shim has the same import-time failure shape, the probe seam is shared, and it costs one step on a runner that already has a display.
- **Decided:** the oracle is the request log the Bun side records, and it settles on `getSettings`, because that one name proves both halves: any request at all means the adapter was constructed and its transport answers (a bundle that throws on import, or an adapter that cannot connect, sends nothing), and `getSettings` comes only from Studio's own entry, after its platform gate, on whatever adapter is registered, so it means Studio is running on the launcher's adapter and not refusing. It is not Studio's first request (the recent-projects hydration precedes it) but its last unconditional boot hydration (`hydrateSettings()` has one caller), sent after `await mountShellTree()` and `await paneGridReady()`, so settling on it also proves the entry ran past its shell mount. Rejected: reading the webview over CDP (a shipped Electron application has no debugging port, and opening one to allow it would be the less safe binary); a report the webview pushes (a failed boot has no transport to push on); `webContents.executeJavaScript` from the shell (it answers only when the page already works, so it adds nothing the log does not prove).
- **Decided:** the pull-request leg packages with `bun run --cwd packages/desktop package --target <os> --arch <arch> -- --dir` from a bare `actions/checkout`, `setup-bun`, `bun install` and `bun run build`, exactly as the lanes prepare, because the unpacked tree is directly runnable, needs no signing secrets (electron-builder skips signing and notarization loudly when no credential is set), and runs the same `stage-app.ts` assembly, bundle, Bun and `resources` layout as the installer; it differs in installer wrapping and signing only. The boot job never receives the release lanes' signing secrets. The staged backend's `bun run smoke` stays where it is (`desktop-bundle`, and every release lane), and the probe adds the window half it cannot reach.
- **Decided:** the probe is honoured in every build, switched only by the environment, and boots a welcome window (no project), because one code path is what makes the tested binary the shipped one, whoever controls a process's environment can already do more than make it quit, and §3.3 is about registration, not project loading (§4). The Electron main process starts the backend with its own environment, so the variable reaches `startBackend` without a new channel.
- **Decided:** the runner owns the deadline and the launcher rewrites its report on every new request name, because on a timeout the partial report (for example `["githubToken"]`) is the diagnosis, and a launcher-side timer would have to quit before CI could photograph the boot-failure screen, which prints the recorded error.

## Implementation

**1. Seam: `packages/desktop/src/boot-probe.ts` (new; imports only `node:fs`/`node:path`, so both Bun-side entries load it).**

- `BOOT_PROBE_ENV = "JX_STUDIO_BOOT_PROBE"`; `BOOT_SETTLE_REQUEST = "getSettings"`.
- `interface BootReport { launcher: "electron" | "chromium"; requests: string[]; settled: boolean; firstRequestMs: number | null; settledMs: number | null }`: `requests` holds distinct names in first-seen order.
- `interface BootProbe { note(name: string): void; readonly report: BootReport }`.
- `createBootProbe({ launcher, path, now, write, quit })`: `note` appends an unseen name and rewrites the report (write `path + ".tmp"`, then `renameSync`, so a reader never sees a torn file); on `BOOT_SETTLE_REQUEST` it sets `settled`, writes, and calls `quit()` once; after settling it is inert.
- `bootProbeFromEnv(env, launcher, quit)`: `null` when the variable is unset or empty. The caller supplies `quit`, so the table of how each entry ends lives at the two call sites (below) and not in closures here: the hub sends the protocol's `quit` message, which the shell turns into `app.quit()`; the chromium launcher does `process.kill(process.pid, "SIGTERM")`, which its existing SIGTERM handler turns into `chrome.kill()` and `process.exit(0)`.
- `recordBootRequests<H extends Record<string, (...args: never[]) => unknown>>(probe: BootProbe | null, handlers: H): H`: returns `handlers` itself when `probe` is null; otherwise a map with the same keys whose functions call `probe.note(name)` and then delegate with the same arguments, returning (or throwing) exactly what the handler does.
- `judgeBootReport(report: BootReport | null): { ok: boolean; summary: string }`, pure, one sentence per state: no report ("the launcher never started a probe; is `JX_STUDIO_BOOT_PROBE` reaching it?"); no requests ("the window's adapter never called its backend: the init bundle threw or never constructed the adapter; the boot-failure screen names the error"); requests without `getSettings` ("the adapter answered (…names…) but Studio's entry never called it"); settled (pass, with the two timings). Header comment cites desktop.md §3.3; `@docs extending/contributing/monorepo`.

**2. Wiring (straight-line calls only, so existing suites cover them).**

- `src/hub/backend.ts`: `startBackend` builds `const bootProbe = bootProbeFromEnv(env, "electron", () => send({ type: "quit" }))` and passes it to `createWindowHub` as a new option, `bootProbe`. In `window-hub.ts` `openWindow`, `const handlers = recordBootRequests(bootProbe, buildWindowHandlers(window, control))`. `buildWindowHandlers` stays raw for the parity tests.
- `src/chromium/index.ts`: `const bootProbe = bootProbeFromEnv(process.env, "chromium", () => process.kill(process.pid, "SIGTERM"))` near `defaultSession`, and `handlers: recordBootRequests(bootProbe, handlers)` inside it. The exported `handlers` stays raw for `_rpc-parity.ts`.
- The only request before Studio's is `githubToken` (from `bootLauncher`); nothing here names it. `plan:desktop/github-token-stays-in-launcher` changes `githubSignIn`'s answer, and `plan:desktop/settings-patch-cross-process-lock` changes the settings store behind `getSettings`, not the request name; neither is an edge in either direction. `plan:desktop/single-file-mode` adds `open-path` beside `open-project` in the same files and welcomes a probe launch the same way, since a launch with no path opens a welcome window under both.

**3. Runner: `packages/desktop/scripts/boot-probe-runner.ts` (library, tested) and `packages/desktop/scripts/run-boot-probe.ts` (thin CLI, untested, like `package-app.ts` over its library code).** The library is counted by the per-file bar once a test imports it, and the tests run on Linux only, so every per-OS choice below takes an explicit `platform` argument and gets its process calls (`spawnSync`, `process.kill`) injected: the darwin and win32 branches must be covered from a Linux run.

- `locateApp(artifactsDir, platform = process.platform): { path: string | null; searched: string[] }`, globbing with `Bun.Glob`: darwin `mac*/*.app/Contents/MacOS/*`, win32 `win-unpacked/*.exe` (excluding the uninstaller), linux `linux*-unpacked/*` (the executable that is not `chrome-sandbox`) under `packages/desktop/artifacts`. The macOS tree is confirmed by the one a local `--dir` build leaves (`mac-arm64/Jx Studio.app`); the Linux and Windows names are confirmed on the first labelled run, where a miss prints the artifacts tree.
- `probeEnvironment(base, tmpDir, platform)`: copies `base`, sets `JX_STUDIO_BOOT_PROBE` to `tmpDir/boot-report.json`, points the profile at `tmpDir` (`HOME`, `XDG_CONFIG_HOME`, `XDG_DATA_HOME`; `APPDATA`, `LOCALAPPDATA` on Windows; the application pins its own user-data directory under the platform's application-data directory, so this is also what keeps the single-instance lock off the runner's), deletes `JSONSX_PROJECT_ROOT` and `ELECTRON_RUN_AS_NODE` (with no argument the application opens a welcome window), and sets `JX_STUDIO_NO_PROJECT=1` (the chromium launcher's welcome-window switch, §9.2 step 1).
- `runBootProbe({ command, env, reportPath, timeoutMs = 120_000, screenshot?, spawn? })`: spawns the command directly (on macOS the bundle's executable, not `open`, which drops the environment), tees stdout and stderr to `tmpDir/launcher.log`, waits for exit or the deadline; on the deadline takes a best-effort screenshot (`screenshotCommand(platform, file)`: `import -window root` under Xvfb, `screencapture -x` on macOS, `null` on Windows; a failed capture is logged, never the verdict) and kills the process tree (`killTree(pid, platform, deps)`: `process.kill(-pid, "SIGKILL")` for the POSIX group the spawn made with `detached: true`, `taskkill /T /F /PID` on Windows). Then reads the report, returns `judgeBootReport`'s verdict plus the log tail.
- `run-boot-probe.ts electron | chromium [--timeout-ms N] [--out DIR]`: resolves the command (the located application; or `process.execPath src/chromium/index.ts` with the caller's `CHROMIUM_BIN`), prints the verdict, leaves report, log and screenshot in `--out`, exits 1 on failure. `packages/desktop/package.json` gains `"boot-probe": "bun scripts/run-boot-probe.ts"`.

**4. CI.**

- New `.github/workflows/desktop-boot.yml`, `on: workflow_call` and `workflow_dispatch`, `permissions: contents: read`, one job with `timeout-minutes: 45` and a `fail-fast: false` matrix: `ubuntu-latest` (linux-x64), `macos-15` (the lane's pin, and its reason), `windows-latest`. Steps: `actions/checkout@v7`, `oven-sh/setup-bun` at the pin the lanes use, `bun install`, on Linux `xvfb` and `imagemagick` (for `import`) plus Electron's runtime libraries, `bun run build`, `bun run --cwd packages/desktop package --target <os> --arch <arch> -- --dir`, then `bun run --cwd packages/desktop boot-probe electron --out "${{ runner.temp }}/boot"` (an expression, not `$RUNNER_TEMP`: the Windows leg's default shell is pwsh; on Linux under `xvfb-run -a -s "-screen 0 1920x1080x24"`). Two Linux contingencies, applied only if the first labelled run needs them: `--no-sandbox` is NOT one of them (it would hide the sandbox's own failure), but `sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0` before the launch is, if Ubuntu 24.04's AppArmor refuses the unpackaged application's Chromium sandbox (§7.6 says the same restriction is why the snap is the recommended Ubuntu channel), and `LIBGL_ALWAYS_SOFTWARE=1` in the step env if Electron cannot get a GL context under Xvfb. Linux only, after that: `bun run --cwd packages/desktop scripts/pre-build-rpc.ts` (it overwrites `assets/studio/dist/init.js` with the chromium shim), then `CHROMIUM_BIN=$(command -v google-chrome) xvfb-run -a bun run --cwd packages/desktop boot-probe chromium --out "${{ runner.temp }}/boot-chromium"`. Last, `actions/upload-artifact@v7` with `if: failure()`, named per platform, holding the report, log and screenshot.
- test.yml: a `desktop-boot` job, `if: startsWith(github.head_ref, 'release-please--') || contains(github.event.pull_request.labels.*.name, 'desktop-boot')`, `uses: ./.github/workflows/desktop-boot.yml`, with a comment modelled on `nix`'s; add it to `ci`'s `needs`. `skipped` stays green. test.yml's `pull_request` keeps its default activity types (no `labeled`: that would re-run the whole matrix on every label anyone adds), so the comment says how to opt in: apply the label, then push. A re-run replays the original event's payload and does not see a label added after it.
- Repository setting, not code: create the label (`gh label create desktop-boot --description "Boot the packaged desktop app on each OS in this pull request's CI"`).
- `.github/AGENTS.md`, the "Release-only workflows are unexercised" bullet: add that the release pull request boots an unpacked build of the release commit on all three OSes (`desktop-boot.yml`), so what remains unexercised is the lanes' own steps and signing.

**Integration contract.** Once this lands, a plan may rely on: `JX_STUDIO_BOOT_PROBE=<path>` making either entry write a `BootReport` there and quit after Studio's first `getSettings`; `recordBootRequests`, `bootProbeFromEnv`, `judgeBootReport` and `BootReport` exported from `packages/desktop/src/boot-probe.ts`; `bun run --cwd packages/desktop boot-probe electron|chromium` as the local check; the `desktop-boot` job in `ci` on release pull requests and labelled ones. A plan that renames `getSettings` or stops Studio's entry from hydrating settings at boot must move `BOOT_SETTLE_REQUEST` with it. §7.4's tree stays by kind, so `src/boot-probe.ts` is named in §3.3 and not drawn there.
