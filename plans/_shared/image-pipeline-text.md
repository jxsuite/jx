# The image pipeline is stated once, in site-architecture.md §9.2, and its cache, format rules and Markdown images do what that text says

## Context

Two specs restate one build-time image pipeline, and eight of their sections have drifted from the code and, in places, from each other. The compiler census stubbed its half, the site-architecture census the other, and each expected to cite rather than restate the other; they are one plan because the halves share the decisions below, and a rewrite of either half alone would leave the specs disagreeing again.

The markers (all eight were unmarked before the census, except §7.7, which carried only the trailing `Implemented` marker at line 616 that stays):

`specs/compiler.md` §7.1, line 488:

> **Status: Partial.** The table omits `picture` (default `true`: `DEFAULTS.images` in `packages/compiler/src/site/site-loader.ts`, `packages/schema/defs/image-config.schema.ts`). And `optimize` is not a master switch: `site-build` calls `transformImageNodes` whatever it says, and the loading pass applies `lazyLoad` on its own, yielding to `fetchpriority="high"` (`imgLoadingAttrs` in `packages/compiler/src/site/img-loading.ts`), as `site-architecture.md` §9.2.1 and §9.2.7 state.

`specs/compiler.md` §7.2, line 518:

> **Status: Partial.** With two or more formats (the default `webp` and `avif`) and `picture` not `false`, `wrapInPicture` in `packages/compiler/src/site/image-transform.ts` rewrites the node into a `<picture>` with one `<source type>` per format, best compression first, carrying the `srcset` and `sizes`, while the `<img>` keeps `src`, dimensions and loading attributes; only a single-format config gets the bare `<img srcset>` described below (`site-architecture.md` §9.2.2 states the shipped form). Variants are written to the image cache's `_optimized/` directory (`processImage` in `image-optimizer.ts`) and copied to `dist/images/_optimized/` after the routes build, not written to `dist/` directly. And the concurrency sentence does not hold: `processImage` starts every encode as it builds the width × format list, and its `CONCURRENCY = 4` loop only awaits the already-running promises four at a time.

`specs/compiler.md` §7.3, line 552:

`specs/compiler.md` §7.5, line 589:

The config hash also folds in `PIPELINE_VERSION` (`image-optimizer.ts`); the key format, persistence and pruning ship as described.

`specs/compiler.md` §7.7, line 608:

Every quoted fact re-verified against the tree. Most of the drift is deliberate code the prose predates: `<picture>` exists because `srcset` carries no format (`resolveVariants`, `image-transform.ts` line 437), the cache sits in npm's cache so CI hosts that persist `~/.npm` keep variants (header of `image-cache.ts`), and the top-rung cap, the decodable `src` and container-derived `sizes` were written into `compiler.md` §7.2 and §7.2.1 on purpose (commit f1a1537b; `PIPELINE_VERSION`'s comment cites §7.2). The concurrency sentence is a code defect that `plan:compiler/image-sizes-and-encode-limit` fixes, with §7.2.1's within-node width; this plan requires it so that both markers flip in one step.

**Corrections to the census reading.** Detailing found defects inside the claimed sections that a text rewrite cannot honestly describe, which moves this plan from `reconcile` to `implement`:

1. **A quality change never re-encodes.** `processImage` names a variant `variantFilename(stem, width, contentHash, format)`, a digest of the source bytes only, and skips any variant whose file already exists. A new `quality` is a new cache key, but the re-process finds the old files under the same names and keeps them, and pruning keeps them too because the new entry names the same paths. The URL is served `immutable` (`site-architecture.md` §14.3), so a host with a cold cache that does encode at the new quality ships different bytes under a URL returning visitors hold for a year.
2. **Two projects with one directory name share a cache.** `getImageCacheDir` keys the npm-cache directory by `basename(projectRoot)` alone. `saveCache(…, { prune: true })` drops every key the current build did not touch, so each error-free build of one project deletes the other's variants, and the next build of the other re-encodes everything.
3. **Step 6b copies the whole cache directory.** `site-build.ts` (line 836) `cpSync`s the cache's `_optimized/` into `dist/images/_optimized/`, not the variants the build used; `site-build.test.ts` "copies cached variants from the global npm cache dir to dist" asserts that a file no entry names reaches `dist`. §9.2.5's "only contains images the current build uses" holds only while every file there belongs to an entry.
4. **A local file Sharp cannot decode fails its route.** With the denylist, `/favicon.ico` or `/images/scan.bmp` reaches `processImage`; `getImageMetadata` rejects, nothing catches it before `buildSite`'s per-route `catch` (line 819), and every page whose layout holds that `<img>` fails to compile. This is the practical case for the allowlist.
5. **The two halves of `image-transform.ts` disagree**, and neither spec says so. `transformInnerHtmlImages` (pre-rendered `innerHTML`, i.e. Markdown content) never applies `fallbackSrc`, writes `sizes="${config.sizes}"` whatever the tag or its container says (a duplicate attribute when the tag has one, `sizes="undefined"` when the project sets none), and `attrValue`'s `\bsrc=` also matches `data-src=`. Conversely `transformImgNode` overwrites an authored `srcset`, while the `innerHTML` half leaves it ("The candidate list is the author's", `image-optimizer.test.ts`). The docs page promises Markdown images "go through the same transformation".
6. Small: `getCached`'s comment claims it checks the variant files (the check is `resolveManifest`, line 127, against the cache directory), and `transformImageNodes`' comment says variants go to `.cache/images/_optimized/`.

**What exists**: `transformImageNodes`, `walkAndTransform`, `transformImgNode`, `transformInnerHtmlImages`, `resolveVariants`, `resolveManifest`, `shouldSkip`, `isAllowedRemote`, `SKIP_EXTENSIONS`, `resolveImagePath`, `fallbackVariant`, `containerWidthOf`, `sizesForContainer`, `wrapInPicture`, `renderPictureTag`, `attrValue`, `resolveCfMeta` (`image-transform.ts`); `processImage`, `variantFilename`, `contentHash`, `configHash`, `PIPELINE_VERSION = 2`, `getImageMetadata` (`image-optimizer.ts`); `getImageCacheDir`, `cacheKey`, `loadCache`, `saveCache`, `pruneStale`, `getCached`, `setCached` (`image-cache.ts`); step 6 (line 533) and step 6b (line 828) of `site-build.ts`, and the `transformImageNodes` call at line 1451 that runs whatever `optimize` says. Tests: `image-transform.test.ts` (mocks the optimizer and cache modules), `image-optimizer.test.ts`, `image-cache.test.ts`, `image-optimizer-nosharp.test.ts`, `image-optimizer-sharp-fallback.test.ts`, `img-loading.test.ts`, and the image blocks of `site-build.test.ts` (Sharp mocked file-wide, `toFile` a no-op).

## Decisions

- **Open:** which spec holds the text? Recommendation: `site-architecture.md` §9.2 states every behaviour (configuration, eligibility, markup, `sizes`, dimensions, overrides, cache, the Cloudflare service, loading), and each `compiler.md` §7 subsection keeps its heading as a short paragraph naming the implementing functions and citing its §9.2 counterpart. `compiler.md` keeps only what is about the compiler itself: the per-image encode limit (§7.2) and the build-integration steps (§7.7). §7.2.1's resolution order moves into §9.2.2 once the prerequisite has made it true. Because site-architecture is the author-facing contract (its §3 table's `images` row points at §9.2, §9.2.1 and §9.2.7 are already complete and verified, and its Standards Alignment row binds WHATWG HTML responsive images to §9.2), the compiler census recorded the pipeline as site-architecture's, and `compiler.md`'s subject is compiled artifacts. The reverse would move the Implemented §9.2.7 and the verified §9.2.1 into `compiler.md` for no reader's benefit.
- **Open:** raster allowlist or denylist (`compiler.md` §7.3, `site-architecture.md` §9.2.3)? Recommendation: build the allowlist for local sources (`.jpg`, `.jpeg`, `.png`, `.webp`, `.avif`, `.tif`, `.tiff`; `.tif` is the same format as `.tiff`), skip every GIF and say so, and keep the remote rule a denylist of `.svg` and `.gif`. Because a local file Sharp cannot decode fails its page today (correction 4), and the allowlist makes it an image the build leaves alone apart from loading attributes. An animation check would cost a Sharp read per GIF to rescue still GIFs, a rare case. A remote URL often has no extension, so an allowlist there would refuse most of what `remoteDomains` exists for.
- **Open:** does `width`/`height` injection run with `optimize: false`, as §9.2.2 step 5 promises? Recommendation: no, reconcile the text: dimensions come from the variant pass, so with `optimize` off, for an ineligible image or one that opts out, the author writes them. Because `optimize: false` is how a project keeps the build from opening image files (Sharp unavailable, or fast builds), and a header read per image would bring Sharp back in exactly that mode; §9.2.7's loading pass, the precedent the step cites, needs no file at all. The alternative is a memoized header read for every local image the variant pass did not handle, in both halves, degrading without Sharp as `resolveCfMeta` does, plus its tests.
- **Open:** do the two halves of `image-transform.ts` apply one set of rules (correction 5)? Recommendation: yes. The `innerHTML` half gains the `src` fallback and the `sizes` order (its container is the node holding the `innerHTML`), writes no duplicate or `undefined` `sizes`, and reads attributes only at a name boundary; the node half gains the `innerHTML` half's rule that an authored `srcset` leaves the image to its author. Because the docs page already promises it, Markdown content is where most of a content site's images live, and no comment or test defends any of the differences; writing them into the spec would make accidents a contract.
- **Decided:** a variant's filename digest covers its encode settings: `{stem}-{width}-{hash}.{format}` keeps its shape, and `{hash}` becomes `variantHash(contentHash, format, quality)`. `PIPELINE_VERSION` goes to 3 so entries recorded under the old names re-encode once. Because correction 1 is otherwise unfixable without ever reusing a file, and it makes §14.3's "a changed image is a changed URL" true of a changed quality too. The cost is one cold re-encode per project, the precedent `PIPELINE_VERSION` 2 set.
- **Decided:** the npm-cache directory is `jxsuite-images/<basename>-<8 hex of md5(resolved project root)>`. Because of correction 2. CI hosts build from a fixed path, so a persisted cache still hits after the one cold build the previous decision already costs; the old directory is left in place and never read, since it may belong to a project still on an older compiler.
- **Decided:** step 6b copies the variants of the entries this build resolved (`cache.touched`), not the directory. Because of correction 3: it makes the pruning sentence exact whatever else the directory holds.
- **Decided:** in the build service, an eligible source Sharp cannot read, or a Sharp that cannot load, stays an error for the routes that use it, and §9.2.2 says so. Because the variants cannot be produced, and shipping the original silently would hide a corrupt file or the dependency `compiler.md` §7.7 requires; the allowlist removes the case where the file was never a raster image. The Cloudflare service keeps its degrade (`resolveCfMeta`), since it only reads dimensions.

## Implementation

Written for the recommendations; an Open answered the other way drops its steps and its tests, and its spec text becomes the reconcile described in that decision. All code is in `packages/compiler/src/site/` and builds on the prerequisite's `processImage` task list and `containerWidthOf`.

1. `image-transform.ts`
   - Replace `SKIP_EXTENSIONS` with `RASTER_EXTENSIONS` (the seven extensions) and `REMOTE_SKIP_EXTENSIONS = new Set([".svg", ".gif"])`. `shouldSkip` keeps its string, empty, template and external checks, then returns `!RASTER_EXTENSIONS.has(extname(src).toLowerCase())`; `isAllowedRemote` uses `REMOTE_SKIP_EXTENSIONS`.
   - `attrValue`: ``new RegExp(`(?:^|\\s)${name}="([^"]*)"`, "i")``, so `data-src` is not `src`.
   - `walkAndTransform`: pass `containerWidthOf(node, containerWidth)` to `transformInnerHtmlImages` as a new last parameter, `containerWidth: number | null`.
   - `transformInnerHtmlImages`: `const ownSizes = attrValue(attrs, "sizes")`; `const resolvedSizes = ownSizes ?? sizesForContainer(containerWidth) ?? config.sizes`. The single-format branch appends `srcset`, and appends ` sizes="…"` only when `ownSizes === undefined` and `resolvedSizes` is non-empty. When `variants.fallbackSrc` is set and the srcset is non-empty, the tag's `src` value is replaced in a copy of `attrs` (`/(^|\s)src="[^"]*"/i`), and that copy is what both output shapes write. `renderPictureTag` takes `resolvedSizes` and omits `sizes` on a `<source>` when it is empty or undefined, as `wrapInPicture` does.
   - `transformImgNode`: `resolveVariants`' `optedOut` becomes `attrs["data-no-optimize"] !== undefined || attrs.srcset !== undefined`.
   - `transformImageNodes`' comment: variants go to the image cache's `_optimized/` (`getImageCacheDir`), and the build copies the ones it used into `dist/`.
2. `image-optimizer.ts`
   - Export `variantHash(hash8: string, format: string, quality: number): string`: the first 8 hex characters of the MD5 of `hash8`, `format` and `quality` joined by `:`. In `processImage`, compute `quality` before the filename and name the file `variantFilename(stem, width, variantHash(hash8, format, quality), format)`; the `existsSync` skip stays, and is now safe. `ImageManifest.contentHash` stays the source hash.
   - `PIPELINE_VERSION = 3`, with a comment line `2 → 3: a variant's filename digest covers its format's quality (site-architecture.md §9.2.5).`; the `1 → 2` line's citation becomes `site-architecture.md §9.2.2`.
3. `image-cache.ts`
   - `getImageCacheDir`: the npm branch returns ``resolve(base, "jxsuite-images", `${basename(projectRoot)}-${digest}`)``, `digest` being the first 8 hex characters of the MD5 of `resolve(projectRoot)`; the header and function comments say why. The fallback is unchanged.
   - Export `usedVariantPaths(cache: CacheManifest): string[]`: the `absolutePath` of every variant of every entry whose key is in `cache.touched`, deduplicated.
   - `getCached`'s comment: the variant-file check belongs to the caller.
4. `site-build.ts`, step 6b: after `saveCache`, copy each existing path from `usedVariantPaths(imageCache)` to `resolve(outDir, "images/_optimized", basename(path))` with `copyFileSync`, creating the directory only when there is something to copy; drop the `cpSync` of the directory and any import it leaves unused.
5. Comments only: `IMMUTABLE_PATTERN` (`headers-emitter.ts`) and `CACHE_FIRST_PREFIX` (`service-worker.ts`) say the digest covers the source bytes and the encode settings.

**Integration contract.** Once this lands, behaviour of the image pipeline is specified in `site-architecture.md` §9.2 alone: a plan changing it edits §9.2 and, at most, the naming paragraph of the matching `compiler.md` §7 subsection. `compiler.md` §7.2 states the four-encode limit and names `transformImageNodes(doc, config, projectRoot, cache, metaCache?, mounts?)` → `{ imageRefs }`, which `plan:compiler/shared-utilities-signatures` may cite. `image-optimizer.ts` exports `variantHash`; `image-cache.ts` exports `usedVariantPaths`, and `getImageCacheDir(root)` returns `<npm cache>/jxsuite-images/<basename>-<digest>` or `<root>/.cache/images`. Both halves of `image-transform.ts` apply one set of rules, so a rule added to one is added to the other.
