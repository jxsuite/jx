## Spec-wide decisions

- **Head-entry shape.** The examples that did not match the shipped authoring shape (a `$head` of `{ tagName, attributes }` plus a top-level `title`, and a layout that is body content) were one census decision over seven anchors. Detailing split it by disposition: `plan:site-architecture/head-and-layout-shape` reconciles the text of §3, §5.1, §5.2, §8.2, §8.3 and §8.5, and `plan:site-architecture/head-and-layout-shape-root-title` owns §8.1, the one anchor with a code half (a page's `title` rendering on its root element). The second requires the first, as do `plan:site-architecture/nested-layout-head` (it widens the §8.3 item 2 the first writes) and `plan:site-architecture/seo-structured-data-editor` (its editor reads only `attributes`, on the first plan's decision that the build never honours a top-level key).
- **The page title and its carriers** are three questions with three owners, landing in this order where they depend: `plan:site-architecture/nested-layout-head` decides what a layout's `title` contributes and narrows `_pageTitle` and `_pageHead` to the page's own values; `plan:site-architecture/page-context-props` then reads the page's facts with `readPageFacts`, removes both carriers and stops `injectContext` reading `doc.title`; `plan:site-architecture/head-and-layout-shape-root-title` deletes whatever `title` the composed root still carries, in each host, after the title is read. The last has no edge on the other two: each edits lines beside the others, and whichever lands later rebases against the others' contracts.
- **§5.5's marker** is edited by three plans. `plan:site-architecture/site-state-scope` and `plan:site-architecture/locale-negotiation-gaps` each delete only their own clause from its second sentence, which reads "`$page.description`, `$page.$head`, `$page.frontmatter` and `$site.$head` are never injected." once both have landed; `plan:site-architecture/page-context-props` requires both and replaces the whole marker. §5.5's two tables are the one list of what `$page` and `$site` carry, so a plan that injects a new key adds its row (`plan:site-architecture/collection-pagination`'s `$page.pagination`), whichever of it and `plan:site-architecture/page-context-props` lands second keeping the other's rows.
- **Route tables.** `plan:site-architecture/route-pattern-validation` decides which page file names are routes, `plan:site-architecture/route-specificity-order` decides their order and what the build does when two routes generate one URL, and `plan:site-architecture/collection-pagination` generates its paged routes through `expandDynamicRoutes`, so the collision rule reaches them whenever it lands. None requires another; each states its outcome without assuming the others' has landed.
- **§14.1's `"cloudflare-pages"` cell** is edited by `plan:site-architecture/build-output-prose` (its `_redirects` tail goes) and `plan:site-architecture/locale-negotiation-gaps` (its condition widens). With both landed it reads "`dist/_worker.js` (advanced-mode Hono server) + `dist/_routes.json`, unless the site has no server entries, no active extension mounts and no root to negotiate (§13.6)".
- **Previewing a media value against a named document** is one change to `packages/studio/src/canvas/asset-refs.ts`, shared by `plan:site-architecture/entry-editor-widgets` and `plan:site-architecture/library-collection-views`: `previewAssetSrc(value, documentPath?: string | null)`, which reads the active tab only when the argument is `undefined`. Whichever lands first adds it with its `asset-refs.test.ts` case, and the second calls it.
- **Studio's `HeadLayers`**: `plan:site-architecture/nested-layout-head` replaces `layout` and `layoutName` with `layouts`, one named level per layout, and `plan:site-architecture/seo-structured-data-editor`'s `inheritedStructuredData` takes the whole `HeadLayers` so that change stays inside one function; whichever lands second makes it walk `layouts`, each level its own donor.
- A divergence earns its section a marker; only incidental wording in a section no plan claims rides with the plan whose subject it is: §7.1 with `plan:site-architecture/library-collection-views`, §7.3 with `plan:site-architecture/entry-editor-widgets`, §3.2's "read-only" parenthetical and §10.1's "Site `state` (read-only)" cell with `plan:site-architecture/site-state-scope`, §13.1 and §13.4 with `plan:site-architecture/locale-negotiation-gaps`, §12.1's "else per-route _server.js" pipeline line with `plan:_shared/no-adapter-server-tier`. A divergence inside a section some plan claims belongs to that section's owner, which is why §14.1.1's step 5 and its undocumented `build.deploy` key are `plan:_shared/page-server-entries`'s, and §14.1's `_redirects` row sits under its own marker with `plan:site-architecture/build-output-prose`.
- Where another plan makes the decision a claimed section needs, the owner requires it rather than sharing the claim: `plan:site-architecture/page-context-props` requires `plan:site-architecture/site-state-scope` (which rewrites §5.5's `$site.state` row with §10.4 item 1) and `plan:site-architecture/locale-negotiation-gaps` (whose `resolveI18n` change makes `$site.locales` default-first), and `plan:_shared/image-pipeline-text` requires `plan:compiler/image-sizes-and-encode-limit`, which builds the four-encode cap that §9.2.2 and compiler.md §7.2 both state. `plan:site-architecture/locale-negotiation-gaps` requires `plan:_shared/page-server-entries` for the `skipWorker` and `_routes.json` lines both rewrite, so §5.5 waits on that plan too; splitting the `resolveI18n` order out as an enabling plan was weighed and declined, because `plan:_shared/page-server-entries` requires nothing.
- Three items here are one code change with an item another census owns, and each pair is one plan under `plans/_shared/` claiming both anchors: §15.2 with extensions.md §11.1 (`plan:_shared/db-push-section-owners`), §14.1.1 with compiler.md §6.3 (`plan:_shared/page-server-entries`), and §15.4 with compiler.md §6.2 (`plan:_shared/no-adapter-server-tier`, which requires the second).
