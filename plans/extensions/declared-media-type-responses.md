# Every server Jx runs sends a registered format's files with the media type its class declares

## Context

`specs/extensions.md` §7, line 259:

> **Status: Partial.** The block, `mediaType` validation (`mediaTypeProblem`, `packages/schema/src/media-type.ts`) and `(extension, capability)` exclusivity ship (`packages/schema/src/format-registry.ts`). The declared `mediaType` reaches only the studio's file-picker `accept` map and editor language id (`packages/studio/src/files/file-ops.ts`, `packages/studio/src/canvas/canvas-render.ts`): no icon or label reads it, and the dev server and `jx preview` set `Content-Type` from a fixed core table (`MEDIA_TYPE_BY_EXTENSION`) that knows only `.md`, `.markdown`, `.yaml` and `.yml`, so a format's declared type is never served.

The `mediaType` row says the value is "Used for icons, labels and HTTP responses", and the paragraph after the table justifies validating it by the value reaching "an HTTP header, an editor's file association and a Studio label". Verified at the audited tree, with the census's evidence corrected:

- **The registry has no answer by extension.** `FormatEntry.mediaType` and `mediaTypeEssence` are set in the constructor, and the `FormatRegistry` constructor rejects a malformed value through `mediaTypeProblem`. Nothing looks a type up by extension. Two classes may claim one extension with disjoint capabilities, and nothing notices when they declare different types.
- **Studio has three readers, not two, and none is an icon or label.** The open picker's `accept` map and `exportFile`'s save type (`packages/studio/src/files/file-ops.ts`, lines 129 and 418) and the editor language id (`packages/studio/src/canvas/canvas-render.ts`, line 157) all key on `mediaTypeEssence`. Format glyphs come from `$studio.icon` (extensions.md §10).
- **Seven lanes serve files, and the census saw two.** None consults the registry:

  | Lane                                                            | Code                                                                     | `Content-Type` today                                                                            |
  | --------------------------------------------------------------- | ------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------- |
  | Dev server: absolute path, server root, project root, `public/` | `fileResponse` in `packages/server/src/server.ts`                        | Bun's inference, corrected by `mediaTypeForPath`                                                |
  | Dev server: asset mounts (extensions.md §8.5)                   | `serveProjectFile` branch in `server.ts`                                 | Bun's inference, uncorrected                                                                    |
  | `jx dev`'s built pages                                          | `createDistMiddleware` in `packages/server/src/dev.ts`                   | Bun's inference, uncorrected                                                                    |
  | Desktop project server                                          | step 6 of `createProjectServer`, `packages/server/src/project-server.ts` | Bun's inference, uncorrected                                                                    |
  | Built-site preview origin                                       | `serveSiteOutput` in `packages/server/src/site-output.ts`                | Bun's inference, uncorrected                                                                    |
  | Live preview origin (server.md §3.4)                            | `serveSite` → `contentTypeFor` in `packages/site/src/paths.ts`           | its own table: `.md` as `text/markdown; charset=utf-8` with no `variant`, `.yaml` as a download |
  | `jx preview`                                                    | `MIME_TYPES` in `packages/compiler/src/site/preview-server.ts`           | a fixed table with the core table spread in, otherwise `application/octet-stream`               |

  So parser.md §16's RFC 7763 row ("every host that serves a `.md` file off disk sends the same thing") is false today for five of the seven lanes.

- **The per-response lookup is already paid for.** The stub hedged that a registry lookup per static response might be the wrong trade. It is not one: `loadProjectEntry` (`packages/server/src/resolve.ts`) builds the project's extension registry into an mtime-keyed cache, and the dev server reads that cache on every request (`projectSiteBase`), the project server on every static request (`projectAssetMounts`). Keeping the format registry on the cached entry makes the lookup a map read.
- **Text that goes stale with the change.** server.md §3 item 7 ("every other extension keeps the inferred type"), parser.md §3 ("the static file servers, which have no registry to consult"), the module header of `media-type.ts` and the `FormatRegistry` constructor comment ("a Studio label"), and in the docs `formats.md` ("What a static file server sends", the row, "a Studio label") and `framework/build/dev-server.md` ("Static files and npm packages").
- **A deployed site is typed by its host.** The build's `dist/_headers` sets `Content-Type` only for four named outputs (`contentTypeRules`, `packages/compiler/src/site/headers-emitter.ts`). The two hosts that read the file disagree on what `/*.md` matches: Netlify matches a wildcard inside one path segment, Cloudflare's splat greedily matches across segments, and Cloudflare caps the file at 100 rules. See Decisions.

## Outcome

- extensions.md §7 → Implemented. Every server Jx runs answers a file whose extension an enabled format claims with that format's declared `mediaType`, rendered canonically with `charset=utf-8` added to a `text/*` type that names none. Any other extension keeps the host's answer, corrected by the core table. The registry build refuses two classes that declare different types for one extension. The row and the validation paragraph name the real consumers, and a deployed site's static files are stated as typed by their host.
- Rides along: the core table's `.md` and `.yaml` corrections reach the four lanes that never had them (asset mounts, `jx dev`'s built pages, the project server, the built-site preview), and the live preview's `.md` gains its `variant`.

## Decisions

- **Decided:** implement, not reconcile, because every editing server already builds the registry per project in the cache it reads per request, so the only new cost is keeping `registry.formats` on that entry.
- **Decided:** a declared type wins over the core table, and the table answers only for extensions no enabled format claims (and for hosts with no registry), because the class is the contract §7 describes and the table's own doc comment says it corrects a platform lookup, not a declaration. The Markdown class and the table's `.md` entry already agree, and the drift test keeps them agreeing.
- **Decided:** the served form is the parsed value re-rendered by `formatMediaType`, with `charset=utf-8` appended when the type is `text` and declares no `charset`, because RFC 7763 §2 makes `charset` required for `text/markdown`, every host reads a format's source as UTF-8, and it keeps the header a project with `@jxsuite/parser` sends byte-identical to the one a project without it gets from the table (`text/markdown; variant=GFM; charset=utf-8`). A non-text type (`application/toml`) goes out as declared, canonicalised.
- **Decided:** all seven lanes in the Context table, because a partial set leaves the same file typed differently in the editor, the two previews and `jx preview`, which is the defect this plan closes.
- **Decided:** one resolver, `mediaTypeForPath(path, declared?)` in `@jxsuite/schema/media-type`, taking a structural `DeclaredMediaTypes` (`{ mediaTypeFor(ext) }`) rather than a `FormatRegistry`, because `format-registry.ts` already imports `media-type.ts` and the module must stay browser-safe with no import back.
- **Decided:** the live preview types files from the saved `project.json`'s registry through the shared cache, not from the overlay its page parser reads, because rebuilding a registry per asset request would read every manifest per file, and an unsaved `extensions` edit changes what renders, not what a file is called.
- **Decided:** `jx preview` builds the registry once at startup from the project root, silently skips it when there is no `project.json`, and warns once and falls back to the core table when the registry cannot build, because `dist/` is fixed output (a changed `extensions` list needs a rebuild anyway) and a preview server that refuses to start over a broken extension helps nobody.
- **Decided:** an editing server whose project entry fails to load (a registry that throws, a broken `project.json`) answers from the core table, because `loadProjectEntry` already degrades to `null` for every other consumer and a static response is not the place to report a configuration error the build and Studio already report.
- **Open:** two classes claiming one extension declare different media types. Recommendation: the registry build fails, comparing the served (canonical) forms so case, spacing and an added `charset` do not count, and a class that declares no type defers to one that does, because the alternative is declaration order the author cannot see, and §7 already treats an ambiguous `(extension, capability)` pair as a build failure. No first-party pair conflicts (`Markdown` claims `.md`, `Csv` claims `.csv`).
- **Open:** does a deployed site send the declared type? Recommendation: no; §7 states that a deployed site's static files are typed by its host, with no `Future` marker, because a `/*<ext>` rule in `_headers` means one path segment on Netlify and any depth on Cloudflare, a rule per sidecar would exhaust Cloudflare's 100-rule cap, and the servers Jx runs are where the header is Jx's to send. The alternative, if a maintainer wants it: a `> **Status: Future.**` remainder naming a Cloudflare-scoped `/*<ext>` rule keyed on `build.adapter`.

## Implementation

1. **`packages/schema/src/media-type.ts`**
   - `export interface DeclaredMediaTypes { mediaTypeFor(ext: string): string | null }`, with a doc comment saying it is the registry's answer, typed structurally so this module imports nothing.
   - `export function servedMediaType(declared: unknown): string | null`: `parseMediaType`, then when `type === "text"` and `parameters.charset` is absent add `charset: "utf-8"`, then `formatMediaType`. Null for a value that does not parse.
   - `mediaTypeForPath(path: string, declared?: DeclaredMediaTypes | null)`: after the existing extension extraction, return `declared?.mediaTypeFor(ext) ?? MEDIA_TYPE_BY_EXTENSION[ext] ?? null`. Update its doc comment (a registry answer first, the table second, null to leave the host's own answer).
   - Module header: "reaches an HTTP header, an editor's file association and a Studio label" becomes "reaches an HTTP header, a file picker's `accept` filter and an editor's language id". The `MEDIA_TYPE_BY_EXTENSION` comment gains one sentence: a registered format's declaration answers first, so the table speaks for extensions no enabled format claims.
2. **`packages/schema/src/format-registry.ts`**
   - `FormatRegistry.mediaTypeFor(ext: string): string | null` (it satisfies `DeclaredMediaTypes`): `normalizeExt`, null for `.json`, then the first entry that claims the extension and declares a type, through `servedMediaType`.
   - In the constructor, after the validity loop: for every claimed extension, collect the served forms of the declaring entries; two different forms throw `Format conflict: "<A>" and "<B>" both claim "<ext>" with different media types ("<a>" and "<b>")`. The constructor comment's "a Studio label" becomes "an editor's language id".
3. **`packages/server/src/resolve.ts`**
   - The `projectContextCache` entry gains `formats: FormatRegistry` (`registry.formats`, built in `loadProjectEntry` already).
   - `export async function projectMediaType(projectRoot: string, path: string): Promise<string | null>`: `mediaTypeForPath(path, (await loadProjectEntry(projectRoot))?.formats)`. Doc comment cites extensions.md §7.
   - `export async function withProjectMediaType(res: Response, projectRoot: string, path: string): Promise<Response>`: sets `Content-Type` when `projectMediaType` answers, returns `res`.
4. **`packages/server/src/server.ts`**: `fileResponse` becomes async and reads `projectMediaType(activeProjectRoot ?? absRoot, file.name)` (the same root `projectSiteBase` is read for). The asset-mount branch sets `Content-Type` on its copied `Headers` when `projectMediaType(activeProjectRoot, path)` answers. Drop the direct `mediaTypeForPath` import and rewrite the comment above `fileResponse` (the registry first, then the two corrections, then Bun's inference).
5. **`packages/server/src/project-server.ts`**, step 6: `return withProjectMediaType(fileRes, root, normPath)`.
6. **`packages/server/src/dev.ts`**, `createDistMiddleware`: the non-HTML branch returns `withProjectMediaType(new Response(Bun.file(filePath), { headers: { "Cache-Control": "no-cache" } }), root, filePath)`.
7. **`packages/server/src/site-output.ts`**, `serveSiteOutput`: the direct-file branch wraps its `serveContained` result in `withProjectMediaType(res, projectRoot, direct)` when non-null. The index and `.html` branches are HTML and stay as they are.
8. **`packages/site/src/serve.ts`**: `ServeOptions` gains `mediaType?: (path: string) => Promise<string | null>`, documented as the host's `Content-Type` for a project-relative file, tried before this package's table. The file loop uses `(await options.mediaType?.(candidate)) ?? contentTypeFor(candidate)`.
9. **`packages/site/src/paths.ts`**, `contentTypeFor`: `mediaTypeForPath(path) ?? CONTENT_TYPES[extension] ?? "application/octet-stream"`, and the `md` entry leaves `CONTENT_TYPES`, since the core table answers `.md` and `.markdown` (and now `.yaml`/`.yml`, which were downloads). `@jxsuite/site` already depends on `@jxsuite/schema`.
10. **`packages/server/src/live-preview.ts`**: the `serveSite` call passes `mediaType: (path) => projectMediaType(projectRoot, path)`.
11. **`packages/compiler/src/site/preview-server.ts`**
    - `startPreviewServer(distDir: string, port: number, projectRoot?: string)`. When given, it starts `previewFormats(projectRoot)` once; the request handler awaits that promise and sends `mediaTypeForPath(filePath, formats) ?? MIME_TYPES[ext] ?? "application/octet-stream"`.
    - `previewFormats(projectRoot)` (module-private): no `project.json` → null; otherwise `JSON.parse` it and return `(await buildProjectExtensionRegistry(projectRoot, config)).formats` from `./format-host.ts`; on any error, one `console.warn` ("jx preview: <reason>; files are typed by the core table") and null.
    - `MIME_TYPES` drops its `...MEDIA_TYPE_BY_EXTENSION` spread, since `mediaTypeForPath` answers those extensions first; the table comment is rewritten to say so. The module header's "Dependency-free" stays true: `format-host.ts` is the compiler's own node-only module.
    - If `plan:extensions/capability-timing-dispatch` lands first, `buildProjectExtensionRegistry` takes an environment; pass `"compiler"` (the registry here reads JSON and never calls a capability).
12. **`packages/compiler/src/cli.ts`**, `preview`: `startPreviewServer(distDir, port, projectRoot)`.

**Integration contract.** Once this lands: `@jxsuite/schema/media-type` exports `DeclaredMediaTypes`, `servedMediaType`, and `mediaTypeForPath(path, declared?)`, which answers a declared type first and the core table second. `FormatRegistry.mediaTypeFor(ext)` returns an extension's served type or null, never for `.json`, and the registry build refuses conflicting declarations (as the Open decision lands). `@jxsuite/server/resolve` exports `projectMediaType` and `withProjectMediaType`; every file-serving lane in `@jxsuite/server` sends what they answer. `@jxsuite/site/serve`'s `ServeOptions.mediaType` lets any host (a Worker included) type files ahead of the package table, which itself now applies the core corrections. `startPreviewServer` takes an optional project root. extensions.md §7 names these consumers. Tests that need a registry build it with `new FormatRegistry([new FormatEntry(...)])`, not the imports-scanning `buildFormatRegistry`, which `plan:_shared/formats-from-extensions` may retire.
