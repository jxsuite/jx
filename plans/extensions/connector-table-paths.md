# A connector table drives dynamic page paths through its own resolvePaths discriminator, and the studio preview expands every discriminator the build does

## Context

`specs/extensions.md` §8, line 291:

> **Status: Partial.** Every role below is declared in `EXTENSION_CAPABILITIES` (`packages/schema/src/format-registry.ts`) and by a first-party descriptor under `extensions/*/src/`. `resolvePaths` dispatches by discriminator in the site build only (`packages/compiler/src/site/pages-discovery.ts`); the studio preview's parameter picker hard-codes `contentType` and offers nothing for any other discriminator (`resolveParamValues`, `packages/studio/src/page-params.ts`). The connector `table` discriminator is not built: no connector descriptor declares `resolvePaths`, so `contentType` is the only registered discriminator. Two Consumers cells name callers that do not exist: only `jx db push` calls `bindings`, and only the studio's data grid reaches `testConnection`.

The section was unmarked before the census; its own prose (line 325) already called the `table` discriminator "**planned**", as does §5.3's paths row (line 180, "a connector table source is planned"). Re-verified on 2026-09-26.

**What ships**

- One build-side expansion: `resolvePathEntries` (private, `packages/compiler/src/site/pages-discovery.ts`) handles the legacy array, `values` and `$ref` inline, then routes any other object to the first key `registry.byPathsDiscriminator` (`packages/schema/src/extension-registry.ts`) knows, calling `resolvePaths($paths, { data, locale, projectConfig, root })`. `expandDynamicRoutes` strips `_meta` and lifts `_meta.mtime` into `sourceMtime`. It has no error handling: a throwing `resolvePaths` rejects `buildSite`, which aborts `jx build` and, through `startDev`'s up-front `await rebuild()` (`packages/server/src/dev.ts`), `jx dev` startup.
- The studio mirror: `resolveParamValues` (`packages/studio/src/page-params.ts`) tests `contentType` first (before `values`, unlike the compiler), resolves it through `ContentCollection` over `platform.resolveClass` (`POST /__jx_resolve__`), and returns `{}` for every other discriminator.
- The reference discriminator: `Content.resolvePaths` (`extensions/parser/src/content-loader.ts`, declared in `Content.class.json`) and `ContentPathsSource` in `extensions/parser/schemas/document.fragment.schema.json`. Composition unions every `$defs` member of a manifest's `schemas.document` into `PathsValue` (`fragmentDefsRefs`, `packages/schema/src/project-schemas.ts`).
- The connector: `Data` (`extensions/connector/src/Data.class.json`, implemented in `worker.ts`) owns the `data` section with `projectData` and `mount` only. Node-side table reads go through `openTable` in `extensions/connector/src/table-node.ts` (`queryTable`, `getEntry`), which `TableQuery` and `TableEntry` use at compiler timing and under the dev server's resolve proxy: it calls `resolveDialect` on the declared provider with `process.env` only (no `.dev.vars`), applies no `local:` stand-in, so D1 is reached over its HTTP API (`d1.ts`) and Supabase through `urlEnv`, and a failure degrades to a warning plus an empty result (`table-state.ts`). `worker.ts` writes `updated_at` as ISO text on every insert and update when the table keeps `timestamps` (the default, `planTable` in `columns.ts`). The connector ships no document fragment (`extensions/connector/jx-extension.json`), and only one tracked project enables it: `scripts/screenshots/fixtures/data/`.

**What the stub missed**

- The studio's round trip has to reach the desktop app, the only end-user studio: a new backend operation means the protocol route table (`packages/protocol/src/routes.ts`) and the desktop RPC bridge (`packages/desktop/src/rpc-schema.ts`, `project-session.ts`, `handlers.ts`, `window-manager.ts`, `chromium/index.ts`, `platform.ts`, `chromium/platform.ts`), so `packages/protocol` and `packages/desktop` join the workspaces, and `scripts` does for the regenerated fixture schema.

The canvas bakes a picked row through `resolveClass` (`resolveParamBoundState`, `packages/studio/src/page-params.ts`), whose `/__jx_resolve__` instance calls `getEntry` with `process.env` alone, while the studio's secrets surface writes `CLOUDFLARE_API_TOKEN` to `.dev.vars` (`packages/server/src/data-api.ts`). The data grid and the dev server's `/_jx/data` mount apply the `local:` stand-in; `openTable` does not.
- A project whose `data` section is non-empty and which sets no `build.adapter` is refused by `buildSite` before routes expand (`site-build.ts`, the `activeMounts` check near line 326), so any build-level fixture reading a table needs an adapter.
- desktop.md §5.4 names the route-parameter picker as `resolveClass?`'s user, and §3.1's family table lists every optional member; both go stale once the picker stops calling `resolveClass`.
- The spec table's lost row: line 323 ends the "Declaring both capabilities" paragraph with the `testConnection` row (signature `(connection, env) → { ok, error? }`, Consumers "studio connections UI, CLI"), and the table has no `head` row. ## Decisions

- **Open:** which database a `table` source reads. Recommendation: the connection as declared, everywhere, through `openTable` with the host's `env`, and no `local:` stand-in. The routes a build writes must be rows the deployed site serves (a `[id]` page's `TableEntry` lowers to a client fetch of the deployed `/_jx/data`), and in the studio the picker reads the database the canvas's param-bound `TableEntry` bake reads, because both go through `openTable`. The costs, stated in the docs: while developing against a D1 stand-in, `jx dev` needs `CLOUDFLARE_API_TOKEN` to list a table's routes, lists production ids rather than the stand-in rows the data grid edits, and queries D1 on every rebuild a save triggers. The two reads still differ in credentials (Context): with the token only in `.dev.vars`, the picker lists ids whose preview bakes to `null` with a warning, because `getEntry` reads `process.env` alone. That split belongs to the node-side state reads, which this plan leaves unchanged (the `env` decision below); closing it means handing `/__jx_resolve__` instances the host env, outside §8. Signed the other way (the stand-in in dev hosts, the declared connection in `jx build`), every node-side table read (`TableQuery` and `TableEntry` bakes, the resolve proxy, this source) must learn whether its host is a dev host, including a build the dev server starts; that becomes an enabling plan this one requires, since changing only this source would split the picker from the canvas.
- **Open:** what a build does when a `$paths` source throws (an unknown table, an unreachable connection, a missing credential, or any extension's failure). Recommendation: a collected build error naming the route, which then generates no pages, while every other page still builds, so `jx build` exits 1 and `jx dev` keeps serving. A warning would let a production build deploy a site whose every product page 404s with a green run, and nothing at runtime recovers a route the build never wrote; a `TableQuery` bake degrades to empty safely only because its lowered fetch re-reads at runtime. The rejection that aborts `buildSite` today is the other wrong answer.
- **Decided:** the source shape is `{ table, param?, field?, filter? }`: `param` and `field` default to `id` (the `pages/posts/[id].json` shape `docs/studio/data/tables.md` already teaches, and `TableEntry`'s key), `field` goes through `columnForField` so a reference field reads its `<field>_id` column, and `filter` is the content grammar `TableQuery` takes (`applyFilter`). No `sort`, `limit` or `offset`: the route table orders routes, and a paged route set is `plan:site-architecture/collection-pagination`'s. The fragment closes the shape (`additionalProperties: false`), as the core `values` and `$ref` members are, so a misspelled key is a schema error.
- **Decided:** `env` joins the `resolvePaths` context beside the `locale` the compiler already passes: `{ ...process.env, ...<.dev.vars>, JX_PROJECT_ROOT: root }`, the recipe `jx db push` and the data API already build, because §13 routes secrets to extension code only through a capability's `env` and a studio user stores `CLOUDFLARE_API_TOKEN` in `.dev.vars`. `openTable` takes it as an optional override, so `queryTable` and `getEntry` are unchanged.
- **Decided:** a row with a null, `undefined` or `""` field value yields no route (an integer `0` does), and a table keeping `timestamps` carries `_meta: { mtime: updated_at }` when that is a non-empty string, so the sitemap dates the route by its row (`site-architecture.md` §8.4.1). The source ignores `locale`: tables are not localized.
- **Decided:** `Data.resolvePaths` lives on the existing `Data` object in `worker.ts` and loads `table-node.ts` through an opaque specifier, the pattern `table-state.ts` already uses, because `resolvePathEntries` dispatches only to a class owning a project section and the generated site worker imports `worker.ts`, which must not pull in node dialects.
- **Decided:** the studio keeps the three core shapes in-process and sends every other object to a new optional protocol route, `POST /__studio/paths`, backing an optional platform member `resolvePaths`; the backend answers with the build's own `resolvePathEntries`, so the studio mirrors no discriminator. Not `/__jx_resolve__`: that is the runtime's class-instance proxy (`server.md` §3.2), and an optional route carries the protocol's documented degradation for a backend without it (the cloud adapter, which also omits `resolveClass`). The backend refuses a `$ref` outside the project, because the studio never sends a core shape and the route must not become a reader of any JSON file the process can open.
- **Decided:** a table's candidate list is cached like every `$paths` enumeration, until the project's file listing changes (`invalidateDerivedCaches` in `packages/studio/src/studio.ts` clears `page-params`' cache and the bar's per-document memo in `panels/pane-context.ts`), so a row added in the data grid reaches the picker after the next file change or a reload. A write-triggered invalidation would be a second trigger for both caches and a dependency from the grid onto the context bar; a stale candidate costs one empty preview, because the canvas bakes the chosen row live.
- **Decided:** the two Consumers cells are corrected rather than consumers built, because no issue, spec or docs page asks for a `jx` connection-test command or for scaffolding that writes bindings; the cells were the only claim. The table regains its `testConnection` row and gains `head`.
- **Decided:** server.md and site-architecture.md §4.3 are not edited: server.md defers the route list to `STUDIO_ROUTES`, whose generated reference documents the new route, §4.3's marker belongs to `plan:site-architecture/collection-pagination`, and §8 owns the discriminator contract. desktop.md is edited only where slice 2 makes it false (§3.1's member list, §5.4's `resolveClass?` example).
- **Decided:** no `requires` edge; four plans touch the same code and whichever lands second adapts. `plan:extensions/capability-timing-dispatch` makes `buildProjectExtensionRegistry` name an environment and already lists `resolve.ts`'s registry as a server host; `resolveProjectPaths` builds none of its own, and `Data.resolvePaths`' `["compiler", "server"]` passes both hosts. `plan:relationships/cross-domain-references` adds `include` to `queryTable` and `getEntry` without touching `openTable`'s signature. `plan:site-architecture/collection-pagination` reuses `expandDynamicRoutes`' `options.errors` and restores the by-name class lookup this plan deletes from `page-params.ts`, as its own text says. `plan:extensions/publish-canonical-schema-urls` rewrites the adjacent §5.3 row.
