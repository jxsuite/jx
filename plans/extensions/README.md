## Dispositioned without a plan

- §8.6 marker corrected from Implemented to Partial: `collectExtensionHead` (packages/compiler/src/site/site-build.ts) gates on an absent or `null` section only, while the section and the function's own doc comment say it gates like `emit` and `assets`, which also skip an empty object.
- §5.4, §6.1, §8, §8.1, §9, §9.1, §9.2, §11.1 and §12, unmarked, gained leading Partial markers for the unbuilt parts the auditors found and this census confirmed; each names what ships and what does not.
- Review of the census found four more unmarked sections the first pass had listed as verified, and each gained a leading Partial marker and a stub; it also narrowed §8's marker:
  - §3: the lowering branch of `resolvePrototypes` (packages/compiler/src/site/prototype-resolver.ts) calls `registry.byName($prototype)` before `imports` is read, so a local class named like a lowering manifest class is shadowed. `plan:extensions/local-imports-precedence`.
  - §7: the declared `mediaType` feeds only the studio's `accept` map (packages/studio/src/files/file-ops.ts) and editor language id (packages/studio/src/canvas/canvas-render.ts); both servers take `Content-Type` from `MEDIA_TYPE_BY_EXTENSION` (packages/schema/src/media-type.ts, used by packages/server/src/server.ts and packages/compiler/src/site/preview-server.ts). `plan:extensions/declared-media-type-responses`.
  - §8.4: `loadProjectSections` (packages/compiler/src/site/project-sections.ts, also the dev server's through packages/server/src/resolve.ts) gates on the key being present, and `buildRuntime` (packages/server/src/jx-mounts.ts) activates every mount. Owned with §8.6 by `plan:extensions/empty-section-gating`, since both are the missing shared predicate.
  - §10: `$studio.icon` reaches `StudioFormatHints` (packages/studio/src/format/format-host.ts) and nothing draws it; `fileIconName` (packages/studio/src/files/files.ts) and `fileIcon` (packages/studio/src/panels/quick-search.ts) pick glyphs by extension. `plan:extensions/format-icon-hint`.
  - §8: discriminator dispatch ships in the site build only, since `resolveParamValues` (packages/studio/src/page-params.ts) hard-codes `contentType`, and two Consumers cells name callers that do not exist (`bindings` is called only by packages/compiler/src/site/db-push.ts, `testConnection` only through packages/server/src/data-api.ts from the studio's data grid).
- §11, unmarked, gained a leading Partial marker for a divergence rather than an unbuilt part: `buildMountSpecs` requires `server.module` where the table says it falls back to `$implementation`. The code is right (§12 already says Workers cannot import filesystem paths), so its stub is a `reconcile`.
- §15's "Open design note" (no registry hook by which a non-connector section materialises a `data` table) is a note inside an informative worked example, not a status marker, and stays as written. The example's `jx db push` step is false today and is closed by the §11.1 stub.
- The whole-spec header stays `Partial`; there is no preamble marker, so it is not an item of its own. No roadmap, status ledger or stale status cell.
- A forward from the site-architecture census, to merge this spec's §11.1 stub and site-architecture.md §15.2's into one `plans/_shared/` stub, was verified here (packages/compiler/src/site/db-push.ts calls only the connector's `deploySchema`; `pushDataSchema` in packages/server/src/data-api.ts composes the section owners after it) and applied after both censuses, since it writes outside either one's directory: `plan:_shared/db-push-section-owners` claims extensions.md#11.1 and site-architecture.md#15.2, and the two per-spec stubs are deleted.
- The search client's highlighter splits a word written with combining marks: `wordScanner()` in extensions/search/src/client.ts scans `/[\p{L}\p{N}_]+/gu`, so `नमस्ते` becomes `नमस` and `त`, and `matchSpans` cannot mark a Devanagari or Thai query in a title or excerpt (found while detailing parser.md §3's heading anchors, verified in the closing pass of the detailing program). Not an open item: no spec states the client's matching rule. §8.4 specifies `emit` and the index it writes, site-architecture.md §12 the build pipeline, and the whole-word highlighting is described only by docs/framework/site/search.md. It is a defect outside this program, fixed by scanning with `[\p{L}\p{M}\p{N}_]+` (or segmenting with `Intl.Segmenter`, as `$wordCount` does in extensions/parser/src/md.ts) in an ordinary bug-fix pull request with a Devanagari case in extensions/search/tests; no marker and no plan.

## Spec-wide decisions

- §6.1 step 5 and §8.1 are one contract stated twice, so one plan owns both anchors, and §6.1 step 1's reconcile rides with it because it shares the anchor. No host locates a manifest through `"jx"`; the catalogue reads it only as the §9.2 hint (`declaresJxField`, packages/server/src/extension-catalog.ts, served by the dev server and desktop), as does scripts/check-extension-catalog.ts.
- §8.4's comparison and §8.6's gating are one missing predicate, so `plan:extensions/empty-section-gating` owns both anchors.
- The §9.1 settings `icon` and the §10 format `icon` share one rule (what an extension-declared glyph key must name, and what draws when it names nothing) but live on different surfaces and anchors, so they are two plans. `plan:extensions/format-icon-hint` decides the rule (a kit glyph name, an unknown one treated as undeclared), states it in §10, and owns the two strings that carry it, `declaredGlyph`'s warning and the `check-icons.ts` problem text, both worded to hold for a file row and a settings row. `plan:extensions/settings-section-vocabulary` requires it, cites §10 and reuses both strings unchanged.
- §11.1 is the same code change as site-architecture.md §15.2, so one plan, `plan:_shared/db-push-section-owners`, owns both anchors.
- §9's `referenceable` is closed by a registry view and pointer validation (`plan:extensions/referenceable-sections`); the studio's reference controls reading it belong to `plan:relationships/studio-reference-picker`, which names this plan as its prerequisite. The flag already reaches the studio in the extensions payload's `contributions[].project` (packages/compiler/src/site/format-host.ts).
- Mixed dispositions under one anchor (§9.1: drawing `icon` is an implement, the controls list a reconcile, `renderer` implement-or-remove) stay in one plan, since an anchor has one owner; the detail phase records the disposition per part.
- §11's text has two owners. `plan:extensions/empty-section-gating` owns its first sentence (the "iff" that gains the §8.4 gate); `plan:extensions/server-module-required` owns its marker and `module` row, and requires the gating plan, because flipping §11 to Implemented asserts that sentence, which is false for the worker until both hosts gate and the sentence says so.
- §5.3's union table is edited by three plans, one part each, in any order: the paths row by `plan:extensions/connector-table-paths`; the fields row's extras sentence (and §4's `schemas` row) by `plan:extensions/publish-canonical-schema-urls`; a separate closing sentence in the fields row, the paragraph after the table, the §5.2 example and §5.5 by `plan:extensions/referenceable-sections`. The same split holds for the two tables in `docs/extending/extensions/schema-composition.md`.
- §9's `description` row belongs to `plan:extensions/referenceable-sections`, whose Open decision recommends rewriting it to what ships. If it is signed the other way (Studio draws the text), the drawing moves to `plan:extensions/settings-section-vocabulary` and `plan:extensions/referenceable-sections` gains that plan as a prerequisite; neither plan widens §9.1's table for Feed's `$studio.settings.description` meanwhile.
- `plan:extensions/capability-timing-dispatch` makes `createNodeFormatIO`, `buildProjectExtensionRegistry` and `buildProjectFormatRegistry` take a required environment. Plans that add a call site do not wait for it: `plan:extensions/local-imports-precedence` (`prototype-resolver.ts`), `plan:extensions/declared-media-type-responses` (`preview-server.ts`) and `plan:extensions/connector-table-paths` (its compiler test fixtures) pass `"compiler"`, and whichever lands second adds the argument, which the typecheck finds. The same plan's first Open decision (whether any extension code runs in the studio) is the one `plan:extensions/settings-section-vocabulary`'s `renderer` decision follows.
- `buildMountSpecs` and step 1c of `buildSite` are touched by three plans: `plan:extensions/empty-section-gating` filters `activeMounts`, `plan:extensions/server-module-required` then moves `buildMountSpecs` up to step 1c (the edge above), and `plan:extensions/capability-timing-dispatch` adds its mount-timing refusal inside `buildMountSpecs` after the `server.module` check, so it fires before `dist/` is cleaned once the move lands, in either order.
- Five plans each move one description or property in `packages/schema/defs/class-def.schema.ts` (`plan:extensions/capability-timing-dispatch` `timing`, `plan:extensions/connector-serve-key` the connector `serve` key, `plan:extensions/declared-media-type-responses` `mediaType`, `plan:extensions/referenceable-sections` `referenceable`, `plan:extensions/server-module-required` the server `module`). Each regenerates with `bun run schema:sync`; a conflict in a generated `*schema.json` is resolved by regenerating, never by hand. The stray `packages/schema/--cwd` is `plan:extensions/connector-serve-key`'s to delete, and the other plans' acceptance pathspecs stay correct whether or not it has.
- `loadProjectEntry`'s cache entry (`packages/server/src/resolve.ts`) gains `formats` in `plan:extensions/declared-media-type-responses` and `config`, `registry` and `sections` in `plan:extensions/connector-table-paths`; whichever lands second keeps the other's fields, and reads `formats` from the cached registry if it is there.
- The `local:` stand-in covers exactly the dev server's data mount, Studio's data routes and Studio's schema push (`plan:extensions/connector-serve-key`'s §12 row). Node-side table reads, a table `$paths` source included (`plan:extensions/connector-table-paths`), and `jx db push` (`plan:_shared/db-push-section-owners`) read the connection as declared.
- Every plan here, on landing, rewords each `plan:` citation of itself left under `plans/`, this README included, and removes itself from every dependent's `requires` (`grep -rn 'plan:extensions/<slug>' plans/`), because `plans:check` reports a leftover as `citation-unknown` or a dangling edge.
