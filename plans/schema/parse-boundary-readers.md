# The I-JSON and NFC parse boundary judges every number literal and every key collision, and every reader of a Jx document crosses it, Studio and jx validate included

## Context

`specs/schema.md` §3.4, line 157:

> **Status: Partial.** `parse.ts` enforces `ijson.ts` wherever the compiler, `packages/site` and the server's class resolution call `parseJxDocument`, `parseProjectConfig` or `parseClassDef`, but `isSafeJsonNumber` exempts every literal with an exponent as well as every fraction, so an integer written `1e400` passes as `Infinity` and is written back as `null`. Other readers bypass the boundary with a bare `JSON.parse`: Studio's tab-open path (`parseJsonDocument`, `packages/schema/src/json-layout.ts`), its layout resolver (`packages/studio/src/site-context.ts`) and its `project.json` reads; `jx validate` (`packages/compiler/src/site/validate-command.ts`, `packages/schema/src/validate-project.ts`) for `project.json`, pages, components, layouts and class definitions; and `packages/site`'s `project.json` read. On those paths a repeated name is dropped silently and an unsafe integer is rounded.

`specs/schema.md` §3.5, line 172:

> **Status: Partial.** `parse.ts` puts every key and every string value into NFC for its callers (the compiler, `packages/site`'s documents, the server's class resolution). The readers §3.4's marker names as bypassing it apply no normalization, Studio's `parseJsonDocument` and layout resolver and `jx validate` among them, so a declaration and a reference typed in different forms still resolve to nothing in Studio's canvas and collab room, although the build joins them.

Both markers read Implemented before the census. One plan owns both because the two checks are one crossing (`parseObject` in `packages/schema/src/parse.ts` runs `findIJsonProblems`, then `normalizeIdentifiers`), so routing a reader through it closes both. Re-verified against the tree on 2026-09-27; three findings go beyond the stub.

**The boundary itself has two holes.**

- `isSafeJsonNumber` (`packages/schema/src/ijson.ts`) returns `true` for any literal matching `/[.eE]/`. Probed: `1e400` and `12345678901234567890e0` both pass (the latter reads back as `12345678901234567000`). `packages/schema/tests/ijson.test.ts` locks the exemption ("anything with a fraction or exponent passes", `1e400`; "a float literal is left alone", `1e999`).
- **New:** `normalizeIdentifiers` silently merges two keys that differ only by normalization form. `{"state": {"\u00e9tat": 1, "e\u0301tat": 2}}` (the same name precomposed and decomposed) is not a duplicate to `findIJsonProblems`, both survive `JSON.parse`, and the NFC pass keeps the second: probed, `parseJxDocument` answers `{"state":{"état":2}}` with no error. Its own comment calls the case unreachable; it is the exact data loss §3.4 exists to refuse, created by §3.5.

- schema.md §3.5 → Implemented: the same readers normalize; two keys equal after NFC are a parse failure; Studio's save keeps an unedited spelling (per the Open decision).
- studio.md §9.4 stays Implemented and records the fourth layout fact, if the Open decision is signed as recommended.
- No Future remainder.

## Decisions

- **Decided:** a literal is judged by the decimal value it denotes, not its spelling. It fails when its double is non-finite (any spelling, fraction or not, since nothing of it survives), or when it denotes an integer and `String(Number(literal))` denotes a different decimal; any other fraction is never judged, as §3.4 already says. Because that comparison is exactly "the next serialization writes the same number": `1e21` (written back `1e+21`) and `1.7976931348623157e308` pass, `12345678901234567890e0` and `1e400` fail, `1e-400` (a fraction) is not judged, and `-0` stays flagged in every spelling as it is written plainly today. Reconciling §3.4 to exempt exponent literals was rejected: it keeps a value the next save writes as `null`.
- **Decided:** two keys of one object that are equal after NFC are a parse failure, reported like a repeated name, because the NFC pass would otherwise discard the first silently, which is the loss §3.4 refuses. The check lives in the NFC walk (the only place that sees both forms); `findIJsonProblems` stays a text scan.
- **Decided:** `parseJsonDocument` crosses the boundary itself, taking an optional `sourcePath`, rather than each Studio caller crossing `parse.ts` first, because it already throws on a syntax error and every caller already handles that throw, so the change adds no failure mode, and one crossing covers the open, reload, picker, Code view, collab and settings paths together. It keeps accepting a non-object top level, as today: the object check stays with the three typed parsers.
- **Decided:** the layout record is keyed by each key's NFC form in both `deriveJsonLayout` and `serializeJson`, because the tab holds the composed document, and a pointer built from a decomposed source key would miss every layout fact beneath it.
- **Decided:** the boundary covers the three kinds `parse.ts` types (Jx documents, `project.json`, `.class.json`, including an extension's classes and manifest, which one loader reads) wherever a reader turns their text into a value it builds, renders, validates, edits or serves, generated read-backs included so the rule has no carve-out to remember. Exempt, and said so in §3.4: data files (`data/`, content collections, `$paths.$ref`, `page-params.ts`) as their loaders read them, because those values become URLs and text, so normalizing them would change built output. A reader that rebuilds a data file from its parsed value judges it anyway: Studio opens any `.json` through `parseJsonDocument` (so does `plan:site-architecture/library-collection-views`' JSON collection reader), and the refactor engine's `loadDoc` rewrites a data file a rename touches; the spelling record keeps an unedited string's bytes, and a refusal there is the silent loss it would otherwise write. Also exempt: a format extension's own `parse` (already §7's exemption); generated JSON Schemas and extension schema fragments, which are not Jx files; `packages/create`'s re-stamp of a starter's `project.json`, which depends only on `@jxsuite/starters` and whose input `jx validate` already judges in every starter root; and a value parsed once and handed on (clones, canvas bridge messages, storage, clipboard nodes, a backend's answer over the wire). The cloud host's backend is outside this repository, so its obligation is written into §3.4 and the backend protocol doc. The assistant's write gate (`ai-project-tools.ts`) reads any `.json` it is about to write with `parseJson`: it writes the text verbatim, so the only effect is refusing a repeated key or an unsafe integer before it reaches disk, data file or not.
- **Decided:** each reader answers a boundary failure the way it answers a syntax error today, and only `jx validate` changes: it reports a file that does not parse, or fails the boundary, as an issue naming it and checks the rest, because its contract is that validation failures are data and a run that stops at the first bad file hides the others. The silent answers elsewhere (Studio's project-info probe reading a bad `project.json` as "not a site") are a defect syntax errors already share, and out of scope.
- **Decided:** the NFC pass is not a shared-document version bump under `plan:collab/room-schema-skew`'s rule, so this plan does not require it. A peer at the previous version reads a composed string like any other and loses nothing (the two forms are the same text, UAX #15); the refusals happen before a room is joined (the open fails) or leave the reconciler on its last good structure; and with the spelling record an unedited line keeps its bytes in the shared source text. In a mixed room one client's tree may hold the decomposed form until it leaves, the state every room is in today.
- **Open:** whether text entering an already-open document (an Inspector field, a paste, an assistant edit) is normalized as it enters. Recommendation: no; §3.5 binds the parse boundary, that text crosses it on the next read (the build, a reopen), and §3.5 says so. The cost to sign: under §3.5's own premise (a macOS keyboard types decomposed), a reference typed into the Inspector against a precomposed declaration renders nothing in the canvas until the tab is reopened, though the build joins it. The alternative normalizes every string and key at Studio's mutation layer, which history replay and collab ops also cross, so it is a second normalization site with its own tests and a studio.md edit, and would enlarge PBR1.1.
- **Decided:** no dependency on `plan:spec/expression-build-checks`'s open question of whether `jx build` validates against the schema: the build already crosses the boundary, and this plan changes only how `jx validate` reads files, not what it validates.
- **Open:** what a save writes for a key or string whose source was not NFC and which the edit did not change. Recommendation: the source's own spelling, recorded as a fourth layout fact, because studio.md §9.4 (Implemented) promises that a one-value edit is a one-line diff, and a save that composes every decomposed line is #308's whole-file diff again. The cost is two optional maps on `JsonLayout` and one lookup per string in the serializer. The alternative writes NFC, converges the file after one save, and needs §9.4 amended to say a save may touch lines the edit did not reach.

## Implementation

Line numbers are as of 2026-09-27. Every comment cites spec sections (`schema.md §3.4`), never this plan.

### PBR1.1: the boundary (`packages/schema`, and the Studio callers' paths)

1. **`src/ijson.ts`**
   - Add a private `decimalOf(literal): { negative: boolean; digits: string; exponent: number } | null`: match `/^(-?)(\d+)(?:\.(\d+))?(?:[eE]([+-]?\d+))?$/`, join integer and fraction digits, subtract the fraction length from the exponent, strip leading zeros, then strip trailing zeros into the exponent; zero is `digits: ""`, `exponent: 0`. `null` when the literal does not match.
   - Rewrite `isSafeJsonNumber`: `const value = Number(literal)`; not finite → `false`; `written = decimalOf(literal)`, `null` → `false`; `written.digits !== "" && written.exponent < 0` → `true` (a fraction); else compare `written` with `decimalOf(String(value))` field by field. Rewrite its doc comment: judged by value, fractions exempt, overflow judged in any spelling.
   - `describeIJsonProblem`: for an `unsafe-number` whose `Number(detail)` is not finite, say it "is outside the range of a double and would be written back as null (RFC 7493 §2.2)"; the other wording is unchanged.
2. **`src/parse.ts`**
   - Export `parseJson(text: string, sourcePath: string, what = "JSON document"): unknown`: `JSON.parse` (same wrapped message), `findIJsonProblems` (same message), then the NFC walk. The private `parseObject` becomes `parseJson` plus the `isJsonObject` check; the three typed parsers keep their signatures.
   - `normalizeIdentifiers(value, path, collisions)`: when a normalized key is already in `out`, push `{ path, key }` (the NFC form) instead of overwriting. `parseJson` throws `Invalid ${what} at ${sourcePath}: key "K" in <where> is spelt twice, in two Unicode normalization forms, and normalizing (UAX #31 §R4) would discard the first`, one clause per collision joined with `; ` (`<where>` as `describeIJsonProblem` words it, the path dotted as `findIJsonProblems` paths it). The key is named once because its two spellings render identically. Replace the "cannot happen" comment with the reason for the check.
   - Module header: one sentence that `parseJson` is the crossing for a reader that takes any JSON value, and `parseJsonDocument` crosses it; add `@docs framework/agents/authoring-rules`, the page that documents both checks.
3. **`src/json-layout.ts`**
   - `import { parseJson } from "./parse.ts"`. `parseJsonDocument(text, sourcePath = "the given text")`: `document = parseJson(text, sourcePath) as Record<string, unknown>`, layout from `deriveJsonLayout(text)`. Update its doc comment and the header's "already been through `JSON.parse`" note.
   - A private `pointerKey(key)`: `segment(NOT_ASCII.test(key) ? key.normalize("NFC") : key)` (the module's own `NOT_ASCII`; `parse.ts`'s `NON_ASCII` is private). Use it for every member pointer in `deriveJsonLayout` (`value`'s object branch) and `serializeJson` (`flat` and `render`).
   - (Per the Open decision.) `JsonLayout` gains optional `spelled?: Map<string, string>` (a string's decoded source text by pointer) and `spelledKeys?: Map<string, string>` (a key's decoded source text by member pointer), each set only where the decoded text is not NFC. In `deriveJsonLayout`, decode a value string with `JSON.parse(raw)` only when `raw` holds a non-ASCII character or recorded a `\u` escape (ASCII strings stay on the fast path). In `serializeJson`, write a recorded spelling whenever its NFC equals the current value's NFC (then apply `escaped` to it, so a source's `e\u0301` comes back escaped), and the current value otherwise. Document the fourth fact in the header's "What is recorded" paragraph.
4. **`packages/studio/src`**: every `parseJsonDocument` caller gains the boundary with no other change; each passes the path it already holds as `sourcePath` (`path` in `files/files.ts`, `fileRelPath` in `studio.ts`, `name` and `tab.documentPath ?? tab.id` in `files/file-ops.ts`, `tab.documentPath ?? tab.id` in `canvas/canvas-render.ts`, `PROJECT_CONFIG_PATH` in `tabs/project-config.ts`, `to` in `format/convert-file.ts`), so the failure Studio reports names the file.
