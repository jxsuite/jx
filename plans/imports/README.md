## Spec-wide decisions

- The studio canvas's two gaps in §1.1 and §1.4 have one root cause (project-level `imports` and `$elements` are applied as though written relative to the open document) and one decision (where the rebase happens), and rebasing `$elements` is the precondition for §1.4's resolved-path dedup, so one plan owns both sections.
- The directive-name restriction in §6 was split with parser.md §7 at census; the detail phase merged the two halves into one plan, `plan:_shared/collection-directive-elements`, which claims both sections and requires `plan:imports/cem-discovery-on-every-backend` (its tag-name resolution reads that plan's `discoverNpmComponents`) and `plan:_shared/component-discovery`.
- §2 is judged on every Studio backend, not on the dev server alone: the desktop app is the end-user path, so a feature only the dev server serves is open. That qualification lives in §2's marker alone. §5 describes the Packages panel's package sections as drawn from what §2 discovers, which is true on every backend in either landing order, so `plan:imports/packages-panel-section` does not require `plan:imports/cem-discovery-on-every-backend` (the cross-spec review proposed the edge) and deletes §5's dev-server clause with its marker.
- The `requires` graph inside this spec is one edge: `plan:imports/canvas-project-context` → `plan:imports/packages-panel-section`, because the canvas stops registering an undeclared component outside `components/<tag>.json` and that is only free of an authoring regression once a card click imports as a drop does. `plan:imports/canvas-project-context` also requires `plan:studio/canvas-injects-context` (the one `injectContext` call and the recording layout loader it fills) and `plan:_shared/component-discovery` (§1.4's build half). `plan:imports/cem-discovery-on-every-backend`, `plan:imports/cem-route-payload`, `plan:imports/packages-route-payload` and `plan:imports/packages-panel-section` require nothing. The cross-spec review's `plan:imports/packages-panel-section` → `plan:_shared/component-discovery` is not drawn: §5 and §5.1 cite studio.md §5.3 and §5.4 without restating them, and the one sentence both plans write (studio.md §5.4's "dropped", which becomes "placed") is handled by whichever lands second.
- Markers owned elsewhere are edited conditionally. `plan:imports/cem-discovery-on-every-backend` rewrites the "only the dev server" clause of imports.md §5, desktop.md §6.2 and studio.md §5.4 only where that marker still stands; each owner (`plan:imports/packages-panel-section`, `plan:desktop/component-scope-sections`, `plan:_shared/component-discovery`) deletes its marker for text that names no host, so neither side waits for the other.
- `packages/server/src/studio-api.ts` has three readers of a dependency's manifest, one per plan: the components scan (`plan:imports/cem-discovery-on-every-backend`, which also always deletes the local `Cem`, `CemModule` and `CemDeclaration`), the `/__studio/packages` list (`plan:imports/packages-route-payload`) and the `/__studio/cem` route (`plan:imports/cem-route-payload`, which deletes the `CemManifest` import the first plan leaves on its handler). Whichever of the three lands last deletes `PackageJson.customElements`, which then has no reader. `plan:imports/cem-route-payload` and `plan:imports/packages-route-payload` may share a pull request; neither requires the other.
- `docs/studio/projects/dependencies.md` ends in three stray `code:` list items that `plan:imports/cem-discovery-on-every-backend` and `plan:imports/packages-panel-section` both move into the frontmatter: the first of the two to land moves them, and the second adds only its own `code:` path.
- No plan graduates imports.md unconditionally. Ten items are open across eight plans (the five here, and `plan:_shared/formats-from-extensions` §1.2, `plan:_shared/component-discovery` §1.3, `plan:_shared/collection-directive-elements` §6). Whichever pull request closes the last one (`bun run plans:status --spec imports` there) sets the header to `Implemented`, runs `bun run spec:bump imports.md <level> -m "…"` in place of its imports.md fragment (the level its fragment would have had: major for the §4.3 removal, minor for an implement), and deletes this directory. `plan:_shared/component-discovery` can never be last, since `plan:imports/canvas-project-context` requires it.
