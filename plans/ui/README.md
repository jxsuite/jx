## Spec-wide decisions

- **Text that the code has moved past is an open item.** A section whose marker is a status, and whose normative prose says something the code does not, is marked Partial and owned by a `reconcile` stub. This applies even when every element the section specifies ships. §2, §3.2, §3.3, §5.5 and §7 are marked on that rule. The census does not rewrite the prose, because that is the reconcile plan's job.
- **One ride-along, and why it is not a marker.** §11's CSS Scoping row was the only drift the census found that rides on a stub instead of carrying a marker (detailing found a second; see "A §11 row rides with the plan that owns the section it binds" below). §11 is a standards table: its cells are conformance classes under specs/standards.md, not statuses, and each row's tier is derived from the marker of the section it binds. The row binds §3, so a Partial on §11 would be read as a second statement about §3. The correction goes with `plan:ui/principles-text`, because it describes the same light-DOM decision as principle 2.
- **One stub per open anchor, even when its parts have different dispositions.** The census writes one stub per open item. Where an anchor's parts need different dispositions, the stub takes the disposition of the part that needs code, owns the paper part as well, and names both in its Context. This covers `plan:ui/menu-radio-rows` (radio row implement, `jx-menu-group` defer), `plan:ui/studio-toast-host` (adoption implement, `jx-popover` row reconcile), `plan:ui/overlay-transitions-and-slot` (transitions implement, command naming reconcile, the overlay slot either), `plan:ui/theme-ramp-only-colours` (hexes implement, spinner hooks either) and `plan:ui/element-contract-text` (reconcile, unless its events clause becomes implement). plans/README.md says to split a plan whose parts have different dispositions. The detail phase does that split, with an enabling plan that claims nothing, wherever the parts would land in different pull requests.
- **Detailing split nothing.** Every plan above lands all its parts, code and paper, in one pull request, so the split the previous bullet provides for never applies: `plan:ui/menu-radio-rows` lands the radio row with the `jx-menu-group` Future marker, `plan:ui/studio-toast-host` the adoption with the `jx-popover` row, `plan:ui/overlay-transitions-and-slot` the transitions and the slot with the command text, `plan:ui/theme-ramp-only-colours` the hexes with the spinner hooks, and `plan:ui/element-contract-text` its two `composed` sites with the text.
- **One edge, and who owns principle 5.** The only `requires` edge between these plans is `plan:ui/principles-text` → `plan:ui/behaviour-list-text`. §2 principle 5's allowed set (the sentence beginning "A behaviour sidecar may call") is edited by `plan:ui/behaviour-list-text` alone, as a ride-along of §3.3 and §7, and `plan:ui/principles-text` never touches it; its new §2 marker credits principle 5 whole, which is true only after that edit. If review moves the edit into `plan:ui/principles-text` (the Open both plans carry), it moves unchanged and the edge stays, because the moved sentence cites the §3.3 and §7 text the other plan writes.
- **§2 closes on its own text; the rules it restates are held where they are specified.** Principle 1's rules about a surface's own boxes are §3.1's (`plan:ui/surface-classes-to-parts`) and §5.2's (`plan:ui/studio-toast-host`), and principle 4's Studio half is studio-ui-guidelines.md §12's. `plan:ui/principles-text` therefore requires neither ui plan, and each of them is right in either landing order: `plan:ui/surface-classes-to-parts` writes into §3.1's body the addressing rule principle 1 defers to (`part`, or the id a host adopts a box by), and `plan:ui/studio-toast-host` strips the toast clause from the old §2 marker only if `plan:ui/principles-text` has not replaced it. This is `plan:ui/principles-text`'s second Open; if review declines it, that plan gains both edges and nothing else changes.
- **A list in a marker is edited one entry per plan.** §5's "What remains" list (`plan:ui/menu-radio-rows`, `plan:ui/studio-toast-host`, `plan:ui/jx-table`, `plan:ui/builder-section-text`) and §10's "(§5.1, §5.2, §5.4, §6)" (`plan:ui/menu-radio-rows`, `plan:ui/studio-toast-host`, `plan:ui/jx-table`, `plan:ui/overlay-transitions-and-slot`) each lose only the landing plan's own entry, rebased onto the text found at landing, and the plan that removes the last entry deletes the sentence. §3's "(§3.1, §3.2, §3.3)" is `plan:ui/behaviour-list-text`'s alone. Two plans editing one sentence or cell elsewhere touch independent clauses and rebase: the §5.1 marker (`plan:ui/menu-radio-rows`, and `plan:ui/element-contract-text`'s form-association clause), §11's WAI-ARIA row (`plan:ui/jx-table`'s table clause, `plan:ui/menu-radio-rows`'s menu clause), the §5.3 `jx-field` row (`plan:ui/element-contract-text`, `plan:studio-ui-guidelines/inline-error-role`), and `docs/extending/ui-kit.md`'s frontmatter, where each plan adds its own `spec:` line in section order.
- **A §11 row rides with the plan that owns the section it binds.** A standards row carries no marker (the second bullet above), so a row's correction or new evidence lands with the plan that closes the section the row binds: CSS Scoping and CSS Anchor Positioning with `plan:ui/principles-text`, CSS Color 5's "every semantic colour" note with `plan:ui/theme-ramp-only-colours` (the second drift, §4), CSS Transitions 2 with `plan:ui/overlay-transitions-and-slot`, and WAI-ARIA with `plan:ui/jx-table` and `plan:ui/menu-radio-rows`.
- **The conformance gates are independent of each other and of the plans that add to the kit.** `plan:ui/principles-text` (no own anchor, no `:host`), `plan:ui/element-contract-text` (names as props, the slot table, bubbling uncomposed declared events) and `plan:ui/theme-ramp-only-colours` (ramp-only colours) each add a gate that passes on today's tree and on the output every other ui plan specifies: `plan:ui/jx-table`'s four elements have no named slot, event or `aria-*` prop, `plan:ui/menu-radio-rows` adds a part, a prop and token colours, and `plan:ui/overlay-transitions-and-slot` adds transitions with no anchor. So no gate plan is a prerequisite; a plan that adds to the kit meets whichever gates have landed before it.
- **Whoever closes the last item graduates ui.md.** Every plan's "nothing graduates" is a snapshot. At landing, each runs `bun run plans:status --spec ui`; the one that closes the last open item sets the header to `**Status:** Implemented`, runs `bun run spec:bump ui.md patch -m "…"` in place and deletes `plans/ui/`, as `plan:ui/jx-table` spells out. `plans:check`'s `graduation-ready` error makes that pull request do it.
