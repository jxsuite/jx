# An image asset is edited where it is opened: a crop, quarter turns, flips, a downscale and one tone pass, baked once and written over the master

## Context

This plan and the item it claims landed together, which is what `unclaimed-open` requires: `specs/studio.md` had no §9.5 before it (§9 File Management ended at `### 9.4 Saving a JSON document keeps its layout`), and the section now sits there carrying this marker:

> **Status: Pending.** Nothing below ships. Media is shown rather than edited today (§4.2): the viewer draws the file and says what it is, and §9.3's two write doors are an upload, which never overwrites, and **Replace**, which overwrites a path with bytes chosen from disk. This section adds the third: the same path, overwritten with bytes Studio computed from the ones already there.

Verified against the working tree on 2026-11-03; paths under `packages/studio/src/` unless they name another workspace.

**What ships already, and is the reason this is tractable.** Two pieces of the feature landed earlier as their own pull requests:

- `saveFile` refuses a media tab. `hasSerializableDocument` (`files/file-ops.ts:317`) returns `!isMediaFile(tab.documentPath ?? "")` and is checked in `saveFile` at `:375`, after the `collabReadOnly` refusal. Before it, a media tab's stub document reached `serializeDocument`, whose native-JSON tail is `JSON.stringify`, and the Save chord wrote a placeholder document over the image and reported success. The guard is keyed on the FILE rather than on the mode, deliberately, because an `.svg` in its `source` alternate has the same stub behind it.
- `StudioPlatform.readFileBytes?(path): Promise<ArrayBuffer>` (`types.ts:411`) returns a project file's raw bytes. `readFile` decodes UTF-8 and Bun replaces invalid sequences with U+FFFD, so a JPEG through it is unrecoverable. It is implemented on all four adapters (`platforms/devserver.ts:356`, `platforms/cloud.ts:1060`, `packages/desktop/src/webview/platform.ts:473` over a base64 RPC, with the backend at `packages/desktop/src/backend/project-session.ts:1011`), served by `GET /__studio/file/bytes` (`packages/server/src/studio-api.ts:1265`, declared at `packages/protocol/src/routes.ts:152`), and gated as `"readFileBytes"` in `CAPABILITIES` (`commands/context.ts:42`) whose comment already names this feature as its reason.

**What the two media surfaces are**, because they are easy to conflate and the host decision turns on the difference:

| Surface                  | Mode         | Dispatched by                             | Module                                                   |
| ------------------------ | ------------ | ----------------------------------------- | -------------------------------------------------------- |
| the single-file viewer   | `media`      | `canvas/canvas-render.ts:1400`            | `media/media-pane.ts` + `surfaces/media-pane.json`       |
| the Media workspace home | `media-home` | `workspace/workspace-home.ts:102,115,135` | `media/media-library.ts` + `surfaces/media-library.json` |

`MEDIA_HOME_MODE = "media-home"` is at `media/media-library.ts:105`. Both are surface documents already; neither is lit.

**What is missing** is everything between the bytes and the write: a model of an edit, a preview, a bake, and the one door that performs it. There is no crop, rotate, resize or tone code anywhere in `packages/studio/src`, and `src/media/` holds only `media-commands.ts`, `media-library-model.ts`, `media-library.ts`, `media-open.ts` and `media-pane.ts`.

**Measured rather than assumed.** Five properties of the host were measured in the repository's own Chromium (Playwright, `--force-color-profile=srgb`, `deviceScaleFactor: 1`) because each one decides a contract in §9.5, and three of them fail silently:

1. `OffscreenCanvas`'s 2D context supports `.filter`, and `getComputedStyle(img).filter` and `ctx.filter` round-trip the identical string. So one recipe drives both renderers.
2. They do **not** share a pixel pipeline. Over 42 samples (6 filter stacks x 7 colours) the composited preview and the baked output differ by at most **2/255** on any channel, only where filter functions are chained, and are identical under an empty recipe. A test therefore asserts a tolerance, not equality.
3. `convertToBlob` with a type the host cannot encode **does not reject and does not throw**: it returns a blob whose `type` is `image/png`. Asking for `image/gif` or `image/avif` yields PNG bytes, which written to a `.gif` path is exactly the failure §9.3 names for Replace, "bytes the address does not describe".
4. Past the maximum drawing surface the failure is also silent: at 20000x20000 `getContext("2d")` returns a context, `fillRect` appears to succeed and `getImageData` reads back zeros. 16384x16384 and 16384x8192 are fine.
5. `imageSmoothingQuality` defaults to `"low"`, and a reduction of more than about a factor of two in one step aliases visibly. The build's own derivative path uses sharp (`packages/compiler/src/site/image-optimizer.ts`), and under `images.service: "cloudflare"` there is no sharp pass at all, so the default would ship.

`createImageBitmap` also **downscales at decode** (`{ resizeWidth }` alone preserves aspect: 4000x3000 to 500x375), and `ImageBitmap.prototype.close` exists, so no preview ever needs full-resolution pixels and the one full-resolution allocation can be released promptly.

**Found while verifying, not in the original scoping:**

- **EXIF orientation is not a hazard here, and the real consequence is the opposite one.** Chromium applies an orientation tag in `createImageBitmap` regardless of `imageOrientation` (`"none"` left the spec enum in favour of `"from-image"` as the default), and an `<img>` of the same bytes agrees: a 40x20 source with Orientation 6 reports 20x40 in all four paths. So decode and preview cannot disagree. What a save does is **normalise the orientation into the pixels and drop the tag**, which is correct and still swaps the file's recorded width and height.
- **PNG alpha round-trips exactly**, including alpha 1/255, through `putImageData` to `convertToBlob` to `createImageBitmap` to `drawImage` to `getImageData`. The premultiplication concern does not apply to this pipeline. It was not tested with a `ctx.filter` set, which is why a test covers that case rather than inferring it.
- **The canvas PNG encoder cannot write a palette**, so a flat graphic a dedicated optimiser stored as an indexed image re-encodes as full-colour and grows. This is a property of the encoder, not a measured ratio.
- **`assetCapabilities.maxUploadBytes` is declared by no adapter.** It is typed at `packages/protocol/src/types.ts:151` and read twice (`files/media-upload.ts:327`, `:420`), and a grep over every adapter finds nothing that sets it. `replaceAsset`'s size refusal is therefore dead code on every current host, so the source ceiling here must be a Studio-side constant rather than borrowing its shape.
- **A byte-level signature check must not go through `TextDecoder`.** Every Latin-1 label is windows-1252 in the Encoding Standard, which remaps 0x80 to 0x9F: `new TextDecoder("latin1").decode([0x89])` is U+2030, not U+0089, and 0x89 is the PNG signature's first byte. The sniff compares bytes directly.
- **`specs/studio.md` §13.4's `capability` row already lists `readFileBytes`** (line 1575). `plans/studio/README.md` says twice that the row omits it and assigns the fix to `plan:studio/file-tree-command-records`; that note is stale and there is nothing here to coordinate.
- **`collab.readOnly` exists on the command context** (`commands/context.ts:265`, populated at `live-context.ts:200`) and nothing in Studio gates on it.
- **The `studio.js` ceiling is 1,100,000 bytes**, last measured 1,079,992 (`packages/studio/bundle-budget.json`). Earlier scoping carried a 3 MB figure, which is the pre-Spectrum-removal, pre-minify number in that file's `$ratchet-kit-coexistence` note.

Owned elsewhere and left alone: §4.2's marker and the shape of its Modes table (`plan:studio/canvas-modes-table`); §22.6's two unbuilt filters (`plan:studio/media-alt-and-tag-filters`); §6.1's media-picker widget names (`plan:studio/style-sections-table`); §13.5's `probe.idle()` source clauses (`plan:studio/panel-scheduler-text`), which this plan does not add a source to.

- `studio.md` §19 gains a WHATWG HTML row, `**Pending**` with `gap:studio-image-editing` while §9.5 is, and `**Subset**` with evidence when it is not.

## Decisions

- **Decided:** a new `image` canvas mode on the media tab, not a stage of the Media workspace home and not a dialog, because §14.7 already owns the hardest problem this feature has. Its `showSaveDiscardDialog` prompt is asked by `⌘W` and the tab's `×` "through one implementation"; its close is conditional on the write, "never concurrent with it", which is why `saveFile` returns a boolean; and it already specifies the **two-answer** variant headlined _Changes Cannot Be Saved_ for a read-only collaborator. A destructive editor that keeps no backup needs all three, and the library home cannot have them: `detachMediaLibrary` (`media/media-library.ts:1096`) is synchronous and is called from `workspace-home.ts:115` on mode change, tab switch and project close, so it cannot await a prompt, and `homeChoice` is module-level so its selection is not even per-pane. `session.ts:285` then restores the mode across a relaunch for free, because it keeps `stored.canvasMode` whenever `tab.capabilities.modes` includes it.
- **Decided:** the `media` mode stays read-only and the editor is its sibling, so §4.2's "shown rather than edited" and the Media row `plan:studio/canvas-modes-table` plans to write both stay true. `mediaTabModes` (`media/media-open.ts:36`) already returns a second mode for one media type, `[MEDIA_MODE, "source"]` for `.svg`, so a media tab offering a second editor is shipped behaviour.
- **Decided:** no `requires` edge on `plan:studio/canvas-modes-table`, because its own integration contract settles it: "a pull request that adds a mode string adds a row", and "plans editing neighbouring text touch different lines and rebase on this text without depending on it". An edge would also pin this plan at `drafted` indefinitely, since `requires-not-ready` refuses a `ready` plan whose prerequisite is `drafted`.
- **Decided:** a row in `EditorKind`, `EDITOR_KIND_BY_MODE` and `EDITOR_KIND_LABELS` is mandatory, not optional. An unmapped mode resolves to `"canvas"`, which is the defect `commands/context.ts`'s own header records as having let `⌘V` paste an element node into `project.json`. No row in `CANVAS_MODES` or `SELECTABLE_CANVAS_MODES`: the mode is reached by the Editor switch and by a command record, never by `canvas.setMode`, which is the reasoning §4.2 already records for `git-diff`.
- **Decided:** the crop is stored in **source-bitmap coordinates**, before any turn or flip, and exactly two pure functions cross between that frame and the one the author is looking at. `drawImage`'s source rectangle is in source coordinates, so storing the crop anywhere else forces an inverse map at the one place a mistake is invisible: the preview looks right and the bake crops elsewhere. A handle is named for where it sits on screen, so under one quarter-turn the top handle moves the source's left edge and a flip reverses that again; both directions are pure, and a round trip over all 8 handles x 4 turns x 2 flips x 2 flips is identity.
- **Decided:** the preview is CSS over the image the author is already looking at, and the bake is an `OffscreenCanvas`. No `<canvas>` is needed in the editor's DOM at all, which sidesteps the surface rules rather than litigating them, and `OffscreenCanvas` is not a DOM node so no part of the bake is imperative DOM construction. Crop geometry rides as interpolated custom properties in the surface document's own `style` block, which `surfaces/block-action-bar.json:13` and `surfaces/formula-palette.json:12` already do and whose `$description` records believing otherwise as a past mistake: "They used to travel as a `style` ATTRIBUTE the flow assembled into one string, on the belief that a document cannot bind a style declaration to state. It can, and always could."
- **Decided:** one write door, with the refusals inside it. The chord, the editor's own control and the command record all call one `saveImage`, which performs the read-only refusal itself; and the command record's `when` gates on `collab.readOnly` as well, so the verb is not offered either. This is the shape Phase 1 used for `hasSerializableDocument` (inside `saveFile`, not on the `file.save` command) precisely so a second caller could not miss it.
- **Decided:** `⌘S` delegates rather than refuses. `saveFile`'s media guard keeps its job for every other media mode and gains one branch for `image` mode, so the chord stays the same key for the same intent and there is still one door.
- **Decided:** the save reuses `replaceAsset` (`files/media-upload.ts:408`) rather than calling `uploadFile` directly, so an edit cannot acquire a different story about caches, usages or a backend that stored the file elsewhere than the Replace gesture beside it. It supplies the format refusal, `forgetVersions([path, written])`, `invalidateUsages()`, `announceMediaChanged(parentDir(path))` (whose handler at `studio.ts:608` reaches `invalidateMediaMeta` through `invalidateMediaCache`), and the `written !== path` Problem rather than a toast. It also fires its own `notify.success(\`Replaced ${name}\`)` at `media-upload.ts:454`, carrying no size, so reusing it unchanged would mean either the wrong toast or two of them: it gains one optional detail argument, which is the smallest seam that keeps one toast per write.
- **Decided:** the bake verifies before the write, because every relevant host failure is silent. The output must be within the maximum drawing surface, the encoded `blob.type` must equal the MIME the path's extension promises, and the blob must be large enough to be an image. Without the second, widening the editable set later would corrupt a file rather than fail; without the first and third, a surface that produced nothing would be written over a file that was something.
- **Decided:** a save re-decodes from the bytes it wrote before it resets the recipe. The decoded source and the recipe are always of the same generation, so an empty recipe always means "what is on disk". Resetting the recipe over a stale source leaves the next save writing the original bytes back and silently undoing the first edit, which with no backup is the worst thing this section could do.
- **Decided:** the editable set is decided from the bytes, not the extension. A still `.png` and an animated one share one, so the container is sniffed: the PNG signature with an `acTL` chunk before the first `IDAT`, or `RIFF`/`WEBP` with the animation bit in a `VP8X` header. An animated `.png` or `.webp` is refused for the reason `.gif` is. Without this the exclusion rule contradicts itself and an animated WebP loses every frame but the first in silence.
- **Decided:** the recipe, its undo stack and its dirty flag are **per-tab**; only the mount and an in-flight drag are per-pane. The first draft of this plan had them per-pane, copying `media/media-pane.ts`, and that is wrong because `canvasMode` is per-TAB (`tab.session.ui.canvasMode`, resolved by `canvasModeOfTab` and `canvasModeOfPane` in `canvas/canvas-utils.ts`): two panes showing one image tab are necessarily both in the editor and cannot differ, so a per-pane recipe gives `saveImage(tab)` no addressable subject and makes two pending crops for one file. The repo's precedent for per-tab state that must differ per pane is `zoomOf` carrying it on the derivation, and its docstring says why it applies there: "a LENS shares its tab with the pane beside it, so under a lens the two stages would zoom together, which is exactly what 'the same page at another breakpoint' must not do". A crop is not that case. It is a property of the file, not of the viewport, so two panes showing one pending crop is the correct answer rather than a compromise, and it makes `saveImage(tab)`, `imageEditorDirty(tab)` and `shouldWarnOnClose(tab)` all well-defined on the subject they already take.
- **Decided:** the editor's dirty state is its own and is not `tab.doc.dirty`. A media tab carries `MEDIA_STUB_DOCUMENT` (`media/media-open.ts:27`), and treating a stub document as the subject is what the Phase 1 guard exists to stop. §14.7's single implementation learns to consult it, which is an edit to shared machinery and is in the integration contract.
- **Decided:** enlarging is not offered, and **Fit for web** reads the project's own `images.widths` rather than importing `@jxsuite/compiler`. A bake cannot add detail and a larger master costs every derivative; and reading the project keeps Studio's dependencies as they are, so `scripts/ci/affected.ts` needs no `EXTRA_EDGES` entry.
- **Decided:** no confirmation dialog on save, one permanent sentence instead. A confirm on every write is a tax the author learns to dismiss unread; naming the path, the absence of a backup and source control as the recovery path, in view whenever the control that writes is in view, is the honest form of the instruction that there be no backup. `showSaveDiscardDialog` stays the single dialog, for leaving dirty.
- **Decided:** the v1 tool set is crop, quarter turns, both flips, a downscale with **Fit for web**, encode quality where it means something, one scale-invariant tone pass (brightness, contrast, saturation) and Reset. Blur, sharpen, vignette and grain are deferred because none is scale-invariant or expressible in the shared filter grammar, so each needs a pass of its own and a preview that disagrees with its bake. Straightening needs an automatic crop and a corner decision; format conversion is a rename (§9.1.1) and then an edit; raster text is invisible to search, a screen reader and §16.6's report; background removal is an order of magnitude larger than the whole bundle and produces alpha, which for a `.jpg` is a format change.
- **Decided:** a save mints a **repaint key**, and this is the defect the first draft of this plan missed. `previewFileSrc` (`files/media-paths.ts:128`) applies `withVersion` only on the `space === "repo"` branch and otherwise returns `loopbackAssetSrc(...)` with no cache key at all, and only `platforms/cloud.ts` declares `assetSpace: "repo"`; `forgetVersions` (`files/asset-versions.ts`) sets `changed` only inside a successful `versions.delete(path)`, so on a host that never vouched a version no epoch moves either. So on `jx dev` and both desktop launchers an in-place overwrite leaves a byte-identical URL, and every `<img>` already decoded in the DOM — the viewer, the library tile, the detail preview, the Site panel, every artboard — keeps the old pixels. Re-listing the directory does not help, because the `src` string does not change. The fix is a second, clearly separate channel: `noteLocalWrite(path)` stamps a monotonic token that both asset-URL builders append in **both** of their branches. It is deliberately **not** written as `v`: §3.4 binds that name to a version the host issued and may answer immutably, and a Studio-minted token is neither.
- **Decided:** the save marks its own write as a local mutation first. `markLocalMutation` (`files/fs-events.ts:50`) opens the window that absorbs the watcher's echo of Studio's own write, and `files/asset-versions.ts:20` documents it as "forgets the paths Studio is about to write". `replaceAsset` does not call it: `grep markLocalMutation packages/studio/src/files/media-upload.ts` prints nothing, while `format/convert-file.ts` and `media/media-library.ts`'s delete flow both do. So **Replace diverges from §3.4 today**, and the slice that adds the repaint key repairs both doors at once rather than giving the editor a behaviour its neighbour lacks.
- **Decided:** an identity recipe writes nothing and says so. A lossy round trip for a Save that meant nothing degrades the master for no edit, and the measured parity result is that an empty recipe is the one case that is exactly identical, so there is nothing to gain by writing it.
- **Decided:** `replaceAsset`'s `false` return is honoured rather than ignored. It reports `written !== path` as a Problem, because two files then exist and the author has a decision to make; `saveImage` must not reset the recipe or re-decode on that path, or the editor would claim a save that went somewhere else.
- **Decided:** the eight crop handles are **one** roving tab stop, not eight, and an arrow nudge is announced through `services/announce.ts`. Eight stops between the image and the controls is the keyboard trap a composite widget is supposed to avoid, and a nudge that moves one pixel with no readout is invisible to a screen-reader user. Two of the glyphs this needs are absent from the kit's 107-entry manifest (`packages/ui/icons/list.json`): **`crop`** and **`flip-horizontal`**, while `flip-vertical`, `arrows-clockwise`, `image`, `sliders-horizontal` and `check` are present. They are added to that manifest in the slice that first names them, because `check-icons.ts` records that an absent `icon:` key "draws nothing above the label and warns once in the console, which a screenshot does not show". Rotate-left needs no new glyph: `jx-icon` takes `mirror`, so it is `arrows-clockwise` mirrored.
- **Decided:** the three tone controls ship on `jx-number-field` and `jx-slider` is not built. Studio contains no range input of any kind today and does not name `jx-color-slider` once, while `jx-number-field` is in six surfaces; `packages/ui` is at `functions = 1.0`, so a new element and its sidecar need every function tested; and SC 2.5.7 means the numeric control has to exist either way, so a slider would always be the second control rather than the only one. `specs/ui.md` §5.5 records the procedure and its outcome: five proposed elements were audited after every consuming surface had converted without them, and none was built. If a built surface then demonstrably fails to convert, that is when §5.5's own procedure says to add the element.
- **Open:** do the three tone controls ship in v1 at all? Recommendation: **yes**, which is what §9.5 says. They are the cheapest tools here, because CSS does the preview and the bake reuses the same string; against that, they are the lowest-frequency tools for someone building a site and they carry the whole preview-versus-bake tolerance. Cutting them is a `minor` edit to §9.5's two tone paragraphs and its deferred list, and it removes the only reason the slider question could come back.
- **Open:** when a `.png` re-encode comes back larger than the file it would replace, does the save write it anyway and report the growth, write it with a prominent note, or refuse? Recommendation: **write it and report the size**, because the author asked for a crop and refusing loses the crop over a size concern they may not share; the growth is reported either way, since the browser's encoder cannot write a palette and a flat graphic stored as an indexed image can grow several times over. §9.5 currently says only that the size written is reported, so either of the other two answers is a one-sentence spec edit.
- **Decided:** a foreign change to the file between open and save is **not** detected in this scope, and §9.5 says so rather than implying otherwise. `markLocalMutation` suppresses Studio's own echo, which is the opposite direction. What is in scope is that the save re-decodes after it writes, so the next save is never stale; detecting an outside rewrite needs the fs-event stream to mark the stage stale and refuse Save until re-decoded, which is a follow-up and is named as one.

## Implementation

Paths under `packages/studio/` unless they start with `specs/`, `docs/` or another package.

1. **`src/media/image-recipe.ts`** (new, pure, no DOM and no canvas). The `ImageRecipe` record: `crop` in source coordinates, `turns` (0 to 3), `flipH`, `flipV`, `width`, `quality`, `brightness`, `contrast`, `saturation`. `IDENTITY`, `isIdentity`, `outputSize(recipe, source)` (the crop's, swapped on an odd turn), `filterString(recipe)` (the CSS filter, empty when all three are neutral), and the two coordinate mappings `sourceToDisplay` and `displayToSource`. Nothing here knows about a file, a tab or a host primitive.
2. **`src/media/image-format.ts`** (new, pure). `sniffImage(bytes: Uint8Array)` returning the container and whether it is animated, by direct byte comparison with no `TextDecoder`; `mimeForPath(path)`; `isEditableImage(path, bytes)` combining the extension set with the still-image requirement; and `sourcePixelCeiling` with the arithmetic behind it in a comment, since `assetCapabilities.maxUploadBytes` is set by nobody.
3. **`src/media/image-bake.ts`** (new, the only module that touches pixels). `bakeImage(recipe, bytes, mime, { createBitmap, Offscreen })`, with both host primitives as parameters defaulting to `globalThis.createImageBitmap` and `globalThis.OffscreenCanvas`, so the module is exercised under happy-dom against fakes with no `mock.module()` of a first-party file. It decodes with `imageOrientation: "from-image"` stated explicitly, sizes the destination to `outputSize`, transforms the context by the turns and flips, sets `imageSmoothingQuality = "high"` and `ctx.filter = filterString(recipe)`, draws the stored source rectangle directly, encodes, closes the bitmap, and then verifies: the target within the maximum surface, `blob.type` equal to `mimeForPath`, and a plausible size. A failed verification returns a reason and writes nothing.
4. **`src/media/image-editor.ts`** (new, the flow). **Two maps, at two scopes.** The recipe, its undo stack, the decoded source and the dirty flag live in a per-TAB map keyed by `documentPath`, because the mode is per-tab and a crop belongs to the file; the mount, its `effectScope` and any in-flight drag live in a per-pane map keyed by `paneId`, with `attached()` so the next canvas repaint cannot tear down an in-flight mount, as `media/media-pane.ts:73` does. Exports `IMAGE_MODE`, `renderImageMode(surface, tab)`, `imageEditorMounted(paneId, tab)`, `detachImageEditor(paneId)` (which releases the pane's mount and, when it was the last pane showing that tab, the decoded source too), the recipe stack (push on gesture end, whole-record undo), `imageEditorDirty(tab)` for `shouldWarnOnClose` to consult, and `saveImage(tab)` as the one write door, performing the read-only refusal against that tab's own collab state and then `replaceAsset`, re-decoding from the written bytes before resetting the recipe. A pane repaint after a gesture in another pane follows from the recipe being one reactive record both mounts project.
5. **`src/surfaces/image-editor.json`** and **`src/surfaces/image-editor.ts`** (new). The document declares the stage, the `<img>` whose `src` is a same-origin blob URL, the crop frame with eight `<button>` handles each carrying an `aria-label` (`packages/schema/src/a11y.ts:365` names a button from content or `aria-label`, and a `div` has no naming route), the control accordion, and the permanent overwrite sentence. Crop geometry is four custom properties interpolated from state in the document's own `style` block; the drag's hot path writes the property directly on the element, as `panels/block-action-bar.ts` does when it clamps, releasing its previous write before it measures. The adapter computes a flat view of pre-formatted strings and discriminant words and pushes it with `.update(view)`, and its handle also exposes `attached()` beside `ready`, `update` and `dispose` — `media/media-pane.ts:83` calls `panel.surface.attached()`, and `SurfaceHandle` itself (`ui/surface.ts:107`) carries only `scope`, `root`, `elements` and `dispose`, so that predicate is the adapter's to add.
6. **`src/media/media-open.ts`**: `mediaTabModes` returns `[MEDIA_MODE, IMAGE_MODE]` for a path whose extension is in the editable set on a host that has `readFileBytes`, keeping `source` for `.svg`.
7. **`src/commands/context.ts`**: `EditorKind` gains `| "image"`, `EDITOR_KIND_BY_MODE` gains `image: "image"`, `EDITOR_KIND_LABELS` gains `image: "Image"`. `keyScopeStack` needs no edit: its default is the global stack, which is correct, because there is nothing here to paste a node into.
8. **`src/canvas/canvas-render.ts`**: a `canvasMode === IMAGE_MODE` branch beside the `media` one at `:1400`, and an `imageEditorMounted(paneId, tab) && !modeChanged` fast path beside `:1181`.
9. **`src/files/file-ops.ts`**: `saveFile`'s media branch delegates to `saveImage` when the active mode is `IMAGE_MODE`, and otherwise refuses as it does now. The comment above `hasSerializableDocument` gains the sentence saying why the guard is still keyed on the file.
10. **`src/media/media-commands.ts`**: a fifth record, `media.edit { path }`, whose `when` is `ctx.project.open && ctx.capability.readFileBytes`, with its flow dynamically imported on first run as the other four are. It does **not** gate on `ctx.collab.readOnly`: `live-context.ts:199` populates that from `collabState(tab)` for the FOCUSED tab, so a record taking a `path` would gate on a different file's session. The refusal therefore lives where it can read the right tab, inside `saveImage`, and the editor's entry point withholds itself by asking `collabState` for the path's own tab. The Media library's detail pane gains the action beside Replace and Delete, withheld on the same conditions the record gates on, so the palette and the UI cannot give two answers to one question.
