# The Studio canvas composes a page the way the build does: its whole layout chain, and the `$site`, `$page` and project `state` the build injects

## Context

`specs/studio.md` §4.1, line 162 (unmarked before the census; the cross-spec review found the gap):

> **Status: Partial.** The canvas renders through `@jxsuite/runtime` and applies the site's styles, custom properties, `$media` and `$head` (`packages/studio/src/site-context.ts`). It does not inject the page context the build injects (`injectContext` in `packages/site/src/context.ts`): it never supplies `$site` or merges project `state`, and supplies `$page` only for a page with route params, where `substitutePreviewParams` (`packages/studio/src/page-params.ts`) gives it `params`, `title` and `url` alone, so a binding on any of the rest renders differently in the canvas than in the build.

§4.1 promises "no simulation or approximation" and §3.6 that "the canvas always shows what the file will look like in the context of the full site". The function that produces that context was made platform-free for this host: the header of `packages/site/src/context.ts` names "the studio's canvas" as a renderer that binds `${$site.name}` and `${$page.url}` exactly as a built page does. `@jxsuite/studio` already depends on `@jxsuite/site` (`routes`, `site-style`), and `context.ts` and `layout.ts` import only `@jxsuite/schema`. A reconcile would write down that the canvas renders a site page without its site.

**Verified at the current tree (2026-09-27).**

- `injectContext` has two callers and the canvas is not one: the build (`compilePage`, `packages/compiler/src/site/site-build.ts` line 1279, through `packages/compiler/src/site/context-injection.ts` with `nodeImportRebaser`, the locale's `i18n` and translation set, and a concrete route from `expandDynamicRoutes`) and the live preview (`composePage`, `packages/site/src/compose.ts`, `null` rebaser, no translation set). The "cloud's preview origin" the header also names is a backend outside this repository.
- `resolveCanvasDocument` (`packages/studio/src/canvas/canvas-live-render.ts`) composes the render document itself. `distributePageIntoLayout` (`site-context.ts`) wraps one level deep and carries `state`, `$media`, `style` and `attributes`, never the page's `title`, `$head` or `$elements`. It then applies `getEffectiveElements`, `getEffectiveImports`, `getEffectiveMedia` and `getEffectiveHead`. No `$site` token exists in `packages/studio/src`.
- `$page` comes only from `substitutePreviewParams` (`page-params.ts` lines 240–259, called at line 229) for a page with chosen `previewParams`: `title` is `doc.title` or `""` (the layout's title under a wrap), `url` is the pattern (`/blog/:slug`), and there is no `locale`, `dir` or `alternates`.
- Edit and Design show a binding as its expression (`prepareForEditMode` in `utils/edit-display.ts`), so the artboard differs in Preview. In every mode the difference is in the iframe's `dataScope` snapshot (`serializeDataScope` posts every scope key; adopted in `canvas/iframe-host.ts`), which the Data panel and `services/preview-eval.ts` read, and in `Intl/*` formulas, which take `$page.locale` when the call names no locale (`withPageLocale` in `packages/runtime/src/expression.ts`).

**Found while detailing** (closed here, because each is the canvas composing a page differently from the build):

1. **Nested layouts.** The museum starter's `layouts/ar.json` and `layouts/fr-ca.json` are `{ $layout: base.json, state, children: [slot] }`. The canvas wraps an Arabic page in `ar.json` alone, so it renders with none of `base.json`'s header, language navigation or footer. `resolveLayout` (`packages/site/src/layout.ts`) follows the chain.
2. **Format-backed pages.** `splitFormatDocument` (`packages/studio/src/format/format-host.ts`) keeps only `state`, `imports` and `children` on a content document and moves every other key to `tab.doc.content.frontmatter`, which never reaches `resolveCanvasDocument`. So a markdown page's `title`, `$head`, `$layout` and `$lang` are invisible to the canvas; the fitness-studio, professional-firm and event starters' markdown pages declare `title` there. The build parses them from the same file.
3. **What a page is.** `isPage` is "under `pages/`", so a co-located `pages/blog/_card.json` component is wrapped in the default layout on the canvas. The build never routes, wraps or injects a file `isRoutedPageFile` (`@jxsuite/site/routes`) rejects.
4. **The in-place write.** `injectContext` assigns into `doc.state` and adds keys to an existing `doc.imports`. In Edit and Design, `stripEventHandlers` (`utils/strip-events.ts`) copies `state` but passes `imports` by reference, so a direct call on an unwrapped page would write the project's imports into the tab's document, and a save would keep them. `$media` and `$elements` are reassigned, not written.

**Not claimed, no owner** (recorded for whoever next touches them): a format-backed page's frontmatter `$elements`, `$media`, `style` and `attributes` still never reach the canvas; and in the build a layout-wrapped page's `$page.locale` reads the layout's `$lang`, because `resolveLayout` does not carry the page's `$lang` onto the composed document, while `<html lang>` reads the page's (site-architecture.md §5.5 and §13.4). The canvas inherits the second by construction.

This plan enables three others: `plan:imports/canvas-project-context` fills the rebaser and project config of the call added here, `plan:studio/site-state-in-data-panel` gets live values for the project's entries in the `dataScope` snapshot, and each property `plan:site-architecture/page-context-props` adds to `injectContext` reaches the canvas with no canvas change.

What cannot be computed for one document is stated (Open below).

## Decisions

- **Decided:** a page is composed by the build's two functions, `resolveLayout` then `injectContext`, and the canvas stops applying `getEffectiveMedia`, `getEffectiveImports` and `getEffectiveElements` to a page's render document, because a second merge beside the build's is how the two came to differ. `getEffectiveHead` stays, fed the layout level and then the page's own `$head`: `injectContext` merges no head (the build merges it with `mergeHead`), and the canvas injects `$head` itself (`injectHead` in `canvas/iframe-render.ts`).
- **Decided:** the wrap is `resolveLayout` with a loader over `resolveLayoutDoc` that stamps `markLayoutNodes` on each level it loads, followed by `unionElements` (`@jxsuite/site/compose`, `composePage`'s own rule) for the page's `$elements`; the bundler keeps only the export it calls, and the bundle budget check confirms it. `distributePageIntoLayout` and its `fillSlots` are deleted. A layout that cannot load, or a chain `resolveLayout` rejects, renders the page unwrapped, as a missing layout does today. Nested layouts (finding 1), and whatever `resolveLayout` gains later, then reach the canvas with no canvas change, and each level's nodes are marked with their own file, so Open Layout still opens the file that holds the node.
- **Decided:** a page is a file under `pages/` of a site project that `isRoutedPageFile` accepts, for the wrap, the context and the component-props gate alike (finding 3), because that is the build's definition, and an `_` file is a component.
- **Decided:** the route is `canvasPageRoute(documentPath, previewParams)`: `sourcePath` the project path, `_pathParams` the chosen values, and `urlPattern` the pattern with those values filled in by `fillRoutePattern`, a catch-all's named value standing for `*`. That is `expandDynamicRoutes`' route for the page the values name. With no value chosen it is the pattern and `{}`, because the build has no route without values and the pattern is the honest placeholder.
- **Decided:** `$page.locale` and `$page.dir` follow the route, not the pane's rendering language, because §20.2 already says that language changes `lang` and `dir` on the artboard "and nothing else". So a French page in an English pane formats its dates in French, as it will when built.
- **Decided:** the page's facts (`title`, `$head`), its `$layout` and its `$lang` are read from the tab's source document merged over its frontmatter, not from the render copy, because Edit rewrites a templated `title` into its display token and a format-backed page keeps those keys in frontmatter (finding 2).
- **Decided:** before the call the render document gets its own `state`, `imports` and `$elements` (shallow copies), because `injectContext` writes into the first two in place (finding 4); the `$elements` copy also keeps the discovery block's `push` off the tab's document for a page. `substitutePreviewParams` keeps only its `#/$params/` substitution and runs after the injection, as `resolvePrototypes` runs after `injectContext` in `compilePage`. Inherited entries meet the same Edit/Design gates as the page's own (`setSkipServerFunctions`, `setSkipAutoRequests` in `iframe-render.ts`), so nothing more is stripped.
- **Decided:** this plan requires `plan:site-architecture/page-context-props`, because the call needs its `PageFacts` parameter, `readPageFacts` and `fillRoutePattern`, and until it lands the build's `$page.title` on a wrapped page is the layout's, so the canvas has no right value to match. That plan asked for the edge, and its conditional canvas step (its step 7) then never applies. No `packages/site` source changes here.
- **Open:** what does a document that is not a page receive (a layout, a component definition, a content entry opened on its own)? Recommendation: no page context, only §3.6's site context as today, because the build injects into a page and nothing else, a layout's `$page` is whichever page it wraps, and components receive nothing implicitly (site-architecture.md §10.4). A layout is seen filled in by opening a page that uses it. The alternative, `$site` and project `state` for a layout, needs a `$page`-less variant of `injectContext` in `packages/site` and still leaves every `$page` binding empty in Preview.
- **Open:** what of the two values the build computes from more than the page in front of it? Recommendation: `$page.alternates` is absent and a templated `title` or description reaches `$page` as written, and §4.1 and the canvas docs say so, which is the limit `plan:site-architecture/page-context-props` records for the live preview. A translation set is a property of the whole route table (every page's route and `$translationKey`, every dynamic route's expansion), and `translationSets` in `packages/compiler/src/site/i18n.ts` warns that deriving it twice is how the two would disagree unseen; the Languages panel is where Studio says which translations exist. A templated title is evaluated by the build against resolved state, and the canvas resolves state in the iframe, after the document is composed, with no template evaluator in the parent realm. Visible cost: the museum starter's header language switcher (`items: { $ref: "#/state/$page/alternates" }` in `layouts/base.json`) is empty in Preview, as it is today and in the live preview. The alternative moves `translationSets` to `@jxsuite/schema/locale`, keeps a project page index with declared keys (the scan `readDeclaredKeys` in `panels/i18n-panel.ts` does) invalidated on file changes, and answers a dynamic sibling only for the chosen values; it adds `packages/schema` and `packages/compiler` and makes this plan L.

   - Site context: for a page, skip the imports and `$media` merges (done by `injectContext`) and set `$head` to `getEffectiveHead([...(layoutWrapped ? (renderDoc.$head ?? []) : []), ...(facts.head ?? [])])`. For any other document all four merges stay as they are.

**Integration contract.** Once this lands, `resolveCanvasDocument` calls `injectContext` exactly once, for a page only, after the wrap and before the params substitution, with `rebaseImport` `null`, `projectState.projectConfig` as the project config, `getEffectiveLocales()`, an empty translation set and the page's facts; `plan:imports/canvas-project-context` passes its rebaser and a rebased view of the config at that call and needs no second merge. The wrap is `resolveLayout` over `loadCanvasLayout`, called once per level, so a per-layout rewrite (rebasing a layout's `$elements`) belongs in that loader, and a merge added to `resolveLayout` (the page `imports` merge) reaches the canvas unchanged. A page's render document owns its `state`, `imports` and `$elements` objects. Its `state` carries `$site`, `$page` and every inherited project entry the page does not declare, so the `dataScope` snapshot has their values (`plan:studio/site-state-in-data-panel`); a document that is not a page carries none of them and keeps the `getEffective*` merges. `canvasPageRoute(documentPath, params)` is exported from `page-params.ts`, and `substitutePreviewParams` takes `(renderDoc, params)`.
