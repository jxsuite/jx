# Every placement in the matrix is read by the surface it names: the pane menu projects `context/pane`, and the rows no surface reads leave the table

## Context

`specs/studio-ui-guidelines.md` §12.1, line 744:

> **Status: Partial.** The matrix ships as `PLACEMENT_MATRIX` and `PANEL_PLACEMENT_MATRIX` (`packages/studio/src/commands/levels.ts`), checked by `scripts/check-command-levels.ts` and by `registerPanel()`. Five rows reach no renderer that reads them: the outline's right-click (`src/panels/layers-panel.ts`) draws `context/element` rather than `context/layer`; the pane context bar's preset menu (`src/panels/pane-context.ts`), the one renderer of `context/pane`, builds its rows by id for `pane.derive`, `pane.pin` and `pane.unsplit`, so `pane.splitRight` and `pane.compareWith` declare the placement and are never drawn there; and the status bar picks its items by command id (`src/surfaces/statusbar.ts`) rather than projecting its three placements, of which no record declares `statusbar/selection`.

Verified against the tree; paths below are under `packages/studio/src/` unless rooted.

**`context/layer`.** Two records declare it, `selection.duplicate` and `selection.delete` (`commands/defaults.ts`), both beside `context/element`. The outline's `contextMenu` host callable (`panels/layers-panel.ts`, the `mountOutlineSurface` options) calls `showContextMenu(event, path, { rerender })`, and `editor/context-menu.ts` draws `buildRows(opts.placement ?? "context/element")`. Sixteen records declare `context/element`: ten in `editor/context-menu.ts` (`elementCommands`, `clipboardCommands`), `selection.findUsages` (`panels/properties-panel.ts`), `selection.convertToComponent` and `selection.editComponent` (`panels/block-action-bar.ts`), and `selection.duplicate`, `selection.repeat` and `selection.delete` (`commands/defaults.ts`). `docs/studio/design/layers.md` promises the outline "the same context menu as the canvas".

**`context/pane`.** Five records declare it: `pane.splitRight`, `pane.compareWith` and `pane.unsplit` (`paneCommands`, `workspace/workspace.ts`), `pane.derive` and `pane.pin` (`derivationCommands`, `workspace/pane-derive.ts`). The ⟲ menu's `presetRows(paneId)` builds derive rows from `DERIVE_PRESETS`, `declaredMedia(tab)` and `getEffectiveLocales()`, then `pane.pin` and `pane.unsplit` by literal id. It answers per pane (`deriveRefusal`, `presetRefusal`, `pinRefusal`) because `registry.disabledReason` resolves the FOCUSED pane: `tests/lens-chrome.test.ts` ("a pane's rows are the same wherever the keyboard is") and rule 4 of `packages/studio/scripts/check-pane-singletons.ts` (`disabledReason` and `isEnabled` are in `FOCUS_NAMES`) hold it there, and `packages/studio/scripts/check-lens-mutants.ts` has eight mutant rows whose `find` strings are lines of `presetRows` and `menuRow`. `menuRow` prints no chord and no divider and runs `activeRegistry()?.run` bare after `focusPane(row.pane)`.

The census missed that **`pane.compareWith` is drawn nowhere**. `placedTabItems` (`panels/tab-strip.ts`) skips a record whose required argument `tabRowFacts` cannot answer, and `path` is required (`argsSchema` requires every property); `paletteArgs` (`panels/quick-search.ts`) answers `unsupported` for a free string, so command mode omits it. Only `registry.run` reaches it. `pane.splitRight` is drawn in the tab menu and the palette.

## Decisions

- **Open:** the status bar's three rows. Recommendation: retire them from the table and `PLACEMENT_MATRIX`, drop them from the four records' `menus`, and state in studio-ui-guidelines.md §12.1 that the status bar is not a placement: it reports ambient state in three fields ordered by the level of the state each item reports, and an item that can act names the command that shows or changes that state, whatever its level. Because: four of the seven doors would fail their field's single-level row, the problems door is fixed by `studio.md` §16.3 as an application verb, and a status item's text is state, so projecting records would need a per-record label projection owned by the wrong module (`view.setBottomTab` does not own the problem count). The alternative, keeping the rows, widening each to admit `application`, and adding a record field that projects a status label beside `run`, touches every door's module and is size L.
- **Open:** `context/layer`. Recommendation: retire it; the outline's right-click is `context/element`, whose note becomes "the element menu, opened on a canvas element or an outline row". Because the two menus are one menu by design (the docs promise it), no record draws differently in them, and a second placement with the same sixteen members is a second list that drifts the day one record forgets it. The alternative is `placement: "context/layer"` in `layers-panel.ts` and fourteen more records declaring it, with the fallback registry in `contextMenuRegistry()` filtering on both.
- **Open:** which records the pane menu draws. Recommendation: `pane.derive`, `pane.pin` and `pane.unsplit` as today, plus **Split Right** in the primary pane only (the one pane whose document it moves right; from the secondary it would move the document left under a label that says right), and `pane.compareWith` declares `menus: ["never"]`, because no surface can supply its `path` (a document picker is new scope, not a rendering fix). The alternative drops `context/pane` from `pane.splitRight` too, leaving the menu's content unchanged.
- **Decided:** the pane menu reads membership through a new `registry.declaredIn(placement)` and asks each record for its rows through a new optional record field `paneRows(paneId)`, rather than `forPlacement` or `plan:studio-ui-guidelines/name-and-chord-gaps`'s `placementRows`, because both evaluate `when` and `enablement` against the focused pane, which the lens-chrome case and check-pane-singletons rule 4 forbid in a per-pane menu. The per-pane answers already live beside the records (`deriveRefusal`, `pinRefusal` in `pane-derive.ts`), so the rows move there too and the menu decides nothing. This is also why this plan does not require that one: it uses none of its exports.
- **Decided:** `pane.derive` takes `group: "4_pane"` (it declares only `context/pane`, so nothing else reorders), so its rows lead, the exits follow, and the divider between them is derived from the group change as studio-ui-guidelines.md §8.4 requires.
- **Decided:** `blockbar/format` is read by membership (`declaredIn`), not `forPlacement`, because the format records' `when` (`ctx.caret.inCanvas`) would remove the cluster for a block selected from the outline, where it is drawn disabled today.
- **Decided:** the peers count moves to the document field, because `collabState` is per tab and its tooltip already says "in this document", and the rewritten rule has each field hold its own level's state.
- **Decided:** a source-scanning test names the module that reads each placement, as `tests/run-reported.test.ts` does for bare runs, because the defect was invisible to the level check, which reads declarations only.
